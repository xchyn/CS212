1.What a GUI is, and the words for its parts

Last time you learned two things that probably felt abstract. An abstract class can declare a method with no body and force every subclass to write one. An interface is a pure list of method headers that any class can promise to fulfil, and a class that says implements Runnable is signing a contract: I will supply every method on that list.

Today is the payoff. Everything you are about to write — every button that responds to a click, every window that notices you pressed its close box — works by you writing a class that implements an interface Java already defined. That is the entire mechanism. Keep the word interface in your head for the next fifty minutes; by §7 it will be doing all the work.

Every program you have written so far has talked to the user through a scrolling stream of text. That is a console program. The other kind is the kind you actually use all day.

Definition— graphical user interface

A GUI (graphical user interface, pronounced "gooey") is a visual way for users to interact with programs. Instead of typing at a prompt and reading lines of text, the user looks at a picture on the screen and clicks, types and drags.

The standard elements are:

  • Windows — portions of the screen containing GUI components.
  • Menus — lists of choices.
  • Buttons — clickable elements to perform actions.
  • Text fields — areas for entering or displaying text.
  • Labels — text descriptions for other components.

Three more words are worth pinning down now, because Java's class names are built out of them and the exam questions use them without explanation.

Definition— component, container, frame, panel

A component is any single GUI element that can be added to something: a button, a label, a text field. In Java these are the classes whose names start with J — JButton, JLabel, JTextField.

A container is a component that can hold other components. This is the important idea: a container is a component, so containers can be put inside other containers, and a GUI is a tree.

A frame is the top-level container — a real window with a title bar, a border, and minimise/maximise/close buttons drawn by the operating system. In Java the class is JFrame, and it is the subject of the rest of this lecture.

A panel is a plain rectangular container with no decoration, used to group components inside a frame. The class is JPanel. We only name it today; it becomes central next lecture.

Key Idea

A console program decides the order of events: it prints, then reads, then prints. A GUI program does not. It puts a window on the screen and then waits. The user decides what happens next, and in what order. Your job stops being "write the sequence" and becomes "write what to do when". That is called event-driven programming, and it is the real subject of the next five lectures.

Quick Check 15.1

Open any window on your own computer — a text editor, a browser's settings dialog — and name one thing in it that is a menu, one that is a button, one that is a text field, and one that is a label. Then answer: is the window itself a component, a container, or both?

Plan. Use the definitions literally. A menu is a list of choices; a button is clicked to perform an action; a text field is somewhere you type; a label is text that describes something else and that you cannot type into.

In a browser's find bar, for example: File / Edit / View across the top is the menu, Find Next is a button, the box you type your search into is a text field, and the word Find: printed beside that box is a label. The label is the one people get wrong — the giveaway is that clicking it does nothing and you cannot type into it.

The window is both. It is a component (it can be moved, resized, shown, hidden) and it is a container (it holds the menu, the button, the field and the label). That is not a trick answer; it is the whole design. Because a container is also a component, containers nest, and a GUI is a tree of components with the frame at its root.

Things to notice. Every one of these has a Java class waiting for it: JMenu, JButton, JTextField, JLabel, JFrame. Learning the vocabulary now means that when an exam question says "the GUI has three buttons across the bottom" you already know it is asking for three JButton objects.

2.Swing, AWT, and the three packages

Java's GUI story has two layers, and you need both. The older one is AWT; the newer one is Swing, which is built on top of it. In practice you write Swing components and import a few AWT support classes, and the imports look inconsistent until you know why.

Definition— Swing and AWT

Swing is a GUI toolkit for Java providing platform-independent GUI components. Swing draws its own buttons and menus in Java code, so a Swing program looks the same everywhere — the same WORA promise from Lecture 1, applied to pixels.

AWT is the Abstract Window Toolkit, the original Java GUI library. It provides the basic GUI machinery Swing is built on: the notion of a component, a container, a layout, a color, and the whole event system.

That split is exactly why your import lines come from three different places:

PackageWhat lives thereExamples you will use today
javax.swingThe core Swing components. Class names start with J.JFrame, JLabel, JButton, JPanel, JTextField
java.awtBasic GUI functionality inherited from AWT.Color, Container, BorderLayout
java.awt.eventEvent classes and listener interfaces.WindowEvent, WindowListener, WindowAdapter, ActionListener
Common Mistake— the x in javax

It is javax.swing, with an x, and java.awt, without one. Writing import java.swing.JFrame; produces a package java.swing does not exist error that students stare at for five minutes because the line looks right. The x is a historical marker: Swing arrived as an extension to Java rather than part of the original core, and the name stuck.

It is also java.awt.event in the singular, not java.awt.events.

You will see import javax.swing.*; in a lot of code, including on the exams. The star imports every class in the package. It is convenient and it is what most GUI code does, because a real window needs six or eight Swing classes. Naming them one at a time, the way the examples in this lecture do, is clearer while you are learning which class lives where.

Quick Check 15.2

For each class, give the single import line you would write.

(a) JLabel

import javax.swing.JLabel; — it starts with J, so it is a Swing component.

(b) Color

import java.awt.Color; — a color is not a component, it is basic drawing machinery, so it lives in AWT. There is no JColor.

(c) WindowEvent

import java.awt.event.WindowEvent; — every event class and every listener interface is in java.awt.event.

(d) Container

import java.awt.Container; — this one surprises people, because you get a Container by calling getContentPane() on a Swing JFrame. But Container is the old AWT class that JFrame ultimately inherits from, and Swing never renamed it.

Things to notice across all four parts. The rule that gets you 90% of the way: if the class name starts with a capital J, it is javax.swing; if it ends in Event or Listener or Adapter, it is java.awt.event; otherwise try java.awt. When in doubt, import javax.swing.*; and import java.awt.*; and import java.awt.event.*; covers everything in this course — and note that the star is not recursive, so java.awt.* does not bring in java.awt.event.

3.Your first window

A JFrame is an ordinary Java object. You make one with new, you call methods on it, and one of those methods puts it on the screen. There is no special syntax anywhere.

Definition— JFrame

JFrame is the main window class in Swing: it provides the framework for a GUI application. A JFrame

  • represents a top-level window with a title and a border,
  • can contain other Swing components,
  • has a content pane where components are added, and
  • supports window events — open, close, resize and so on.
Procedure— the three calls every window needs
  1. Create it. JFrame gui = new JFrame(); — the window exists as an object, but nothing is on the screen yet.
  2. Size it. gui.setSize(width, height); — width first, then height, both in pixels. A frame you never size has width and height of zero.
  3. Show it. gui.setVisible(true); — this is the line that makes the window appear. Nothing you do before it is visible to the user; everything after it happens to a window already on the screen.
Worked Example— a window in four lines

This is the smallest useful Swing program there is. Read it and notice what is not there: no println, no loop, no return, and nothing that looks like it keeps the program alive.

Example1.java

import javax.swing.JFrame;

public class Example1 {
   public static void main(String args[]) {
      JFrame gui = new JFrame();     // Create a new JFrame window
      gui.setSize(500, 600);         // Set window dimensions (width, height)
      gui.setVisible(true);          // Make the window visible
   }
}

Before you open the toggle, answer two questions on paper. What does the window look like? And once main reaches its closing brace, does the program end?

A blank window appears, 500 pixels wide and 600 pixels tall, positioned at the top-left corner of the screen. Its title bar is empty, because we never called setTitle. The inside is a plain empty area in whatever the default background color of your system is. The exact look of the title bar and its buttons is drawn by your operating system, so a Mac, a Windows machine and a Linux desktop each decorate the same frame differently.

And no, the program does not end. main finishes and returns immediately, but the program keeps running and the window stays on the screen. This is the first genuinely new thing in the lecture. Calling setVisible(true) caused Java to start another thread — the event dispatch thread — whose whole job is to sit in a loop waiting for mouse clicks and key presses and to deliver them to your components. A Java program does not exit while a non-daemon thread like that is still alive, so the program outlives main.

That single sentence is all you need about the event dispatch thread today. It matters for one practical reason: everything that touches a Swing component after the window is showing runs on that thread, which is why a slow calculation inside a button handler freezes the whole interface. We come back to threads properly in Lecture 23.

Warning— running a GUI program where there is no screen

A Swing program needs a display. If you run one over a plain SSH connection, or inside a server or container with no graphical environment, new JFrame() cannot succeed and Java tells you so at that exact line:

Quick Check 15.3

Each of these is a variation on Example1. Say what the user sees.

(a) You delete the line gui.setVisible(true);.

Nothing appears at all, and the program ends immediately. The JFrame object was created in memory and sized, but a window that is never made visible is never shown and never becomes displayable, so no event dispatch thread starts. main returns and the JVM has nothing left to do.

This is the single most common "my GUI does not work" bug, and it produces no error message of any kind — which is exactly what makes it hard.

(b) You delete the line gui.setSize(500, 600);.

A window does appear, but it has width 0 and height 0. On most systems you get a tiny stub in the corner of the screen — sometimes just the title bar and its buttons, sometimes almost nothing you can see or click. The program is running perfectly; it simply drew a window with no area.

Later you will meet pack(), which sizes a frame automatically to just fit whatever is inside it. Until then, always call setSize.

(c) You swap the last two lines, so setVisible(true) comes before setSize(500, 600).

You end up with the same 500 by 600 window, because setSize works on a visible window too — it just resizes it. On a fast machine you would not notice, though in principle the window flashes at its zero size first and is then resized.

Things to notice across all three parts. setVisible(true) is a switch, not a "finish and display" command. The window is a live object the whole time, and every method you call on it applies immediately, whether it is on the screen or not. The convention of setting everything up first and calling setVisible(true) last exists so that the user never sees a half-built window — not because Java requires it.

4.Closing the window

Run Example1, click the close box in the corner of the window, and something odd happens. The window disappears — and the program is still running. On most systems you will find it still listed in your task manager, or your IDE will still be showing a red stop button. Nothing you did was wrong; that is Swing's default behavior, and it is a deliberate one.

Definition— setDefaultCloseOperation

setDefaultCloseOperation(int operation) tells a JFrame what to do when the user clicks its close box. There are four constants, all inherited into JFrame:

ConstantValueWhat happens on close
JFrame.DO_NOTHING_ON_CLOSE0Nothing. The window stays. Use this when a listener of yours will decide.
JFrame.HIDE_ON_CLOSE1The window is hidden but not destroyed. This is the default.
JFrame.DISPOSE_ON_CLOSE2The window is hidden and its screen resources are released.
JFrame.EXIT_ON_CLOSE3The whole application exits, as if you had called System.exit(0).
Key Idea— why hiding is not stopping

The default is HIDE_ON_CLOSE because Swing cannot know whether your one visible window is your application. A real program may have five windows open, or may want to ask "save your changes?" first. So Swing does the only safe thing: it takes the window off the screen and leaves your program alive to decide what that meant.

A hidden window is still a live, displayable object, so the event dispatch thread keeps running, so the JVM never exits. That is the whole explanation for the program that will not die.

The fix is one line, and it belongs in every window you write from now on:

CloseDemo.java

import javax.swing.JFrame;
import javax.swing.JLabel;

public class CloseDemo extends JFrame {
   public CloseDemo() {
      super("Close Demo");
      setSize(300, 200);
      setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
      getContentPane().add(new JLabel("  Close me and the program really stops."));
   }

   public static void main(String args[]) {
      CloseDemo gui = new CloseDemo();
      gui.setVisible(true);
   }
}

Two details in there are new and are explained properly in §5 and §6: the class extends JFrame and sets itself up in its own constructor, and super("Close Demo") passes a title straight to the JFrame constructor. Everything else you have already seen.

Common Mistake— EXIT_ON_CLOSE is a sledgehammer

EXIT_ON_CLOSE ends the entire JVM. In a program with one window that is exactly right. In a program with three windows open, closing any one of them kills the other two without warning. If you want a window to close and the rest of the program to survive, use DISPOSE_ON_CLOSE instead — and note that once the last displayable window has been disposed, the event dispatch thread finishes and the program ends on its own.

Quick Check 15.4

A student writes a JFrame program, runs it from the command line, clicks the close box, and gets their shell prompt back. Their friend writes what looks like the same program, clicks the close box, and the terminal just sits there until they press Ctrl-C. Give one plausible difference between the two programs.

Plan. The window vanished in both cases, so the difference is not about showing or hiding — it is about whether anything was left alive afterwards.

The first student called setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE); (or DISPOSE_ON_CLOSE on their only window, which amounts to the same thing here). The second student left it out, so the default HIDE_ON_CLOSE applied: the window was hidden but never destroyed, it is still displayable, the event dispatch thread is still looping, and the JVM will not exit.

A second plausible answer that is just as good: the first student registered a WindowListener whose windowClosing method calls System.exit(0). That is the older technique, and it is what your instructor's WindowDestroyer class does — we build it in §8.

Things to notice. "The window went away" and "the program stopped" are two completely separate events in Swing, and the whole point of setDefaultCloseOperation is that you choose the relationship between them. Get in the habit of asking, for any window you write: what should happen to the program when the user closes this window?

5.The normal pattern: a class that extends JFrame

Example1 builds its window out in the open, inside main. That is fine for four lines. It stops being fine the moment the window has a title, a background color, three labels, two buttons and a listener — because then main is forty lines long, and if you want a second window just like it you have to copy all forty.

So there are two ways to use JFrame, and only one of them scales.

Instantiate a JFrame (Example1)Extend JFrame (FirstWindow)

Making a second oneCopy every line againnew FirstWindow()
Adding your own fields and methodsImpossible — JFrame is not yoursNormal inheritance

Key Idea— "is a window" versus "has a window"

Writing class FirstWindow extends JFrame says a FirstWindow is a kind of window. Everything you learned about inheritance in Lecture 12 applies unchanged: FirstWindow inherits setSize, setTitle, setVisible, getContentPane and about three hundred other methods, and inside the constructor you call them with no receiver at all — setSize(WIDTH, HEIGHT); means this.setSize(WIDTH, HEIGHT);.

That dropped this. is what confuses people most on first reading. There is no object named gui any more. The object is the one being constructed.

Worked Example— FirstWindow, and two of them at once

Here is the pattern in full. Two files: one class that is the window, and one tiny class whose main creates it. Read the constructor line by line and notice that every method call in it is an inherited JFrame method being called on this.

FirstWindow.java

import javax.swing.JFrame;
import javax.swing.JLabel;

public class FirstWindow extends JFrame {
   public static final int WIDTH = 300;
   public static final int HEIGHT = 200;

   public FirstWindow() {
      super();                      // Call the JFrame constructor
      setSize(WIDTH, HEIGHT);       // Set window size

      // Add content to the window
      JLabel myLabel = new JLabel("Please don't click that button!");
      getContentPane().add(myLabel);

      // Add a window listener for the close button
      WindowDestroyer listener = new WindowDestroyer();
      addWindowListener(listener);
   }
}

FirstWindowDemo.java

public class FirstWindowDemo {
   public static void main(String args[]) {
      FirstWindow window1 = new FirstWindow();
      window1.setVisible(true);

      FirstWindow window2 = new FirstWindow();
      window2.setVisible(true);
   }
}

WindowDestroyer is the class we write in §8; for now, take it on trust that it is a listener that ends the program when the window is closed. Before you reveal: how many windows appear, and where is the label's text inside each one?

Two windows appear, each 300 pixels wide and 200 tall, each with an empty title bar (FirstWindow never calls setTitle), each showing the text Please don't click that button!. They land on top of one another at the top-left corner of the screen, because neither one was told where to go — so at first glance it looks like one window, and you have to drag the top one aside to find the second.

The label's text sits at the left edge, vertically centered. That is worth knowing precisely, because it surprises everybody who expects it in the middle. Two separate rules combine to produce it, and both are explained in §6.

Two design points to take away.

  • WIDTH and HEIGHT are public static final int. They are constants belonging to the class, not to any one window, which is exactly what static meant in Lecture 9. Any other code can write FirstWindow.WIDTH to find out how wide these windows are, and there is one place to change if you want them bigger.
  • super(); is optional here and written anyway. Java inserts a call to the no-argument superclass constructor automatically if you do not write one, so this line changes nothing. It is there for the reader: it says out loud "a JFrame is being built first, and then I customise it". If you wanted a title you would write super("First Window"); instead, calling the JFrame(String) constructor — and then it would not be optional.
Quick Check 15.5

Rewrite Example1 — the 500 by 600 blank window from §3 — using the extends JFrame pattern instead. Put the size in two named constants, do the setup in a constructor, and keep main down to two lines. Call the class BigWindow.

Plan. Move each line of the old main into the right home. The new JFrame() disappears entirely — the object being constructed is the frame. setSize moves into the constructor and loses its gui. prefix. setVisible(true) stays in main, because a constructor should build an object, not display it. That separation is the convention every exam answer follows: the constructor sets the window up; main shows it.

BigWindow.java

import javax.swing.JFrame;

public class BigWindow extends JFrame {
   public static final int WIDTH = 500;
   public static final int HEIGHT = 600;

   public BigWindow() {
      super();
      setSize(WIDTH, HEIGHT);
   }

   public static void main(String args[]) {
      BigWindow gui = new BigWindow();
      gui.setVisible(true);
   }
}

Things to notice. main can live inside BigWindow itself, as it does here, or in a separate demo class the way FirstWindowDemo does. Both are common; her SecondWindow in §6 puts main inside the window class, and the exam questions do too. Keeping main out of the window class is slightly cleaner design, because a class that is a window arguably should not also be a program, but nothing breaks either way.

Notice also what did not move: setVisible(true). Putting it at the end of the constructor would work, and you will see code that does it — but then the window appears the instant you write new BigWindow(), which makes it impossible to build a window now and show it later.

Quick Check 15.6

Inside the FirstWindow constructor the line is setSize(WIDTH, HEIGHT); with no object in front of it. In Example1 the same call was gui.setSize(500, 600);.

(a) Which object is being resized by the call in the constructor, and where is setSize defined?

The object being constructed — this. A call with no receiver is shorthand for this.setSize(WIDTH, HEIGHT);. setSize is not defined in FirstWindow at all; it is inherited, ultimately from java.awt.Component, through JFrame. Inheritance means FirstWindow has it just as surely as if you had typed it.

(b) Could you write gui.setSize(...) inside the constructor instead?

No — there is no variable called gui anywhere in FirstWindow. That name only existed in Example1's main. This is the mental switch the pattern demands: you stop holding a window in a variable and start being one.

Things to notice across both parts. If you ever genuinely need to refer to the window as an object from inside its own constructor — and you will, in §7, when a listener needs to know which window it belongs to — the word is this. addWindowListener(this); is a perfectly ordinary line in a class that is both a window and its own listener, and it is exactly what the exam questions ask you to write.

6.The content pane: putting something in the window

You cannot add a component straight to a JFrame. Underneath the frame's decorations there are several layers — a place for a menu bar, a glass pane for overlays — and the one you want has a name.

Definition— the content pane

The content pane is the container inside a JFrame where components are added. You get it by calling getContentPane(), which returns a java.awt.Container, and then you call add on that:

JLabel label = new JLabel("Hello, World!");
getContentPane().add(label);

You can also keep it in a variable, which is tidier when you are going to use it more than once:

Container contentPane = getContentPane();
contentPane.add(label);
contentPane.setBackground(Color.BLUE);

Here are the JFrame methods worth memorising. Everything in this lecture and the next four is built out of them.

MethodWhat it does
setSize(width, height)Sets the dimensions of the frame, in pixels.
setVisible(boolean)Shows or hides the frame.
setTitle(String)Sets the text displayed in the frame's title bar.
getContentPane()Returns the content pane, where components are added.
setDefaultCloseOperation(int)Says what the close box should do.
addWindowListener(WindowListener)Registers a window event listener.
Worked Example— SecondWindow: a title, a color, two constructors

This is FirstWindow with three additions: a title, a background color, and a second constructor that lets the caller choose the color. Notice that both constructors do almost exactly the same work — that duplication is a real design smell, and we will come back to it after you reveal.

SecondWindow.java

import java.awt.Color;
import java.awt.Container;

import javax.swing.JFrame;
import javax.swing.JLabel;

public class SecondWindow extends JFrame {
   public static final int WIDTH = 300;
   public static final int HEIGHT = 200;

   public SecondWindow() {
      super();
      setSize(WIDTH, HEIGHT);
      Container contentPane = getContentPane();
      JLabel myLabel = new JLabel("Now available in color!");
      setTitle("Second Window");              // Set the window title
      contentPane.add(myLabel);
      contentPane.setBackground(Color.BLUE);  // Set the background color
      addWindowListener(new WindowDestroyer());
   }

   public SecondWindow(Color customColor) {
      super();
      setSize(WIDTH, HEIGHT);
      Container contentPane = getContentPane();
      JLabel myLabel = new JLabel("Now available in color!");
      setTitle("Second Window");
      contentPane.add(myLabel);
      contentPane.setBackground(customColor); // Use a custom color
      addWindowListener(new WindowDestroyer());
   }

   public static void main(String args[]) {
      SecondWindow window1 = new SecondWindow();
      window1.setVisible(true);

      SecondWindow window2 = new SecondWindow(Color.PINK);
      window2.setVisible(true);
   }
}

Before you reveal: two windows again. What is different about them, and what is the same? And where exactly does the text appear this time?

Two windows, both 300 by 200, both titled Second Window, both showing Now available in color! at the left edge, vertically centered. The first has a blue interior; the second is pink. They overlap at the top-left corner of the screen, so you have to drag one aside to see both.

Why the text is at the left, and why the color shows through. Two separate rules, and this is the place to learn both.

  1. A frame's content pane starts out using a BorderLayout. Adding a single component with no further instructions puts it in the center region, and BorderLayout stretches whatever is in the center to fill all the available space. So the JLabel really does occupy the entire content pane — it is 300 pixels wide.
  2. A JLabel draws its text at its leading edge horizontally and centered vertically by default. So the label fills the pane, but the words sit at the label's left edge, halfway down. That is why the text is neither centered nor in the corner.

And the background is visible because a JLabel is not opaque by default: it paints its text and lets whatever is behind it show through. Had you called myLabel.setOpaque(true) and given the label its own background, you would see a colored rectangle exactly the size of the pane instead.

Layout managers are the entire subject of the next lecture. Today all you need is the consequence: a lone component added to a content pane fills it.

The duplication. Those two constructors are identical except for one argument. The clean fix is the one from Lecture 7 — have the no-argument constructor call the other one:

public SecondWindow() {
   this(Color.BLUE);     // delegate to the constructor below
}

public SecondWindow(Color customColor) {
   super();
   setSize(WIDTH, HEIGHT);
   Container contentPane = getContentPane();
   JLabel myLabel = new JLabel("Now available in color!");
   setTitle("Second Window");
   contentPane.add(myLabel);
   contentPane.setBackground(customColor);
   addWindowListener(new WindowDestroyer());
}

this(...) calls another constructor of the same class and, like super(...), must be the very first statement. Nineteen lines become nine, and a change to the window now has one place to happen instead of two.

Common Mistake— setBackground on the frame

setBackground(Color.BLUE); inside a JFrame subclass compiles perfectly — JFrame inherits setBackground from Component — and then nothing changes on screen. The frame's own background is completely covered by its content pane, so you never see it. The color has to go on the thing that is actually visible:

getContentPane().setBackground(Color.BLUE);     // right

This is a compile-clean, error-free, silently-wrong bug, which is the worst kind. When a color does not appear, the first question is always which component am I actually painting?

Quick Check 15.8

FirstWindowDemo creates two FirstWindow objects, and each one registers its own WindowDestroyer, which calls System.exit(0). The user closes one of the two windows. What happens to the other?

Plan. Follow the call. Closing window 1 fires a window event, which is delivered to window 1's listener, which calls System.exit(0).

Both windows disappear and the whole program ends. System.exit(0) does not close a window — it shuts down the entire JVM. It does not matter that window 2 was never touched, or that it has its own separate listener object; there is one JVM and it is gone.

To close only the window the user actually clicked, ask the event which window it came from:

WindowCloser.java

import java.awt.event.WindowAdapter;
import java.awt.event.WindowEvent;

public class WindowCloser extends WindowAdapter {
   public void windowClosing(WindowEvent e) {
      e.getWindow().dispose();   // close only the window that fired the event
   }
}

Things to notice. This is the first time the WindowEvent parameter has been used for anything. Up to now e has been ignored, and it looked like decoration. It is not: e.getWindow() tells the listener which window this event came from, which is exactly what lets a single listener object serve several windows.

With dispose(), closing one window leaves the other running. Close the second one too and the program ends by itself — once the last displayable window is disposed there is nothing left for the event dispatch thread to do, and the JVM exits. So you get the behavior most people actually want, without ever calling System.exit.

7.The event model: source, event, listener

Now the part that makes GUIs work, and the part that makes Lecture 14 worth having sat through.

Definition— event, event source, listener

An event is an object that represents an action — a button click, a key press, a request to close a window. It is a real Java object of a real class, such as WindowEvent or ActionEvent, and it carries information about what happened.

The event source is the component the action happened to: the button that was clicked, the window whose close box was pressed. A source fires events.

A listener is an object that has agreed to be told when those events happen. A listener class implements a listener interface — WindowListener, ActionListener — and the interface's methods are the ones the source will call.

Registration connects the two: addWindowListener(listener) tells the frame "when you fire a window event, call this object".

Procedure— the event flow, in four steps
  1. The user interacts with a GUI component.
  2. The component fires an event — it constructs an event object describing what happened.
  3. The event is passed to every registered event listener.
  4. The listener's event-handling method processes the event.
Key Idea— this is why interfaces exist

The people who wrote JFrame in 1998 needed to call a method in a class you had not written yet. They could not know its name, its package, or what else it does. What they could do was publish a list of method headers — windowClosing(WindowEvent) and six others — and require that anything you hand to addWindowListener implements that list.

That is an interface, and this is what interfaces are for. In Lecture 14 an interface was a way to promise behavior. Here it is a way for library code written twenty-five years ago to call code you write this afternoon. addWindowListener takes a parameter of type WindowListener, and by Lecture 13's rules your WindowDestroyer object can be passed for it, and dynamic binding sends the call to your body.

Put the three roles against the concrete example and the whole mechanism fits in one table:

RoleIn FirstWindowWhat it is
Event sourceThe FirstWindow objectA JFrame, which knows how to fire window events
Event objectThe WindowEvent handed to windowClosingAn object describing what happened; e.getWindow() says where
Listener interfaceWindowListenerSeven method headers, no bodies
Listener objectThe WindowDestroyerYour class, implementing that interface
RegistrationaddWindowListener(listener)The line that connects source to listener
Common Mistake— writing the listener but never registering it

A listener class that is never passed to addWindowListener (or addActionListener) does absolutely nothing. It compiles, it is correct, and it is never called, because nothing ever told the source it existed. When a button "does not work", the first thing to check is not the handler — it is whether the registration line is there.

Quick Check 15.9

A program has a window whose close box, when clicked, should print Goodbye and then quit. Identify each of the following, by name where the name exists.

That is next lecture, and it will feel like revision.

8.WindowListener, all seven methods, and WindowAdapter

So a listener implements an interface. Let us actually do it, without shortcuts, and see what it costs.

Definition— WindowListener

WindowListener is an interface in the java.awt.event package containing seven abstract methods, one for each thing that can happen to a window. Each of them receives a WindowEvent describing the event:

MethodFired when
windowOpened(WindowEvent)the window is made visible for the first time
windowClosing(WindowEvent)the user asks to close it (the close box)
windowClosed(WindowEvent)the window has been disposed of
windowIconified(WindowEvent)the window is minimised
windowDeiconified(WindowEvent)the window is restored from minimised
windowActivated(WindowEvent)the window becomes the active one
windowDeactivated(WindowEvent)the window stops being the active one

Any class directly implementing WindowListener must provide implementations for all seven. That is not a Swing rule, it is the plain rule about interfaces from Lecture 14: implementing an interface means implementing every method on it.

Try it the honest way. You want a class that quits the program when the window closes, so you write the method you care about:

WindowDestroyer.java

import java.awt.event.WindowListener;
import java.awt.event.WindowEvent;

public class WindowDestroyer implements WindowListener {
   public void windowClosing(WindowEvent e) {
      System.exit(0);
   }
}

And javac refuses:

WindowDestroyer.java:4: error: WindowDestroyer is not abstract and does not override abstract method windowDeactivated(WindowEvent) in WindowListener
public class WindowDestroyer implements WindowListener {
       ^
1 error
Key Idea— read that error carefully

It names only one missing method, windowDeactivated, because the compiler stops at the first one it notices. Six are missing. And notice the phrase is not abstract: the compiler is telling you your two legal options. Either implement everything, or declare the class abstract and let a subclass finish the job. This is exactly the error from Lecture 14 — the same message you got when a concrete subclass forgot to override an abstract method — and it is worth recognising it here so that GUIs feel like a continuation rather than a new subject.

Worked Example— the long way, then the short way

First, an honest implementation of all seven methods. To make it observable, each one announces itself rather than doing something invisible.

NoisyListener.java

import java.awt.event.WindowEvent;
import java.awt.event.WindowListener;

public class NoisyListener implements WindowListener {
   public void windowOpened(WindowEvent e)      { System.out.println("windowOpened"); }
   public void windowClosing(WindowEvent e)     { System.out.println("windowClosing"); }
   public void windowClosed(WindowEvent e)      { System.out.println("windowClosed"); }
   public void windowIconified(WindowEvent e)   { System.out.println("windowIconified"); }
   public void windowDeiconified(WindowEvent e) { System.out.println("windowDeiconified"); }
   public void windowActivated(WindowEvent e)   { System.out.println("windowActivated"); }
   public void windowDeactivated(WindowEvent e) { System.out.println("windowDeactivated"); }
}

A listener is an ordinary object, so you do not need a window to try one out. This driver creates the listener and calls its seven methods itself, in the order a real session might produce them. Passing null is safe here only because none of the methods looks at e.

Nothing surprising — and that is the point. There is no magic in a listener. It is a plain object with seven plain methods, and the only thing Swing adds is that a real frame calls them for you at the right moments instead of a main calling them in a row.

Now count what that cost: seven methods, six of which you did not want. Every window-closing class in every Java program would carry six empty bodies. Someone noticed, and put a class in the library to carry them for you.

QuietListener.java

import java.awt.event.WindowAdapter;
import java.awt.event.WindowEvent;

   public void windowClosing(WindowEvent e) {
      System.out.println("windowClosing  (this is where System.exit(0) would go)");
   }
}

All seven calls compiled and all seven ran. Six of them landed in inherited methods with empty bodies and returned immediately. The line WindowListener listener = new QuietListener(); compiles because QuietListener really is a WindowListener — it inherits that promise from WindowAdapter.

Definition— WindowAdapter

WindowAdapter is an abstract class in java.awt.event that implements WindowListener with empty method bodies. It is a convenience class: it exists so you do not have to implement all seven methods when you only need one or two.

  • Classes extend WindowAdapter and override only the methods they need.
  • It is not meant to be instantiated directly — it is a base class.
  • The method overridden most often by far is windowClosing.
  • It is Java's standard example of the Adapter design pattern: a class that sits between a fat interface and the small piece of it you actually care about.

So the version you will actually write — and the one in your instructor's notes — is this:

WindowDestroyer.java

import java.awt.event.WindowAdapter;
import java.awt.event.WindowEvent;

public class WindowDestroyer extends WindowAdapter {
   public void windowClosing(WindowEvent e) {
      System.exit(0);  // Terminate the program when the window is closed
   }
}

That is the class FirstWindow and SecondWindow have been using since §5. Swap System.exit(0) for e.getWindow().dispose() and the same class closes just the one window instead of the whole application — both versions appear in the course code, and which one is right depends entirely on whether your program has one window or several.

Common Mistake— extends versus implements

It is extends WindowAdapter and implements WindowListener. WindowAdapter is a class, so you extend it; WindowListener is an interface, so you implement it. Writing implements WindowAdapter gives error: interface expected here, and extends WindowListener gives error: no interface expected here.

There is a real cost to the adapter, too: because WindowAdapter is a class, extending it uses up your one superclass. A class that already extends JFrame cannot also extend WindowAdapter. That is why a frame that wants to be its own listener has to write implements WindowListener and supply all seven methods — or, much more commonly, use a small separate class or an inner class, as you will see in the practice problems.

Quick Check 15.12

Two questions about which method to override, and one about which tool to reach for.

(a) You want to ask "save your changes?" when the user clicks the close box. Which of the seven methods do you override, and why not the other close-sounding one?

windowClosing. It fires when the user requests a close, before anything has happened, so you still have a window to put a question in and you can decide not to close after all. windowClosed fires after the window has been disposed of — by then it is far too late to ask.

You also need setDefaultCloseOperation(JFrame.DO_NOTHING_ON_CLOSE);, or Swing's default behavior hides the window out from under your question.

(b) You want to pause a game whenever its window is minimised and resume when it is restored. Which methods?

windowIconified to pause and windowDeiconified to resume. This is the case that justifies the seven-method interface: the other six methods are not padding, they are events somebody really does need.

(c) For part (b), would you extend WindowAdapter or implement WindowListener?

Extend WindowAdapter and override just those two. You need two of seven methods, so the adapter saves you five empty bodies — that is precisely the situation it was designed for.

The only reason to go back to implements WindowListener is that you have already spent your extends on something else, most often JFrame itself.

Things to notice across all three parts. The decision procedure is always the same two questions. Which of the seven events is the moment I care about? — get that wrong and your code runs at the wrong time or not at all. Then: is my class free to extend WindowAdapter? — if yes, extend it; if no, implement the interface and write the stubs.

Problem 2 — "Are you sure!" (from Exam 2 Practice Problems — the window-listener half)

The original question says: "Modify the program that you wrote for the last gui by adding a windowListener to modify the behavior of the close window button. The first time it is pressed the Gui should display the message Are you sure! in red. The second time it is pressed, the Gui should display Are you really sure! and the third time it is pressed the program should exit. (One tricky issue to solve is how to prevent the gui window from disappearing when the close window button is clicked the first two times.)"

The GUI it refers to is built with layout managers and menus we have not met yet, so attach the same behavior to a window you can build today: a single frame, 400 by 150, titled Are You Sure?, containing one JLabel. Solve the tricky issue.

Plan. Three things have to be true at once.

  • The listener must count, so it needs a field that survives between clicks. Quick Check 15.10 showed exactly this: one listener object, one field, incremented each time.
  • The listener must change the label, so it needs a reference to the label. The neat way is to make the listener an inner class of the frame — an inner class can see the outer object's private fields directly. That is what your instructor's solution does.
  • The tricky issue: by default Swing hides the frame the first time the close box is clicked, so there would be no window left to show the message in. The answer is setDefaultCloseOperation(JFrame.DO_NOTHING_ON_CLOSE); — the one constant that means "the close box does nothing at all; my listener decides".

AreYouSure.java

import java.awt.Color;
import java.awt.event.WindowAdapter;
import java.awt.event.WindowEvent;

import javax.swing.JFrame;
import javax.swing.JLabel;

public class AreYouSure extends JFrame {
   public static final int WIDTH = 400;
   public static final int HEIGHT = 150;

   private JLabel message;
   private int closeAttempts = 0;

   public AreYouSure() {
      super("Are You Sure?");
      setSize(WIDTH, HEIGHT);

      // Without this line the window would vanish on the very first click.
      setDefaultCloseOperation(JFrame.DO_NOTHING_ON_CLOSE);

      message = new JLabel("  Try to close this window.");
      getContentPane().add(message);

      addWindowListener(new Confirmer());
   }

   // An inner class, so that it can see message and closeAttempts.
   private class Confirmer extends WindowAdapter {
      public void windowClosing(WindowEvent e) {
         closeAttempts++;
         if (closeAttempts == 1) {
            message.setText("  Are you sure!");
            message.setForeground(Color.RED);
         } else if (closeAttempts == 2) {
            message.setText("  Are you really sure!");
         } else {
            System.exit(0);
         }
      }
   }

   public static void main(String args[]) {
      AreYouSure gui = new AreYouSure();
      gui.setVisible(true);
   }
}

Click the close box and the label turns red and reads Are you sure!; the window stays. Click again and it reads Are you really sure! in the same red. Click a third time and the program exits.

Things to notice. setForeground sets the color of a component's text; setBackground sets the color behind it. The question says the message is displayed in red, so it is setForeground(Color.RED) on the label. Note it is only set once — the second message inherits it, because setting a color changes the component, not that one string.

Why an inner class. Confirmer needs message and closeAttempts, both private to AreYouSure. Written as a separate top-level class it could not see either, and you would have to pass the label into its constructor and keep the counter inside it. That works and is a perfectly good answer; the inner class is shorter and is what the posted solution uses. What you cannot do is make AreYouSure itself the listener by writing extends WindowAdapter — it already extends JFrame, and Java allows one superclass.

The two lines everybody forgets. DO_NOTHING_ON_CLOSE and addWindowListener(new Confirmer());. Without the first, the window disappears on click one and the rest is invisible. Without the second, the listener class is perfect and never runs.

Problem 3 — Find the three errors (added for these notes)

The following file is meant to display a 300 by 200 window containing the label Hello, where clicking the close box ends the program. Exactly 3 of the numbered lines have errors, and one further error is not on a numbered line at all. Identify each error and give a corrected version. Lines without a number are correct as written.

BrokenWindow.java

import javax.swing.JFrame;

public class BrokenWindow extends JFrame {
    public BrokenWindow() {
        super();
        setSize(300, 200);                            // line 1
        JLabel label = new JLabel("Hello");           // line 2
        add.getContentPane(label);                    // line 3
        setDefaultCloseOperation(EXIT_ON_CLOSE);      // line 4
    }

    public static void main(String args[]) {
        BrokenWindow w = new BrokenWindow();          // line 5
        w.setVisible();                               // line 6
    }
}

Plan. Compile it in your head in the order javac does: first the names (is every class imported?), then the calls (does this method exist, and do the arguments match?). Do not be distracted by line 4, which looks unusual but is fine.

Error 1 — the import, which is not a numbered line. Only JFrame is imported, so JLabel on line 2 is an unknown name. This produces two error messages from one mistake, one for the type and one for the constructor:

BrokenWindow.java:7: error: cannot find symbol
        JLabel label = new JLabel("Hello");           // line 2
        ^
  symbol:   class JLabel
  location: class BrokenWindow
BrokenWindow.java:7: error: cannot find symbol
        JLabel label = new JLabel("Hello");           // line 2
                           ^
  symbol:   class JLabel
  location: class BrokenWindow

Corrected: add import javax.swing.JLabel; (or replace both imports with import javax.swing.*;). Line 2 itself is correct.

Error 2 — line 3. The method name and the object have been swapped. add.getContentPane(label) reads as "the variable add, call getContentPane on it", and there is no variable called add:

BrokenWindow.java:8: error: cannot find symbol
        add.getContentPane(label);                    // line 3
        ^
  symbol:   variable add
  location: class BrokenWindow

Corrected: getContentPane().add(label); — get the container first, then add to it.

Error 3 — line 6. setVisible needs to be told what to set the visibility to:

BrokenWindow.java:14: error: method setVisible in class Window cannot be applied to given types;
        w.setVisible();                               // line 6
         ^
  required: boolean
  found:    no arguments
  reason: actual and formal argument lists differ in length

Corrected: w.setVisible(true);

Line 4 is correct. EXIT_ON_CLOSE with no JFrame. prefix compiles fine inside a subclass of JFrame, because the constant is inherited. JFrame.EXIT_ON_CLOSE is clearer and is what most code writes, but the bare name is not an error.

With all three fixed:

FixedWindow.java

import javax.swing.JFrame;
import javax.swing.JLabel;

        super();

        setDefaultCloseOperation(EXIT_ON_CLOSE);      // line 4

    }
}

Things to notice. javac reported four messages for three mistakes. One missing import produced two of them, because both the declared type and the constructor call are unknown names. Counting error messages is not the same as counting errors, and this is the usual reason why.

Problem 4 — Short answer (added for these notes)

Five one-or-two-sentence questions of the kind that open a GUI exam problem.

(a) Why must a class that implements WindowListener write seven methods, when a class that extends WindowAdapter can write one?

Implementing an interface means implementing every method it declares, and WindowListener declares seven abstract methods. WindowAdapter is a class that has already implemented all seven, with empty bodies; extending it means you inherit those seven implementations and need only override the ones you want to change.

(b) Name the four constants you can pass to setDefaultCloseOperation and say what each one does.

DO_NOTHING_ON_CLOSE — the close box does nothing, leaving the decision to a listener. HIDE_ON_CLOSE — the window is hidden but not destroyed; this is the default. DISPOSE_ON_CLOSE — the window is hidden and its resources released. EXIT_ON_CLOSE — the entire application exits.

(c) A student's window appears but their JLabel does not. They wrote add(myLabel);. Is that the bug?

No — that one actually works. Since Java 5, JFrame.add quietly forwards to the content pane, so add(myLabel) and getContentPane().add(myLabel) do the same thing. Older textbooks and older exam papers insist on the longer form, and it is the one to write in an exam answer because it is what the marking scheme expects, but it is not the cause of a missing label.

Look elsewhere: was setSize called, is the label being added after the window became visible, or is a second component overwriting it in the same BorderLayout region?

(d) Why can a class that already extends JFrame not also extend WindowAdapter, and what do you do instead?

Java has single inheritance: one extends, and JFrame has taken it. The alternatives are to write implements WindowListener on the frame and supply all seven methods, or to keep the listener in a separate class — either a top-level class or an inner class, which is what Practice Problem 2 does.

Note that implements is not limited in the same way: a class may implement any number of interfaces, which is precisely why public class P1 extends JFrame implements ActionListener is a legal and extremely common class header.

(e) Give the three lines, in order, that turn a bare JFrame variable into a window on the screen.

JFrame gui = new JFrame();, then gui.setSize(w, h);, then gui.setVisible(true);.

Things to notice across all five parts. Every one of these is a sentence from §4 to §8 turned into a question, and every one of them has appeared on a GUI exam problem as the part that decides whether the rest of your code can score. Learn the three-line incantation in (e) until you can write it without thinking; then the exam question is only about what you put between lines two and three.

Problem 5 — What is the output? (added for these notes)

This program never opens a window. It builds two listeners and calls their methods directly, which is a perfectly ordinary thing to do to an object. Give the exact output.

ListenerQuiz.java

import java.awt.event.WindowAdapter;
import java.awt.event.WindowEvent;
import java.awt.event.WindowListener;

class Base extends WindowAdapter {
    public void windowOpened(WindowEvent e)  { System.out.println("Base opened"); }
    public void windowClosing(WindowEvent e) { System.out.println("Base closing"); }
}

class Derived extends Base {
    private int count = 0;
    public void windowClosing(WindowEvent e) {
        count++;
        System.out.println("Derived closing " + count);
    }
    public void windowActivated(WindowEvent e) {
        System.out.println("Derived activated");
        windowClosing(e);
    }
}

public class ListenerQuiz {
    public static void main(String args[]) {
        WindowListener a = new Base();
        WindowListener b = new Derived();

        a.windowOpened(null);        // line (a)
        a.windowActivated(null);     // line (b)
        b.windowOpened(null);        // line (c)
        b.windowActivated(null);     // line (d)
        b.windowClosing(null);       // line (e)
        b.windowIconified(null);     // line (f)
    }
}

(a) What is printed at line (a)?

Base opened. a refers to a Base, which overrides windowOpened.

(b) What is printed at line (b)?

Nothing. Base does not override windowActivated, so the call lands in WindowAdapter's empty body and returns.

(c) What is printed at line (c)?

Base opened. Derived does not override windowOpened, so the search goes up one level and finds Base's version. Inheritance, not the adapter, supplies this one.

(d) What is printed at line (d)? There are two lines here.

Derived activated and then Derived closing 1. windowActivated prints and then calls windowClosing(e) on the same object, which runs Derived's version and increments count from 0 to 1.

(e) What is printed at line (e)?

Derived closing 2. Same object, so count is still 1 when the method starts and becomes 2. Base closing never appears — Derived overrides it, and the dynamic type decides.

(f) What is printed at line (f)? Then write out the complete output of the program.

Nothing at line (f) — neither Derived nor Base overrides windowIconified, so WindowAdapter's empty body runs. The whole program prints five lines:

Base opened
Base opened
Derived activated
Derived closing 1
Derived closing 2

Things to notice across all six parts. Six of the twelve calls printed nothing, and every silent one was WindowAdapter absorbing an event nobody cared about. That is the adapter's entire job, seen from the inside.

The method-resolution rule is the one from Lecture 13, unchanged: start at the object's dynamic type and walk up until you find a body. What GUIs add is a guarantee that the walk always terminates in something, because WindowAdapter sits at the bottom with a body for every method. That is why a listener can never fail to handle an event — at worst it handles it by doing nothing.

Line (d) is the trap. Calling windowClosing(e) from inside another method is an ordinary method call on this, and it dispatches on the dynamic type just like any other. Two of the six calls in main produced output from windowClosing, and that is why the counter reads 2 and not 1.

Lecture Summary
  • A GUI is built from windows, menus, buttons, text fields and labels. A component is any one of them; a container is a component that holds other components; a frame is the top-level container, and in Java it is a JFrame.
  • Three packages: javax.swing for the J classes, java.awt for Color and Container, java.awt.event for every Event, Listener and Adapter.
  • The three lines that make a window: new JFrame(), setSize(w, h), setVisible(true). main may finish afterwards — the event dispatch thread keeps the program alive.
  • setDefaultCloseOperation decides what the close box means. The default is HIDE_ON_CLOSE, which is why a program you thought you closed is still running. Use EXIT_ON_CLOSE for a one-window program and DO_NOTHING_ON_CLOSE when a listener of yours will decide.
  • Two ways to use JFrame: instantiate one for a throwaway demo, or write a class that extends JFrame and configures itself in its own constructor. The second is the pattern for every real program and every exam question.
  • Components go in the content pane: getContentPane().add(label). A lone component added there fills it, because the content pane starts out with a BorderLayout.
  • Every Java event has three parts — an event source that fires it, an event object describing it, and a listener that handles it — plus a registration call, addWindowListener, that connects source to listener.
  • A listener is an interface you implement. That is what Lecture 14 was for: addWindowListener takes a WindowListener, and your class satisfying that interface is the whole mechanism by which library code calls yours.
  • WindowListener has seven methods and you must write all seven. WindowAdapter is an abstract class that implements them all with empty bodies, so extends WindowAdapter plus one overridden windowClosing gives you WindowDestroyer in four lines.
