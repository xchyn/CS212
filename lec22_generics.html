1.The problem: a container that holds Object

Last time you built a LinkedList, a Stack and a Queue out of one small Node class, and the lecture ended on a complaint. Every one of those classes stores Integer and nothing else. addTail("hello") is a compile error. To get a list of Strings you would copy all three files and change every Integer to String; to get a list of Points you would copy them again. Her own summary of the situation is one line: "Each data structure implemented with specific data types (e.g., Integer). Limited reusability across different data types."

There is an obvious-looking escape. Every class in Java extends Object, so a field of type Object can hold a reference to anything. Store Object and one set of files serves every element type. This is genuinely how Java's collections worked before 2004, and it is worth seeing exactly what it costs, because that cost is the reason generics exist.

Worked Example— the pre-generics container, and where it breaks

Here is the smallest possible container: a box that holds one thing. Written with Object, it will hold anything at all.

Read it and decide two things before you open the toggle. First, which line will the compiler reject? Second, what does the program print?

ObjectBoxDemo.java

// A container of the kind people wrote before generics existed.
// It holds Object, so it will hold anything -- and it checks nothing.
class ObjectBox {
    private Object item;

    public void set(Object o) { item = o; }

    public Object get() { return item; }
}

public class ObjectBoxDemo {
    public static void main(String args[]) {
        ObjectBox b = new ObjectBox();

        b.set("CSCI 212");
        String s = (String) b.get();          // cast required on the way out
        System.out.println("stored: " + s + ", length " + s.length());

        // Nothing at all stops us putting a different type in the same box.
        b.set(212);
        String t = (String) b.get();          // the compiler is happy with this
        System.out.println("we never reach this line: " + t);
    }
}

The compiler rejects nothing. It compiles cleanly, runs, prints one line, and then dies:

stored: CSCI 212, length 8
Exception in thread "main" java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')
	at ObjectBoxDemo.main(ObjectBoxDemo.java:21)

Three separate problems are visible in that short file, and they are exactly the three that generics fix.

  • A cast on every retrieval. get() returns Object, and an Object has no length(). To do anything useful you must write (String) in front of every single call. That is noise, and every one of those casts is a place to make a mistake.
  • The cast is a promise the compiler cannot check. (String) b.get() is you telling javac "trust me, this is a String." It does trust you. It inserts a run-time check and moves on.
  • The failure arrives at run time. ClassCastException is thrown while the program is running, in front of a user, possibly weeks after you shipped it. The information needed to prevent it — that this box was meant to hold Strings — existed when you wrote the code, but there was no way to write it down.
Definition— generics

Generics let you write classes, interfaces and methods that operate on a type parameter — a stand-in for a type, filled in later at the point where the class or method is used.

Her notes give four benefits, and each one is the mirror image of a problem in the box above:

  • Type safety — errors are caught at compile time, not run time.
  • Elimination of casts — no explicit type casting on the way out.
  • Code reusability — write once, use with multiple types.
  • Better readability — ArrayList<String> says what is in the list; ArrayList does not.

Here is the same box, written once, with the element type left as a blank called T. Compare it line by line with the version above: the only difference is that Object has become T.

Worked Example— the same container, made generic

Before you reveal: how many casts do you see, and what is the type of value on the line int value = n.get();?

BoxDemo.java

// The same container, written once, with the element type left as a blank.
class Box<T> {
    private T item;

    public void set(T o) { item = o; }

    public T get() { return item; }
}

public class BoxDemo {
    public static void main(String args[]) {
        Box<String> b = new Box<String>();
        b.set("CSCI 212");
        String s = b.get();               // no cast
        System.out.println("stored: " + s + ", length " + s.length());

        Box<Integer> n = new Box<>();     // the diamond: Java infers Integer
        n.set(212);
        int value = n.get();              // no cast; auto-unboxed to int
        System.out.println("stored: " + value + ", doubled " + (value * 2));

        // Same class, three different element types, one source file.
        Box<Double> d = new Box<>();
        d.set(3.5);
        System.out.println("stored: " + d.get() + ", halved " + (d.get() / 2));
    }
}

stored: 212, doubled 424
stored: 3.5, halved 1.75

Key Idea

An Object container trades a compile error for a run-time crash. A generic container does not trade anything away: you keep the one-copy-serves-all reuse and you keep full type checking. That is why generics were added to the language in Java 5 and why every collection you have used since Lecture 6 has angle brackets in its name.

Quick Check 22.1

A colleague defends the Object version: "the cast documents the intent perfectly well, and my tests pass."

(a) What is the difference between a cast and a type argument, in one sentence?

A cast is a claim you make that the compiler accepts without evidence and checks later at run time. A type argument is a fact you declare that the compiler enforces on every call, now.

(b) Why do passing tests not settle the question?

Tests only exercise the paths you thought to write. The ObjectBox program above would pass any test that only ever stores a String; the crash appears the first time some other code path stores something else. A compile error, by contrast, is found on every path at once, including the ones nobody has tested yet.

Things to notice across both parts. "It compiles" is a much weaker statement about an Object-based container than about a generic one. Every cast in a program is a small unchecked promise, and generics exist to let you stop making them.

Quick Check 22.2

Using ObjectBox exactly as written above, what does each fragment do — compile error, run-time exception, or run normally? Assume ObjectBox b = new ObjectBox(); each time.

(a) b.set(3.14); double d = (Double) b.get();

Runs normally. 3.14 is auto-boxed into a Double, stored as an Object, cast back to Double, and unboxed into d. The cast is correct, so nothing complains — but notice you still had to write it.

(b) b.set("hi"); int n = b.get().length();

Compile error. get() is declared to return Object, and Object has no length method, so the compiler stops you before it ever considers what is actually inside. This is the "elimination of casts" benefit, seen from the other side: without generics the cast is not optional.

(c) b.set("hi"); Integer n = (Integer) b.get();

Compiles; throws ClassCastException at run time. Casting an Object down to Integer is legal as far as the compiler is concerned, because some Objects really are Integers. The check happens when the line executes, and this one is holding a String.

Things to notice across all three parts. Part (b) is the only one the compiler catches, and it catches it for the wrong reason — not "you stored a String and asked for a number", just "Object has no length". The two parts where the type actually matters, (a) and (c), look identical to the compiler. That is precisely what a type parameter fixes.

2.Using the generic classes and methods you already have

You have been using generics since Lecture 6 without writing one. ArrayList<String> is not a special class called "ArrayList of String" — it is the one and only ArrayList class, told which type it is holding this time. Java's library is full of these: ArrayList, LinkedList, Stack, Queue, HashMap.

Definition— type parameter, type argument, parameterized type

A type parameter is the placeholder written in the class declaration: the T in class Box<T>, or the E in the library's class ArrayList<E>. It is a name for a type that is not known yet.

A type argument is the real type you supply at the point of use: the String in ArrayList<String>.

The combination — class name plus angle brackets plus type argument — is a parameterized type, and it is used exactly like any other type: as a variable type, a parameter type, or a return type.

Her first example is a Stack restricted to Swing buttons. It reads five words from the keyboard, wraps each one in a JButton, pushes the buttons onto a stack, and then pops them into a window — so they appear in reverse order, five at the bottom and one at the top.

Example1.java

import java.awt.Font;
import java.awt.GridLayout;
import java.util.Scanner;
import java.util.Stack;

import javax.swing.JButton;
import javax.swing.JFrame;

// applying a generic class
public class Example1 {
   public static void main(String args[]) {
      Scanner s = new Scanner(System.in);
      Stack<JButton> stack = new Stack<JButton>();
      for (int i = 5; i >= 1; i--) {
         System.out.println("Enter text for label: ");
         JButton b = new JButton("" + i + ". " + s.next());
         b.setFont(new Font("Arial", Font.BOLD, 30));
         stack.push(b);
      }
      JFrame frame = new JFrame();
      frame.setSize(1200, 900);
      frame.setLayout(new GridLayout(5,1));
      while (!stack.empty()) frame.add(stack.pop());
      frame.setVisible(true);
   }
}

This one opens a window rather than printing, so there is no console output to show. What appears is a 1200 × 900 frame divided by a GridLayout(5,1) into five equal rows, each holding one large Arial button. The button labelled 1. is at the top, because it was pushed last and popped first — the Lecture 21 stack material, driving a Lecture 16 layout.

The generics content is the single word JButton inside the angle brackets. Two things follow from it:

  • pop() returns a JButton. frame.add(stack.pop()) compiles because the compiler knows the type. With a pre-generics Stack you would have had to write frame.add((JButton) stack.pop()).
  • push accepts nothing else. Slip a String into that loop and the file does not compile.

ButtonStackDemo.java

import java.util.Stack;
import javax.swing.JButton;

public class ButtonStackDemo {
    public static void main(String args[]) {
        // Exactly her Stack<JButton>, but we print the buttons instead of
        // putting them in a window.
        Stack<JButton> stack = new Stack<JButton>();
        String[] labels = {"one", "two", "three", "four", "five"};

        for (int i = 5; i >= 1; i--) {
            JButton b = new JButton("" + i + ". " + labels[5 - i]);
            stack.push(b);
        }

        }
    }
}

The loop pushes 5. one first and 1. five last, so 1. five is on top and comes off first. In her version those five buttons are added to the frame in that order, top row downward, which is why the finished window reads 1, 2, 3, 4, 5 from top to bottom even though the loop counted backwards.

Generic methods from the library work the same way, except that you usually do not write the type argument at all. Her second example sorts two arrays of different types with one method.

Two things her notes point out about this example.

  • The compiler infers the type. You wrote Arrays.sort(data), not Arrays.<Integer>sort(data). Java looks at the argument, sees Integer[], and works out the type argument for you. This is type inference, and it is the reason generic methods usually look like ordinary methods at the call site.
  • It works for any type that implements Comparable. Integer and Double both do, which is why both calls succeed. Hand it an array of a class of your own that has no ordering and it will not compile — we come back to exactly that in §6.

Note also that these are Integer[] and Double[], not int[] and double[]. That is not decoration; it is forced, and §3 explains why.

Quick Check 22.3

You have ArrayList<String> names = new ArrayList<String>(); and Stack<Integer> s = new Stack<Integer>();. For each line say whether it compiles, and if it does, what its type is.

(a) names.add(42);

Compile error. add on an ArrayList<String> takes a String, and 42 is an int. There is no conversion from int to String — autoboxing turns an int into an Integer, not into text.

(b) int n = names.get(0).length();

Compiles. get(0) returns a String, so .length() is available and returns an int. Compare this with Quick Check 22.2(b), where the same idea failed because get returned Object.

(c) s.push(7);

Compiles. push wants an Integer; the int 7 is auto-boxed into one. Autoboxing happens automatically at the boundary between primitives and their wrapper classes, so push(7) and push(Integer.valueOf(7)) mean the same thing.

(d) String top = s.pop();

Compile error. s.pop() on a Stack<Integer> returns an Integer, and an Integer is not a String. You would have to write Integer top = s.pop(); or String top = "" + s.pop();.

Things to notice across all four parts. Read the declaration first, every time. Once you know a variable is a Stack<Integer>, every method on it behaves as if it had been written specifically for Integer — push takes one, pop returns one — and the answers fall out of that with no further thought. That readability is the fourth benefit on her list, and it is the one students undervalue.

3.Why a type argument must be a reference type

Her examples all use Integer[] and Double[], never int[] and double[], and every collection you have written holds Integer rather than int. That is not a style choice. It is a hard rule of the language.

Key Idea— a type argument is always a reference type

A type argument must name a class, an interface or an array type. The eight primitive types — byte, short, int, long, float, double, char, boolean — are not allowed. ArrayList<int> and Box<int> do not compile.

Read the message: required: reference, found: int. It says exactly what the rule is, and it says it twice — once for the declaration and once for the new.

The reason will make complete sense once you have seen §8, so take it on trust for a moment: the compiler implements a generic class by compiling one copy in which every T behaves like an Object, and a primitive is not an Object. There is nowhere for an int to live in that scheme.

Definition— wrapper class, autoboxing (recall, Lecture 6)

Every primitive type has a matching wrapper class — an object whose only job is to hold one primitive value.

Primitivebyteshortintlongfloatdoublecharboolean
WrapperByteShortIntegerLongFloatDoubleCharacterBoolean

Autoboxing is Java converting a primitive into its wrapper automatically where an object is expected; unboxing is the reverse. Because of them you can write list.add(90) and int n = list.get(0) even though the list really holds Integer objects.

Note the two spellings that catch people: int becomes Integer, not Int; and char becomes Character, not Char.

Worked Example— boxing in and out of a generic container

This program never writes the word Integer except in the declaration, and never writes a cast at all — yet what is actually stored in the list is objects. The fourth line of output proves it.

WrapperDemo.java

import java.util.ArrayList;

public class WrapperDemo {
    public static void main(String args[]) {
        // The type argument is Integer, the wrapper class -- never int.
        ArrayList<Integer> scores = new ArrayList<Integer>();

        scores.add(90);                 // the int 90 is auto-boxed into an Integer
        scores.add(85);
        scores.add(78);

        int total = 0;
        for (int s : scores) total += s;      // each Integer is auto-unboxed

        System.out.println("scores  " + scores);
        System.out.println("total   " + total);
        System.out.println("average " + total / 3.0);

        // What is actually in the list is an object, not a primitive.
        System.out.println("element 0 is really a " + scores.get(0).getClass().getName());

        ArrayList<Character> letters = new ArrayList<>();
        letters.add('J');
        letters.add('a');
        char first = letters.get(0);          // unboxed back to a char
        System.out.println("letters " + letters + "   first as a number " + (int) first);
    }
}
scores  [90, 85, 78]
total   253
average 84.33333333333333
element 0 is really a java.lang.Integer
letters [J, a]   first as a number 74

Three details worth pulling out.

  • for (int s : scores) unboxes on every iteration. The loop variable is declared int, the elements are Integer, and Java inserts the conversion. You could equally write for (Integer s : scores).
  • getClass().getName() is java.lang.Integer. The list holds real objects on the heap, not a block of 32-bit slots. That costs memory and a little speed, which is the honest price of the rule — and the reason int[] still exists and is still the right choice for a million numbers.
  • The average is 84.33333333333333, not 84. total is an int and 3.0 is a double, so real division happens — the Lecture 1 rule, unchanged by any of this.
Common Mistake— comparing boxed values with ==

Autoboxing is so smooth that it is easy to forget the elements are objects. They are, and == on objects compares references — the Lecture 9 lesson. Two Integer objects holding 128 are not == to each other, while two holding 127 usually are, because Java caches the small ones. Inside any generic container, compare elements with equals, never with ==. Last week's contains and indexOf used n.getData().equals(d) for exactly this reason, and making the class generic does not change it.

Quick Check 22.4

Give the type argument you would write for each container, or say why it cannot be written.

Things to notice across all four parts. The rule is about the type argument itself, one level down: ArrayList<int> is out, ArrayList<Integer> and ArrayList<int[]> are both in. When in doubt, ask "could a variable of this type hold null?" If yes, it is a reference type and it is allowed.

4.Writing your own generic class

Using the library's generics is easy because somebody else declared the type parameter. Now you declare one.

Procedure— turning an ordinary class into a generic one
  1. Pick the type that should vary. In last week's Node that is the type of data.
  2. Add a type parameter to the class header: public class Node becomes public class Node<T>.
  3. Replace that type everywhere inside the class with T — in fields, in parameter lists, in return types.
  4. Anywhere the class refers to itself, carry the parameter along: private Node next; becomes private Node<T> next;.
  5. Nothing else changes. No new methods, no casts, no instanceof.
Definition— the conventional names

A type parameter can be called anything a class can be called, but by convention it is a single uppercase letter, so that a reader can tell instantly that T is a placeholder and not a real class:

LetterRead it asTypical use
TTypethe general-purpose choice, and what her notes use
EElementthe element type of a collection — the library's ArrayList<E>
K, VKey, Valuea pair or a map: HashMap<K,V>
NNumbera numeric type parameter
S, U, V—second, third, fourth type parameters

These are conventions, not rules. class Node<ElementType> compiles. It just makes every reader stop and check whether ElementType is a class they have never heard of.

Her notes list what that one letter bought:

  • The type parameter T allows the Node to store any type of data.
  • The class can be instantiated with different types — Node<Integer>, Node<String>.
  • Methods return the exact type that was used to instantiate the class.
  • The next-node reference uses the same type parameter, so a chain of Node<String> can only ever link to more Node<String>.
Key Idea— what T is

T is not a type. It is a name for a type that has not been chosen yet, and it is chosen at the moment somebody writes new Node<String>(...). Inside the class you may use T exactly as if it were a real class name — declare fields of type T, take T parameters, return T — but you may not do anything that requires knowing which class it is: no new T(), no new T[n], no T.someStaticMethod().

Worked Example— one Node class, three element types

This builds a three-node chain of String, then a two-node chain of Integer, using the same class both times. Look closely at the line n.getData().toUpperCase() — that call is only legal because the compiler knows T is String here.

Before you reveal: what does the last line print for c.getNext()?

NodeDemo.java

// Her generic Node, exactly as in the Spring 2025 notes.
class Node<T> {
    private T data;
    private Node<T> next;

    public Node() {
        data = null;
        next = null;
    }

    public Node(T d, Node<T> n) {
        data = d;
        next = n;
    }

    public T getData() { return data; }

    public Node<T> getNext() { return next; }

    public void setData(T d) { data = d; }

    public void setNext(Node<T> n) { next = n; }
}

public class NodeDemo {
    public static void main(String args[]) {
        // A chain of Strings, built back to front exactly as in Lecture 21.
        Node<String> third = new Node<>("green", null);
        Node<String> second = new Node<>("blue", third);
        Node<String> head = new Node<>("red", second);

        Node<String> n = head;
        while (n != null) {
            // getData() is a String here, so String methods are available.
            System.out.print(n.getData().toUpperCase() + " --> ");
            n = n.getNext();
        }
        System.out.println("null");

        // The same class, holding Integers this time.
        Node<Integer> b = new Node<>(20, null);
        Node<Integer> a = new Node<>(10, b);
        System.out.println("sum of the two numbers: "
                           + (a.getData() + a.getNext().getData()));

        // And a node whose data is itself a list-like object.
        Node<Character> c = new Node<>('J', null);
        System.out.println("char node: " + c.getData()
                           + "   next is " + c.getNext());
    }
}

sum of the two numbers: 30
char node: J   next is null

c.getNext() is null, and concatenating a null reference onto a String gives the four characters null rather than throwing — the same behaviour you met in Lecture 4.

Two more things this program demonstrates without saying so:

Definition— the diamond operator

5.Writing your own generic method

A generic class declares its type parameter once, in the class header, and every method in the class shares it. A generic method declares its own, and it belongs to that one method — which means a generic method can live perfectly happily in a class that is not generic at all.

Definition— generic method

A generic method declares its type parameter in angle brackets immediately before the return type:

public static <T> T middle(T[] array)

Read that left to right: public static — the modifiers; <T> — "this method introduces a type parameter called T"; T — the return type; middle(T[] array) — the name and the parameters.

Her notes put it in one line: the type parameter is declared before the return type, and generic methods can be defined in both generic and non-generic classes.

Why there? Because a name has to be introduced before it is used, and the return type is the first place T appears. If <T> came later, the compiler would reach the return type with no idea what T meant — and that is exactly the error you get if you leave it out:

    public static <T> void reverse(T[] array) {
        if (array == null || array.length <= 1) {

            left++;
            right--;
        }
    }

        }

Quick Check 22.8

You want a reversedCopy that leaves the original alone and returns a new, reversed array.

(a) Why can you not simply write T[] copy = new T[array.length];?

Because the JVM has to know the element type of an array when it creates it — that type is stored in the array object and checked on every assignment — and by the time the program runs, T is gone. (b) Write the method anyway, using java.util.Arrays.copyOf.

Plan. Arrays.copyOf(array, n) is itself a generic method, and the crucial thing about it is that it builds the new array by asking the existing array what its element type is. ReverseCopy.java

import java.util.Arrays;

public class ReverseCopy {
    // Returns a NEW array, reversed. The original is left alone.
    public static <T> T[] reversedCopy(T[] array) {
        // new T[n] is illegal. Arrays.copyOf makes an array of the same
        // run-time type as the one it is given, which is exactly what we need.
        T[] copy = Arrays.copyOf(array, array.length);
        for (int i = 0; i < array.length; i++)
            copy[i] = array[array.length - 1 - i];
        return copy;
    }

        System.out.println("original " + Arrays.toString(fruits));
        System.out.println("copy     " + Arrays.toString(backwards));
        System.out.println("copy is really a " + backwards.getClass().getName());
    }
}

6.Bounded type parameters

An unbounded T is a very weak promise. All the compiler knows is that it is some reference type, so all you may call on it are the methods every object has: toString, equals, hashCode. That was enough for middle and reverse, which only ever moved elements around. It is not enough the moment you want to do arithmetic on them, or compare them.

Definition— bounded type parameter

A bounded type parameter restricts which types may be supplied as the type argument, using the keyword extends:

public static <T extends Number> double sum(T[] array)

This says "T may be Number or any subclass of Number". Number is called the upper bound. Two consequences, and they are two sides of one coin:

  • Callers are restricted — sum(stringArray) no longer compiles.
  • You are enabled — inside the method you may call any Number method on a T, because the compiler now knows every possible T has them.

Note the keyword: it is extends even when the bound is an interface. Java reuses the word here rather than adding implements to the grammar, so <T extends Comparable<T>> is normal and correct.

7.Making last week's containers generic

Everything so far has been groundwork for this. Node is already done — §4 showed her generic version. LinkedList, Stack and Queue need the same four-step treatment, and because they are built on top of one another, the type parameter has to be carried up through each layer.

Procedure— the three edits, per class
  1. Add <T> to the class header.
  2. Change every Integer in the class to T.
  3. Change every mention of a class you also made generic so that it carries the parameter: Node becomes Node<T>, and inside Stack the field private LinkedList data; becomes private LinkedList<T> data;.

Nothing else. No method bodies change, no algorithm changes, no casts appear or disappear. If you find yourself rewriting logic, you have gone off the path.

Here is the whole LinkedList, generic. Compare it against last week's file: apart from the header, every difference is the word Integer replaced by T or the word Node replaced by Node<T>.

LinkedList.java

public class LinkedList<T> {
   private Node<T> head, tail;
   private int size;

   public LinkedList() {
      head = tail = null;
      size = 0;
   }

   public int size() { return size; }

   public boolean isEmpty() { return size == 0; }

   public void addHead(T d) {
      Node<T> n = new Node<T>(d, head);
      head = n;
      size++;
      if (tail == null) tail = head;
   }

   public void addTail(T d) {
      Node<T> n = new Node<T>(d, null);
      if (tail == null) head = tail = n;
      else { tail.setNext(n); tail = n; }
      size++;
   }

   public T removeHead() throws Exception {
      if (head == null) throw new Exception("Empty List");
      Node<T> n = head;
      head = head.getNext();
      if (head == null) tail = head;
      size--;
      return n.getData();
   }

   public T peekHead() throws Exception {
      if (head == null) throw new Exception("Empty List");
      return head.getData();
   }

   public boolean contains(T d) {
      Node<T> n = head;
      while (n != null) {
         if (n.getData().equals(d)) return true;
         n = n.getNext();
      }
      return false;
   }

   public String toString() {
      String ans = "";
      Node<T> n = head;
      while (n != null) {
         ans += n.getData();
         ans += "-->";
         n = n.getNext();
      }
      return ans;
   }
}

Two lines are worth a second look. size() still returns int, and isEmpty() still returns boolean — those are not the element type, and turning everything into T is the commonest mistake when doing this conversion. toString() returns String for the same reason. Only the things that were Integer because they held an element become T.

   private LinkedList<T> data;

   public Queue() {
      data = new LinkedList<T>();
   }

   // Remove from front (FIFO principle)
   public T dequeue() throws Exception {
      return data.removeHead();
   }

   // Add to rear
   public void enqueue(T x) {
      data.addTail(x);
   }

   // Look at the front without removing it
   public T front() throws Exception {
      return data.peekHead();
   }

   public boolean isEmpty() { return data.isEmpty(); }

   public int size() { return data.size(); }
}
Key Idea— the parameter travels through composition

private LinkedList<T> data; inside Stack<T> is the line that makes the whole thing hang together. A Stack<String> contains a LinkedList<String>, which contains Node<String> objects. The one type argument you wrote at the top — new Stack<String>() — propagates all the way down to the data field of every node, and the compiler checks each layer.

8.Type erasure: what the compiler actually does

Three times now something has been forbidden for a reason we postponed: no primitive type arguments, no new T[n], no new T(). One idea explains all three, and it also explains an exam question you will meet in the practice section.

Definition— type erasure

Generics are a compile-time feature. The compiler uses the type arguments to check every call, and then erases them: in the .class file that comes out, every unbounded T has become Object, every <T extends Number> has become Number, and the angle brackets are gone. Casts are inserted automatically wherever they are needed.

There is one compiled copy of ArrayList, not one per element type. The information that a particular list was declared ArrayList<String> does not exist at run time.

Worked Example— two lists, one class

If ArrayList<String> and ArrayList<Integer> were really different types, they would have different Class objects. Ask them.

import java.util.ArrayList;

Quick Check 22.12

Answer each part from the erasure rule alone.

(a) Does new Box<String>() and new Box<Integer>() produce objects of the same class at run time?

Yes. There is one compiled Box class, and getClass() returns the same Class object for both. The String and the Integer existed only for the compiler.

(b) A generic class declares <T extends Number>. What does T become in the bytecode?

Number, not Object. Erasure replaces a type parameter with its bound, and the bound is what makes element.doubleValue() compile into an ordinary call on a Number. An unbounded T erases to Object because its implicit bound is Object — which is exactly what the error message in §6 said: T extends Object.

(c) Does the following pair of methods compile in one class? void add(T x) and void add(String x), where T is the class's own unbounded type parameter.

Yes. After erasure they are void add(Object x) and void add(String x), which are genuinely different signatures. The MyGen clash happened because T and V both erase to Object; here only one of them does.

Whether it is a good idea is another question. For a Box<String> both methods would apply to a String argument and the compiler would pick the more specific one, which is the kind of subtlety that produces bug reports.

(d) Somebody proposes adding a method public boolean holdsStrings() { return item instanceof String; } to Box<T>, to find out at run time what a box was declared to hold. Does it work?

It compiles, and it answers a different question from the one intended. item is an actual object, and asking an object whether it is a String is perfectly reasonable — so for a Box<String> holding "hi" it returns true. But for an empty Box<String> whose item is still null it returns false, because null instanceof String is false. The method reports what is in the box right now, not what the box was declared to hold, and the second thing is simply not recorded anywhere at run time.

Things to notice across all four parts. The single sentence to carry away is: generics are checked by the compiler and then erased. Every restriction in this lecture follows from it, and so does the reassurance — the check really did happen, so the absence of the type at run time costs you nothing in safety.

public class Functions {
    // A single generic function: the middle element of an array of any type.
    public static <T> T middleElement(T[] array) {
        if (array == null || array.length == 0) return null;
        return array[array.length / 2];
    }

    public static void main(String args[]) {
        int num = 5;                       // a positive odd number
        Double[] arrayD = new Double[num];
        String[] arrayS = new String[num];
        for (int i = 0; i < num; i++) {
            Double d = (i + 1) / 2.0;      // fixed values instead of Math.random()
            arrayD[i] = d;
            arrayS[i] = "" + d;
        }
        System.out.println(middleElement(arrayD));
        System.out.println(middleElement(arrayS));

        Integer[] arrayI = {3, 1, 4, 1, 5};
        System.out.println(middleElement(arrayI));
        System.out.println(middleElement(new String[0]));
    }
}

The exam's main reads a number from the keyboard and fills the arrays with Math.random(), which would print a different pair of numbers every run. To get output you can check, this version fixes num at 5 and uses (i + 1) / 2.0 instead, so the arrays hold 0.5, 1.0, 1.5, 2.0, 2.5.

        Holder<int> h = new Holder<int>(5);        // line 4
        System.out.println(h.get());
    }
}

Plan. Every one of these is a case of the compiler needing to know something about T that erasure has taken away, or needing T to exist somewhere it does not. Go through them by asking, for each line, "which T is this, and does it exist here?"

Line 1 — a static field cannot use T. A static field belongs to the class, and there is exactly one Holder class shared by Holder<String> and Holder<Integer> alike. There is no single T for it to be.

Holder.java:2: error: non-static type variable T cannot be referenced from a static context private static T shared;
        // line 1
^

Corrected: private T shared; — make it an instance field. (If it genuinely has to be shared across all boxes, its type has to be something concrete, such as Object.)

Line 2 — a static method cannot use the class's T either, for the same reason: there is no object, so there is no type argument.

Holder.java:9: error: non-static type variable T cannot be referenced from a static context public static T identity(T x) { return x; }
        // line 2
^

Corrected: give the method a type parameter of its own — public static <E> E identity(E x) { return x; }. A different letter is used deliberately, so nobody thinks it is the class's T.

Line 3 — new T[n] is generic array creation, forbidden because the JVM would have no element type to record in the new array.

Holder.java:12: error: generic array creation T[] a = new T[n];
        // line 3
^

Corrected: return a collection instead of an array — ArrayList<T> has no such problem, because it stores Object references internally and the compiler does the checking.

Line 4 — a type argument must be a reference type.

Holder.java:18: error: unexpected type Holder<int> h = new Holder<int>(5);
        // line 4
^
  required: reference
  found:    int

Corrected: Holder<Integer> h = new Holder<Integer>(5); — and the 5 is auto-boxed.

import java.util.ArrayList;

class Holder<T> {

    private T item;

    public Holder(T item) { this.item = item; }

    public T getShared() { return shared; }

Problem 6 — A class with two type parameters (added for these notes)

Write a generic class Pair<K, V> with private fields key of type K and value of type V, a two-parameter constructor, getKey, getValue, a toString of the form (key, value), and a method swap() that returns a new pair with the two components exchanged. Think carefully about the return type of swap. Then write a main that makes a Pair<String, Integer>, swaps it, and uses both components at their real types.

Plan. The only hard part is swap. Its return type cannot be Pair<K, V>, because the components have changed places — the key of the result is a V and the value is a K. So the return type is Pair<V, K>, and the body is return new Pair<V, K>(value, key);. Getting that right is the whole exercise; everything else is Problem 2 with two letters instead of one.

PairDemo.java

// A class with two type parameters. K and V are the conventional names
// for a key and a value.
class Pair<K, V> {
    private K key;
    private V value;

    public Pair(K key, V value) {
        this.key = key;
        this.value = value;
    }

    public K getKey() { return key; }

    public V getValue() { return value; }

    // The swapped pair has the type arguments the other way round.
    public Pair<V, K> swap() {
        return new Pair<V, K>(value, key);
    }

    public String toString() { return "(" + key + ", " + value + ")"; }
}

public class PairDemo {
    public static void main(String args[]) {
        Pair<String, Integer> score = new Pair<>("Ana", 95);
        System.out.println("score          " + score);
        System.out.println("key   " + score.getKey().toUpperCase());
        System.out.println("value " + (score.getValue() + 5));

        Pair<Integer, String> flipped = score.swap();
        System.out.println("swapped        " + flipped);
        System.out.println("key + 1 = " + (flipped.getKey() + 1));
        System.out.println("value lower = " + flipped.getValue().toLowerCase());

        // Both type parameters may be the same type. Nothing says they differ.
        Pair<String, String> capital = new Pair<>("France", "Paris");
        System.out.println("capital        " + capital + "  swapped " + capital.swap());
    }
}
score          (Ana, 95)
key   ANA
value 100
swapped        (95, Ana)
key + 1 = 96
value lower = ana
capital        (France, Paris)  swapped (Paris, France)

Things to notice. The four lines after each construction are the proof that the types really did travel. score.getKey().toUpperCase() is a String method; flipped.getKey() + 1 is arithmetic on an Integer. Swap the two and neither line compiles. Declaring swap as returning Pair<K, V> would break flipped.getKey() + 1 immediately, which is how you would catch the mistake even without thinking it through first.

The last line makes the Problem 4 point concretely: Pair<String, String> is perfectly legal, and it is why MyGen could not have two methods called set. Here there is no clash, because getKey and getValue have different names and swap takes no parameters at all.

K and V are only conventions. Pair<A, B> would compile identically. Use K and V when the two really are a key and a value, and T and U when they are just two types.

Lecture Summary
  • A container that stores Object is reusable but unsafe: every retrieval needs a cast, the compiler cannot check the cast, and a wrong one becomes a ClassCastException at run time. Generics give you the reuse and keep the checking.
  • Her four benefits: type safety (errors at compile time), elimination of casts, code reusability, and better readability.
  • A type parameter is the placeholder in the declaration — the T in class Box<T>. A type argument is the real type you supply — the String in Box<String>. Convention: T for type, E for element, K and V for key and value.
  • Instantiate with new Box<String>() or with the diamond, new Box<>(). Leaving the brackets off altogether gives a raw type, which switches the checking back off.
  • A type argument must be a reference type. ArrayList<int> does not compile; use the wrapper class Integer and let autoboxing do the rest.
  • A generic method declares its own type parameter immediately before the return type: public static <T> T middle(T[] array). Omit the <T> and you get cannot find symbol: class T. The type argument is normally inferred from the arguments, so you write middle(a), not Example4.<Integer>middle(a).
  • An unbounded T gives you only Object's methods. A bound — <T extends Number>, <T extends Comparable<T>> — restricts who may call the method and, in exchange, lets you call that type's methods inside it. The keyword is extends even for an interface.
  • Making a class generic is mechanical: add <T> to the header, change the element type to T, and carry the parameter through anything the class holds — Node<T> inside LinkedList<T>, LinkedList<T> inside Stack<T>. size() stays int and toString() stays String.
  • Type erasure: the compiler checks the type arguments and then removes them, so there is one compiled class for every element type and T becomes Object (or its bound). That single fact explains why there are no primitive type arguments, no new T[n], no new T(), no static T field, no instanceof List<String>, and why set(T) and set(V) clash.
