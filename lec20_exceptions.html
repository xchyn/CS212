1.What an exception is

Exam 2 is behind you. It closed out the parking-ticket case study, inheritance, polymorphism, abstract classes and interfaces, and the five GUI lectures. Everything from today onward is new material and it is all on the final: exceptions today, then linked lists, stacks and queues, then generics, then iterators and threads.

Today's topic is the one that has been hanging over the whole course. You have already seen programs die. In Lecture 3 an array index past the end killed one. In Lecture 6 an ArrayList did the same. In Lecture 17 a user typed twenty into a text field and Integer.parseInt gave up. Every one of those lectures said the same thing: we will explain this properly in Lecture 20. This is Lecture 20.

Definition— exception

An exception is an event that occurs during execution and disrupts the normal flow of instructions. Concretely, it is an object — an instance of a class such as NumberFormatException — that carries a description of what went wrong.

When a method cannot do its job, it creates one of these objects and throws it. Throwing stops that method immediately. The object then travels back up the chain of callers looking for someone who has said "I will deal with that kind of problem." If nobody has, the program stops and prints the object's description.

Compare that with what you would have done in C++, or in Java before this lecture: return a special value. A method that reads an age returns −1 for "the user typed nonsense." That approach has three problems, and exceptions fix all three.

Key Idea

An exception separates detecting a problem from deciding what to do about it. The method that discovers the trouble usually has no idea what the right response is — Integer.parseInt cannot know whether your program should reprompt, use a default, or quit. So it throws, and the code that does know catches.

2.try and catch

An exception you never handle is just a crash with better diagnostics. The point of the mechanism is that you can handle it.

Definition— try and catch

A try block encloses code that might throw. A catch block follows it and names one type of exception plus a variable to hold the thrown object:

try {
    // code that might throw } catch (SomeException e) { // what to do about it }

If nothing is thrown, the try block runs to the end and the catch block is skipped entirely. If something is thrown, the rest of the try block is abandoned, the thrown object is bound to e, the catch block runs, and execution then continues with whatever follows the whole try/catch. The program does not stop.

Common Mistake— the rest of the try block is abandoned

A catch does not resume where the throw happened. There is no "try that line again" in Java. If your try block is

try {
    int age = Integer.parseInt(text);
    // throws here System.out.println("You are " + age);  // skipped total = total + age;                   // skipped } catch (NumberFormatException e) { System.out.println("not a number"); }

then both later statements are skipped, and age does not exist outside the block at all. Keep try blocks small and put only the risky work and the work that depends on it inside.

import java.util.Scanner;

public class Example2 {

         System.out.print("How old are you? ");

         } catch (Exception e) {
            System.out.println("Your age must be an integer!");

Three details worth pinning down:

  • The prompt is outside the try. It has to be: it cannot fail, and it must happen on every round whatever happened last round.
  • readAgeFrom has no error handling of its own, and it does not need any. It just lets the exception pass through. That is the whole benefit of the mechanism — the method that detects a problem and the method that handles it can be far apart, with plain, uncluttered code in between.
  • catch (Exception e) catches almost everything. That is convenient here and dangerous in general; §3 and §5 explain why, and Example 3 in §4 shows the bug it hides.

Things to notice. Where you put good++ inside the try matters. If you had written it before readAgeFrom, it would count attempts, not successes, because the increment would already have happened when the throw arrived. Statements after the throwing call are skipped; statements before it are not undone. An exception is not a rollback.

Both counters have to be declared outside the loop, and age cannot be: a variable declared inside a try block dies at the closing brace, which is one more reason to keep those blocks small.

3.The hierarchy: checked and unchecked

catch (Exception e) caught a NumberFormatException in Example 2. That is not a coincidence, and it is not special-case magic in the compiler. It is inheritance — Lecture 12 — doing exactly what you would expect. Every exception class in Java sits in one big family tree, and a catch clause catches its named type and every subclass of it.

Definition— Throwable, Error, Exception, RuntimeException

Throwable is the root. Only an object of a class descended from Throwable can appear after throw or in a catch clause. It has two direct subclasses:

  • Error — serious trouble in the JVM itself, such as OutOfMemoryError or StackOverflowError. Your program is not expected to recover from these, and you should not try to catch them.
  • Exception — conditions an application might reasonably want to catch. This is the branch you live in.

Inside Exception there is one subclass with a special status: RuntimeException. It and everything below it is treated differently by the compiler, which is the subject of the rest of this section.

Here is the part of the tree you will actually meet this semester. Every name in it has already appeared in this course except IOException.

Key Idea— the one line that decides everything

Draw a line under RuntimeException. Everything on or below that line is unchecked. Everything else under Exception is checked.

  • Checked: the compiler forces you to deal with it. Either catch it, or write throws on your method and make it someone else's problem. Nothing else compiles.
  • Unchecked: the compiler says nothing. You may catch it if you want to; you are never made to.

Why the split? Because the two kinds have different causes. A checked exception describes something that can go wrong even though your code is perfect: the file really might not be there, the network really might be down. An unchecked exception almost always means your code has a bug — you indexed past the end, you dereferenced a null, you divided by zero. Java's position is that the first kind deserves a mandatory plan and the second kind deserves a fix, not a catch.

The practical consequence is the dangerous one. An integer division bug announces itself loudly and immediately. A floating-point one does not — it quietly produces Infinity or NaN, and those values then propagate through every later calculation, because anything plus NaN is NaN. You find out ten screens later when an average prints as NaN. This is the trap Quick Check 1.10 warned about back in Lecture 1.

Quick Check 20.4

A method computes the average of an int array. Give the exact result of average(a) for each case below.

static double average(int[] a) {
    int sum = 0;
    for (int i = 0; i < a.length; i++) sum += a[i];
    return sum / a.length;
}

(a) a is {90, 85, 78}.

84.0, not 84.33333333333333. Both sum and a.length are int, so sum / a.length is integer division — 253 / 3 = 84 — and only then is the 84 widened to a double on the way out. This is the Lecture 1 division trap, still alive. The fix is return sum / (double) a.length;.

(b) a is an empty array, new int[0].

It throws ArithmeticException: / by zero. The loop body never runs, so sum is 0 and a.length is 0, and 0 / 0 with two int operands is an integer division by zero. The method never returns; the exception goes to the caller.

(c) Same empty array, but after you apply the fix from part (a) — return sum / (double) a.length;.

Now it returns NaN, silently. The cast made this floating-point division, so 0 / 0.0 is NaN rather than a throw. The caller gets a double back, prints it, and nothing looks broken until someone notices NaN in a report.

Things to notice across all three parts. Fixing the division-trap bug made the empty-array bug harder to find, not easier. That is the trade the floating-point standard makes for you, and it is why you should never rely on a divide by zero to tell you an array was empty. Check a.length == 0 yourself and throw a real exception — which is exactly what Practice Problem 3 asks you to do.

4.throw and throws

So far the exceptions have all been thrown by the library. But Integer.parseInt has no opinion about whether 150 is a plausible age — only your program does. When your code detects a problem, you throw the exception yourself.

Definition— the throw statement

throw is a statement. It takes one expression, which must evaluate to a Throwable object, and it raises that object immediately:

throw new Exception("Age too big!");

You almost always see throw new together, because you construct the object right there. Execution of the current method stops at that instant — a throw is as final as a return, and code after it in the same block is unreachable.

Definition— the throws clause

throws is part of a method signature. It goes after the parameter list and before the opening brace, and it lists the checked exception types this method may let escape:

private static int readAgeFrom(Scanner screen) throws Exception {

It is a declaration to the compiler and to anyone reading your code: callers of this method must be ready for this. It throws nothing by itself. Several types are separated by commas: throws IOException, AgeException.

Warning— throw and throws are not the same word

They differ by one letter and students mix them up in every exam. Learn them as a pair:

Worked Example— both keywords in nine lines

One method uses both. Read the two comments; they mark the two keywords.

ThrowVsThrows.java

public class ThrowVsThrows {
    public static void main(String args[]) {
        try {
            System.out.println(withdraw(100, 30));
            System.out.println(withdraw(100, 250));
        } catch (Exception e) {
            System.out.println("caught: " + e.getMessage());
        }
    }

    //          keyword #2, on the signature: "I might hand one of these back"
    static int withdraw(int balance, int amount) throws Exception {
        if (amount > balance)
            //   keyword #1, a statement: "here is one, right now"
            throw new Exception("Insufficient funds: asked for " + amount
                                + ", balance is " + balance);
        return balance - amount;
    }
}

5.Several catch blocks, and the ordering rule

One try may be followed by as many catch blocks as you like. When something is thrown, Java tries them in the order written and runs the first one whose type matches. At most one catch block ever runs.

Procedure— how Java picks a catch block
  1. An exception object is thrown inside the try block.
  2. Look at the first catch clause. Ask: is the thrown object an instance of that type, or of any subclass of it?
  3. If yes, run that block and skip all the others. Execution continues after the last catch.
  4. If no, move to the next catch clause and repeat.
  5. If none match, the exception leaves this method entirely and the search continues in the caller.

Because the test is "is it this type or a subclass", a catch (Exception e) matches everything. Put it first and nothing after it can ever run — and Java, rather than letting you write dead code, refuses to compile the file at all.

6.Writing your own exception class

Example 3b left us stuck. catch (Exception e) cannot distinguish "the text was not a number" from "the number was out of range", because both arrive as an Exception. Section 5 gives the tool — separate catch blocks — but that only helps if the two failures have different types. So make one.

Definition— a custom exception class

An exception class is an ordinary class that extends Exception (or one of its subclasses). It usually adds no fields and no methods at all — the type name is the information. All it needs is a constructor that takes a message and hands it to the superclass with super(s), so that getMessage() can give it back later.

AgeException.java

public class AgeException extends Exception {
    public AgeException(String s) {
        super(s);
    }
}

Five lines, and now AgeException is a type you can throw, a type you can name in a catch, and a type distinct from everything else in the hierarchy.

Key Idea— extends Exception or extends RuntimeException?

extends Exception makes your class checked: everyone who might throw it must declare it, and everyone who calls them must catch or declare it. extends RuntimeException makes it unchecked: the compiler says nothing at all.

For this course, extend Exception. It is what the instructor's AgeException does, it is what the exam questions ask for — "objects that are exceptions but are not run time exceptions" is exactly this phrase — and it is the choice that makes the compiler help you.

7.finally

There is a third block you can attach to a try, and it exists for one problem: cleanup. If you opened a file, you must close it — whether the read succeeded, whether it threw, whether you returned early. Writing input.close() at the end of the try block does not cover the throwing case; writing it in the catch too duplicates it; writing it after both misses the case where you returned.

Definition— the finally block

A finally block comes after the catch blocks and always runs:

try {
    // code that might throw } catch (Exception e) { // handle it } finally { // always runs }

"Always" means all of these: the try block finished normally; the try block threw and a catch handled it; the try block threw and no catch matched, so the exception is on its way out of the method; the try block or a catch block executed a return. In every one of those cases finally runs before control actually leaves.

You may write try/finally with no catch at all, when you want the cleanup but intend the exception to travel onward.

Worked Example— finally versus return

describe returns from inside the try and again from inside the catch, and it has a finally. Work out the exact order of the printed lines for each of the three calls before you look — in particular, does finally: cleaning up come before or after case 1: ok?

FinallyDemo.java

public class FinallyDemo {
    public static void main(String args[]) {

    }

    static String describe(String text) {
        try {
            int n = Integer.parseInt(text);
            System.out.println("  try: parsed " + n);
            return "ok";
        } catch (NumberFormatException e) {
            System.out.println("  catch: " + e.getMessage());
            return "not a number";
        } finally {

  finally: cleaning up

finally runs before the method actually returns. In case 1 the try block reached return "ok";, but the value does not leave the method until the finally block has run — which is why finally: cleaning up is printed before case 1: ok. Java evaluates the return expression, holds the value, runs finally, and only then hands the value back to the caller.

Case 2 is the same story down the catch path: catch prints, catch returns, finally still runs first.

That is a deliberate decision by the library authors: from parseInt's point of view, null is just one more piece of text it cannot turn into a number. It matters here because the catch clause names NumberFormatException, so case 3 is handled rather than escaping.

        throw new RuntimeException("boom");

    finally {
        return 3;
    }
}

h() returns 3. The RuntimeException is thrown, the finally block starts running on the exception's way out, and its return abandons the exception completely — no stack trace, no catch, no trace of the failure anywhere. That is the single worst thing a finally block can do. Keep finally for cleanup only: close things, release things, print things. Never return and never throw from inside one.

            System.out.println("   " + e.getMessage());
        } finally {
            if (input != null) input.close();
            System.out.println("   (scanner closed: " + (input != null) + ")");
        }
    }
}

   (scanner closed: true)
nosuchfile.txt: could not be opened.
   nosuchfile.txt (No such file or directory)
   (scanner closed: false)

Nothing from the try block on the second call. new Scanner(new File(...)) is the very first statement, and it threw, so the loop and the summary line were never reached. That is also why input is still null in the finally block, and why the if (input != null) guard is essential — without it, the cleanup would itself throw a NullPointerException while trying to close a Scanner that was never created.

main no longer needs throws FileNotFoundException, because report handles it. The obligation stopped travelling as soon as somebody accepted it.

The wording of the message — nosuchfile.txt (No such file or directory) — comes from the operating system, so a Windows machine phrases it differently. Never parse an exception message in code; show it to a human and no more.

Quick Check 20.10

In ReadScoresSafely, why is Scanner input declared before the try block rather than on the line where it is created, as in Lecture 5?

Plan. Ask about scope, then about what finally needs.

A variable declared inside a block exists only inside that block. If you had written

try {
    Scanner input = new Scanner(new File(fileName));
    // declared here ... } finally { input.close();                                      // input is not in scope }

the finally block would not compile: input died at the try block's closing brace. For finally to clean up a resource, the variable naming that resource must be declared outside the try. Initializing it to null is then forced, because the compiler must be sure it is assigned before it is read.

Things to notice. This declare-outside, assign-inside, null-check-in- finally pattern is so common that Java added a shorthand for it, try-with-resources: try (Scanner input = new Scanner(new File(fileName))) { ... } closes the Scanner automatically with no finally block at all. It is worth knowing that it exists; the explicit version above is what this course expects you to write, and it is what makes the role of finally visible.

Lecture 3 and Lecture 6 — the index that was out of bounds

Arrays throw ArrayIndexOutOfBoundsException; ArrayList throws IndexOutOfBoundsException, its superclass. Both are unchecked, so nothing ever forced you to think about them. When the index comes from a user or a file rather than from a loop you wrote, that is a real risk.

Worked Example— the same four indexes against an array and a list

An int[] of length 3 and an ArrayList of size 2, probed with the indexes 0, 2, 3 and −1. Eight accesses, and some of them are legal. Work out which four throw before you reveal.

SafeIndex.java

import java.util.ArrayList;

public class SafeIndex {
    public static void main(String args[]) {
        int[] scores = {90, 85, 78};
        ArrayList<String> names = new ArrayList<String>();
        names.add("Ada");
        names.add("Grace");

        int[] wanted = {0, 2, 3, -1};
        for (int i = 0; i < wanted.length; i++) {
            int k = wanted[i];
            try {
                System.out.println("scores[" + k + "] = " + scores[k]);
            } catch (ArrayIndexOutOfBoundsException e) {
                System.out.println("scores[" + k + "] : " + e.getMessage());
            }
            try {
                System.out.println("names.get(" + k + ") = " + names.get(k));
            } catch (IndexOutOfBoundsException e) {
                System.out.println("names.get(" + k + ") : " + e.getMessage());
            }
        }
    }
}
scores[0] = 90
names.get(0) = Ada
scores[2] = 78
names.get(2) : Index 2 out of bounds for length 2
scores[3] : Index 3 out of bounds for length 3
names.get(3) : Index 3 out of bounds for length 2
scores[-1] : Index -1 out of bounds for length 3
names.get(-1) : Index -1 out of bounds for length 2

Index 2 is the interesting one: legal for the array of length 3, illegal for the list of size 2. There is nothing special about the number; what matters is the length of the thing you are indexing, which is why the message always tells you both.

Two separate try blocks, not one. If both accesses shared a try, a failure in the array line would skip the list line entirely and half the table would be missing. When two operations are independent, give them independent try blocks.

The catch types differ because the classes do: ArrayIndexOutOfBoundsException extends IndexOutOfBoundsException. Writing catch (IndexOutOfBoundsException e) for both would have worked, since a subclass is caught by its superclass; writing catch (ArrayIndexOutOfBoundsException e) around names.get(k) would not, because an ArrayList never throws that subclass.

Warning— do not use catch as a substitute for an if

You could write this:

try {
    total += scores[i];
}
catch (ArrayIndexOutOfBoundsException e) {
    // i was too big; ignore }

Do not. When you can test the condition cheaply yourself — if (i >= 0 && i < scores.length) — the if is clearer, faster, and does not hide genuine bugs. Reserve catch for conditions you cannot test in advance: whether a file exists at the instant you open it, whether a String a user typed happens to parse. The SafeIndex example above is a demonstration of what the exceptions are, not a recommendation for how to loop over an array.

Lecture 17 — the text field the user typed nonsense into

The Lecture 17 GUI read a JTextField with getText() and converted it with Integer.parseInt. It had no way to survive a user typing twenty, and a GUI that dies on bad input is worse than a console program that does — the window vanishes with no explanation. The fix is one try/catch inside actionPerformed.

Worked Example— a text field that cannot be broken

A window with a text field, a button and a label. This program opens a window and prints nothing to the console, so there is no output block below it — what to look at is actionPerformed.

Doubler.java

import java.awt.event.ActionEvent;
import java.awt.event.ActionListener;
import javax.swing.JButton;
import javax.swing.JFrame;
import javax.swing.JLabel;
import javax.swing.JPanel;
import javax.swing.JTextField;

public class Doubler extends JFrame implements ActionListener {
    private JTextField input;
    private JLabel result;

    public Doubler() {
        setTitle("Doubler");
        setSize(320, 120);
        setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);

        JPanel panel = new JPanel();
        input = new JTextField(8);
        result = new JLabel("type a whole number");
        JButton go = new JButton("Double it");
        go.addActionListener(this);

        panel.add(input);
        panel.add(go);
        panel.add(result);
        add(panel);
        setVisible(true);
    }

    public void actionPerformed(ActionEvent e) {
        try {
            int n = Integer.parseInt(input.getText().trim());
            result.setText("Twice that is " + (2 * n));
        } catch (NumberFormatException ex) {
            result.setText("Please type a whole number.");
            input.setText("");
        }
    }

    public static void main(String args[]) {
        new Doubler();
    }
}

What happens on screen: a 320-by-120 window titled Doubler holding a text field, a Double it button and a label reading type a whole number. Type 21 and press the button and the label becomes Twice that is 42. Type twenty and press it and the label becomes Please type a whole number., the field is cleared, and — this is the point — the window is still there and still working. Type 21 again and it doubles it as if nothing had happened.

Three details in actionPerformed are worth copying into your own GUI code:

  • .trim() before parsing. Integer.parseInt(" 21 ") throws; users put spaces in text fields constantly. Trimming first removes the commonest false failure, as Lecture 17 noted.
  • The exception variable is named ex, not e. It has to be: actionPerformed already has a parameter called e, the ActionEvent, and reusing the name inside the catch would not compile.
  • The catch reports through the same label as the success path. The user never sees a console, so a System.out.println in the catch would be invisible; the whole point is to put the message where they are already looking.

Without the try/catch the exception escapes actionPerformed into Swing's event dispatch thread, which prints a stack trace to the console the user cannot see and leaves the window sitting there having silently done nothing. That is the worst of both worlds, and one catch block avoids it.

Quick Check 20.11

Add validation to Doubler. Beyond rejecting text that is not a number, the program should also refuse a number outside 1 to 1000 — and the two failures must produce different messages. They are unrelated types, so their order is free.

RangeException.java

public class RangeException extends Exception {
    public RangeException(String s) {
        super(s);
    }
}
private int readValue() throws RangeException {
    int n = Integer.parseInt(input.getText().trim());
    if (n < 1 || n > 1000) throw new RangeException("Value " + n + " is outside 1 to 1000.");
    return n;

public void actionPerformed(ActionEvent e) {

Quick Check 20.12

Design questions. For each, say whether the situation calls for a try/catch, an ordinary if, or neither.

(a) A for loop over an array using for (int i = 0; i < a.length; i++).

Neither. The loop condition already guarantees the index is in range. Wrapping it in a try adds noise and hides a real bug if one ever appears.

(b) Dividing total by count, where both are int and count was computed from user input.

An if. if (count == 0) is one cheap test you fully control, and it lets you say something meaningful instead of dividing and reacting. Catching ArithmeticException here would work, but it is using an exception where a condition will do.

(c) Opening a file whose name the user typed.

A try/catch, and the compiler will insist on it or on a throws clause because FileNotFoundException is checked. There is no if that helps: even a check that the file exists could be true and then false a millisecond later. This is the textbook case for an exception.

(d) Converting a String from a text field into an int.

A try/catch. In principle you could inspect every character yourself, but you would be reimplementing parseInt — and getting the edge cases wrong, since a leading minus is fine, a leading plus is fine, an empty string is not, and a value beyond Integer.MAX_VALUE is not either. Let the library decide and catch its verdict.

Things to notice across all four parts. The dividing line is whether you can cheaply and reliably test the condition first. If you can, test it. If the answer depends on the outside world or on a library's definition of valid, catch. Nearly every "should this be an exception?" argument comes down to that one question.

Problem 1 — A try-catch block in nine lines (from Exam 3 Practice Problems)

Write a main method with a try-catch block. Inside the block it creates an array of Strings — the array is called list and has size 10. Print the value stored in list[10]. The catch block should catch ArithmeticException and RuntimeException. Your code shouldn't be longer than 9 lines excluding curly braces.

Plan. The body is three lines: declare the array, print the bad element, and one catch. The interesting part of this question is the last sentence of the specification, because as literally written it does not compile — and knowing why is the point.

The trap. The obvious reading is a multi-catch clause, catch (ArithmeticException | RuntimeException e). Java rejects it:

MultiCatchBad.java:6: error: Alternatives in a multi-catch statement cannot be related by subclassing } catch (ArithmeticException | RuntimeException e) {
^
Alternative ArithmeticException is a subclass of alternative RuntimeException
1 error

ArithmeticException extends RuntimeException, and a multi-catch clause may not list two types where one is an ancestor of the other — the first alternative would be completely covered by the second, so naming it adds nothing.

Writing them as two separate catch clauses is legal, but only in one order. Specific first compiles:

}
catch (ArithmeticException e) {
    System.out.println("arith");
}
catch (RuntimeException e) {
    System.out.println("Exception caught: " + e.getMessage());
}

General first does not, for the reason from §5:

TwoClausesBad.java:8: error: exception ArithmeticException has already been caught } catch (ArithmeticException e) {
^
1 error

What to write. Within the nine-line budget, catch (RuntimeException e) alone satisfies the requirement: it already catches ArithmeticException, and every other unchecked exception, including the ArrayIndexOutOfBoundsException this code actually produces.

ArrayCatch.java

public class ArrayCatch {
    public static void main(String[] args) {
        try {
            String[] list = new String[10];
            System.out.println(list[10]);
        } catch (RuntimeException e) {
            System.out.println("Exception caught: " + e.getMessage());
        }
    }
}
Exception caught: Index 10 out of bounds for length 10

Things to notice. new String[10] gives you indexes 0 through 9. list[10] is the eleventh element of a ten-element array — the classic off-by-one, and the reason the question chose that number.

The array is created inside the try, which is what the question asks for and is also fine: new String[10] cannot fail. If you wanted to use list after the block you would have to declare it outside, exactly as with the Scanner in Quick Check 20.10.

Nothing here is checked, so no throws clause appears anywhere, and in fact the try/catch is optional as far as the compiler is concerned. It is the difference between a program that prints one tidy line and one that prints a stack trace and dies.

Problem 2 — RoomCounter and NegativeCounterException (from Exam 3 Practice Problems)

Create a class called RoomCounter which counts the number of people in a room. We know that the number of people in a room can never be negative. The class should have addPerson (adds one person), removePerson (removes one person) and getCount (returns the number of people). If removePerson() would make the number of people less than zero, throw a NegativeCounterException.

(a) Create the class RoomCounter with a default constructor and one instance variable count of type int. Write the three methods and throw an exception where appropriate. The only getter method is getCount().

Plan. count is private — encapsulation, Lecture 7. The default constructor sets it to 0, which Java would do anyway, but the question asks for the constructor. Only removePerson can fail, so only it gets a throws clause. Check before decrementing.

public class RoomCounter {
    private int count;
    public RoomCounter() {
        count = 0;
    }
    public void addPerson() {
        count++;
    }
    public void removePerson() throws NegativeCounterException {
        if (count <= 0) throw new NegativeCounterException();
        count--;
    }
    public int getCount() {
        return count;
    }
}

The test is count <= 0, not count < 0. The rule is that the count may never become negative, so the removal has to be refused while the room is already empty. Writing count < 0 would allow one removal too many and leave the count at −1, which is the exact state the exception exists to prevent.

(b) Define the class NegativeCounterException.

Four lines. Note that removePerson throws it with new NegativeCounterException() and no argument, so the constructor takes no parameter — it supplies the message itself:

NegativeCounterException.java

public class NegativeCounterException extends Exception {
    public NegativeCounterException() {
        super("Cannot remove a person from an empty room");
    }
}

extends Exception makes it checked, which is what forces the throws clause in part (a) and the try/catch in part (c). A no-argument constructor that calls super(...) with a fixed message is a good pattern when the failure only ever means one thing; AgeException took a parameter instead because its message varies with the reason.

(c) In RoomCounter, write a static main(). Create a RoomCounter object, add three people, then in a try-catch block remove one person at a time and catch any exception. After each removal, print the count.

Plan. Add three, then loop four times — three successful removals and one that must fail, otherwise the catch block is never exercised and you have not demonstrated anything. Put the try inside the loop so one failure does not end it.

RoomCounter.java

public class RoomCounter {
    private int count;

    public RoomCounter() { count = 0; }

    public void addPerson() { count++; }

    public void removePerson() throws NegativeCounterException {
        if (count <= 0) throw new NegativeCounterException();
        count--;
    }

    public int getCount() { return count; }

    public static void main(String args[]) {
        RoomCounter room = new RoomCounter();

        room.addPerson();
        room.addPerson();
        room.addPerson();
        System.out.println("Current count: " + room.getCount());

        for (int i = 0; i < 4; i++) {
            try {
                room.removePerson();
                System.out.println("Person removed. Count: " + room.getCount());

Things to notice across all three parts. The print statement sits inside the try, after the call. That is deliberate: on the fourth pass removePerson throws, so the print is skipped and the count is not reported a second time as 0. Had the print been after the whole try/catch, the last line of output would have been a confusing Person removed. Count: 0 following the error message.

getMessage() returns the text the no-argument constructor passed to super. Printing e.getMessage() rather than a hard-coded string in main keeps the wording in one place — the exception class — which is the whole reason to give an exception a message at all.

This design puts the rule inside the object. No caller of RoomCounter can drive the count negative, no matter what they do, because the only way to change it is through methods that enforce the invariant. Compare that with returning a boolean from removePerson, which a caller can simply ignore.

    if (list.size() == 0) throw new EmptyArrayException("Empty list!!!");
    int sum = 0;
    for (int i = 0; i < list.size(); i++) sum += list.get(i);

(c) Modify main to catch any exception thrown by average. P3.java

import java.util.ArrayList;
import java.util.Scanner;

public class P3 {

                ArrayList<Integer> list = readMyArrayList(input);

        ArrayList<Integer> answer = new ArrayList<>();
        System.out.println("How many elements?");
        int size = input.nextInt();
        for (int i = 0; i < size; i++) answer.add(input.nextInt());
        return answer;

A session in which the user's second list is empty. Six lists are entered and five averages are printed, which is the requirement:

Things to notice across all three parts. i-- in the catch is the whole trick, and it is worth being sure why it works: the for header runs i++ after every iteration, including the ones that threw, so decrementing inside the catch leaves i unchanged for that round. Five successful averages therefore require exactly five successful rounds, however many failures happen in between.

It is a technique to use knowingly, not reflexively — a loop whose counter can move backwards can, in principle, never terminate. Here that is the intended behavior: the loop must keep asking until it has five real averages. If the failures were caused by something the user could not fix, this would be an infinite loop.

Note also what the catch clause names. catch (EmptyArrayException e) is specific to the one thing average throws. catch (Exception e) would also compile, and would additionally swallow anything readMyArrayList throws — for instance the InputMismatchException you get when the user types a word where nextInt() wants a number.         ArrayList<Integer> a = new ArrayList<Integer>();
        a.add(4); a.add(0); a.add(9);

        System.out.println(step(a, 0));            // line (a)
        System.out.println(step(a, 1));            // line (b)
        System.out.println(step(a, 5));            // line (c)

        try {
            System.out.println(12.0 / 0);          // line (d)
            System.out.println(12 / 0);            // line (e)
            System.out.println("unreachable");
        } catch (ArithmeticException e) {
            System.out.println("caught " + e.getMessage());
        } finally {
            System.out.println("done");            // line (f)
        }
    }

    static String step(ArrayList<Integer> a, int i) {
        try {
            return "value " + (100 / a.get(i));
        } catch (ArithmeticException e) {
            return "arithmetic";
        } catch (IndexOutOfBoundsException e) {
            return "index";
        } finally {
            System.out.print("[cleanup] ");
        }
    }
}

(a) What is the output at line (a)?

[cleanup] value 25. a.get(0) is 4, and 100 / 4 is 25, so the try block returns. The finally block runs before the value leaves step, and it uses print, so [cleanup] appears first and on the same line.

(b) What is the output at line (b)?

[cleanup] arithmetic. a.get(1) is 0, so 100 / 0 throws ArithmeticException — both operands are int. The first catch matches and returns "arithmetic"; finally still runs on the way out.

(c) What is the output at line (c)?

[cleanup] index. a.get(5) throws IndexOutOfBoundsException before any division is attempted, so the first catch does not match and the second does.

(d) What is the output at line (d)?

Infinity. 12.0 is a double, so this is floating-point division and nothing is thrown. The line prints and execution carries on to line (e).

(e) What is the output at line (e)?

Line (e) itself prints nothing. 12 / 0 with two int operands throws ArithmeticException, so println never receives a value. The catch block runs instead and prints caught / by zero — the message on an ArithmeticException from integer division is the terse / by zero. The "unreachable" line is skipped.

(f) What is the output at line (f), and what is the whole program's output?

done, printed after the catch block has finished. Putting it all together:

[cleanup] value 25
[cleanup] arithmetic
[cleanup] index
Infinity
caught / by zero
done

Things to notice across all six parts. Every line of this problem is one of the three ideas that get tested: does finally run (always), which catch matches (the first compatible one, in written order), and does division by zero throw (only for integers).

The [cleanup] prefix on the first three lines is the giveaway for the finally-before- return rule. If you predicted value 25 [cleanup] you assumed the return leaves immediately; it does not. It evaluates the expression, holds the result, runs finally, and only then departs.

Lines (d) and (e) are the same division written twice, differing only in a .0. One prints a value and one throws. Whenever an exam shows you two adjacent divisions by zero, check the types before anything else.

Lecture Summary
  • An exception is an object describing a failure. It is thrown at the point of failure, and it travels up the call stack until some catch matches it — or until it reaches the JVM, which prints a stack trace and stops the program. Read a stack trace from the bottom up; the first line naming your own file is the one to go and look at.
  • try holds the risky code; catch names one exception type and says what to do about it. The rest of the try block after the throw is abandoned, not resumed, and nothing already done is undone.
  • The hierarchy is Throwable → Error and Exception, with RuntimeException under Exception. Everything at or below RuntimeException is unchecked; everything else under Exception is checked, and a checked exception must be caught or declared at every level of the call chain.
  • throw is a statement that raises an object right now. throws is a clause on a method signature that names types and raises nothing. One letter, two completely different jobs.
  • Several catch blocks may follow one try, and Java runs the first one whose type matches. A subclass clause must therefore come before its superclass, or the file does not compile — exception X has already been caught.
  • Write your own exception with class MyException extends Exception and a constructor that calls super(message). That makes it checked, gives it a distinct type worth a catch clause of its own, and makes getMessage() return your text. getMessage, toString and printStackTrace are the three methods to know.
  • finally always runs — after a normal finish, after a handled throw, on the way out of an unhandled one, and before a return in the try or catch actually delivers its value.
  • Integer division by zero throws ArithmeticException; floating-point division by zero quietly gives Infinity, -Infinity or NaN. The loud one is easier to debug.
  • Use catch for conditions you cannot cheaply test yourself — a file that may not exist, text a user may have mistyped. Use an if when you can.
