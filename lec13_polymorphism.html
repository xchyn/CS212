Polymorphism and Dynamic Binding

One variable, many kinds of object — and the two completely different rules Java uses to decide what you may call and which version actually runs.

1.One variable, many kinds of object

Last time we built a family of classes. Shape was the base; Rectangle and Circle extended it; Square extended Rectangle. We used extends to say who inherits from whom, super(...) to hand values up to the parent constructor, and @Override to replace a parent's toString with a more specific one. All of that still holds today, and today we finally get paid for it.

Here are the four classes again, unchanged, because every example on this page uses them.

Shape.java

public class Shape {
    private final double perimeter;
    private final double area;

    public Shape(double perimeter, double area) {
        this.perimeter = perimeter;
        this.area = area;
    }

    public double getPerimeter() {
        return perimeter;
    }

    public double getArea() {
        return area;
    }

    public String toString() {
        return "Shape with area: " + area + " and perimeter: " + perimeter;
    }
}

Rectangle.java

public class Rectangle extends Shape {
    private final double base;
    private final double height;

    public Rectangle(double base, double height) {
        super(2 * base + 2 * height, base * height);
        this.base = base;
        this.height = height;
    }

    public double getBase() {
        return base;
    }

    public double getHeight() {
        return height;
    }

    @Override
    public String toString() {
        return "Rectangle with base: " + base + ", height: " + height +
               ", area: " + getArea() + ", perimeter: " + getPerimeter();
    }
}

Square.java

public class Square extends Rectangle {

    public Square(double sideLength) {
        super(sideLength, sideLength);
    }

    @Override
    public String toString() {
        return "Square with side length: " + getBase() +
               ", area: " + getArea() + ", perimeter: " + getPerimeter();
    }
}

Circle.java

public class Circle extends Shape {

    private final double radius;

    public Circle(double radius) {
        super(2 * Math.PI * radius, Math.PI * radius * radius);
        this.radius = radius;
    }

    public double getRadius() {
        return radius;
    }

    @Override
    public String toString() {
        return "Circle with radius: " + radius +
               ", area: " + getArea() + ", perimeter: " + getPerimeter();
    }
}

Now the new idea, and it is one line long:

Shape s = new Circle(3);

The variable on the left is declared Shape. The object on the right is a Circle. That compiles, and it is not a trick — it is the whole point of inheritance. A Circle is a Shape, so anywhere a Shape is wanted, a Circle will do.

Definition— polymorphism

Polymorphism — from the Greek for "many forms" — means that an object can be treated as more than one type. In Java this shows up as a rule about references: a reference variable of a superclass type can refer to an object of any of its subclass types.

When a method is called through such a reference, the implementation that runs is chosen at run time, based on the actual object — not on how the variable was declared. That second sentence is the rest of the lecture.

Because there are now two types in play for a single variable, we need two names for them. Get these two terms straight now; everything else on this page is a consequence of the difference between them.

Definition— static type (the declared type)

The static type of a reference variable is the type written in its declaration. In Shape s = new Circle(3); the static type of s is Shape.

It is called static because it is fixed by the text of the program and never changes while the program runs. It is the only type the compiler knows about, and the compiler is the only one who cares about it.

Definition— dynamic type (the actual object)

The dynamic type of a reference variable is the class of the object it is currently pointing at. In Shape s = new Circle(3); the dynamic type of s is Circle.

It is called dynamic because it can change as the program runs — assign s = new Square(7); on the next line and the dynamic type becomes Square, while the static type is still Shape. It is the only type the JVM cares about when it goes looking for a method body to execute.

Key Idea— two types, two audiences

Every reference variable has both types at once. The static type answers "what am I allowed to write?" The dynamic type answers "what actually runs?" Mix those two questions up and every problem in this lecture becomes unanswerable; keep them apart and every problem becomes bookkeeping.

2.Dynamic binding: the object decides

So a Shape variable can hold a Circle. The interesting question is what happens when you call a method on it. Both Shape and Circle define toString. Which one runs?

Definition— dynamic binding (late binding)

Dynamic binding is Java's rule for calling an overridden instance method: the version that runs is chosen at run time, from the dynamic type of the object — never from the static type of the reference.

It is also called late binding, because the decision is deferred until the latest possible moment: the instant the call actually happens. The compiler does not decide; it only checks that some suitable method exists.

Here is the instructor's own demonstration from Lecture 12. Notice the helper method print: its parameter is declared Shape, so inside print the static type is always Shape, no matter what you pass in.

3.The compiler's half of the deal

Dynamic binding is generous: the object always gets to be itself. The compiler is the opposite — strict, and deliberately blind to what the object really is. Its rule is the exact mirror image, and holding both in your head at once is the skill this lecture is teaching.

Key Idea— the two rules, side by side

The static type decides what you are allowed to write. The dynamic type decides which version runs.

The compiler looks only at the declared type of the reference and asks: does that class (or something it inherits from) declare a method with this name and these argument types? If not, your program does not compile — regardless of what the object actually is.

Which produces the single most surprising error of the semester. The object on the heap genuinely is a Circle. It genuinely has a getRadius method. And this still fails:

NoRadius.java

public class NoRadius {
    public static void main(String args[]) {
        Shape s = new Circle(3);
        System.out.println(s.getArea());
        System.out.println(s.getRadius());
    }
}
NoRadius.java:5: error: cannot find symbol
        System.out.println(s.getRadius());
                            ^
  symbol:   method getRadius()
  location: variable s of type Shape
1 error

Read the last line of that message: location: variable s of type Shape. The compiler is telling you precisely what it did. It did not look at the object; it looked at the declaration, saw Shape, went through Shape's methods, and did not find getRadius.

Why is Java being so unhelpful? Because the compiler cannot in general know what the object will be. Change the program to read a number and pick a shape based on it, and the answer is not decidable until the program runs. The compiler's job is to guarantee that every possible run is safe, so it accepts only calls that are safe for every object a Shape variable could ever hold — and a plain Shape has no radius.

Common Mistake— "but I can see that it is a Circle"

Students stare at Shape s = new Circle(3); on one line and s.getRadius() on the next and conclude the compiler is broken. It is not. The compiler is following a rule that ignores the previous line on purpose, because in real programs the previous line is a method call, a loop, or an array subscript, and there is nothing to look at.

The fix, when you really do need the subclass method, is a cast — and there is a right way and a wrong way to write one. That is section 6.

A cast is not a conversion of the object. It changes nothing on the heap. It is a statement to the compiler: "treat this expression as having that static type, and check me at run time."

4.Overloading vs. overriding

You met overloading back in Lecture 2: several methods in the same class sharing a name but taking different parameters. You met overriding last lecture: a subclass replacing a method it inherited. They look similar on the page. They are resolved by opposite rules, and telling them apart is where most exam points in this course are won and lost.

Definition— overload resolution

When several methods share a name, the compiler must pick one. It does this at compile time, using the static types of the arguments, and it picks the most specific version that the argument types will fit into. This is called static binding or early binding.

The choice is then baked into the compiled .class file. Nothing that happens at run time can change it.

The instructor's ShapeProcessor is built precisely to expose this. It has three displayType methods — one taking a Shape, one a Rectangle, one a Circle — and a printDetails method that calls displayType on its Shape parameter.

Key Idea— the one sentence to memorise

Overriding is resolved at run time by the dynamic type. Overloading is resolved at compile time by the static type.

So on a call like x.f(y), do the work in two stages. First, using only the declared types of x and y, decide which signature is being called. Then, using the actual object in x, decide whose body runs for that signature. The argument types are settled first and never revisited.

So how do you get "this is a rectangle" out of a Shape reference? Not with overloading. You need the thing that is dispatched by the object: an overridden instance method.

5.One array, many shapes

Everything so far has been about one variable at a time. The payoff arrives when you have many objects of different classes and want to treat them uniformly, because an array of the superclass type will hold any mixture of subclasses.

Key Idea— the practical payoff

Shape[] shapes is an array whose elements are Shape references. Every element may hold a different subclass. Each element's static type is Shape, so you may call anything Shape declares; each element's dynamic type is whatever you stored there, so the right override runs. One loop, any mixture, no if statements about types.

Worked Example— four shapes, one loop

The array initialiser stores a Shape, a Rectangle, a Square and a Circle into four Shape slots. The loop body mentions none of those class names.

6.Casting down, and instanceof

Section 3 left a loose end. Sometimes you genuinely need a subclass-only method — the radius of a circle is not something every shape has, and no amount of overriding will change that. For those cases Java lets you tell the compiler what you know.

Definition— upcast and downcast

An upcast converts a reference to a supertype: Shape s = new Circle(3); is one, and it is always safe, so Java performs it silently and never asks you to write it.

A downcast converts a reference to a subtype: Circle c = (Circle) s;. It is not always safe — the object might not be a Circle at all — so Java makes you write it out. Writing the cast is a promise. The JVM checks the promise at run time and throws if you were wrong.

Definition— the instanceof operator

x instanceof T is a boolean expression that is true when the object referred to by x is an instance of class T or of any subclass of T, and false otherwise (including when x is null).

It asks about the dynamic type, which is precisely why it is the right guard for a downcast: it checks the very fact the cast is about to assume.

Worked Example— guarded downcasts

describe takes any Shape. The general part — printing it — needs no cast. The extra detail does. Read the order of the two tests carefully before you predict the Square line.

7.What dynamic binding does not do

Dynamic binding applies to overridden instance methods. That phrase is doing real work: everything else in Java is resolved from the static type, and fields are the case that catches people out.

Key Idea— fields are not polymorphic

If a subclass declares a field with the same name as one in its superclass, the subclass field hides the superclass field rather than replacing it. Both exist in the object at once, and which one you read is decided by the static type of the reference — at compile time, like an overload.

Worked Example— a hidden field and an overridden method, side by side

(d)Rectangleshow()SquareSquare.show()
(e)Rectangleshow(int)SquareRectangle.show(int) — no override
(f)Shapeshow(String)SquareSquare.show(String)
(g)Shapelabel()SquareSquare.label()

Do it in that order, one column at a time, and the problem has no difficulty left in it. Try to do both at once and lines (b) and (e) will get you.

Problem 2 — What is printed at each line? (from CSCI 212 Exam 2, Spring 2025, Problem 2)

Consider the following Java program.

MethodTest.java

class A {
    void method(char ch) { System.out.println("A.method() " + ch); }
    String what() { return "Returning A"; }
    void adjust() { System.out.println("Adjusting A"); }
}

class B extends A {
    void method(char ch) { System.out.println("B.method() " + ch); }
    String what() { return "Returning B"; }
    void adjust() { System.out.println("Adjusting B"); }
}

class C extends A {
    void method(char ch) { System.out.println("C.method() " + ch); }
    String what() { return "Returning C"; }
    void adjust() { System.out.println("Adjusting C"); }
}

class D extends A {
    void method(char ch) { System.out.println("D.method() " + ch); }
    String what() { return "Returning D"; }
    void change() { System.out.println("Changed String"); }
    void adjust() { System.out.println("Adjusting D"); }
}

public class MethodTest {
    public static void main(String[] args) {
        A a = new C();
        System.out.println(a.what());  //----------(a)
        A a1 = new B();
        a1.method('X');  //------------------------(b)
        B b = new B();
        b.adjust();  //----------------------------(c)
        A a2 = new D();
        ((D)a2).change();  //----------------------(d)
        A[] arr = {new A(), new B(), new C()};
        arr[1].method('Y');  //--------------------(e)
    }
}

(a) What is printed at line (a)?

Returning C. Static type A (so the call compiles — A declares what()), dynamic type C, and C overrides what().

(b) What is printed at line (b)?

B.method() X. Same reasoning: A declares method(char), B overrides it, the object is a B. The char argument is just passed through and printed.

(c) What is printed at line (c)?

Adjusting B. Here the static and dynamic types are both B, so there is nothing subtle: B's adjust() runs.

Every one of these problems includes a line like this one. It is there to be free marks — take them and move on.

(d) What is printed at line (d)?

Changed String.

change() is declared only in D. The static type of a2 is A, so a2.change() would not compile — this is the getRadius situation from section 3. The cast ((D)a2) changes the static type of the expression to D, which makes the call legal, and at run time the object really is a D, so the cast succeeds.

Note the parentheses: ((D)a2).change(). Writing (D)a2.change() would parse as (D)(a2.change()) — cast the result, not the receiver — and would not compile.

(e) What is printed at line (e)?

B.method() Y.

A[] arr is an array of A references, so arr[1] has static type A and the call compiles. The element at index 1 is a B, so B's override runs. Index carefully: the array is {A, B, C} and arr[1] is the middle one.

Returning C
B.method() X
Adjusting B
Changed String
B.method() Y

Things to notice across all five parts. This program is section 2, section 5 and section 6 of this lecture in five lines: dispatch through a superclass reference, dispatch through an array element, and a downcast to reach a subclass-only method. Not one line involves overloading — every method(char) has the same signature everywhere — which is why every answer follows the object.

Note also that D inherits and overrides adjust() but nothing ever calls it, and that C is never asked to method. Exam programs are usually padded with methods that are never called; identify the five calls first and ignore the rest.

Problem 3 — What will be printed? (from Exam 2 Practice Problems)

What will be printed by the following program?

Question.java

class A {
    int x = 0;

    public void increment() { x++; }

    public String toString() { return "class A: " + x; }

    public B getB() { return new B(); }
}

class B extends A {
    public String toString() { return "Class B: " + x; }

    public A getA() { return getB(); }
}

public class Question {
    public static void main(String[] args) {
        B b = new B();
        A a = b;
        System.out.println(a);          // line A
        b.increment();
        System.out.println(a);          // line B
        a = new A();
        System.out.println(a.getB());   // line C
        System.out.println(b.getA());   // line D
    }
}

(a) What is the output generated at line A?

Class B: 0 — with a capital C, which is how B's toString is written.

A a = b; is an upcast: one object, two references. The static type of a is A, so println(a) compiles; the dynamic type is B, so B's toString runs. x is still 0.

(b) What is the output generated at line B?

Class B: 1.

b.increment() ran A's increment() — B does not override it — which incremented x on the object. a and b refer to the same object, so printing through a sees the change. This is the aliasing idea from Lecture 8 meeting polymorphism: two references, two static types, one object.

(c) What is the output generated at line C?

Class B: 0.

a = new A(); repoints a at a brand-new A object — the B object is untouched and b still refers to it. Then a.getB() runs A's getB(), which returns new B(): a fresh B whose x is 0. Printing it dispatches to B's toString.

The declared return type of getB() is B, but that is not what decides the output — the object is.

(d) What is the output generated at line D?

Class B: 0.

b.getA() runs B's getA(), whose body is return getB();. getB() is inherited from A and returns yet another new B(), with x at 0. The declared return type of getA() is A, so the compiler treats the result as an A — and once again the object is a B, so B's toString runs.

Class B: 0
Class B: 1
Class B: 0
Class B: 0

Things to notice across all four parts. Every line prints Class B:. A's toString is never reached, even at line C where the receiver a is declared A and holds an A — because what gets printed is the returned B, not a. Reading the receiver instead of the argument is the classic way to lose this problem.

The only line where the number is not 0 is B, and it is 1 rather than 0 purely because a and b are aliases. Lines C and D each construct a new B and immediately print it, so no increment() has ever touched them.

Problem 4 — A shape report (added for these notes)

Using the Shape / Rectangle / Square / Circle hierarchy from section 1, write a complete program ShapeReport.java that:

  • builds a Shape[] containing new Circle(3), new Rectangle(5, 4), new Square(7) and new Circle(1), in that order;
  • loops once over the array, printing each shape;
  • for every element that is really a Circle, prints an extra indented line circle of radius followed by its radius;
  • after the loop, prints the number of shapes, the number of circles, and the total area.

Your loop body must not contain a cast that is not guarded.

Plan. Two different jobs happen in the same loop and they need different tools. Printing the shape and adding its area are general jobs: toString and getArea are both visible from Shape, so they need nothing special and dynamic binding handles the rest. Getting the radius is a specific job: getRadius is not visible from Shape, so it needs instanceof and then a downcast, inside the guarded branch.

Keep the counters outside the loop and accumulate as you go, exactly as in CSCI 111.

public class ShapeReport {

Quick Check 13.12

Close the book and answer these in one sentence each. They are the whole lecture.

(a) Which type decides whether x.f() compiles, and which type decides whose f() runs?

The static type of x decides whether it compiles — the compiler looks for a declaration of f() in that class or its ancestors. The dynamic type of the object in x decides whose body runs — the JVM starts at the actual class and walks up until it finds an implementation.

(b) Why can the compiler not simply look at the previous line and see what object was assigned?

Because in general there is no previous line to look at. The reference may have come from a method call, an array element, a Scanner reading user input, or a loop that assigns different subclasses on different iterations. A rule that worked only for the easy cases would not be a rule, so Java applies the strict version everywhere.

(c) You are looking at a call p.g(q) where several methods are named g. In what order do you resolve it?

First pick the signature, at compile time, from the static type of q (and of p, which limits which g methods are visible at all) — the most specific applicable one wins. Then pick the body, at run time, from the dynamic type of p. Overload first, override second, and never let the second decision change the first.

(d) When do you need a cast, and what must you do before writing one?

You need a downcast exactly when you want a member that the static type does not declare. Before writing one, either guard it with instanceof, or be able to point at the line of code that guarantees the dynamic type. An unguarded, unjustified cast is a ClassCastException waiting for a bigger input.

Things to notice across all four parts. Every one of these answers is the same sentence in different words: the declaration is for the compiler, the object is for the JVM. If you can say which of the two a given question is about, you can answer it.

Lecture Summary
  • Polymorphism means a superclass reference can hold a subclass object: Shape s = new Circle(3);. The reverse is never allowed.
  • Every reference has two types. The static type is what the declaration says and never changes; the dynamic type is what the object is and can change on every assignment.
  • Dynamic binding: for an overridden instance method, the dynamic type decides which body runs. That is why one print(Shape) method prints four different strings.
  • The compiler's rule is the mirror image: the static type decides what you are allowed to call. Shape s = new Circle(3); s.getRadius(); is a compile error even though the object has a radius.
  • Overriding is resolved at run time by the dynamic type; overloading is resolved at compile time by the static type. Choose the signature first from the declarations, then the body from the object. This is the single most examined idea in the course.
  • An array of the superclass type holds any mixture of subclasses, and one loop over it does the right thing for each — the practical reason to build a hierarchy at all.
  • A downcast (Circle) s widens what the compiler will let you call, guarded by instanceof. An unguarded one that is wrong throws a ClassCastException at the cast, not at the method call.
  • Field access is not polymorphic. A field is chosen by the static type, so a hidden field and an overridden method reading it can disagree about the same object.
