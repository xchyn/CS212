File Input and Output

How a Java program reads a text file and writes one — and why a forgotten close() leaves you staring at an empty file.

Learning Objectives

By the end of today's session you should be able to:

  1. Explain what a File object actually holds — a pathname, not the contents of a file — and why new File(...) never touches the disk.
  2. Inspect a file before opening it with exists(), length(), getName(), getAbsolutePath(), canRead() and canWrite().
  3. Read a text file with a Scanner built over a File, token by token with next() and line by line with nextLine().
  4. Write a text file with a PrintWriter, using either the PrintWriter(String) or the PrintWriter(File) constructor.
  5. Explain why close() is not optional, and recognise the empty-file symptom of forgetting it.
  6. Say why any program that opens a file needs throws FileNotFoundException on main, or a try/catch.
  7. Read a whole file and process every word in it — trim, split, filter, collect.
  8. Copy one file to another while transforming the text on the way.

1.From the keyboard to the disk

In Lecture 3 you learned to read input with a Scanner:

Scanner scanner = new Scanner(System.in);

That object reads characters typed at the keyboard, hands you the next token with next(), the next whole number with nextInt(), the next line with nextLine(), and tells you whether there is any more with hasNext(). In Lecture 4 you learned the String methods — trim, split, substring, toLowerCase, indexOf — that turn a line of text into something you can compute with.

Today those two things meet. Almost every real program gets its data from a file rather than from a person typing, and produces a file rather than a screenful of text that disappears when the terminal closes. The good news is that you already know most of it.

Key Idea— Scanner does not care where the characters come from

new Scanner(System.in) reads from the keyboard. new Scanner(new File("input.txt")) reads from a file. Everything after that line is identical. The same hasNext(), the same next(), the same nextInt(), the same nextLine(). You are not learning a new way to read input today; you are learning a new place to point the reader you already have.

For output there is a matching idea. System.out writes to the screen with print and println; a PrintWriter writes to a file with print and println. Same two method names, different destination.

ConsoleFile
Readingnew Scanner(System.in)new Scanner(new File("input.txt"))
WritingSystem.out.println(x)output.println(x) where output is a PrintWriter
When you are donenothing to doyou must call close()

The last row is the one that costs people an afternoon, and §5 is entirely about it.

Warning— the word throws you are about to see

Every file program in this lecture has throws FileNotFoundException written on its main method, or wraps the file code in a try/catch. That is because opening a file can fail — the file may not be there — and Java refuses to let you ignore the possibility. Leave it off and the program does not compile:

MissingNoThrows.java:6: error: unreported exception FileNotFoundException; must be caught or declared to be thrown
        Scanner input = new Scanner(new File("input.txt"));
                        ^
1 error

For now, treat throws FileNotFoundException as a required piece of punctuation on any main that opens a file, exactly as the lecture notes do. The machinery behind it — what an exception is, what try, catch and throw really do — is explained properly in Lecture 20.

Quick Check 5.1

You have a working program that reads five integers from the keyboard with Scanner input = new Scanner(System.in); and prints their sum. You now want it to read those five integers from a file called data.txt instead. How much of the program has to change?

Plan. Ask which lines mention the source of the input, and which lines merely use the Scanner.

Exactly one line changes:

Scanner input = new Scanner(new File("data.txt"));

Plus two supporting edits that are not really part of the logic: you add import java.io.File; and import java.io.FileNotFoundException; at the top, and you add throws FileNotFoundException to the main header. The loop, the nextInt() calls, the accumulator and the println at the end are untouched.

Things to notice. This is the whole reason Scanner was designed the way it is. It is a parser, not a keyboard driver: you hand it a source of characters and it hands you tokens. Later in the course you will see the same idea everywhere in Java — a class that does one job well, connected to a source or a destination you choose at construction time.

2.The File class — a name, not the contents

Before you can read or write a file you have to say which file. That is the job of the File class, and its one genuinely surprising property is what it does not do.

Definition— the File class

The File class, from the package java.io, represents file and directory pathnames in an abstract manner. A File object holds a path — a piece of text naming a location in the file system. It does not hold the file's contents, and creating one does not create, open, read or modify anything on disk.

Constructors

  • File(String pathname) — the one you will use in this course: File f = new File("path to file");
  • File(URI uri) — the same idea, given a URI object instead of a string.

Important methods

MethodReturnsWhat it tells you
boolean exists()booleanwhether there really is a file at this path
long length()longthe size of the file in bytes
String getName()Stringthe name of the file or directory, without the directories in front of it
String getAbsolutePath()Stringthe full path, starting from the root of the file system
boolean canRead()booleanwhether this program is allowed to read it
boolean canWrite()booleanwhether this program is allowed to write to it
Key Idea

new File("report.txt") is no more magical than String s = "report.txt";. It records a name. Nothing is opened, nothing is created, and the file does not have to exist. The disk is not consulted until you call a method like exists() — or hand the File to a Scanner or a PrintWriter.

Here is a program that makes the point. It builds two File objects: one for a file that really is sitting in the folder, one for a name I invented.

Worked Example— what a File object knows

The folder this program runs in contains one file, input.txt:

input.txt

Grace Hopper 98
Alan Turing 91

There is no file called nosuchfile.txt anywhere. Before you reveal the output, answer two questions. Does running this program create nosuchfile.txt? And what can length() possibly return for a file that is not there?

The two getAbsolutePath() lines are representative — they show the folder this program happened to run in, and yours will be different. Everything else on the page is the same wherever you run it.

Four things to take away:

  • No file was created. After this program finishes, nosuchfile.txt still does not exist. new File(...) only recorded the name.
  • length() is 0 for a file that is not there. That is a trap: length() == 0 does not mean "the file exists and is empty". It could equally mean "there is no such file". Ask exists() first; you will see in §5 that a real file of length 0 is a distinct and very common bug.
  • canRead() is false for a missing file, for the same reason.
  • getAbsolutePath() works on a name that does not exist. It is pure string arithmetic — the current folder glued in front of the name you gave.

input.txt reports 47 bytes. Count the visible characters and you get 44; the other three are the newline characters at the end of the three lines. Every line of a text file ends with a character you cannot see, and length() counts it.

Quick Check 5.2

Write a complete program FileReport.java with a private static void report(String name) method that prints, for the file named by its parameter: the file's name, and then — only if the file exists — its size in bytes, whether it is readable, and whether it is writable. If the file does not exist it should print (no such file) instead. Call it twice from main, once on poem.txt (which exists, and is 83 bytes) and once on missing.txt (which does not).

Plan. The whole point of the exercise is the if (f.exists()) guard. Asking a missing file for its length() is not an error — it quietly answers 0 — so nothing forces you to check. You have to remember to. Build the File object once at the top of the method and reuse it; there is no reason to construct it three times.

FileReport.java

import java.io.File;

public class FileReport {
    public static void main(String args[]) {
        report("poem.txt");
        report("missing.txt");
    }

    private static void report(String name) {
        File f = new File(name);
        System.out.println("Name:     " + f.getName());
        if (f.exists()) {
            System.out.println("Size:     " + f.length() + " bytes");
            System.out.println("Readable: " + f.canRead());
            System.out.println("Writable: " + f.canWrite());
        } else {
            System.out.println("          (no such file)");
        }
        System.out.println();
    }
}
Name:     poem.txt
Size:     83 bytes
Readable: true
Writable: true

Name:     missing.txt
          (no such file)

Things to notice. There is no throws FileNotFoundException here and none is needed. Nothing in this program opens a file — exists(), length() and friends just ask the operating system a question about a path, and asking about a path that is not there is a perfectly ordinary answer, not a failure. The moment you add a Scanner or a PrintWriter, the throws becomes mandatory.

Checking exists() before opening a file is the polite version of a program that would otherwise crash with a stack trace. We use it in almost every program from here on.

3.Reading a file with Scanner

To read a file, hand the File object to a Scanner. From then on the Scanner behaves exactly as it did with System.in.

Procedure— reading a text file
  1. import java.io.File;, import java.io.FileNotFoundException; and import java.util.Scanner;.
  2. Add throws FileNotFoundException to the main header.
  3. Build the scanner: Scanner input = new Scanner(new File("input.txt"));
  4. Loop while there is more input: while (input.hasNext()) for tokens, or while (input.hasNextLine()) for lines.
  5. Take one item per pass: input.next(), input.nextInt(), input.nextLine().
  6. Call input.close() when the loop is finished.
Definition— token

A token is a run of characters with no whitespace in it. By default a Scanner splits its input at whitespace — spaces, tabs and newlines — so next() hands you one word at a time and does not care which line that word was on. nextLine() ignores tokens entirely and hands you everything up to the next newline, spaces and all.

Worked Example— one token at a time

The file being read is the same three-line input.txt from §2:

input.txt

Ada Lovelace 95
Grace Hopper 98
Alan Turing 91

Before you reveal: how many times does the loop body run?

ReadTokens.java

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class ReadTokens {
    public static void main(String args[]) throws FileNotFoundException {
        Scanner input = new Scanner(new File("input.txt"));
        int count = 0;
        while (input.hasNext()) {
            String token = input.next();
            count++;
            System.out.println(count + ": " + token);
        }
        input.close();
        System.out.println("Tokens read: " + count);
    }
}

Nine times — three tokens on each of three lines. Notice what is missing from the output: any trace of where the lines ended. To next(), the newline between 95 and Grace is just another piece of whitespace. If the whole file had been written on one line the output would have been identical.

Notice also that 95 came back as the String "95", not the number 95. next() always returns a String. If you want the number you either ask for it directly with nextInt(), or convert afterwards with Integer.parseInt(token).

Worked Example— one line at a time

Now the same file read with hasNextLine() and nextLine(). Each line is name surname score, so the score is the last piece after splitting on spaces. This version also guards the file with exists() before opening it — the habit from §2.

ReadLines.java

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class ReadLines {
    public static void main(String args[]) throws FileNotFoundException {
        File f = new File("input.txt");
        if (!f.exists()) {
            System.out.println("Cannot find " + f.getName());
            return;
        }
        Scanner input = new Scanner(f);
        int lineNo = 0;
        int total = 0;
        while (input.hasNextLine()) {
            String line = input.nextLine();
            lineNo++;
            System.out.println(lineNo + " | " + line);
            String parts[] = line.split(" ");
            total += Integer.parseInt(parts[parts.length - 1]);
        }
        input.close();
        System.out.println("Average score: " + total / (double) lineNo);
    }
}
1 | Ada Lovelace 95
2 | Grace Hopper 98
3 | Alan Turing 91
Average score: 94.66666666666667

Three passes this time instead of nine, and each pass sees a whole record. That is the reason to prefer nextLine() whenever the file has a row-and-column shape: the line is the record, and split from Lecture 4 breaks it into fields.

parts[parts.length - 1] is the last field. Writing parts[2] would have worked for this file too, but it would break the day somebody has a middle name. Indexing from the end is the more honest expression of "the score is the last thing on the line".

total / (double) lineNo is the Lecture 1 division trap again. total is 284 and lineNo is 3; without the cast you would get the int 94 and never notice.

Quick Check 5.3

This program opens the same three-line input.txt twice — once with a token loop, once with a line loop. What does it print?

public class CountBoth {
    public static void main(String args[]) throws FileNotFoundException {
        Scanner a = new Scanner(new File("input.txt"));
        int tokens = 0;
        while (a.hasNext()) { a.next(); tokens++; }
        a.close();

        Scanner b = new Scanner(new File("input.txt"));
        int lines = 0;
        while (b.hasNextLine()) { b.nextLine(); lines++; }
        b.close();

        System.out.println("tokens = " + tokens);
        System.out.println("lines  = " + lines);
    }
}

Plan. Count the whitespace-separated words in the file, then count the newline-terminated lines. They are two different questions about the same bytes.

tokens = 9
lines  = 3

Things to notice. The interesting part is why the program needs two Scanner objects. A Scanner is a one-way street: once it has consumed the file there is no rewind() and no reset(). If you need to walk the same file twice you open it twice — or, far more often, you read it once into memory (an array, or the ArrayList of Lecture 6) and walk that.

Notice too that b is opened from a fresh new File("input.txt"). That is not wasteful: File objects are tiny name-holders, and reusing the same one would have worked equally well. It is the Scanner that is used up, not the File.

Common Mistake— new Scanner("input.txt")

Watch the missing new File:

Scanner input = new Scanner("input.txt");          // compiles. reads the wrong thing.
Scanner input = new Scanner(new File("input.txt")); // reads the file

Scanner has a constructor that takes a String, and it scans that string. So the first line builds a scanner over the eleven characters input.txt. Your loop runs once, hands you the token "input.txt", and stops. There is no error message of any kind — the program compiles and runs and produces confident nonsense. If your file-reading loop mysteriously produces exactly one line of output, and that line is the name of your file, this is why.

Quick Check 5.4

The file scores.txt contains five numbers, one per line:

scores.txt

88
94
71
100
65

Write a complete program SumFile.java that reads the numbers with hasNextInt() and nextInt(), and prints how many it read and their sum. Print a message and stop cleanly if the file is not there.

Plan. hasNextInt() is the loop condition: it is true while the next token is something that can be parsed as an int, so the loop stops at the end of the file and stops at the first non-numeric token. Guard with exists() first and return from main if the file is missing.

SumFile.java

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class SumFile {
    public static void main(String args[]) throws FileNotFoundException {
        File f = new File("scores.txt");
        if (!f.exists()) {
            System.out.println("Cannot find " + f.getName());
            return;
        }
        Scanner input = new Scanner(f);
        int sum = 0, count = 0;
        while (input.hasNextInt()) {
            sum += input.nextInt();
            count++;
        }
        input.close();
        System.out.println("Read " + count + " numbers");
        System.out.println("Sum is " + sum);
    }
}
Read 5 numbers
Sum is 418

Things to notice. Because the loop is driven by hasNextInt() rather than hasNext(), this program is also safe against a file that ends with a stray word: it simply stops counting there. That is a feature when the numbers come first and commentary follows, and a silent bug when the stray token is in the middle of the data — everything after it is ignored without a word. If you need to know that happened, loop on hasNext() and test each token yourself.

The return; in the middle of main is not a special file-handling trick. main returns void, so a bare return just means "stop here".

4.Writing a file with PrintWriter

Definition— the PrintWriter class

PrintWriter, also from java.io, provides methods to write formatted data to an underlying Writer. In practice: it is System.out, pointed at a file.

Constructors

  • PrintWriter(String fileName) — name the file directly.
  • PrintWriter(File file) — hand it a File object you have already built and inspected.

The two are interchangeable; use the second when you want to call exists() on the file first, and the first when you do not.

Important methods

  • void print(data) — writes the data.
  • void println(data) — writes the data followed by a line separator.
  • void close() — closes the stream. Not optional. See §5.
Key Idea— a PrintWriter creates and empties the file

Constructing a PrintWriter on a path does two things immediately. If no file is there, it creates one. If a file is there, it throws away everything in it and starts from an empty file. There is no confirmation prompt and no undo.

That truncation is worth seeing rather than being told about.

Worked Example— the second writer wins

This program writes three lines to log.txt, closes the writer, then opens a second PrintWriter on the same file and writes one short line. Before you reveal: how many lines does log.txt contain at the end — four, or one?

Overwrite.java

import java.io.File;
import java.io.FileNotFoundException;
import java.io.PrintWriter;
import java.util.Scanner;

public class Overwrite {
    public static void main(String args[]) throws FileNotFoundException {
        PrintWriter first = new PrintWriter("log.txt");
        first.println("line one");
        first.println("line two");
        first.println("line three");
        first.close();
        System.out.println("after first writer:  " + new File("log.txt").length() + " bytes");

        PrintWriter second = new PrintWriter("log.txt");
        second.println("oops");
        second.close();
        System.out.println("after second writer: " + new File("log.txt").length() + " bytes");

        Scanner in = new Scanner(new File("log.txt"));
        while (in.hasNextLine()) System.out.println("    " + in.nextLine());
        in.close();
    }
}
after first writer:  29 bytes
after second writer: 5 bytes
    oops

One line. The three lines written by first are gone — not appended to, not preserved: gone. 29 bytes became 5 (four letters plus one newline) the instant the second PrintWriter was constructed, before println was called even once.

This is not a bug you can work around with the classes in this lecture. PrintWriter always starts fresh. If you want to add to an existing file you need a FileWriter opened in append mode, which is outside today's scope; the more common answer in this course is to read the old file, keep what you want, and write everything back out in one pass.

Which is exactly why the instructor's own output example starts with a guard. Here is her program, unchanged except for the file name.

Worked Example— saving data to a file, safely

The array of colors is written one per line to colors.txt, but only if that file is not already there. Before you reveal, predict two things: what the program prints on a clean folder, and what it prints if you run it a second time.

FileOutput.java

import java.io.File;
import java.io.FileNotFoundException;
import java.io.PrintWriter;

public class FileOutput {
    public static void main(String[] args) throws FileNotFoundException {
        String colors[] = {"red", "orange", "yellow", "green", "blue"};
        File out = new File("colors.txt");
        if (out.exists()) {
            System.out.println("That file already exists. Be careful!");
            System.exit(0);
        }
        PrintWriter output = new PrintWriter(out);
        for (int i = 0; i < colors.length; i++) {
            output.println(colors[i]);
        }
        output.close();
    }
}

The first run prints nothing at all. Not a single character reaches the screen — every println in the loop is a PrintWriter method, and the PrintWriter writes to the file. Like javac, silence means it worked. The evidence is the new file:

colors.txt — after the first run

red
orange
yellow
green
blue

The second run reaches the guard, finds the file, and stops:

That file already exists. Be careful!

System.exit(0) ends the program immediately, wherever it is called from — the 0 is the "no problems" status code that the operating system sees. It is a blunt instrument. In a main this short you could equally have written return;, and in a method that is called from somewhere else you would have to, because System.exit gives the caller no chance to recover.

Notice the two shapes of println sitting side by side in one program: System.out.println(...) goes to the screen, output.println(...) goes to the file. The method name is the same because the idea is the same; the receiver before the dot is what decides the destination.

And now the round trip. The file we just wrote is a perfectly ordinary text file, so the Scanner from §3 can read it straight back. This is the instructor's Example 2.

Worked Example— reading back what we wrote

FileInput.java

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class FileInput {
    public static void main(String args[]) throws FileNotFoundException {
        Scanner input = new Scanner(new File("colors.txt"));
        while (input.hasNext()) {
            System.out.println(input.next());
        }
        input.close();
    }
}
red
orange
yellow
green
blue

Five tokens, five lines of output. Here next() and nextLine() would have given the same answer, because each line of colors.txt holds exactly one whitespace-free word. That is a property of this particular file, not a general rule — go back to input.txt in §3, where the two loops gave 9 and 3.

FileOutput and FileInput together are the shape of an enormous number of real programs: compute something, write it to a file, and let a different program — possibly written by someone else, possibly written next year — read it back.

Quick Check 5.5

Suppose you delete the four lines of the exists() guard from FileOutput, so the program goes straight to new PrintWriter(out).

(a) What happens the first time you run it in a folder with no colors.txt?

Exactly what happened before: the file is created and the five colors are written to it. The guard never fired on the first run anyway, so removing it changes nothing here.

(b) You now edit colors.txt by hand, adding purple and black, and run the program again. What is in the file afterwards?

The original five colors and nothing else. Constructing the PrintWriter truncated the file to zero bytes, destroying both of your additions, and then the loop wrote red through blue again.

Things to notice across both parts. The guard is not there to protect the program — the program runs fine without it. It is there to protect your data. Any time a program writes to a file whose name it did not just invent, ask what happens if that file already contains something a human cares about. This is also why real tools ask "overwrite?" and why PrintWriter, which never asks, should be pointed at output files rather than at files you are also editing by hand.

5.close(), and the empty-file bug

Every Scanner and every PrintWriter in this lecture ends with a call to close(). For a Scanner that is good manners — it releases the operating system's handle on the file. For a PrintWriter it is the difference between a file with your data in it and a file with nothing in it.

Definition— buffering

Writing to a disk is thousands of times slower than writing to memory, so a PrintWriter does not send your characters to the disk one at a time. It collects them in a buffer — a block of memory, several thousand characters wide — and only writes the whole block out when the buffer fills up, or when you tell it to.

close() is how you tell it to. It empties the buffer to the disk (this is called flushing) and then releases the file. Skip it, and whatever was still in the buffer when your program ended is simply never written.

Common Mistake— the file is there and it is empty

This is the single most common file-output bug, and its symptom is peculiar enough to be worth memorising: the file exists, it has the right name, and it is zero bytes long. Here are two programs that differ by one line.

ForgotClose.java

import java.io.File;
import java.io.FileNotFoundException;
import java.io.PrintWriter;

public class ForgotClose {
    public static void main(String args[]) throws FileNotFoundException {
        PrintWriter output = new PrintWriter("forgot.txt");
        output.println("red");
        output.println("orange");
        output.println("yellow");
        // no output.close();

        File f = new File("forgot.txt");
        System.out.println("exists() = " + f.exists());
        System.out.println("length() = " + f.length());
    }
}
exists() = true
length() = 0

ClosedProperly.java

import java.io.File;
import java.io.FileNotFoundException;
import java.io.PrintWriter;

public class ClosedProperly {
    public static void main(String args[]) throws FileNotFoundException {
        PrintWriter output = new PrintWriter("closed.txt");
        output.println("red");
        output.println("orange");
        output.println("yellow");
        output.close();

        File f = new File("closed.txt");
        System.out.println("exists() = " + f.exists());
        System.out.println("length() = " + f.length());
    }
}
exists() = true
length() = 18

Eighteen bytes: red, orange and yellow are 15 characters, plus three newlines. The version without close() produced a file of length 0 — the three println calls really did run, and their output really is gone.

You might reasonably suspect that the buffer gets flushed when the program ends, and that length() was merely asked too early. It does not, and it was not. Here is a separate program, run after both of the above had finished, which opens the two files from scratch and prints what is in them.

Worked Example— the evidence, after the fact

ShowFile.java

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class ShowFile {
    public static void main(String args[]) throws FileNotFoundException {
        report("forgot.txt");
        report("closed.txt");
    }

6.Worked program: every word in a file

Everything so far has been machinery. This section and the next put it to work on the two text-processing programs from the Spring 2025 notes. Both do the same three things a great many real programs do: open a file, take it apart line by line with the String methods from Lecture 4, and produce something new.

The first one collects every word in a file, folded to lower case, with duplicates removed and the result in alphabetical order. It uses one library class we have not met.

Definition— TreeSet

A TreeSet<String> is a library container that holds a set of String values: adding a value that is already in it does nothing, and iterating over it always visits the values in sorted order. You get de-duplication and sorting for free, without writing a line of either.

You do not need to know how it works to use it here. Its close relative ArrayList is the subject of Lecture 6, and the angle brackets in TreeSet<String> — which say "a TreeSet of String" — are explained properly in Lecture 22.

Worked Example— print all the words in the file

LongWords.java

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;
import java.util.TreeSet;

public class LongWords {
    public static void main(String args[]) throws FileNotFoundException {
        Scanner input = new Scanner(new File("poem.txt"));
        TreeSet<String> dictionary = new TreeSet<String>();
        while (input.hasNextLine()) {

            char c = s.charAt(i);
            if ('a' <= c && c <= 'z') continue;
            if ('A' <= c && c <= 'Z') continue;

        return true;

Four points worth pulling out of this program.

  • split("\\s", -1) splits on a single whitespace character. Two spaces in a row therefore produce an empty string between them — there is nothing between the first space and the second. That is why the !words[i].isEmpty() test is there, and it is not optional: without it, the empty string sails through isWord (a loop over zero characters returns true) and lands in the dictionary as a blank entry. Writing split("\\s+", -1) instead would collapse runs of whitespace and avoid the problem at the source.
  • trim() handles the ends, isEmpty() handles the middle. line.trim() removes leading and trailing whitespace so the split does not produce an empty first or last token; the isEmpty() guard catches the ones in the interior.
  • isWord is all-or-nothing. One non-letter anywhere in the token rejects the whole thing. That is why dogs! disappears entirely rather than being trimmed to dogs. If you wanted dogs, you would strip the punctuation before the test rather than tightening the test.
  • The continue statements read as "this character is fine, move on". Any character that reaches the end of the loop body without hitting a continue triggers return false. It is a compact way to write "reject unless one of these holds".

One honest note about the name. The class is called LongWords, but as written it keeps every word regardless of length — the instructor's own comment on it is "print all the words in the file". Quick Check 5.9 makes the name true.

Quick Check 5.8

Questions about isWord and the split.

(a) What does isWord("") return, and why does that matter?

true. The for loop runs zero times, so control falls straight through to return true. It matters because an empty string is not a word by anybody's definition, so isWord alone would let it into the dictionary. The guard !words[i].isEmpty() in the caller is what actually keeps it out.

This is a general pattern with "do all the elements satisfy P?" loops: they always answer true for an empty collection. That is usually the mathematically right answer and almost never the one your program wants.

(b) The line "can't stop" is split with split("\\s", -1) and each piece is passed to isWord. What ends up in the dictionary?

Only stop. The split gives the two tokens can't and stop; the apostrophe in can't is not in a–z or A–Z, so isWord returns false at the fourth character and the token is dropped.

(c) The file contains Fox on one line and fox on another. How many entries do they contribute?

One. toLowerCase() turns both into fox before add is called, and a TreeSet refuses to store the same value twice.

Things to notice across all three parts. Each of the three filters in this program does exactly one job, and none of them can do another's: isEmpty() rejects nothing-at-all, isWord rejects not-all-letters, toLowerCase() plus the TreeSet rejects duplicates. When a text-processing program gives you a surprising answer, work out which of your filters let the surprise through rather than rewriting all of them.

SplitLines.java

import java.io.File;
import java.io.FileNotFoundException;
import java.io.PrintWriter;
import java.util.Scanner;

public class SplitLines {
    public static void main(String args[]) throws FileNotFoundException {
        Scanner input = new Scanner(new File("wrapme.txt"));
        PrintWriter output = new PrintWriter(new File("wrapped.txt"));
        while (input.hasNextLine()) {
            String line = input.nextLine();
            line = line.replaceAll("\t", "  ");
            while (line.trim().length() > 0) {
                if (line.length() <= 40) {
                    output.println(line);
                    line = "";
                }
                else {
                    String indent = indentationOf(line);
                    int cutAt = cut(line, indent, 40);
                    if (cutAt < indent.length()) {
                        output.println(line);
                        line = "";
                    } else {
                        output.println(line.substring(0, cutAt));
                        line = indent + "  " + line.substring(cutAt);
                    }
                }
            }
        }
        input.close();
        output.close();
    }

    private static int cut(String line, String indent, int desiredLength) {
        if (desiredLength < indent.length()) desiredLength = indent.length() + 1;
        int index = line.lastIndexOf(" ", desiredLength);
        if (index < indent.length()) index = line.indexOf(" ", desiredLength);
        return index;
    }

    private static String indentationOf(String line) {
        String answer = "";
        int i = 0;
        while (i < line.length() && line.charAt(i) == ' ') {
            answer += " ";
            i++;
        }
        return answer;
    }
}

The helper methods are worth a moment each.

  • indentationOf counts the leading spaces and returns a String of exactly that many spaces, so the continuation lines can be lined up under the original.
  • cut finds where to break. line.lastIndexOf(" ", 40) searches backwards from position 40 for a space, which gives the longest piece that still fits. If there is no space that early — a single enormous word — it falls back to line.indexOf(" ", 40), searching forwards, and accepts a line that is too long rather than cutting a word in half.
  • replaceAll("\t", " ") turns every tab into two spaces first, so that counting characters means something. A tab is one character but occupies eight columns on screen, and no amount of length() arithmetic can account for that.

The if (cutAt < indent.length()) test is the safety valve. If cut came back with -1 (no space anywhere after the indent) the program gives up on splitting, writes the long line as it is, and moves on. Without that branch, substring(0, -1) would throw and the program would stop.

Warning— the continuation lines creep to the right

Look at the output above again. The first line's continuations are indented by 3 spaces and then 6; the second line's by 7 and then 10. Each continuation is indented further than the last, which is almost certainly not what was wanted — the intent is clearly a fixed two-space hanging indent.

Two things combine to cause it. First, line.substring(cutAt) starts at the space the cut was made on, so that space is carried over to the new line on top of the two that are added. Second, indentationOf(line) is recomputed inside the inner loop, so on the next pass it measures the indentation of the already-indented continuation and adds two more spaces to that.

Both are fixed by hoisting indent out of the inner loop, where it belongs — the indentation of a line is a property of the line, not of the piece you are currently chopping — and by skipping the space with substring(cutAt + 1):

String line = input.nextLine();
line = line.replaceAll("\t", "  ");

        output.println(line);

            line = "";

            output.println(line.substring(0, cutAt));
            line = indent + "  " + line.substring(cutAt + 1);   // skip the space

Quick Check 5.11

SplitLines keeps a Scanner and a PrintWriter open at the same time and closes both at the end.

(a) What would go wrong if the two file names were the same — input and output both wrapme.txt?

You would destroy the input before reading a byte of it. Constructing the PrintWriter truncates its file to zero length, and that happens on the line before the reading loop starts. The Scanner then finds an empty file, hasNextLine() is false immediately, and you are left with an empty wrapme.txt and no way back.

This is the single most destructive mistake in this lecture, and it is a two-character typo. When a program reads one file and writes another, read the two names side by side before you run it.

(b) The program calls input.close() and then output.close(). Does the order matter?

Not here. They are two independent files; closing one has no effect on the other. What does matter is that output.close() happens at all, and that it happens before anything tries to read wrapped.txt.

Things to notice across both parts. The two closes are also doing different amounts of work. input.close() releases a resource. output.close() releases a resource and flushes the buffer — it is the line that actually puts your data on the disk. If you are ever short of patience for one of them, it is not the writer's.

Problem 1 — Strings and files, two methods (from Exam 1 Practice Problems, also Midterm Practice Problems)

This question is related to Strings and Files. It is a two-part question that requires code for two methods.

(a) Write a private method called removeDuplicates that accepts a String parameter and returns a new String in which consecutive occurrences of a character are removed. If removeDuplicates("football") is called, it returns fotbal after replacing the consecutive os by a single o and the consecutive ls by a single l. Similarly if we pass cookbook!!! as a parameter, it returns cokbok!.

Plan. Walk the string comparing each character with the one before it, and delete the later of any equal pair. Walk backwards, from the end towards the front: if you delete while walking forwards, every deletion shifts the remaining characters left and your index no longer means what you thought it meant. Going backwards, the part you have not looked at yet is in front of i and is never disturbed.

Deleting character i is str.substring(0, i) + str.substring(i + 1) — everything before it, joined to everything after it. String is immutable (Lecture 4), so this builds a new string and reassigns str rather than editing in place.

private static String removeDuplicates(String str) {
    if (str == null || str.length() <= 1) return str;
    for (int i = str.length() - 1; i > 0; i--) {
        if (str.charAt(i) == str.charAt(i - 1)) {
            str = str.substring(0, i) + str.substring(i + 1);
        }
    }
    return str;
}

Trace "football": at i = 7 the pair l,l matches, so one l goes and the string becomes footbal; at i = 2 the pair o,o matches and the string becomes fotbal. No other adjacent pair is equal, so fotbal is the answer — matching the required output.

The str.length() <= 1 guard is what makes i - 1 safe: a string of length 0 or 1 has no adjacent pairs, and the loop condition i > 0 never lets i - 1 go negative anyway. Both belt and braces, and neither costs anything.

(b) Write a private method called removeDuplicatesFromFile that accepts a String parameter naming a text file. It reads the file line by line and removes from each word of the file any consecutive occurrences of a character. It prints the entire modified text with words separated by spaces, and punctuation marks. You may assume the file exists and the words are separated by single spaces.

Plan. The hard part is already done in part (a); this method is pure file plumbing. Open a Scanner on the named file, loop with hasNextLine(), split each line into words, run removeDuplicates on each word, rebuild the line with single spaces, and print it. Note that the output goes to the screen — the question says "prints" and never mentions an output file, so there is no PrintWriter here at all.

This is the one place in the lecture where the instructor's solution uses try/catch rather than throws. The effect is the same: Java is told what to do if the file is not there. Lecture 20 explains the mechanism.

    }

    private static String removeDuplicates(String str) {
        if (str == null || str.length() <= 1) return str;
        for (int i = str.length() - 1; i > 0; i--) {
            if (str.charAt(i) == str.charAt(i - 1)) {
                str = str.substring(0, i) + str.substring(i + 1);
            }
        }
        return str;
    }

    private static void removeDuplicatesFromFile(String fileName) {
        try {
            File inputFile = new File(fileName);
            Scanner scanner = new Scanner(inputFile);
            while (scanner.hasNextLine()) {
                String line = scanner.nextLine();
                String[] words = line.split("\\s", -1);
                String modifiedLine = "";
                for (String word : words) {
                    modifiedLine += removeDuplicates(word) + " ";
                }
                System.out.println(modifiedLine.trim());
            }
            scanner.close();
        } catch (FileNotFoundException e) {
            System.err.println("Error: File not found - " + e.getMessage());
        }
    }
}

With this input file:

myFile.txt

The sky is a deep red!!!
Calvin's skin is a pale green!!
Yellow flowers are now blue!!!!
Theee eeend.
The sky is a dep red!
Calvin's skin is a pale gren!
Yelow flowers are now blue!
The end.

Things to notice across both parts. The method does not know or care that deep is a word and !!! is punctuation — it collapses runs of any repeated character, which is why red!!! becomes red! in the same breath as deep becoming dep. The last line is the giveaway: Theee eeend. becomes The end., which reads like a deliberate joke and is really just the same rule applied twice.

modifiedLine += removeDuplicates(word) + " " appends a trailing space after every word, including the last, and trim() on the way out removes it. That is the standard cheap fix for the separator problem; the alternative is to append the space before every word except the first.

Building a String with += inside a loop creates a brand-new String on every pass, because String is immutable. For a line of text that is invisible. For a loop over a million items it is a genuine performance problem, and the standard answer is StringBuilder. Worth knowing the name now; you will meet it again.

Problem 2 — Read a file, write a report (added for these notes)

The file scores.txt contains one integer per line:

scores.txt

88
94
71
100
65

Write a complete program ScoreReport.java that reads those numbers and writes a file called report.txt containing five lines: how many scores were read, their total, their average as a decimal, the highest and the lowest. Then, to prove the file was really written, read report.txt back and print it to the screen. Print a message and stop if scores.txt is not there.

A sample of what the program should print:

Scores read: 5
Total:       418
Average:     83.6
High:        100
Low:         65

Plan. This is the read-transform-write shape, done in three separate stages so nothing overlaps. Stage one: Scanner on scores.txt, loop on hasNextInt(), accumulate count, total, high and low, then close(). Stage two: PrintWriter on report.txt, five println calls, then close() — and the close() has to come before stage three or there will be nothing to read. Stage three: a fresh Scanner on report.txt, echoing it line by line.

Seed high with Integer.MIN_VALUE and low with Integer.MAX_VALUE so that the very first score, whatever it is, replaces both. Seeding them with 0 is the classic bug: a file of negative scores would report a high of 0 that never appeared in the data.

ScoreReport.java

import java.io.File;
import java.io.FileNotFoundException;
import java.io.PrintWriter;
import java.util.Scanner;

public class ScoreReport {
    public static void main(String args[]) throws FileNotFoundException {
        File in = new File("scores.txt");
        if (!in.exists()) {
            System.out.println("Cannot find " + in.getName());
            return;
        }

        Scanner input = new Scanner(in);
        PrintWriter output = new PrintWriter("report.txt");

        int count = 0, total = 0;
        int high = Integer.MIN_VALUE, low = Integer.MAX_VALUE;
        while (input.hasNextInt()) {
            int score = input.nextInt();
            count++;
            total += score;
            if (score > high) high = score;
            if (score < low) low = score;
        }
        input.close();

        output.println("Scores read: " + count);
        output.println("Total:       " + total);
        output.println("Average:     " + total / (double) count);
        output.println("High:        " + high);
        output.println("Low:         " + low);
        output.close();

        Scanner back = new Scanner(new File("report.txt"));
        while (back.hasNextLine()) System.out.println(back.nextLine());
        back.close();
    }
}
Scores read: 5
Total:       418
Average:     83.6
High:        100
Low:         65

And the file itself, which is what actually matters:

report.txt

Scores read: 5
Total:       418
Average:     83.6
High:        100
Low:         65

Things to notice. total / (double) count gives 83.6; without the cast you would get 83 and never see the .6. Integer division has now cost somebody marks in every lecture of this course, and it will keep doing so.

Delete output.close() and this program does not merely produce a wrong file — the echo stage prints nothing at all, because report.txt is zero bytes and hasNextLine() is false on the first test. A program that suddenly falls silent at the end is worth checking for exactly this.

Notice that input and output are both open at the same time, on different files. That is fine, and it is what SplitLines does too. What you must never do is open a PrintWriter on the file you are simultaneously reading.

Problem 3 — Find the three errors (added for these notes)

The following program is meant to copy input.txt to copy.txt, line for line, and then print Copied.. Exactly 3 of the numbered lines are wrong — one of them stops the program compiling, and two of them let it compile and run and then do the wrong thing. Identify the 3 errors by line number, and give a corrected version of each line. Any line without a number is correct as written.

CopyFile.java

import java.io.File;
import java.io.PrintWriter;
import java.util.Scanner;

public class CopyFile {
    public static void main(String args[]) {                   // line 1
        Scanner input = new Scanner("input.txt");              // line 2
        PrintWriter output = new PrintWriter("copy.txt");      // line 3
        while (input.hasNextLine()) {                          // line 4
            output.println(input.nextLine());                  // line 5
        }
        input.close();                                         // line 6
        System.out.println("Copied.");                         // line 7
    }
}

For reference, input.txt is the three-line file from §2:

input.txt

Ada Lovelace 95
Grace Hopper 98
Alan Turing 91

Plan. Compile it first, in your head: which line mentions something that can fail? Then, assuming it compiled, ask the two questions this lecture keeps asking. Where do the characters come from? And where do the characters go?

Error 1 — line 1. main opens files, so it must declare that opening them can fail. This is the error that stops the compile:

CopyFile.java:8: error: unreported exception FileNotFoundException; must be caught or declared to be thrown
        PrintWriter output = new PrintWriter("copy.txt");      // line 3
                             ^
1 error

Corrected: public static void main(String args[]) throws FileNotFoundException {, together with import java.io.FileNotFoundException; at the top. Note that javac pointed at line 3, where the failure could happen, not at line 1, where the fix goes — a good reminder that the caret shows you the symptom, not always the cure.

Error 2 — line 2. new Scanner("input.txt") scans the eleven-character string input.txt, not the file of that name. It compiles and it is silent about it. Add the File:

Corrected: Scanner input = new Scanner(new File("input.txt"));

Error 3 — line 7 (a missing line, really). There is no output.close() anywhere, so whatever the loop writes stays in the buffer and is discarded when the program ends.

Corrected: insert output.close(); immediately after line 6.

To see that errors 2 and 3 really are independent of the compiler, here is the program with only error 1 fixed, plus a line at the end reporting the size of copy.txt:

public static void main(String args[]) throws FileNotFoundException {
    Scanner input = new Scanner("input.txt");
    PrintWriter output = new PrintWriter("copy.txt");

        output.println(input.nextLine());
    }
    input.close();
    System.out.println("Copied.");
    System.out.println("copy.txt length = " + new File("copy.txt").length());
}

copy.txt length = 0

It compiles, it runs, it announces success, and it produced an empty file. With all three fixed:

CopyFile.java

import java.io.File;
import java.io.FileNotFoundException;
import java.io.PrintWriter;
import java.util.Scanner;

public class CopyFile {
    public static void main(String args[]) throws FileNotFoundException {
        Scanner input = new Scanner(new File("input.txt"));
        PrintWriter output = new PrintWriter("copy.txt");
        while (input.hasNextLine()) {
            output.println(input.nextLine());
        }
        input.close();
        output.close();

        System.out.println("copy.txt length = " + new File("copy.txt").length());
    }
}

47 bytes — exactly the size of input.txt, which is what "copy" ought to mean.

Things to notice. One error out of three was caught by the compiler. The other two produced a program that ran to completion and printed a cheerful Copied. Compiling is the beginning of testing, not the end of it, and "it ran without errors" is not evidence that it did anything.

Both of the silent errors have the same shape: a plausible line that points at the wrong thing or stops one step short. Those are the errors worth building habits against — new File inside every Scanner, close() typed at the same time as new PrintWriter.

Problem 4 — What does each expression give? (added for these notes)

A folder contains one file, input.txt, whose contents are the three lines shown in Problem 3, and nothing else. For each expression, give the value and the type, or say that the line does not compile.

File f = new File("input.txt");
File g = new File("report.txt");

(a) f.getName()

The String "input.txt". getName() returns the last component of the path, so it would still be "input.txt" if you had written new File("/home/data/input.txt").

(b) g.exists()

false, a boolean. Constructing g did not create anything — a File object is a name, and there is no report.txt in the folder.

(c) g.length()

0, a long. Not an error and not a crash — a missing file reports a length of zero. This is precisely why length() == 0 is not a usable test for "the file is empty": ask exists() first.

(d) f.length()

47, a long. Three lines of 15, 15 and 14 visible characters is 44, plus one newline character at the end of each line, is 47.

(e) new Scanner(f).nextLine()

Does not compile on its own — new Scanner(File) can throw FileNotFoundException, so the enclosing method needs throws FileNotFoundException or a try/catch. Given that, the value is the String "Ada Lovelace 95".

(f) new Scanner("input.txt").next()

Compiles with no throws at all, and gives the String "input.txt". This is the Scanner-over-a-String constructor: it scans the characters you handed it, and those characters happen to spell a file name. The absence of a required throws is the tell — if the compiler is not making you promise anything, you are not opening a file.

Things to notice across all six parts. Parts (b), (c) and (f) are the three ways this topic goes quietly wrong: a File that does not correspond to anything, a length that means two different things, and a Scanner pointed at a name instead of a file. None of them produces an error message. All three produce confident, wrong answers.

Lecture Summary
  • A File object holds a pathname, not the contents. new File(...) touches nothing on disk. Its constructors are File(String pathname) and File(URI uri); its useful questions are exists(), length(), getName(), getAbsolutePath(), canRead() and canWrite().
  • To read a file, point a Scanner at it: new Scanner(new File("input.txt")). Everything after that is the Scanner you already knew — hasNext/next for tokens, hasNextLine/nextLine for lines, hasNextInt/nextInt for numbers.
  • new Scanner("input.txt") compiles and scans the string. Never omit the new File.
  • To write a file, use a PrintWriter, built from either a name or a File. It has print, println and close, and it writes to the file what System.out writes to the screen.
  • Constructing a PrintWriter creates the file, or empties an existing one. Guard it with exists() when the file might matter.
  • close() is not optional on a PrintWriter. Output sits in a buffer until it is flushed; without close() the file is left existing, correctly named, and zero bytes long.
  • Anything that opens a file may fail, so main needs throws FileNotFoundException or a try/catch. Lecture 20 explains what that really means.
  • Reading a whole file is a nextLine() loop plus the Lecture 4 String methods: trim, split, isEmpty, toLowerCase, substring, charAt.
