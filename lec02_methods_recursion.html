1.From main to methods

Last time we established the skeleton every Java program starts from — a public class with a public static void main(String args[]) inside it — and we filled that main with variables, arithmetic, loops and if statements. Everything we wrote lived in one method. That works for ten lines. It does not work for a hundred.

In CSCI 111 the fix was to write a function. Java has the same idea under a different name, and with one structural difference you already met in Lecture 1: there are no free-floating functions in Java. Every function belongs to a class.

Definition— method

A method is Java's word for a function: a named, reusable block of code that you can call, optionally hand some values to, and optionally get a value back from.

The only structural difference from a C++ function is location. A method is always written inside a class body, between the braces of the class declaration — never above it, never outside it. main is itself a method; it is not special except that the JVM knows to call it first.

Key Idea— and it is nearly a quotation

In Java, functions are also called methods, and at this stage of the course they are all declared static. We will unpick exactly what static buys us in §2, and we will come back to non-static methods once we have objects to attach them to, from Lecture 7 onward.

Here is the smallest possible example: one method that prints a greeting, and a main that calls it three times.

Worked Example— one method, three calls

Two methods are defined in this class, sayHello and main. Only one of them is run by the JVM directly. Before you open the toggle, decide how many lines this prints and in what order the two method bodies execute.

Hello2.java

public class Hello2 {
    public static void sayHello() {
        System.out.println("Hello");
    }

    public static void main(String args[]) {
        sayHello();
        sayHello();
        sayHello();
    }
}
Hello
Hello
Hello

The JVM starts at main. It reaches sayHello();, jumps into the body of sayHello, runs the one println there, and then comes back to exactly where it left off in main. That happens three times. Defining sayHello above main in the file did not make it run first — nothing runs until it is called.

Notice what we have bought for three lines of typing: if the greeting has to change, there is exactly one place to change it. That is the entire argument for methods, and it only gets stronger as the method gets longer.

Quick Check 2.1

In Hello2.java above, sayHello is written before main. In the class notes' MyFunctions.java — which we will see in full in §5 — the method add is written after main, and main calls it anyway. Does the order of the method definitions in the file matter? What would C++ have required?

Plan. Ask what the compiler knows, and when it knows it.

Order does not matter in Java. The compiler reads the entire class body before it checks any method call, so by the time it looks at add(111, 212) inside main it already knows every method the class declares. You may write your methods in whatever order reads best — alphabetical, most-important-first, or main at the top so a reader sees the story before the details.

C++ was stricter. A C++ compiler reads top to bottom in one pass, so a function had to be either defined before its first use or announced first with a prototype:

C++ (CSCI 111) — for comparison only

int add(int x, int y);      // prototype, needed before main can call add

int main() {
    cout << add(111, 212) << endl;
    return 0;
}

int add(int x, int y) { return x + y; }

Things to notice. Java has no prototypes and no header files at all — the class body is the declaration. This is one of the ways Java's designers simplified C++, and it is why you will never see a .h file in this course.

2.The title line, word by word

The first line of a method — everything up to the opening brace — is the part you have to get exactly right, and it is the part the exam asks about most often. The class notes give it as a template:

Definition— title line (signature)

The title line of a static method has this shape:

The template

public static result_type method_name ( define_parameters ) { … }

You may also hear it called the method's signature. It is the method's contract with the rest of the program: what it is called, what it must be handed, and what it hands back.

Take a real one and read every word:

public static String sayHelloTo(String name) {
    return "Hello, " + name + "!";
}
WordWhat it is doing
publicThe access modifier. public means any class may call this method. private would mean only code inside this same class may call it — you will see private on the exam problems in the practice section.
staticThe method belongs to the class itself, not to any object. You call it without first creating anything. Everything we write for the next several lectures is static.
StringThe return type: the type of the value this method hands back to whoever called it. If it hands nothing back, the return type is the keyword void.
sayHelloToThe method name. Java convention is lowerCamelCase, starting with a verb: sayHello, numDigits, rowSum.
(String name)The parameter list: for each value the method expects, a type and a name, separated by commas. Empty parentheses mean the method takes nothing — but the parentheses are never optional.
Definition— parameter vs. argument

A parameter is the variable named in the title line: the name in sayHelloTo(String name). It exists only inside the method.

An argument is the actual value written at the call: the "CSCI 212" in sayHelloTo("CSCI 212").

The two are matched up left to right, by position, and the types must be compatible. Names never have to match anything — the caller has no idea what the method's parameters are called.

Now the word that always gets skipped: static. Lecture 1 said main must be static because when the JVM starts there are no objects for it to call main on. The same reasoning applies to every method we call from main.

Key Idea— static means "call it on the class"

A static method can be called using only the name of its class. A non-static method must be called on an object, and we do not know how to make an object yet — that is Lecture 7. Until then, every method you write gets static, because main is static and a static method has no object to work with.

Leave static off and the compiler tells you so in a sentence that is worth memorising, because you will meet it many times:

NoStatic.java

public class NoStatic {
    public void sayHello() {              // static is missing
        System.out.println("Hello");
    }

    public static void main(String args[]) {
        sayHello();
    }
}
NoStatic.java:7: error: non-static method sayHello() cannot be referenced from a static context
        sayHello();
        ^
1 error

"Static context" means main. The message is telling you that main, having no object, cannot reach a method that needs one. The fix at this stage is always the same: add static to the method you are trying to call.

Quick Check 2.2

Write the title line only — no body — for each of these methods. Each is a static method of the same class.

(a) A method perimeter that is given the length and width of a rectangle as decimals and gives back the perimeter.

public static double perimeter(double length, double width)

Both dimensions can be fractional, so double; the answer is also fractional, so the return type is double. Every parameter needs its own type — writing (double length, width) is a syntax error in Java, even though the two share a type.

(b) A method printLine that is given a whole number n and prints a row of n stars. It gives nothing back.

public static void printLine(int n)

"Gives nothing back" is the definition of void. A method that prints and a method that returns are different things: this one does its work by side effect, and calling it in an expression would be an error.

(c) A method isEven that is given a whole number and answers yes or no.

public static boolean isEven(int n)

"Answers yes or no" means boolean, not an int that is 0 or 1. Java will not let you use that int as a condition anyway — see Lecture 1.

(d) A method repeat that is given a piece of text and a whole number n, and gives back that text written out n times in a row.

public static String repeat(String text, int n)

Things to notice across all four parts. Deriving a title line is a two-question routine, and it is worth doing in this order every time:

  1. What does it need? One type and one name per value, in the order the caller will supply them. That is the parameter list.
  2. What does it give back? That is the return type — or void if the answer is "nothing".

The public static on the front is fixed for now, so the whole job is those two questions. Practice Problem 1 is the exam version of this exercise, worked backwards from calls instead of from descriptions.

3.Returning a value, or not

Every method falls into one of two camps, and mixing them up is the most common method-related error there is.

Definition— void methods and value-returning methods

A void method hands nothing back. A call to it is a complete statement on its own: sayHello();. It cannot appear inside a larger expression, because there is no value there to use.

A value-returning method declares a real type — int, double, boolean, String — and must execute a return statement carrying a value of that type. A call to it is a value: you can print it, assign it, or pass it on to another method.

Worked Example— the two kinds, side by side

These two methods are from the class notes. sayHello prints; sayHelloTo builds a String and returns it without printing anything. The middle line of main is the interesting one — it calls sayHelloTo and does not print the result.

ReturnDemo.java

public class ReturnDemo {
    public static void sayHello() {
        System.out.println("Hello");
    }

    public static String sayHelloTo(String name) {
        return "Hello, " + name + "!";
    }

    public static void main(String args[]) {
        sayHello();
        sayHelloTo("CSCI 212");
        System.out.println(sayHelloTo("CSCI 212"));
    }
}

Three calls, but how many lines of output?

Hello
Hello, CSCI 212!

Two lines, from three calls. The middle call ran perfectly happily: it built the String "Hello, CSCI 212!", returned it — and nobody caught it, so it was discarded on the spot. sayHelloTo never prints; printing is the caller's job.

That is not a compile error and Java gives you no warning about it. It is, however, almost always a bug, and it is worth training your eye: a value-returning call standing alone as a statement is a value being thrown away.

If the title line names a return type, every path through the method must reach a return carrying a value of that type. Printing is not returning:

Quick Check 2.3

For each line, say whether it compiles, and if it does not, what the compiler objects to. Assume both methods from ReturnDemo above are in scope.

(a) String s = sayHelloTo("Ana");

Compiles. sayHelloTo returns a String and s is a String, so the value has somewhere to go. This is the normal way to use a value-returning method.

(b) sayHello("Ana");

Does not compile. sayHello was declared with an empty parameter list, so it accepts no arguments. The compiler says method sayHello in class ReturnDemo cannot be applied to given types, and adds reason: actual and formal argument lists differ in length. The number of arguments must match the number of parameters exactly — Java has no default arguments.

(c) int n = sayHelloTo("Ana");

Does not compile. A String cannot be stored in an int; the message is incompatible types: String cannot be converted to int. The return type in the title line is a promise the compiler checks at every call site.

(d) System.out.println("Greeting: " + sayHelloTo("Ana"));

Compiles, and prints Greeting: Hello, Ana!. The call is an expression of type String, so it can sit on either side of a + exactly like a literal would.

Things to notice across all four parts. Two independent things get checked at every call: the arguments going in (count and types) and the returned value coming out (its type versus what you do with it). Part (b) fails on the way in, part (c) on the way out. When you read a javac complaint about a method call, first work out which of the two directions it is talking about — that alone usually tells you what to fix.

4.Calling a method: arguments, copies and order

A call does three things in a fixed order: it evaluates the arguments, it copies them into the parameters, and then it runs the body. Two consequences follow, and both show up on exams.

Procedure— what happens at a call
  1. Each argument expression is evaluated, left to right. If an argument is itself a method call, that inner call runs to completion first.
  2. The resulting values are copied into the parameters. The parameters are brand-new local variables belonging to the called method.
  3. The body runs. When it finishes — by reaching return, or by falling off the end of a void method — control goes back to the caller, carrying the returned value if there is one.
  4. Every local variable of the method, parameters included, disappears.
Worked Example— when does each call actually happen?

Each call announces itself, so the output records the order in which things really happened. The last line has a call nested inside a call. Work out the full output before revealing — there are seven lines.

Step 2 of the procedure said the arguments are copied. That word is doing a lot of work.

Worked Example— a method cannot change its caller's variable

doubleValue assigns to its parameter x. The question is whether n back in main changes too.

ValueDemo.java

public class ValueDemo {
    public static void doubleValue(int x) {
        x = 2 * x;
        System.out.println("Inside the method, x is " + x);
    }

    public static void main(String args[]) {
        int n = 10;
        doubleValue(n);
        System.out.println("Back in main, n is " + n);
    }
}
Inside the method, x is 20
Back in main, n is 10

n is unchanged. What was passed was the value 10, copied into a fresh variable called x that belongs to doubleValue. Assigning to x overwrites the copy and leaves the original alone. When the method returns, x ceases to exist.

This is called pass by value, and Java does it for every argument, always. There is no C++ & reference parameter in Java and no way to ask for one.

So how does a method give something back? Only through its return value:

public static int doubled(int x) {
    return 2 * x;
}
// at the call site:
n = doubled(n);        // this is how n changes

One honest caveat, flagged now and settled properly in Lecture 8: when the argument is an object rather than a primitive, the value being copied is a reference to that object, and the method can change what the object contains — though it still cannot make the caller's variable point at something different. Her exam problems test exactly that distinction. For today, every argument is a primitive or a String, and the picture above is the whole story.

5.Method overloading

In Lecture 1 we noticed that + means two different things depending on its operands: addition between numbers, concatenation as soon as a String appears. Java lets you do the same thing with methods you write yourself.

Definition— overloading

Overloading is defining two or more methods in the same class with the same name but different parameter lists. The compiler decides which one a given call means by looking at the number and types of the arguments.

"Different parameter lists" means a different number of parameters, or different types, or the same types in a different order. It does not mean different parameter names, and it does not mean a different return type.

Worked Example— MyFunctions.java, the class notes' example in full

This is the complete first example from the class notes. It has four methods besides main, and two of them are called add. Notice that add is defined after main and called from inside it, which as Quick Check 2.1 established is perfectly fine.

You have already been using overloaded methods without noticing: System.out.println is overloaded a dozen ways — one version for int, one for double, one for char, one for String, one that takes nothing at all. That is why println accepts anything you hand it, and why println() with empty parentheses is legal.

What happens when the argument types match neither version exactly? Java does not give up; it looks for a version it can reach by widening.

Common Mistake— the return type is not part of the deal

Two methods whose parameter lists are identical are the same method as far as Java is concerned, no matter what they return:

public static int add(int x, int y) {
    return x + y;
}

public static double add(int x, int y) {     // same parameters — not an overload
    return x + y;
}
BadOverload.java:6: error: method add(int,int) is already defined in class BadOverload

                         ^

The reason is easy to see from the caller's side. In add(1, 2); written as a statement, the return value is discarded, so there would be nothing at all to tell the two apart. Renaming the parameters does not help either — add(int a, int b) is still add(int, int).

Quick Check 2.6

A class contains exactly these three methods:

public static int f(int a)                { return 1; }
public static int f(double a)             { return 2; }
public static int f(int a, int b)         { return 3; }

What does each call return?

(a) f(7)

1. Exact match on f(int). The f(double) version could also be reached by widening, but an exact match always wins.

(b) f(7.0)

2. 7.0 is a double; there is an exact match. Narrowing a double to an int is never done automatically, so f(int) is not a candidate.

(c) f(7, 8)

3. The argument count is checked first, and only one method takes two arguments.

(d) f('x')

1. There is no f(char), so Java widens. A char widens to int and also to double, but int is the nearer of the two, so f(int) is selected.

Things to notice across all four parts. The compiler works through a short checklist for every call: how many arguments? are any of them an exact type match? if not, what is the smallest widening that reaches a candidate? If you can run that checklist you can answer any overloading question on the exam. And note that all three methods here return int — the return type played no part in any of the four answers, because it never does.

Quick Check 2.7

Which of these pairs may legally appear together in one class? For the illegal ones, say what the compiler will object to.

(a) public static void p(int n) and public static void p(double n)

Legal. Different parameter types, so they are distinguishable at every call site.

(b) public static void p(int n) and public static void p(int value)

Illegal — method p(int) is already defined. Parameter names are private to the method body; the caller never writes them and the compiler ignores them when comparing signatures.

(c) public static int p(int n) and public static void p(int n)

Illegal, for the same reason. The return type is not part of what distinguishes two methods.

(d) public static void p(int a, double b) and public static void p(double a, int b)

Legal. The order of the types differs, so p(1, 2.0) and p(1.0, 2) each pick out exactly one of them.

Things to notice across all four parts. Ask one question: could the compiler always tell, from the argument list alone, which one I meant? In (b) and (c) it could not, so they are rejected. A useful footnote on (d): p(1, 2) with two int arguments would be ambiguous — each version needs exactly one widening, so neither is better, and that call would be a compile error even though the two declarations themselves are fine.

6.Calling a method in another class

So far every call has been to a method in the same class, written with just its name. A static method of a different class is called by putting the class name in front.

Procedure— the three ways a static method gets called
  1. From main or another method of the same class: method_name(arguments).
  2. From a different class: class_of_the_method.method_name(arguments).
  3. From itself. A method that calls itself is a recursive method, and that is §7.

You have been doing case 2 since your very first program without thinking about it. Math is an ordinary class in the Java library, full of static methods, and you reach them exactly this way:

7.Recursion

A method may call any method, and there is nothing in that rule that excludes itself.

Definition— recursion, base case, recursive case

A recursive method is one that calls itself. Every correct recursive method has two parts:

  • A base case: an input small or simple enough to answer outright, with no further call.
  • A recursive case: which answers the current input in terms of the answer to a strictly smaller input, obtained by calling itself.

"Strictly smaller" is what makes the process finish: each call must move measurably closer to the base case.

The class notes' example counts the digits of an integer, and it is four lines long:

public static int numDigits(int n) {
    if (n < 10 && n > -10) return 1;
    return numDigits(n/10) + 1;
}

Read it as two English sentences. A number with only one digit has one digit. That is the base case: anything strictly between −10 and 10 has a single digit, so return 1. Otherwise, chop the last digit off and the answer is one more than the answer for what is left. That is the recursive case: n/10 is integer division, which discards the final digit, and the + 1 counts the digit we just removed.

Worked Example— numDigits(31415926), traced by the program itself

Using the same numDigits from the class notes, what does each of these return? Two of them are edge cases worth checking deliberately.

Quick Check 2.10

Write a static method digitSum that returns the sum of the digits of a non-negative int. digitSum(31415926) must return 31, and digitSum(7) must return 7. Model it directly on numDigits: same base case, a different recursive step.

8.Making recursion safe

Two things go wrong with recursion, and they are worth meeting on purpose rather than at 2am.

Common Mistake— no base case, or one that is never reached

Delete the base case from numDigits and the recursive step is still perfectly sensible — it just never stops:

NoBase.java

public class NoBase {
    public static int numDigits(int n) {
        return numDigits(n / 10) + 1;        // base case deleted
    }

    public static void main(String args[]) {
        System.out.println(numDigits(31415926));
    }
}

It compiles without complaint — the compiler does not attempt to work out whether a recursion terminates. Running it gives:

Exception in thread "main" java.lang.StackOverflowError
	at NoBase.numDigits(NoBase.java:3)
	at NoBase.numDigits(NoBase.java:3)
	at NoBase.numDigits(NoBase.java:3)
	at NoBase.numDigits(NoBase.java:3)

The listing goes on for thousands of identical lines; the exact number depends on your machine, so yours will differ. What matters is the diagnosis. Each unfinished call occupies a slot on the JVM's call stack; the stack has a finite size; a recursion that never reaches its base case fills it and the JVM gives up.

Note that n reaches 0 quickly here and then stays there forever, because 0 / 10 is 0. The calls are not getting smaller any more. StackOverflowError almost always means: missing base case, or a recursive call that does not make the problem smaller. Those are the two things to check, in that order.

The second problem has nothing to do with recursion as such, but recursive methods run into it early because they are so often written on numbers that grow fast.

Worked Example— recursive factorial, and where it stops being true

Factorial is the textbook recursion: 1! is 1, and n! is n times (n−1)!. Written straight out of that definition:

Factorial.java

public class Factorial {
    public static int factorial(int n) {
        if (n <= 1) return 1;
        return n * factorial(n - 1);
    }

    public static void main(String args[]) {
        for (int i = 1; i <= 13; i++)
            System.out.println(i + "! = " + factorial(i));
    }
}

Every one of those thirteen lines prints. Are all thirteen of them correct? Lecture 1 has the clue you need.

1! = 1
2! = 2

4! = 24
5! = 120

The first twelve are right. The thirteenth is nonsense: 13! is 6,227,020,800, and what was printed is 1,932,053,504. Nothing failed and nothing was reported — 13! simply does not fit in an int, whose maximum is 2,147,483,647, so the arithmetic wrapped around silently.

The recursion is not at fault; 12! = 479001600 proves it works. The fault is the choice of return type. Changing int to long in both places buys you up to 20!, and beyond that you would need java.math.BigInteger.

Two more things about this method:

  • The base case is n <= 1, not n == 1. Written n == 1, a call with n of 0 or negative would skip the base case entirely, count down past it and overflow the stack. Prefer a base case that catches everything at or below the boundary.
  • Depth versus size. factorial(13) makes only thirteen nested calls, which is nothing. Recursion depth and numeric overflow are separate concerns, and here it is the numbers that break first.
Key Idea— the recursion checklist

Before you run a recursive method, check three things.

  1. Is there a base case? Some input must return without calling again.
  2. Does every recursive call get closer to it? Smaller number, shorter remaining work — something must be strictly decreasing.
  3. Does the recursive case combine the sub-answer correctly? The + 1 in numDigits, the n * in factorial. This is where the arithmetic bugs live.
Quick Check 2.11

Each of these methods is broken. Say which of the three checklist items it fails, and what happens when you run it.

(a) public static int count(int n) { return count(n - 1) + 1; }

Fails item 1: there is no base case at all. It compiles, then throws StackOverflowError for every input. Note that the calls are getting smaller — that is not enough on its own, because there is nothing for them to stop at.

(b) public static int f(int n) { if (n == 0) return 0; return f(n) + 1; }

Fails item 2. There is a base case, but f(n) calls itself with the same n, so nothing ever changes and n == 0 never becomes true for any non-zero input. Same symptom: StackOverflowError. f(0) happens to work, which is the sort of thing that makes this bug survive a careless test.

(c) public static int fact(int n) { if (n <= 1) return 1; return factorial(n - 1); }

Fails item 3 — and item 1, in a way that is easy to miss. It terminates and it returns a value, so there is no crash: it just returns 1 for every input, because the n * was left out of the combining step. Worse, the recursive call names factorial rather than fact, so unless a method called factorial also exists this will not even compile.

Things to notice across all three parts. Only two of the three failure modes announce themselves. A missing or unreachable base case crashes loudly, which is annoying but honest. A wrong combining step returns a plausible-looking number and says nothing — which is why item 3 of the checklist should be tested with an input whose answer you already know.

Plan. Read the arguments left to right for the parameter list, then look at what the caller does with the result for the return type.

The arguments are z (an int[]) and c (a boolean[]). The call setToFive(z, c); stands alone as a statement, so nothing is done with a returned value and void is the best answer.

Plan. There are two calls to f on this line, and they must both be satisfied by one title line. Work out the parameter list from either of them, then use the inner call to pin down the return type.

Parameters, from the inner call f(20, a || b): an int and a boolean, since a || b is a boolean expression. The outer call f(numberStrings(0, u, 0), data(...)) agrees — numberStrings returns an int and data returns a boolean.

Return type: this is the part that catches people. The outer call sits alone as a statement, so its result is discarded, and void looks tempting.    public static void main(String args[]) {
      int a[][] = { {1, 2, 3, 4}, {0, 1, 2, 3} };
      int b[] = {3, 1, 4, 1};
      int x = 1, y = 2;
      String s = "hello";
   // (a) Return true if at least one of x and y is positive. Here Yes is printed
      if (positive(x, y)) System.out.println( "Yes" );
   // (b) Return the sum of the first row. Here 10 is printed.
      System.out.println(rowSum(a));
   // (c) Return the smallest element. Here 1 is printed.
      System.out.println(smallest(b));
   // (d) Remove the first letter. Here ello is printed.
      System.out.println(removeFirst(s));
   // (e) Insert an X at the specified position. Here heXllo is printed.
      s = addX(s, 2);
      System.out.println(s);
   }
}

(a) private static boolean positive(int x, int y)

Plan. "At least one" is ||. The whole method is the condition itself, so return it directly rather than writing an if that returns true or false.

private static boolean positive(int x, int y) {
    return x > 0 || y > 0;
}

Writing if (x > 0 || y > 0) return true; else return false; is correct but longer, and it is a habit worth breaking: a method returning boolean should usually just return the condition.

Note the title line says private, not public. Here that is fine — main is in the same class, and private only blocks access from outside the class.

(b) private static int rowSum(int[][] a)

Row 0 of a is {1, 2, 3, 4}, which sums to 10 — matching the required output. a[0] is itself an int[], and a[0].length is how many elements it has.

private static int rowSum(int[][] a) {
    int sum = 0;
    for (int i = 0; i < a[0].length; i++) sum += a[0][i];
    return sum;
}

The parameter is the whole two-dimensional array even though only the first row is used — the given title line says so, and you must match it.

(c) private static int smallest(int[] b)

Plan. Start the running minimum at the first element, not at 0 and not at some large constant, then compare the rest against it.

private static int smallest(int[] b) {
    int min = b[0];
    for (int i = 1; i < b.length; i++)
        if (b[i] < min) min = b[i];
    return min;
}

Starting from int min = 0; is the classic wrong answer: it returns 0 for any array whose elements are all positive, which is the case here.

(d) private static String removeFirst(String s)

s.substring(1) is everything from index 1 onward — the string with its first character dropped.

private static String removeFirst(String s) {
    return s.substring(1);
}

The parameter s is a copy of the caller's reference, and String objects cannot be modified in place anyway, so the original "hello" in main is untouched. That is why the method has to return the shortened text rather than altering its parameter — and it is why line (e) of main writes s = addX(s, 2); with an assignment.

(e) private static String addX(String s, int i)

Cut the string at position i, put an X in the gap, and join the three pieces.

private static String addX(String s, int i) {
    return s.substring(0, i) + "X" + s.substring(i);
}

Things to notice across all five parts. The title lines were given, and that is the point of the question format: the marks are for producing a body that fits a stated contract. Before writing a line, read the title line and answer two questions — what am I handed, and what type must I return? A boolean method must return a boolean on every path; an int method may not print instead of returning.

Every one of these is short, and that is deliberate: her instruction says "a short function of only a few lines". If your answer is running long, you have probably misunderstood what the method is for.

Problem 4 — Two recursive mysteries (from Exam 1 Practice Problems)

In both parts, read the code and predict the output.

(a) What does this method return?

public static double mystery(double d[], int l, int r) {
   if (l == r) return d[l];
   int m = l + (r-l)/2;
   double x = mystery(d, l, m);
   double y = mystery(d, m+1, r);
   if (x > y) return x;
   else return y;
}

Plan. Do not try to trace every call — there are too many. Read the three parts of the structure instead: what does the base case return, how is the problem split, and how are the two sub-answers combined?

  • Base case: when l == r there is one element in the range, and it returns that element.
  • Split: m is the midpoint, so the range l..r is cut into l..m and m+1..r — two halves that between them cover everything exactly once.
  • Combine: return whichever of the two sub-answers is larger.

"Largest of the left half, largest of the right half, take the bigger" is the definition of a maximum. mystery returns the largest element of d in the index range l to r inclusive.

Checking it on {3.0, 1.0, 4.0, 1.0, 5.0, 9.0, 2.0} with l = 0 and r = 6:

9.0

This shape — halve, recurse on both halves, combine — is called divide and conquer, and it is how merge sort and binary search are built. Note m = l + (r-l)/2 rather than (l+r)/2; the two agree here, and the first is the form that stays correct when l + r would overflow.

(b) What will be printed by System.out.println(mystery1(2,10));?

public static int mystery1(int b, int n) {
   if ( n == 0) return 1;
   int y = mystery1(b, n/2);
   int z = y * y;
   if (n%2 == 0)
      return z;
   else
      return z*b;
}

Plan. n halves each time, so the descent is short — five calls, not ten. Build the table down to n == 0, then come back up squaring as you go.

Things to notice across both parts. Neither part wants a full trace of every call — they want you to recognise the pattern. Both methods have the same three landmarks: a base case, a way of shrinking the problem, and a rule for combining. Read those three and the meaning usually falls out, and you can confirm it with a single small input like mystery1(2, 1).

Halving rather than decrementing is what makes this fast: mystery1(2, 10) makes five calls, and mystery1(2, 1000) would make about ten. Problem 5 asks you to write this method from scratch.

Problem 5 — A fast recursive power (from Exam 1 Practice Problems)

Write a fast recursive method for evaluating an, where n is a non-negative integer and a is a positive integer greater than 1. Your method must match this title line:

public static int fastPower(int a, int n)

(Hint: use the equalities a2k = (ak)2 and a2k+1 = a × a2k. "Fast" means the number of calls should grow with the number of bits of n, not with n itself — so n must be halved, not decremented.)

Plan. Three cases. If n is 0 the answer is 1 — that is the base case, and it must come first. If n is even, compute an/2 once, store it, and square it. If n is odd, peel off one factor of a and recurse on n - 1, which is now even.

FastPower.java

public class FastPower {
    public static int fastPower(int a, int n) {
        if (n == 0) return 1;
        if (n % 2 == 0) {
            int half = fastPower(a, n / 2);
            return half * half;
        }
        return a * fastPower(a, n - 1);
    }

    public static void main(String args[]) {
        System.out.println(fastPower(2, 10));
        System.out.println(fastPower(3, 5));
        System.out.println(fastPower(7, 0));
    }
}

Things to notice. The local variable half is not a stylistic nicety, it is the whole point of the exercise. Writing

return fastPower(a, n / 2) * fastPower(a, n / 2);      // WRONG — not fast at all

gives the same answers and calls the method twice at every level, which doubles the work at each step and throws away the speed-up entirely. Compute the sub-answer once and use it twice.

The odd branch could also be written int half = fastPower(a, n / 2); return half * half * a;, using the fact that for odd n, n / 2 is (n-1)/2. Either is fine; recursing on n - 1 is easier to read and the very next call is even, so no efficiency is lost.

Two limits worth knowing. The return type is int, so this overflows silently for large results exactly as factorial did in §8 — fastPower(2, 31) is already wrong. And the base case is n == 0; a negative n would recurse forever, which is why the problem says n is non-negative.

The title lines are:

public static boolean isNegative(int n)
public static int digitSum(int n)
public static double larger(double a, double b)
public static int larger(int a, int b)

Plan. Parts (a) and (b) are single methods; (c) and (d) are a deliberate overload pair. Before writing anything, notice why part (d) needs its own method: if only larger(double, double) existed, the call larger(2, 4) would still compile — both int arguments would widen — but it would print 4.0, and the required output is 4. The exact-match int version is what produces an int result.

P3b.java

public class P3b {
    public static void main(String args[]) {
        int n = 31415926;
        double p = 2.5, q = 3.5;
        if (isNegative(n)) System.out.println("Yes");
        else               System.out.println("No");
        System.out.println(digitSum(n));
        System.out.println(larger(p, q));
        System.out.println(larger(2, 4));
    }

    public static boolean isNegative(int n) {
        return n < 0;
    }

    public static int digitSum(int n) {
        if (n < 10 && n > -10) return n;
        return digitSum(n / 10) + n % 10;
    }

    public static double larger(double a, double b) {
        if (a > b) return a;
        return b;
    }

    public static int larger(int a, int b) {
        if (a > b) return a;
        return b;
    }
}

Things to notice. This one problem exercises the three ideas of the lecture at once.

  • Title lines. Each body is constrained by a contract you did not choose. isNegative must return a boolean, so it returns the condition directly.
  • Recursion. digitSum is the class notes' numDigits with + 1 replaced by + n % 10 and the base case returning n instead of 1. Once you have seen one recursion over the digits of an integer, you have seen them all.
  • Overloading. Two methods called larger, distinguished only by their parameter types, and the compiler picks correctly at each call. The two bodies are character-for-character identical apart from the types — which feels like duplication, and is. Java's answer to that is generics, in Lecture 22.

One thing that would not work: adding a third method public static double larger(int a, int b). It differs from the int version only in its return type, so it is not an overload at all — it is a duplicate definition, and the compiler says method larger(int,int) is already defined.

Lecture Summary
  • A method is Java's word for a function, and it always lives inside a class. Order of definition within the class does not matter.
  • The title line is public static result_type method_name(define_parameters). Derive it by asking what the method is handed and what it hands back.
  • Everything is static at this stage, because main is static and a static method has no object. Forget it and you get non-static method ... cannot be referenced from a static context.
  • A void method returns nothing and cannot be used in an expression; a value-returning method must return a value of the declared type on every path.
  • Arguments are evaluated first, innermost call first, then copied into the parameters. A method cannot change its caller's primitive variable — only its return value can.
  • Call a method in the same class by name; in another class as ClassName.method(args) — exactly how Math.sqrt works.
  • Overloading is two methods with the same name and different parameter lists. Argument types choose between them; the return type plays no part, and two methods differing only in return type will not compile.
  • Recursion needs a base case, a step that gets strictly closer to it, and a correct rule for combining the sub-answer. Trace it with a table: down to the base case, then back up. A StackOverflowError means the first two of those went wrong.
