1.From an English problem to a list of classes

Exam 1 is behind you. Everything on it — primitives, loops, arrays, String, Scanner, files, ArrayList, and then classes, objects, references and static — was taught one idea at a time, with a small example built to show off that one idea. Real programs are not like that. Today we take a single problem, in English, and turn it into a working design that uses almost all of it at once.

This is the problem, exactly as it was posed:

Definition— the parking ticket problem

A street contains 20 parking spaces where various vehicles come and go throughout the day. Each space can either be empty or occupied by a car with specific characteristics — make, model, color, and license plate number.

The players. Cars randomly arrive and depart, representing different manufacturers (Toyota, Honda, BMW, etc.) and styles (Sedan, SUV, Station Wagon). Police officers patrol irregularly, checking for parking violations. Each parking space has a meter that counts down paid time.

The rules. Every 5 minutes, the following events may occur: a 5% chance a police officer appears to check vehicles; a 9% chance a parked car leaves; a 20% chance an empty space gets filled.

The violations. When a meter expires: first hour, a $25 fine; additional hours, $10 extra per hour.

The documentation. Each parking ticket includes the vehicle information (color, make, model, license), the fine amount, and the officer's badge number.

Notice what that description does not contain. There is no mention of a loop, an array, an if, or a variable. It is written entirely in terms of things — cars, officers, meters, tickets — and what those things do. That is the whole reason object-oriented design exists: if the problem is described in terms of things, a program made of things will be shorter, and it will survive the customer changing their mind.

So the first job is not typing. It is deciding what the things are.

Procedure— from a problem statement to a set of classes
  1. Underline every noun. Go through the description with a pen and mark each noun and noun phrase. Do not judge them yet. For our problem that gives: street, parking space, vehicle/car, make, model, color, license plate number, police officer, violation, meter, paid time, ticket, fine, hour, badge number, day.
  2. Cross out the ones that are not part of the program. Day and hour are units of time; they will be loop counters, not objects. Violation is not a thing you can hold — it is the situation that causes a ticket to exist, and the ticket is the thing.
  3. For each survivor ask: does it have data of its own and behavior of its own? If it has both, it wants to be a class. If it is a single value that just sits there, it wants to be a field inside some other class. A license is a piece of text that does nothing — field. A meter holds a number and counts down and knows the fine schedule — class.
  4. Ask: will there be many of them at once? Twenty cars, several officers over a day, dozens of tickets. Many-of-them is a strong signal for a class, because a class is a blueprint you stamp out copies from.
  5. For each class, list what it KNOWS. Those become the instance variables. Write the type next to each one.
  6. For each class, list what it DOES. Those become the methods. Write the parameter types and the return type next to each one. A constructor counts.
  7. Decide who holds a reference to whom. Whenever a sentence in the problem says "an X has a Y", the class X gets an instance variable of type Y. This is the step that turns a list of classes into a design.
  8. Only now start typing. Fields first, then the constructor, then the methods, one at a time.

Run steps 1 through 4 on the parking problem and you get exactly four classes.

Key Idea

A noun becomes a class when it has state and behavior. A noun becomes a field when it is a single value that only ever gets stored and read. Ask "would I ever want to call a method on this?" — if the answer is no, it is a field.

Quick Check 10.1

Here is a different one-paragraph problem. "A library owns many books. Each book has a title, an author, an ISBN, and a due date, and can be checked out or returned. A member has a name, a card number, and a list of the books they currently have out. A member may not check out more than five books at a time."

(a) List the nouns and classify each one as a class or a field.

Plan. Underline every noun, then apply the test: data plus behavior, and many of them.

(b) Where does the rule "no more than five books at a time" live?

Inside Member, in the method that checks a book out. The member is the object that knows how many books it currently holds, so it is the only object in a position to enforce the rule. A method like

public boolean checkOut(Book b) {
    if (booksOut.size() >= 5) return false;
    booksOut.add(b);
    return true;
}

keeps the rule next to the data it constrains.

Things to notice across both parts. The rule is the interesting part of the design, and notice where it did not go: not in main, not in Book. Putting a rule about a member's books anywhere except Member means some other piece of code has to reach in and count them — and then a second piece of code will forget to. The general principle is "put the behavior with the data it needs", and it is the reason ParkingMeter and not PoliceOfficer computes the fine.

Quick Check 10.2

In the parking problem, the fine is described as "$25 for the first hour, $10 extra per hour after that". Three classes could plausibly own that calculation: ParkingMeter, PoliceOfficer, or ParkingTicket. Which one should, and why?

Plan. Ask which object already has the data the calculation needs.

The fine depends on exactly one number: how far past zero the meter has gone. The only object that knows that number is the ParkingMeter, because timeLeft is its instance variable. So ParkingMeter owns getFine.

Putting it in PoliceOfficer would mean the officer has to read timeLeft out of the meter first — which means timeLeft would have to stop being private, and now every class in the program can see it. Putting it in ParkingTicket is the same problem one step later.

Things to notice. This is the single most useful design question you can ask: who already has the data? Behavior goes where the data is. When you find yourself adding a getter only so that some other class can do a calculation, that is a signal the calculation is in the wrong class.

Turning that table into type-annotated signatures gives a UML-style class diagram. It is worth learning to read one, because it is how designs are communicated before any code exists — and it is how one of your exam questions supplies a class you are told to use but not to write.

Definition— UML class listing

A UML class listing is a box with three compartments: the class name, then the fields, then the methods. A leading - means private; a leading + means public. Each field is written name : Type, and each method name(parameterTypes) : ReturnType. An arrow from one box to another means "this class has an instance variable of that type" — a has-a relationship.

Notice what a UML listing deliberately leaves out: method bodies. It shows the interface — what you can call and what you get back — and says nothing about how any of it is done. That is exactly the level at which you make design decisions.

Quick Check 10.3

Answer each of these from the UML listings alone, without looking at any code.

(a) ParkingMeter has no getter for timeLeft. Given the listing, how would a PoliceOfficer find out whether a car is over its time?

It cannot ask for the number, and it does not need to. It asks the car the yes-or-no question instead: car.expiredMeter() returns a boolean. The car passes the question on to its meter's isExpired().

This is the design working as intended. The officer needs an answer, not a measurement, and the class that owns the measurement is the one that turns it into an answer.

(b) What is the return type of issueTicket, and what does that tell you about who creates ParkingTicket objects?

It returns a ParkingTicket. So the officer is the object that calls new ParkingTicket(...) — tickets are created by officers, not by main and not by cars. That matches the real world, which is a good sign about the design.

(c) adjustMeter(int) returns void. What does a void return type usually tell you about a method?

That the method exists for its effect, not for its answer. adjustMeter changes the state of the object it is called on and hands nothing back. Methods split fairly cleanly into these two kinds: queries that return a value and change nothing (getMake, isExpired, getFine), and commands that change something and return void (remove, adjustMeter).

Things to notice across all three parts. Every one of these questions was answerable from the box alone. That is what the diagram is for: you can review a design, spot a missing method, or spot a field that everybody needs and nobody can reach, before a single line has been written.

3.ParkedCar has a ParkingMeter

Step 7 of the procedure was: decide who holds a reference to whom. The problem statement says "each parking space has a meter that counts down paid time", and in this design the meter travels with the car that is parked in the space. That single sentence produces one line of Java.

Definition— has-a, and composition

A has-a relationship between two classes is implemented by giving one of them an instance variable whose type is the other. Building an object out of other objects this way is called composition.

Composition is the ordinary way that big designs are built out of small ones. You already used it without naming it: an object with a String field or an ArrayList field is composed of those objects. The only new thing here is that the part is a class you wrote.

Here is ParkingMeter in full — it is the smallest class in the system, and the only one that stores a number.

ParkingMeter.java

import java.util.Random;

public class ParkingMeter {
    private int timeLeft;

    public ParkingMeter() {
        timeLeft = (((new Random()).nextInt(20)) + 1) * 5;
        // pay for up to 100 minutes. (multiple of 5)
    }

    public boolean isExpired() {
        return timeLeft < 0;
    }

    public String getFine() {
        if (timeLeft > -60) return "$25";
        int fine = 25 + (-10) * ((timeLeft + 5) / 60);
        return "$" + fine;
    }

    public void remove(int x) {
        timeLeft -= x;
    }
}

The constructor draws nextInt(20), which gives 0 through 19, adds 1 to get 1 through 20, and multiplies by 5. So a new meter always starts somewhere between 5 and 100 minutes, always a multiple of 5. That "always a multiple of 5" is not decoration — the whole simulation advances in 5-minute steps, and we will lean on it in §5.

And here is ParkedCar, whose fifth field is the interesting one.

ParkedCar.java

import java.util.Random;

public class ParkedCar {
    static String makes[] = {"Toyota", "Honda", "Hyundai", "BMW",
                             "Porsche", "Maserati", "Ford", "Chevrolet"};
    static String models[] = {"Sedan", "Station Wagon", "SUV", "Light Truck"};
    static String colors[] = {"Red", "Orange", "Yellow", "Green",
                              "Blue", "White", "Silver"};

    private String make;
    private String model;
    private String color;
    private String license;
    private ParkingMeter meter;

    public ParkedCar() {
        make = pickOne(makes);
        model = pickOne(models);
        color = pickOne(colors);
        license = generateLicense();
        meter = new ParkingMeter();
    }

    private String generateLicense() {
        Random x = new Random();
        String answer = "";
        for (int i = 0; i < 3; i++)
            answer += (char) ('A' + x.nextInt(26));
        for (int i = 0; i < 4; i++)
            answer += (char) ('0' + x.nextInt(10));
        return answer;
    }

    private String pickOne(String[] choices) {
        Random x = new Random();
        return choices[x.nextInt(choices.length)];
    }

    public boolean expiredMeter() {
        return meter.isExpired();
    }

    public void adjustMeter(int x) {
        meter.remove(x);
    }

    public String getMake()    { return make;    }
    public String getModel()   { return model;   }
    public String getColor()   { return color;   }
    public String getLicense() { return license; }

    public String toString() {
        return getColor() + " " + getMake() + " " + getModel() +
               " License number: " + getLicense();
    }

    public String getFine() {
        return meter.getFine();
    }
}

Read the three arrays first. They are static, which from Lecture 9 you know means one copy for the whole class, not one copy per object. There are eight makes in the world regardless of how many cars are parked, so a per-object copy would be eight wasted String references per car. This is the textbook use of static data.

Now read the constructor. Four of its five lines fill in a piece of text. The fifth, meter = new ParkingMeter();, creates a whole second object and stores a reference to it. After that line runs there are two objects on the heap, and one of them holds the other.

Key Idea— delegation

Look at three of ParkedCar's methods:

  • expiredMeter() returns meter.isExpired()
  • adjustMeter(x) calls meter.remove(x)
  • getFine() returns meter.getFine()

Each is one line, and each one does nothing but pass the request on to the meter. That pattern is called delegation: the object that receives the message is not the object that answers it. ParkedCar does not know what "expired" means and does not want to — it knows who does.

Delegation looks like pointless typing until you ask what the alternative is. Without it, the simulation loop would have to reach through the car to get at the meter: street[i].getMeter().isExpired(). Now ParkedCar needs a getMeter() that hands out its private meter, and the loop needs to know that a car even has a meter. Delegating keeps that fact private.

Quick Check 10.4

The city adds a rule: a car may top up its meter, buying more time without leaving. Add a method addTime(int minutes) to ParkedCar and whatever it needs in ParkingMeter. Write both, in the style of the delegating methods above.

Plan. The field being changed is timeLeft, and it lives in ParkingMeter, so the real work is a method there. ParkedCar gets a one-line delegator, exactly like adjustMeter. Buying time is the opposite of remove, so in ParkingMeter it is an addition.

// in ParkingMeter
public void add(int x) {
    timeLeft += x;
}

// in ParkedCar
public void addTime(int minutes) {
    meter.add(minutes);
}

Things to notice. There was a shortcut available: ParkingMeter already has remove, and meter.remove(-minutes) would add time. Resist it. A method named remove that is routinely called with a negative number to mean "add" is a method whose name lies, and the next person to read the simulation loop will misread it. Two clearly named methods cost four lines.

Notice also that ParkedCar.addTime does not touch timeLeft. It cannot — timeLeft is private to ParkingMeter, and §4 shows exactly what the compiler says if you try.

Worked Example— the car answers a question it cannot answer itself

This program creates one car, asks whether its meter has expired, runs 105 minutes of simulated time through it in 5-minute ticks, and asks again. The car's meter starts somewhere between 5 and 100 minutes, so both answers are the same on every run — work out what they are before you open the toggle, and be ready to say why 105 was chosen rather than 100.

MeterDemo.java

public class MeterDemo {
    public static void main(String args[]) {
        ParkedCar car = new ParkedCar();

        System.out.println("Expired the moment the car arrives? " + car.expiredMeter());

        // The meter is bought with at most 100 minutes, so 105 minutes of
        // simulated time is guaranteed to run it out.
        for (int tick = 0; tick < 21; tick++) car.adjustMeter(5);

        System.out.println("Expired 105 minutes later?          " + car.expiredMeter());
    }
}
Expired the moment the car arrives? false
Expired 105 minutes later?          true

The first answer is false on every run because the constructor's smallest possible value is 5, and isExpired asks timeLeft < 0.

The second is true on every run because the largest possible starting value is 100, and 21 ticks remove 105 minutes, so timeLeft finishes somewhere between −100 and −5. Stopping at 100 minutes would not have been safe: a meter that started at exactly 100 would land on timeLeft == 0, and 0 < 0 is false. The meter would read "no time left" and still not count as expired.

Now follow one of those adjustMeter(5) calls all the way down. It is three objects and two hops:

StepWho is runningWhat happens
1maincar.adjustMeter(5) — main holds a reference to a ParkedCar and sends it a message.
2ParkedCarThe body is meter.remove(x). meter is this car's own instance variable, so the call goes to that meter and no other.
3ParkingMetertimeLeft -= x — the only line in the whole program that changes a meter's time.

Step 3 is the payoff. There is exactly one place in the system where timeLeft changes. If the meter ever ends up with a wrong value, there is one method to look at.

Quick Check 10.5

Suppose main does this:

ParkedCar a = new ParkedCar();
ParkedCar b = new ParkedCar();
a.adjustMeter(60);

(a) How many ParkingMeter objects exist, and is b's meter affected by the call?

Two meters exist, one per car, because each ParkedCar constructor ran meter = new ParkingMeter(); and new always makes a fresh object. b's meter is untouched: a.adjustMeter(60) runs meter.remove(60) where meter is a's field.

(b) Now suppose someone writes b = a; instead of creating b with new. How many cars and how many meters are there then?

One car and one meter. b = a; copies a reference, not an object — this is Lecture 8's aliasing, and it does not become any less true because the objects are now ones you designed. a and b are two names for the same ParkedCar, and that one car has one meter. a.adjustMeter(60) and b.adjustMeter(60) would take 120 minutes off the same meter.

Things to notice across both parts. new is the only thing that ever creates an object. Counting new calls is how you count objects — here, two per new ParkedCar(), because its constructor performs a new of its own. Assignment between object variables never copies anything but an arrow.

4.Encapsulation: private fields and what the getters are for

Every instance variable in this design is private, and every one of them is reachable from outside only through a method. That is not a stylistic habit; it is what makes the design hold together when the program grows.

Definition— encapsulation

Encapsulation means keeping an object's data private and exposing only a chosen set of methods. Code outside the class can ask questions and issue commands; it cannot reach in and change a field.

The benefit is not secrecy. It is that the class gets to keep a promise. ParkingMeter promises that timeLeft is only ever changed by remove. It can only keep that promise if nobody else can assign to timeLeft.

Which brings us to the question students reasonably ask the first time they meet getters: if getLicense() just returns license, what was the point of making it private? Three answers, in increasing order of importance.

  • Read-only is a real thing. getLicense() lets you read the plate. There is no setLicense, so you cannot change it. A public field gives you both or neither; a getter with no setter gives you exactly one.
  • The getter can do work later. Today it returns the field. Tomorrow it can normalize the format, log the access, or compute the value instead of storing it — and no calling code changes. ParkedCar.getFine() is already like this: it looks like a getter, but there is no fine field anywhere in ParkedCar. It asks the meter.
  • The class controls its own invariants. ParkingMeter can guarantee timeLeft is always a multiple of 5, because the only two ways it ever changes are its own constructor and its own remove. The moment the field is public, that guarantee is a hope.
Common Mistake— a getter that hands out the object itself

Suppose you added this to ParkedCar, thinking it was harmless:

public ParkingMeter getMeter() {     // dangerous
    return meter;
}

meter is private, so this compiles, and it looks like every other getter on the class. But the value it returns is a reference to the car's actual meter, not a copy of it. Any caller can now write car.getMeter().remove(500) and take eight hours off a meter the car was supposed to be protecting.

Making a field private protects the field, not the object it points at. This is why the design has expiredMeter(), adjustMeter(int) and getFine() instead: each hands back a boolean or a String, never the meter.

Quick Check 10.6

ParkedCar declares its three arrays as static String makes[], with no private.

(a) Given that, is ParkedCar.makes[0] = "Yugo"; legal in another class in the same folder?

Yes. Leaving off private gives a field package access: any class in the same package can see it. Since the array is also static, the assignment reaches it through the class name and permanently changes the list of makes for every car created afterwards.

(b) Would writing private static String makes[] make the array's contents safe from outside change?

Yes, in this case — but only because no method hands the array out. The rule from the Common Mistake box applies to arrays too: an array variable is a reference, so a method like public static String[] getMakes() { return makes; } would let a caller write ParkedCar.getMakes()[0] = "Yugo"; right past the private.

Things to notice across both parts. private is about who can name the variable, not about who can modify what it points to. For a design that wants a genuinely fixed list, mark it private static final and never return it — final stops the variable being reassigned, and private stops anyone else naming it. Practice Problem 3's COLORS array is written exactly that way.

Quick Check 10.7

Write a class ParkingSpace that represents one of the twenty spaces on the street. It knows its number and which car is in it (or null if the space is empty). Give it a constructor taking the space number, plus isEmpty, park, vacate and toString. Keep both fields private.

Plan. Two fields: an int number and a ParkedCar occupant. The second is another has-a relationship, and the interesting part is that it is allowed to be null — "empty" is represented by the absence of an object. That makes isEmpty() a one-line null test, and vacate() a one-line assignment of null.

ParkingSpace.java

public class ParkingSpace {
    private int number;
    private ParkedCar occupant;

    public ParkingSpace(int number) {
        this.number = number;
        occupant = null;              // a new space starts out empty
    }

    public int getNumber() {
        return number;
    }

    public boolean isEmpty() {
        return occupant == null;
    }

    public ParkedCar getOccupant() {
        return occupant;
    }

    public void park(ParkedCar car) {
        occupant = car;
    }

    public void vacate() {
        occupant = null;
    }

5.The fine calculation

Everything so far has been structure. This section is the one piece of genuine, testable logic in the design, and it repays being taken slowly.

The rule in English: first hour, $25; each additional hour, $10 more. The rule in Java, from ParkingMeter:

public String getFine() {
    if (timeLeft > -60) return "$25";
    int fine = 25 + (-10) * ((timeLeft + 5) / 60);
    return "$" + fine;
}

Three facts make that line work, and none of them are obvious.

  • timeLeft is negative when the meter is expired, and the amount it is overdue by is -timeLeft. A meter reading −65 is 65 minutes past its time.
  • timeLeft is always a multiple of 5, because it started as a multiple of 5 and only ever loses 5 at a time. So the values that can actually occur are −5, −10, −15, and so on — never −7.
  • Java's integer division truncates toward zero. From Lecture 1: -55 / 60 is 0, not −1, because the true answer −0.9166 is chopped toward zero. That is what turns a division into a "how many complete hours" counter here, and it is also what makes the + 5 necessary.
Worked Example— where does the fine step up?

Rather than reason about that expression, test it. This program lifts the rule out of ParkingMeter into a static method so we can feed it any meter reading we like, then walks timeLeft down in 5-minute steps and prints a line only when the answer changes.

FineDemo.java

public class FineDemo {
    // Exactly the rule ParkingMeter uses, pulled out so we can test it on its own.
    public static String getFine(int timeLeft) {
        if (timeLeft > -60) return "$25";
        int fine = 25 + (-10) * ((timeLeft + 5) / 60);
        return "$" + fine;
    }

    public static void main(String args[]) {
        String previous = "";
        for (int timeLeft = -5; timeLeft >= -245; timeLeft -= 5) {
            String fine = getFine(timeLeft);
            if (!fine.equals(previous)) {
                System.out.println("timeLeft = " + timeLeft +
                                   "  (" + (-timeLeft) + " minutes overdue)" +
                                   " -> fine is now " + fine);
                previous = fine;
            }
        }
    }
}

Common Mistake— the off-by-one-tick version

public String getFine() {

Quick Check 10.8

Work these out on paper, using version B of the rule.

(a) A meter reads timeLeft = -95. What does getFine() return?

-95 is not greater than -60, so the if does not fire. (-95 + 5) / 60 is -90 / 60, which truncates toward zero to -1. Then 25 + (-10) * (-1) is 35, so the method returns "$35". Sanity check: 95 minutes overdue is into the second hour, so $25 plus one $10 — correct.

(b) A meter reads timeLeft = 15. What does getFine() return, and is that a problem?

It returns "$25". 15 > -60 is true, so the if fires immediately.

Whether that is a problem depends on who calls it. In this program getFine is only ever reached after expiredMeter() came back true, so a meter with time still on it is never asked. But nothing in the class enforces that, and a method that cheerfully reports a $25 fine on a perfectly legal car is a trap for whoever next uses the class. Returning "$0" when timeLeft >= 0 would cost one line.

(c) isExpired() is timeLeft < 0. Why does it not matter here that a meter reading exactly 0 counts as not expired?

Because time only ever moves in 5-minute steps. A meter sitting at 0 will be at -5 five minutes later and will be flagged then. The driver gets at most one extra 5-minute tick of grace.

Things to notice across all three parts. All three answers turned on the same fact: timeLeft is always a multiple of 5. That invariant is what makes the class simple — and it is only true because timeLeft is private and the only thing that ever changes it is remove, which the simulation always calls with 5. Change the simulation to tick every 3 minutes and parts (a) and (c) both need rechecking.

Quick Check 10.9

The city switches to a cleaner rule: $25 for the first hour and $10 for every additional hour, where any part of an hour counts as a whole hour. Write two static methods, hoursOverdue(int timeLeft) returning the number of hours the meter is over (rounded up), and fineFor(int timeLeft) returning the fine as an int number of dollars — 0 if the meter is not expired at all.

Plan. Work in positive numbers as early as possible; the negative timeLeft is what made the original hard to read. Let minutesOver = -timeLeft. public class FineRules {
    // How many whole hours late is a meter whose counter reads timeLeft?
    // timeLeft is 0 or negative here, and always a multiple of 5.
    public static int hoursOverdue(int timeLeft) {
        int minutesOver = -timeLeft;
        return (minutesOver + 59) / 60;        // round up: 1..60 -> 1, 61..120 -> 2
    }

    // $25 for the first hour, $10 more for every hour after that.
    public static int fineFor(int timeLeft) {
        int hours = hoursOverdue(timeLeft);
        if (hours <= 0) return 0;
        return 25 + 10 * (hours - 1);
    }

    public static void main(String args[]) {
        int tests[] = {0, -5, -55, -60, -65, -120, -125, -185};
        for (int i = 0; i < tests.length; i++) {
            int t = tests[i];
            System.out.println("timeLeft " + t + ":  " + hoursOverdue(t)
                               + " hour(s) over, fine $" + fineFor(t));
        }
    }
}

6.PoliceOfficer, ParkingTicket, and the object graph

The last two classes are the smallest, and between them they show the second half of step 7: an object can hold a reference to another object without owning it.

PoliceOfficer.java

import java.util.Random;

public class PoliceOfficer {
    private int badgeNumber;

    public PoliceOfficer() {
        badgeNumber = (new Random()).nextInt(20) + 1;
    }

    public int getBadgeNumber() {
        return badgeNumber;
    }

    public ParkingTicket issueTicket(ParkedCar parkedCar) {
        return new ParkingTicket(this, parkedCar);
    }
}

issueTicket is four words long and it is the most interesting method in the system. It takes a ParkedCar as a parameter — the officer does not own the car, it is just handed one to look at — and it passes this as the first argument to the ticket's constructor.

Key Idea— this as an argument

You met this in Lecture 7 as a way to say "the field, not the parameter": this.name = name. Here it is doing something different and more literal. this is a reference to the object the method was called on, so new ParkingTicket(this, parkedCar) means build a ticket that knows about me.

Whenever an object needs to hand itself to something else — a ticket, a list, a callback — this is how it does it.

ParkingTicket.java

public class ParkingTicket {
    private String officer = "Officer badge number: ";
    private String car = "Parked Car information: ";
    private String fine = "Fine: ";

    public ParkingTicket(PoliceOfficer policeOfficer, ParkedCar parkedCar) {
        officer += policeOfficer.getBadgeNumber();
        car += parkedCar.toString();
        fine += parkedCar.getFine();
    }

    public String toString() {
        return car + " | " + fine + " | " + officer;
    }
}

Look carefully at what the constructor stores. It receives two object references, and it keeps neither of them. It asks each object a question, turns the answer into text, and stores the text. The ticket that comes out is a snapshot: a printed document, not a live link back to the car.

The snapshot version, for this problem. A parking ticket in the real world records what was true when it was written; a fine does not go up because the officer walked away slowly. Storing the references would give you a document that quietly rewrites itself.

But the reference version has a real advantage too: the ticket could then answer questions the snapshot cannot, such as "which car is this?" for a lookup, or "has this car been ticketed before today?" Things to notice across both parts. This is Lecture 8's aliasing question wearing a suit. Sometimes that is the feature and sometimes it is the bug — but it is never an accident you can afford to leave undecided.

Quick Check 10.11

Inside PoliceOfficer.issueTicket, could you replace new ParkingTicket(this, parkedCar) with new ParkingTicket(badgeNumber, parkedCar) and change the ticket's constructor to take an int? What would you gain and what would you lose?

Plan. Ask what ParkingTicket actually uses the officer for.

It compiles and it works. The constructor only ever calls getBadgeNumber(), so the badge number is all it needs, and passing an int makes ParkingTicket independent of PoliceOfficer altogether — the two classes would no longer be coupled at all.

What you lose is room to grow. The moment a ticket needs the officer's name, precinct or shift, you are back to changing the constructor signature and every call to it. Passing this says "here is who I am, ask me what you need"; passing badgeNumber says "here is one number, and I have decided in advance that it is all you will ever want".

Things to notice. Neither choice is wrong, and being able to argue both sides in a sentence each is the actual skill. As a rule of thumb: pass the object when the receiver is a peer that may need more later, pass the plain value when the receiver is a simple record. A ticket is arguably a simple record — which is exactly why this design already reduces the officer to a String one line later.

7.Design decisions you could have made differently

A finished design looks inevitable. It never is. Four places in this one could reasonably have gone the other way, and being able to say why is worth more than being able to type the code.

1. Where does the meter live? The problem says "each parking space has a meter", which reads like ParkingSpace should own the ParkingMeter. This design puts the meter inside ParkedCar instead. That is a simplification with a consequence: when a car drives away, its meter goes with it, and the next car gets a brand-new meter with fresh random time. Physically wrong — a real meter keeps whatever the last driver paid for. It is a fair trade for a first version, and it is the first thing to fix if the simulation is ever meant to be realistic.

2. Is there a ParkingSpace class at all? In this design, no. The street is just ParkedCar street[] = new ParkedCar[20]; and an empty space is a null entry. That is compact and it works. It also means the space number is an array index rather than something a space knows about itself, and there is nowhere to hang "this space is a loading zone" when that requirement arrives. Quick Check 10.7 wrote the class that would fix it.

3. Should getFine return a String? Returning "$25" means the fine is formatted at the moment it is computed, deep inside the meter. Anything that later wants to total the day's fines has to take the "$" back off and parse the number. Returning an int and formatting at the point of printing — Quick Check 10.9 — is the more flexible choice, and it costs nothing.

4. Should each object build its own Random? ParkedCar creates a new Random inside pickOne, and another inside generateLicense, every time either is called. It works, but a single shared generator is both cheaper and more conventional:

private static Random rng = new Random();     // one per class, not one per call

That is the same static reasoning as the makes array. There is one source of randomness in the program conceptually, so there should be one object for it.

}

Problem 2 — The BankAccount class (from CSCI 212 Midterm, Summer 2026)

Plan. Count the methods against the specification before writing anything: constructor, two getters, two commands, one toString — six, and no setters. That is the shape of nearly every class-design question on these exams.

The only decision is what withdraw does when the money is not there. The specification says subtract "only if there is enough", so the natural reading is: silently do nothing otherwise. An if with no else.

BankAccount.java

public class BankAccount {
    private String owner;
    private double balance;

    public BankAccount(String owner, double balance) {
        this.owner = owner;
        this.balance = balance;
    }

    public String getOwner() {
        return owner;
    }

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount <= balance) balance -= amount;
    }

    public String toString() {
        return owner + " has balance " + balance;
    }
}

Things to notice. The third line is the same as the second: withdrawing 1000 from 750 did nothing at all. That is the specification working, and it is also the thing to test — a withdraw that always subtracts passes every test where the account has enough money.

balance is a double, so it prints as 500.0 rather than 500. The specification demanded exactly that format, so leave it. Real money should not be a double at all — binary fractions cannot represent 0.10 exactly, and repeated deposits drift — but that is a conversation for a course with more time.

The System.out.println(a) calls print the account without naming toString. That is Lecture 9's rule: println of an object calls its toString for you.

Problem 3 — The TrafficSignal class (from Exam 1 Practice Problems)

Write complete code for a class called TrafficSignal. The class represents a traffic signal that cycles through four states: green, yellow, red and leftTurn, in this order — meaning leftTurn comes just after red and before green.

The class should have only one attribute, light, of type int. The value of this attribute determines the state of the signal; for example, if light has value 0 the signal shows green. The class should have one (default) constructor and only three additional methods. The default color of the light should be red. The three methods are currentLight(), which returns the integer corresponding to the current state, changeLight(), which changes light from the current state to the next state, and toString(), which returns the state as green, yellow and so on.

Plan. Only one instance variable is allowed, so the four color names cannot be fields. They are the same for every signal ever created, which is the definition of static — put them in a private static final array and let the index do the work. That array is not an "attribute" in the sense the question means; the object's state is still the single int.

"Cycles" is the word that tells you the operator: wrapping 3 back round to 0 is %. Write (light + 1) % COLORS.length rather than % 4, so that adding a fifth state later means editing one line instead of two.

Red is index 2, so the default constructor sets light = 2.

TrafficSignal.java

public class TrafficSignal {
    private int light;
    private static final String COLORS[] = {"green", "yellow", "red", "leftTurn"};

    public TrafficSignal() {
        light = 2;                       // the default color is red
    }

    public int currentLight() {
        return light;
    }

    public void changeLight() {
        light = (light + 1) % COLORS.length;
    }

    public String toString() {
        return COLORS[light];
    }
}

SignalDemo.java

public class SignalDemo {
    public static void main(String args[]) {
        TrafficSignal s = new TrafficSignal();
        for (int i = 0; i < 6; i++) {
            System.out.println(s.currentLight() + "  " + s);
            s.changeLight();
        }
    }
}
2  red
3  leftTurn
0  green
1  yellow
2  red
3  leftTurn

Things to notice. Six steps through a four-state cycle gets you back where you started plus two, which is exactly what the output shows — a cheap way to check that the wraparound is right. Testing only four steps would not have exercised the wrap at all.

The array is private static final: static because there is one set of color names for the whole class, final because the variable must never be pointed at a different array, and private because nobody outside needs it. That is the combination §4 recommended.

toString returning COLORS[light] is a good illustration of why encapsulation pays. The outside world sees the word "red"; whether that is stored as an int, a String or an enum is nobody's business but the class's.

Problem 4 — The Distance class (from Exam 1 Practice Problems)

Answer the parts in order; each builds on the last.

(a) Write a class Distance with the following specification. There are two instance variables, feet and inches, stored as integers; a private constant called INCHES_IN_A_FOOT with value 12; and a no-argument constructor to initialize a Distance as zero feet, zero inches.

public class Distance {
    private int feet;
    private int inches;
    private static final int INCHES_IN_A_FOOT = 12;

    public Distance() {
        feet = 0;
        inches = 0;
    }
}

private static final is how Java writes a named constant: final so it cannot be reassigned, static because 12 inches to the foot is a fact about the world rather than about any one Distance, and the ALL_CAPS name is the universal convention for a constant.

(b) Write a two-argument constructor for Distance that accepts two positive integers for feet and inches. Write an access (get) method for feet and a mutator (set) method for inches.

public Distance(int feet, int inches) {
    this.feet = feet;
    this.inches = inches;
}

public int getFeet() {
    return feet;
}

public void setInches(int inches) {
    this.inches = inches;
}

Both parameters shadow their fields, so both assignments need this.. Note the class now has two constructors — that is overloading, and it is legal because their parameter lists differ.

(c) Write a public method add that accepts another Distance object as a parameter and adds that distance to the current one. For example, if x1 is 5 feet 8 inches and x2 is 2 feet 7 inches, then after x1.add(x2) the object x1 is 8 feet 3 inches.

Plan. 8 + 7 is 15 inches, which is 1 foot 3 inches. So total the inches first, carry total / 12 into the feet, and keep total % 12 as the inches — the same integer division and remainder pair from Lecture 1, doing exactly the job they are for.

public void add(Distance other) {
    int total = inches + other.inches;
    feet = feet + other.feet + total / INCHES_IN_A_FOOT;
    inches = total % INCHES_IN_A_FOOT;
}

other.inches reads a private field of a different object, and that is legal: private is per class, not per object, so any Distance may read any other Distance's fields. That is what makes methods like this one writable at all.

The order matters. Compute total before overwriting inches, or the carry is computed from the value you just destroyed.

(d) Write a public method metricDistance that returns, as a double, the number of meters in the distance. The method should contain a private variable for the number of meters in a foot (1 foot = 0.3048 meters).

public double metricDistance() {
    final double METERS_IN_A_FOOT = 0.3048;
    return (feet + inches * 1.0 / INCHES_IN_A_FOOT) * METERS_IN_A_FOOT;
}

The * 1.0 is the whole problem. inches / INCHES_IN_A_FOOT is int / int, so 3 inches would become 0 feet and the method would silently lose up to eleven inches on every call. Multiplying by 1.0 first promotes the division to double. Writing inches / 12.0 would do the same job, but then the named constant is no longer being used.

(e) Modify the constructor from part (b) so that if the number of inches is greater than 11, it prints Illegal number of inches and sets inches to 11.

Plan. This is Lecture 7's validating setter idea moved into a constructor: the object refuses to be built in an impossible state.

Distance.java

public class Distance {
    private int feet;
    private int inches;
    private static final int INCHES_IN_A_FOOT = 12;

    public Distance() {
        feet = 0;
        inches = 0;
    }

    public Distance(int feet, int inches) {
        this.feet = feet;
        if (inches > INCHES_IN_A_FOOT - 1) {
            System.out.println("Illegal number of inches");
            this.inches = INCHES_IN_A_FOOT - 1;
        } else {
            this.inches = inches;
        }
    }

    public int getFeet() {
        return feet;
    }

    public void setInches(int inches) {
        this.inches = inches;
    }

    public void add(Distance other) {
        int total = inches + other.inches;
        feet = feet + other.feet + total / INCHES_IN_A_FOOT;
        inches = total % INCHES_IN_A_FOOT;
    }

    public double metricDistance() {
        final double METERS_IN_A_FOOT = 0.3048;
        return (feet + inches * 1.0 / INCHES_IN_A_FOOT) * METERS_IN_A_FOOT;
    }

    public String toString() {
        return feet + " feet, " + inches + " inches";
    }
}

DistanceDemo.java

public class DistanceDemo {
    public static void main(String args[]) {
        Distance x1 = new Distance(5, 8);
        Distance x2 = new Distance(2, 7);
        x1.add(x2);
        System.out.println("x1 is now " + x1);
        System.out.println("x1 in meters: " + x1.metricDistance());

        Distance bad = new Distance(3, 15);
        System.out.println("bad is " + bad);

        Distance zero = new Distance();
        System.out.println("zero is " + zero);
    }
}
x1 is now 8 feet, 3 inches
x1 in meters: 2.5146
Illegal number of inches
bad is 3 feet, 11 inches
zero is 0 feet, 0 inches

Things to notice across all five parts. The class was built the way §1's procedure says to build one: fields and the constant, then the constructors, then the accessors, then the real behavior, then the validation. Each part compiled and ran before the next was added.

A toString was added so the demo could print a Distance — the exam question does not ask for one, and on the exam you should not write code you were not asked for. Outside an exam, a class you intend to debug should always have one.

Notice the hole the specification leaves: setInches does no validation at all, so x1.setInches(99) walks straight past the check the constructor makes. A class that validates on the way in and not afterwards has not really validated anything. The fix is to have the constructor call setInches and put the check there, once.

Problem 5 — Design the classes for a laundromat (added for these notes)

Read this description and produce a design — no method bodies, just the classes, their fields with types, and their method signatures with parameter and return types. Say for each class why it is a class rather than a field, and draw the has-a arrows.

A laundromat has 12 washing machines and 8 dryers. Each machine has a number, is either free or running, and if it is running it has a number of minutes left on its cycle. A customer has a name and a loyalty-card number, and may be using several machines at once. A wash costs $3.50 and a dry costs $2.00 for a 30-minute cycle; a customer's running total is the sum of what they have started.

Plan. Nouns: laundromat, washing machine, dryer, machine, number, minutes left, customer, name, loyalty-card number, cycle, wash, dry, cost, running total. Cross out the units and the money amounts — cost is a number, not a thing. What is left with both data and behavior is: machine, and customer. Washer and dryer differ only in price and in what they are called, so one Machine class with a type field will do for now; when they start behaving differently, that is what inheritance is for, and it is Lecture 12.

A reasonable design

+-------------------------------------+        +------------------------------------+
|              Machine                |        |             Customer               |
+-------------------------------------+        +------------------------------------+
| - number      : int                 |        | - name       : String              |
| - isWasher    : boolean             |        | - cardNumber : int                 |
| - minutesLeft : int                 |        | - machines   : ArrayList<Machine>  |
+-------------------------------------+ has-a  | - total      : double              |
| + Machine(int number, boolean wash) |<-------+------------------------------------+
| + getNumber()     : int             |        | + Customer(String name, int card)  |
| + isFree()        : boolean         |        | + getName()      : String          |
| + start()         : void            |        | + getTotal()     : double          |
| + tick(int mins)  : void            |        | + use(Machine m) : void            |
| + getMinutesLeft(): int             |        | + toString()     : String          |
| + getPrice()      : double          |        +------------------------------------+
| + toString()      : String          |
+-------------------------------------+

Why each is a class. A machine holds three pieces of data and answers real questions about itself (isFree, getMinutesLeft), and there are twenty of them — class. A customer holds data and does something (use) — class. The name, the card number and the minute count are single values with no behavior — fields.

Where the has-a arrow goes. Customer has an ArrayList<Machine>, because the description says a customer may be using several machines. The arrow points from Customer to Machine, not the other way: a machine has no reason to know who is using it, and adding a back-reference would mean keeping two things in step instead of one.

Where the rules live. getPrice() is on Machine, because the price depends on isWasher, which is the machine's own data — that is Quick Check 10.2's test. use(Machine m) is on Customer because it does two things at once: it starts the machine and it adds the price to that customer's total, and only the customer knows the total.

Things to notice. The laundromat itself did not become a class. There is exactly one of it, it has no behavior beyond holding the arrays, and an array of machines in main covers it — the same call this lecture's design made about the street. Two fields deliberately have collection or object types, and one int (number) is doing a job an array index could do; both of those are the arguable parts, and an answer that made the other choice and said why is just as good.

Problem 6 — A daily fine report (added for these notes)

The city wants a summary at the end of each day: the total dollars collected, and how many tickets were written at each rate. Using the fineFor and hoursOverdue methods from Quick Check 10.9, write a program that takes an array of meter readings (the timeLeft values at the moment each car was ticketed) and prints the total and a breakdown by number of hours overdue.

Use this test data:

int readings[] = {
    -5, -65, -20, -125, -60, -70, -185, -35, -120, -125}
;

Plan. This is the concrete reason §7 argued that getFine should return an int: you cannot add up "$25" and "$35". With fineFor returning a number, the total is a one-line accumulation.

For the breakdown, hoursOverdue already turns a reading into a small positive integer, so it can be used directly as an index into a counting array — the same tallying pattern as counting letter frequencies. Size the array from the largest value present rather than guessing, and remember that hour 1 lands in slot 1, so the array needs one extra slot.

FineReport.java

public class FineReport {
    public static int hoursOverdue(int timeLeft) {
        int minutesOver = -timeLeft;
        return (minutesOver + 59) / 60;
    }

    public static int fineFor(int timeLeft) {
        int hours = hoursOverdue(timeLeft);
        if (hours <= 0) return 0;
        return 25 + 10 * (hours - 1);
    }

    public static void main(String args[]) {
        int readings[] = {-5, -65, -20, -125, -60, -70, -185, -35, -120, -125};

        int worst = 0;
        for (int i = 0; i < readings.length; i++)
            if (hoursOverdue(readings[i]) > worst) worst = hoursOverdue(readings[i]);

        int counts[] = new int[worst + 1];
        int total = 0;
        for (int i = 0; i < readings.length; i++) {
            total += fineFor(readings[i]);
            counts[hoursOverdue(readings[i])]++;
        }

        System.out.println("Tickets written: " + readings.length);
        System.out.println("Total collected: $" + total);
        System.out.println("Breakdown:");
        for (int h = 1; h < counts.length; h++)
            if (counts[h] > 0)
                System.out.println("  " + h + " hour(s) over, $" + fineFor(-60 * h)
                                   + " each: " + counts[h] + " ticket(s)");
    }
}
Tickets written: 10
Total collected: $350
Breakdown:
  1 hour(s) over, $25 each: 4 ticket(s)
  2 hour(s) over, $35 each: 3 ticket(s)
  3 hour(s) over, $45 each: 2 ticket(s)
  4 hour(s) over, $55 each: 1 ticket(s)

Check it by hand: four $25s is 100, three $35s is 105, two $45s is 90, and one $55 — and 100 + 105 + 90 + 55 is 350. The report agrees with itself.

Things to notice. fineFor(-60 * h) in the last loop is a small trick: to print the rate for "h hours over" it feeds the method a reading that is exactly h hours over. It works only because hoursOverdue rounds up and 60×h maps to h — check the Quick Check 10.9 output, where −60 gives 1 hour and −120 gives 2. Reusing the rule instead of writing 25 + 10 * (h - 1) a second time means there is still only one place the fine schedule is defined.

counts is sized from the data, not from a guess. Writing new int[5] would work today and break the first time a car sits for six hours — the kind of assumption that survives every test you thought to run.

Slot counts[0] is allocated and never printed, because the loop starts at h = 1. Wasting one array element to keep the index and the meaning identical is almost always the right trade; the alternative, storing hour h at index h−1, saves four bytes and costs you an off-by-one every time you touch the code.

Lecture Summary
  • Design starts with nouns. Underline them, throw away the ones that are not part of the program, and for each survivor ask: does it have data and behavior, and will there be many of them? Yes to both means a class; otherwise it is a field.
  • For every class, write down what it knows (fields, with types) and what it does (methods, with parameter and return types) before typing anything. A UML-style listing is exactly that information and nothing else.
  • The four classes here are ParkedCar, ParkingMeter, PoliceOfficer and ParkingTicket. Each exists because it has state of its own that no other class should be poking at.
  • Has-a becomes a field whose type is another class. ParkedCar has a ParkingMeter — that is composition, and it is the reason Lecture 7 spent time on objects as instance variables.
  • Delegation keeps the has-a private: expiredMeter(), adjustMeter() and getFine() are one-liners that forward to the meter, so nothing outside ParkedCar needs to know a meter exists.
  • Fields are private so the class can keep a promise — timeLeft is only ever changed by remove. Getters are not ceremony: they make a field read-only, they can do work later, and they let the class protect its invariants. A getter that returns the object itself gives all that away.
  • The fine is $25 for the first hour and $10 more for each additional hour. Getting the hour boundary right is the whole difficulty, and the way you get it right is to test at 60 minutes and one tick on either side.
  • issueTicket passes this so the ticket knows who wrote it. The ticket stores text, not the car — a snapshot, not a live link — and that choice is the same reference-versus-copy question as Lecture 8's aliasing.
