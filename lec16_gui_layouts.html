1.Who decides where things go

Last time you got a window on the screen. You learned the three lines that make one appear — new JFrame(), setSize, setVisible(true) — the extends JFrame pattern that every exam question uses, the content pane that components are added to, and the event model: a source fires an event object at a listener, and a listener is an interface you implement.

Every window in Lecture 15 held exactly one thing. That was not an accident — it was a way of avoiding today's question. Put a second component in and you immediately have to answer it: where does it go?

Notice what you did not do last time. You never wrote a line saying "put the label 40 pixels from the left and 12 pixels from the top." There is no such line in any of the programs. Yet the label appeared somewhere definite, and it moved when you resized the window. Something decided that, and it was not you.

Definition— layout manager

A layout manager is an object that controls how components are positioned and sized within a container.

Every container has one. When the container needs to arrange its children — when it is first shown, and again every time it is resized — it does not decide anything itself. It hands the job to its layout manager, which walks the list of components and sets the position and size of each one. You choose the manager; the manager chooses the pixels.

Its purpose, in your instructor's words:

  • it automatically adjusts component positions when the window is resized;
  • it provides consistent arrangement across different platforms;
  • it eliminates the need for hard-coded positions.

You install one with setLayout:

Container contentPane = getContentPane();
contentPane.setLayout(new FlowLayout());
Key Idea— why not just give coordinates?

Because the numbers you would type would be wrong on somebody else's computer. The height of a button depends on the font the operating system draws it with; the width of the text Save Memo 1 is different on a Mac and on Windows; and the moment the user drags the corner of the window, every coordinate you chose is stale.

A layout manager is a rule rather than a set of numbers. "Left to right, wrap when you run out of room" and "three equal columns" stay true at any window size, in any font, on any machine. That is the same WORA promise from Lecture 1, applied to where things sit on the screen.

Java does let you switch the manager off entirely — setLayout(null) — and then you position everything by hand with setBounds. Nobody does it, and this course never will.

Three managers cover essentially everything in this course and on your exams. Each one is a class in java.awt.

ManagerThe rule it followsIt is the default for
FlowLayoutLeft to right, wrap to a new row when the row is full. Components keep their preferred size.a JPanel
BorderLayoutFive named regions — NORTH, SOUTH, EAST, WEST, CENTER — one component in each.a JFrame's content pane
GridLayoutA grid of equal-sized cells, filled left to right, top to bottom.nothing — you always ask for it

Those two defaults are worth committing to memory, because they explain behavior you have already seen and behavior you are about to see. They are also easy to check, and a claim you can check is better than a claim you memorise.

Worked Example— asking a container which manager it has

getLayout() returns the layout manager object a container is currently using. This program never opens a window; it just builds two containers and interrogates them. A JFrame needs a real screen, so instead of one we use a JRootPane — the object a JFrame builds internally, and the thing that actually manufactures the content pane getContentPane() hands you.

DefaultsProbe.java

import java.awt.BorderLayout;
import java.awt.Container;
import java.awt.FlowLayout;
import java.awt.LayoutManager;

import javax.swing.JPanel;
import javax.swing.JRootPane;

public class DefaultsProbe {
   public static void main(String args[]) {
      // A brand new JPanel, with no setLayout call at all.
      JPanel panel = new JPanel();
      LayoutManager panelLayout = panel.getLayout();
      System.out.println("a new JPanel is laid out by a FlowLayout?  "
                         + (panelLayout instanceof FlowLayout));

      FlowLayout f = (FlowLayout) panelLayout;
      System.out.println("   its alignment is CENTER?                "
                         + (f.getAlignment() == FlowLayout.CENTER));
      System.out.println("   its gaps are hgap " + f.getHgap() + ", vgap " + f.getVgap());

      // A JFrame needs a screen, but the content pane a JFrame hands you is
      // built by a JRootPane, and that can be created without one.
      Container contentPane = new JRootPane().getContentPane();
      System.out.println("a content pane is laid out by a BorderLayout?  "
                         + (contentPane.getLayout() instanceof BorderLayout));
   }
}

Before you reveal: four lines of output, and you should be able to guess three of them.

a new JPanel is laid out by a FlowLayout?  true
   its alignment is CENTER?                true
   its gaps are hgap 5, vgap 5
a content pane is laid out by a BorderLayout?  true

Both defaults confirmed, and two extra facts fell out that will explain some numbers in §2. A default FlowLayout centers each row rather than pushing it to the left, and it leaves a five-pixel gap horizontally between components and vertically between rows.

This also explains a mystery from last lecture. A single JLabel added to a content pane filled the whole window, and the note said "because the content pane starts out with a BorderLayout". Now you can see the machinery: add(label) with no region named puts the label in CENTER, and CENTER is the region that expands to take everything left over. With no other component in the pane, everything is left over, so the label gets all of it.

Quick Check 16.1

Three short questions about the idea, before any of the three managers.

(a) A student adds three buttons to a content pane and never calls setLayout. Have they avoided using a layout manager?

No. They have used the default one, which for a content pane is a BorderLayout. There is no such thing as a container without a layout manager unless you explicitly write setLayout(null).

Their three buttons will all land in CENTER, one on top of another — see §3 for what really happens. "I did not choose a manager" always means "I got the default", and the default is the source of a great many surprises.

(b) Why does a layout manager have to run again when the user drags the corner of the window?

Because its answers were relative to the container's size, not absolute. "Three equal columns" means one width when the window is 300 pixels across and another when it is 600. The container asks the manager again, the manager recomputes every position and size, and the components move.

This is exactly what you would have to write by hand if you positioned things with coordinates — and it is exactly what nobody writes by hand correctly.

(c) Write the two lines that give a frame's content pane a GridLayout with two rows and four columns.

Container contentPane = getContentPane();
contentPane.setLayout(new GridLayout(2, 4));

Rows first, then columns. That is the opposite way round from setSize(width, height), which takes the horizontal number first, and the mismatch is exactly why people transpose them. GridLayout(2, 4) is short and wide; GridLayout(4, 2) is tall and narrow.

Things to notice across all three parts. setLayout takes a layout-manager object, so there is always a new in the call. Writing contentPane.setLayout(GridLayout(2, 4)); without the new is a compile error, and it is one of the commonest typos in GUI code — you will meet the exact message it produces in Practice Problem 3.

2.FlowLayout

Definition— FlowLayout

FlowLayout is the default layout manager for a JPanel. Its rule is the one a word processor uses for words:

  • it arranges components left to right, in the order they were added;
  • when a row is full, the next component wraps to a new row below;
  • every component keeps its preferred size — the size it says it wants, big enough for its text. FlowLayout never stretches anything.

It is simple, and it is limited: you cannot say "this one on the left, that one on the right". For a row of buttons it is exactly right, and that is what it is normally used for.

Worked Example— FlowLayoutDemo, and where the labels really land

Your instructor's first layout program. Five labels, added in a loop, into a content pane that has been given a FlowLayout.

FlowLayoutDemo.java

import javax.swing.*;
import java.awt.*;

public class FlowLayoutDemo extends JFrame {
    public static final int WIDTH = 300;
    public static final int HEIGHT = 200;

    public FlowLayoutDemo() {
        super();
        setSize(WIDTH, HEIGHT);
        setTitle("FlowLayout Demo");

        Container contentPane = getContentPane();
        contentPane.setLayout(new FlowLayout());

        for (int i = 1; i <= 5; i++) {
            JLabel label = new JLabel("Label " + i);
            contentPane.add(label);
        }

        // Set up window closing behavior
        setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
    }

    public static void main(String[] args) {
        FlowLayoutDemo demo = new FlowLayoutDemo();
        demo.setVisible(true);
    }
}

A Swing program prints nothing — it puts a window on the screen. But a layout manager is an ordinary object doing ordinary arithmetic, and we can watch it work without a screen at all. This driver builds a JPanel with the same FlowLayout and the same labels, tells it what size to pretend to be, calls doLayout() (the method a container calls on itself when it needs arranging), and then prints the rectangle each component ended up with.

FlowProbe.java

import java.awt.Component;
import java.awt.FlowLayout;
import java.awt.Rectangle;

import javax.swing.JLabel;
import javax.swing.JPanel;

public class FlowProbe {

   // Build a panel of n labels, lay it out at a given size, and print where
   // the layout manager put every one of them.
   public static void show(String title, int n, int width, int height) {
      JPanel panel = new JPanel();
      panel.setLayout(new FlowLayout());
      for (int i = 1; i <= n; i++)
         panel.add(new JLabel("Label " + i));

      panel.setSize(width, height);
      panel.doLayout();

      System.out.println(title);
      for (Component c : panel.getComponents()) {
         Rectangle r = c.getBounds();
         System.out.printf("   %-8s at (x=%3d, y=%3d)  size %3d x %3d%n",
                           ((JLabel) c).getText(), r.x, r.y, r.width, r.height);
      }
      System.out.println();
   }

   public static void main(String args[]) {
      show("5 labels in a 300 x 200 container:", 5, 300, 200);
      show("7 labels in the same 300 x 200 container:", 7, 300, 200);
      show("the 5 labels again, container narrowed to 150 wide:", 5, 150, 200);
   }
}

Every rule in the definition is visible in those numbers.

  • Left to right. In the first block, y is 5 for all five labels — one row — and x climbs 12, 68, 124, 180, 236. The step is 56, which is the label's width of 51 plus the five-pixel hgap the previous section measured.
  • Preferred size. Every label is exactly 51 by 15, in every block. The container got wider and narrower and the labels never changed size. That is what "components maintain their preferred size" means, and it is the single biggest difference between FlowLayout and the other two.
  • Wrapping. Seven labels no longer fit across 300 pixels, so labels 6 and 7 appear at y = 25, a second row 20 pixels lower (15 tall plus the five-pixel vgap). Nothing was resized and nothing was clipped; the extra ones simply went to the next line.
  • The rows are centered. The two labels on the second row start at x = 96, not at x = 12. That is the default CENTER alignment: each row is centered independently. In the last block, look at Label 5 sitting alone at x = 49 — it is centered in the 150-pixel container by itself.

Definition— FlowLayout alignment

new FlowLayout() centers each row. The one-argument constructor takes an alignment constant instead:

ConstructorEach row is
new FlowLayout(FlowLayout.LEFT)pushed against the left edge
new FlowLayout(FlowLayout.CENTER)centered — the same as new FlowLayout()
new FlowLayout(FlowLayout.RIGHT)pushed against the right edge

Three labels 51 pixels wide, in a 300-pixel container, laid out three times:

new FlowLayout(FlowLayout.LEFT)   -> x positions:  5  61  117
new FlowLayout(FlowLayout.CENTER) -> x positions:  68  124  180
new FlowLayout(FlowLayout.RIGHT)  -> x positions:  132  188  244

LEFT starts at the 5-pixel gap. RIGHT finishes at 244 + 51 = 295, five pixels short of the right edge. CENTER splits the leftover space in half. There is a two-argument form, new FlowLayout(FlowLayout.LEFT, 20, 10), which sets the horizontal and vertical gaps as well.

Quick Check 16.2

A JPanel is given a FlowLayout and three JButton objects are added to it, labelled One, Two and Three. The panel is 400 pixels wide, and each button is about 70 pixels wide.

(a) Sketch where the three buttons appear.

All three on one row — three buttons at 70 pixels plus gaps is about 220 pixels, comfortably inside 400 — in the order they were added, and centered horizontally with roughly 90 pixels of empty space on either side. Vertically they sit at the top, five pixels down.

(b) The user drags the window until the panel is only 200 pixels wide. Now what?

The buttons do not shrink. One and Two stay on the first row — two buttons and their gaps come to roughly 150, which still fits — and Three wraps to a second row below them, centered on its own. Narrow the panel further and you get three rows of one.

Notice what the layout manager will not do: squeeze a button. A button narrower than its own label would be unreadable, so FlowLayout moves it instead.

(c) You want the three buttons hard against the left edge instead of centered. What changes?

One line: panel.setLayout(new FlowLayout(FlowLayout.LEFT));

Things to notice across all three parts. Everything a FlowLayout does follows from two sentences — keep the preferred size, wrap when you run out. If you can hold those two, you never have to memorise anything else about it. The place it is genuinely the right tool is a strip of buttons along the bottom of a window, which is what §5 builds and what half your exam questions ask for.

Quick Check 16.3

Write a complete class Toolbar that extends JFrame and shows a 400-by-100 window titled Toolbar whose content pane uses a left-aligned FlowLayout and contains four buttons reading New, Open, Save and Quit. Clicking the close box must end the program. The buttons do not have to do anything yet. Include a main.

Plan. This is the Lecture 15 checklist with one new line in the middle. Class header, constants, constructor: super(), setTitle, setSize, setDefaultCloseOperation, get the content pane, set its layout, add the four buttons in order. Then the two-line main. A loop over an array of names is tidier than four near-identical pairs of lines, and it is worth getting into the habit.

Toolbar.java

import java.awt.Container;
import java.awt.FlowLayout;

import javax.swing.JButton;
import javax.swing.JFrame;

public class Toolbar extends JFrame {
   public static final int WIDTH = 400;
   public static final int HEIGHT = 100;

   public Toolbar() {
      super();
      setTitle("Toolbar");
      setSize(WIDTH, HEIGHT);
      setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);

      Container contentPane = getContentPane();
      contentPane.setLayout(new FlowLayout(FlowLayout.LEFT));

      String names[] = {"New", "Open", "Save", "Quit"};
      for (int i = 0; i < names.length; i++) {
         contentPane.add(new JButton(names[i]));
      }
   }

   public static void main(String args[]) {
      Toolbar gui = new Toolbar();
      gui.setVisible(true);
   }
}

Things to notice. The setLayout call has to come before — or at least along with — the add calls in any code you write, because setLayout on a container that already holds components throws its arrangement away and starts again. 3.BorderLayout

FlowLayout has no vocabulary for "put this at the top and that at the bottom". BorderLayout is nothing but that vocabulary, and it is the manager your exams lean on hardest.

Definition— BorderLayout

BorderLayout is the default layout manager for a JFrame's content pane. It divides the container into five regions, named by constants on the class itself:

ConstantWhereHow it is sized
BorderLayout.NORTHa strip across the topfull width of the container; its own preferred height
BorderLayout.SOUTHa strip across the bottomfull width of the container; its own preferred height
BorderLayout.WESTdown the left, between north and southits own preferred width; full remaining height
BorderLayout.EASTdown the right, between north and southits own preferred width; full remaining height
BorderLayout.CENTERthe box in the middleeverything left over, in both directions

Two rules go with it, and both are examinable:

  • Each region holds one component. You add with a second argument naming the region: contentPane.add(theLabel, BorderLayout.NORTH);
  • You do not have to use all five. An unused region simply takes up no space, and its share goes to CENTER.
Key Idea— CENTER is the one that grows

North and south are as tall as they need to be. East and west are as wide as they need to be. Center gets whatever is left — and when the window is resized, center absorbs the entire change while the other four stay the size they were.

That single sentence tells you how to design almost any window in this course: the thing you want to fill the window goes in CENTER, and the trim goes round the edges. A row of buttons along the bottom is SOUTH; a toolbar is NORTH; the drawing, the text area or the colored panel the program is really about is CENTER.

Worked Example— BorderLayoutDemo, and what resizing does

Your instructor's program puts a label in each of the five regions, so you can see all of them at once. Read the add calls: every one names its region.

BorderLayoutDemo.java

import javax.swing.*;
import java.awt.*;

public class BorderLayoutDemo extends JFrame {
    public static final int WIDTH = 300;
    public static final int HEIGHT = 200;

    public BorderLayoutDemo() {
        super();
        setSize(WIDTH, HEIGHT);
        setTitle("BorderLayout Demo");

        Container contentPane = getContentPane();
        contentPane.setLayout(new BorderLayout());

        JLabel northLabel = new JLabel("North Region", JLabel.CENTER);
        contentPane.add(northLabel, BorderLayout.NORTH);

        JLabel eastLabel = new JLabel("East Region");
        contentPane.add(eastLabel, BorderLayout.EAST);

        JLabel centerLabel = new JLabel("Center Region", JLabel.CENTER);
        contentPane.add(centerLabel, BorderLayout.CENTER);

        JLabel westLabel = new JLabel("West Region");
        contentPane.add(westLabel, BorderLayout.WEST);

        JLabel southLabel = new JLabel("South Region", JLabel.CENTER);
        contentPane.add(southLabel, BorderLayout.SOUTH);

        // Set up window closing behavior
        setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
    }

    public static void main(String[] args) {
        BorderLayoutDemo demo = new BorderLayoutDemo();
        demo.setVisible(true);
    }
}

Notice that the regions are added out of order — north, east, center, west, south — and it makes no difference at all. BorderLayout places by name, not by arrival. That is the opposite of FlowLayout, where order is everything.

Common Mistake— two components in one region

"Each region can hold one component" sounds like a warning about a compiler error. It is not. Adding a second component to a region compiles cleanly, runs cleanly, and quietly loses one of them. Here is what really happens — two labels into NORTH, one into CENTER:

SameRegionProbe.java

import java.awt.BorderLayout;
import java.awt.Component;
import java.awt.Rectangle;

import javax.swing.JPanel;

public class SameRegionProbe {
   public static void main(String args[]) {

      panel.add(new JLabel("first"),  BorderLayout.NORTH);

the layout manager's NORTH is: second

All three labels are still children of the panel — getComponentCount() says 3, and nothing was thrown away. But the layout manager only remembers one component per region, and the second add overwrote the first. first was left with a size of 0 by 0: it is there, it is a real object, and it occupies no pixels, so it is invisible.

The last one added wins. That is the rule, and the reason it costs people so much time is that there is no error to search for — just a component that never appears. When something you added is missing from your window, the first question is: did something else go into the same region afterwards?

The fix is never "add them both anyway". It is to put a JPanel in that region and add both components to the panel — which is exactly what §5 is about.

Common Mistake— forgetting the region argument

contentPane.add(theButton); in a BorderLayout container compiles, because add has a one-argument form. The component goes to CENTER:

add(c) with no region: bounds 300 x 200 at (0, 0) is it the CENTER component? true

So three components added that way all land in CENTER, each overwriting the last, and only the third is ever seen. This is the real explanation for the student in Quick Check 16.1(a) whose three buttons produced one button.

Quick Check 16.4

Consider this constructor body, inside a class that extends JFrame and is sized 400 by 300.

Three: Bottom as a full-width strip across the top, Left down the left side, and Middle filling everything else. Top is invisible — it was overwritten in NORTH by the last add, and has size 0 by 0.

The button labelled Bottom appearing at the top is the joke, and it is the kind of thing an exam question does to check that you are reading the region constant rather than the button's text.

(b) Nothing was added to EAST or SOUTH. What happens to those two strips of the window?

They take up no space at all, and CENTER expands into them. An empty region is not an empty gap — it simply is not there. So Middle runs all the way to the right edge and all the way to the bottom edge of the window.

(c) The user drags the window out to 800 by 600. Give the new size of each visible button, in words.

Bottom in NORTH: now 800 wide, same height as before. Left in WEST: same width as before, now taller by 300. Middle in CENTER: 400 pixels wider and 300 taller than it was — it absorbed the entire change in both directions.

Things to notice across all three parts. Every BorderLayout question is answered by the same two facts: one component per region, last one wins, and CENTER takes what is left. Read the add calls, note the region on each, and the picture draws itself.

4.GridLayout

Definition— GridLayout

GridLayout arranges components in a grid of equal-sized cells. You construct it with the shape you want:

panel.setLayout(new GridLayout(2, 3));   // 2 rows, 3 columns

Rows first, then columns. Its rules:

  • every cell is exactly the same size, and the whole container is divided up with nothing left over;
  • each component fills its entire cell — unlike FlowLayout, GridLayout stretches things, and a component's preferred size is ignored;
  • components are placed left to right, then top to bottom, in the order they were added — the order you read a page in.

It is the manager for anything genuinely regular: a calculator keypad, a row of equally wide buttons, a form of paired labels and fields.

Quick Check 16.5

A panel 600 pixels wide and 400 tall is given new GridLayout(3, 2), and then five buttons are added, labelled A through E.

(a) How big is each button, and where is D?

Three rows and two columns of a 600-by-400 panel gives cells of 600/2 = 300 wide and 400/3 ≈ 133 tall. Every button is that size, including E, which sits alone on the bottom row.

Filling left to right then top to bottom: A B on row one, C D on row two, E at the start of row three. So D is the right-hand cell of the middle row. The sixth cell, beside E, is empty.

(b) The same five buttons, but the layout is new GridLayout(2, 2). Now what?

The row count wins: two rows are kept, and the columns grow to fit. Five components in two rows needs three columns, so you get a 2-by-3 grid with cells 200 wide and 200 tall. A B C across the top, D E and an empty cell across the bottom.

The 2 you wrote for columns had no effect whatsoever. This is the behavior the worked example measured, and it is the reason GridLayout(0, cols) is usually the safer thing to write when you are not certain how many components there will be.

(c) You want five buttons in a single vertical column. Give the setLayout line, two ways.

panel.setLayout(new GridLayout(5, 1)); if you know there are exactly five, or panel.setLayout(new GridLayout(0, 1)); for "one column, as many rows as I add". The second keeps working when you add a sixth button later.

Things to notice across all three parts. 5.JPanel: layouts inside layouts

Each of the three managers is too simple on its own for a real window. BorderLayout gives you five regions and one component each — but a window needs three buttons along the bottom. GridLayout makes everything the same size — but a window is not a grid. So how does anyone build anything?

By using more than one manager in the same window. And the object that makes that possible is the plainest class in Swing.

Definition— JPanel

A JPanel is a general-purpose container with no decoration of its own: no title bar, no border, no visible edge. It exists to group components.

The crucial fact is that a JPanel is both a container and a component:

  • as a container, it has its own layout manager — FlowLayout by default — and its own children;
  • as a component, it can be added to another container, including a single region of a BorderLayout.

Put those together and the whole thing opens up. A panel counts as one component as far as the outer container is concerned, so it satisfies "one component per region" — while holding as many components as you like inside itself, arranged by a completely different manager.

Key Idea— a window is a tree of containers

Lecture 15 said "a container is a component, so containers nest, and a GUI is a tree." This is where that sentence starts paying. A real window is not one layout; it is a small tree:

The structure of a typical window

JFrame +-- content pane                 (BorderLayout) +-- CENTER: JPanel         (its own GridLayout, holding the real content) +-- SOUTH:  JPanel         (its own FlowLayout, holding a row of buttons)

Every window you build for the rest of this course is a variation on those four lines. When an exam question shows you a picture of a GUI, the first thing to do is draw that tree: what is in the middle, what is round the edges, and which of the edge pieces is really a panel of several things.

Procedure— building any nested layout, in five steps
  1. Get the content pane and give it a BorderLayout. Container contentPane = getContentPane(); contentPane.setLayout(new BorderLayout());
  2. Make a JPanel for each region that needs more than one thing in it. JPanel buttonPanel = new JPanel();
  3. Give each panel its own layout manager. buttonPanel.setLayout(new GridLayout(3, 1));
  4. Add the panel to its region. contentPane.add(buttonPanel, BorderLayout.WEST);
  5. Add the components to the panel, not to the content pane. buttonPanel.add(redButton);

Steps 4 and 5 can be done in either order — a panel can be filled before or after it is added — but doing them in this order keeps the code reading top-down like the tree.

Worked Example— PanelDemo: a column of buttons down one side

The content pane is a BorderLayout; its WEST region holds one JPanel; that panel has a GridLayout(3, 1) and holds the three buttons. 6.JButton, ActionListener and actionPerformed

Everything so far has been arrangement. Nothing on any of these windows does anything when you click it. Now we add the component the whole event model was invented for — and you will find that Lecture 15 already taught you the mechanism, with different nouns.

Definition— JButton

A JButton is a component that triggers an action when it is clicked. You construct one with the text that will appear on it:

JButton stopButton = new JButton("Red");

To make a button useful there are exactly four steps:

  1. Create the JButton.
  2. Register an ActionListener on it, with addActionListener.
  3. Add it to a container.
  4. Implement the actionPerformed method that says what a click does.

Steps 2 and 3 can come in either order. Miss step 2 and the button is a decoration; miss step 3 and it is invisible; miss step 4 and the program does not compile.

Definition— ActionListener

ActionListener is an interface in java.awt.event with exactly one method:

public void actionPerformed(ActionEvent e)

A class that says implements ActionListener is promising to supply that method, and any object of that class can then be handed to addActionListener. When the button is clicked, it builds an ActionEvent describing the click and calls actionPerformed on every listener registered with it.

Compare it with WindowListener from last lecture, which had seven methods and needed WindowAdapter to make it bearable. ActionListener has one, so there is no ActionAdapter and there never needed to be.

Line the two events up and you can see that the mechanism has not changed at all — only the names have:

The listener object has to be something. The pattern this course uses — and the one every GUI question on your exams expects — is to make the frame its own listener:

public class PanelDemo extends JFrame implements ActionListener

Read it as two separate promises. extends JFrame says this object is a window. implements ActionListener says this object can also handle button clicks. A class may extend only one class but implement any number of interfaces, so the two never compete.

Then the registration line inside the constructor is:

redButton.addActionListener(this);

7.Telling the buttons apart

PanelDemo has three buttons and one actionPerformed. Every click, whichever button caused it, arrives at that same method. So the first job inside the method is always the same: work out which button this was.

There are two ways, and both appear in your instructor's material. Learn both; they are not interchangeable.

Definition— the action command

Every ActionEvent carries a String called its action command, read with e.getActionCommand(). For a JButton it defaults to the button's label — the text you passed to new JButton("Red").

So an actionPerformed shared by three buttons is a chain of string comparisons:

public void actionPerformed(ActionEvent e) {
    String command = e.getActionCommand();
    if (command.equals("Red"))    contentPane.setBackground(Color.RED);
    if (command.equals("Orange")) contentPane.setBackground(Color.ORANGE);
    if (command.equals("Green"))  contentPane.setBackground(Color.GREEN);
}

Compare with .equals, never with ==. Lecture 4's rule about comparing strings has not stopped applying just because we are in a window.

Definition— the event source

e.getSource() returns the object that fired the event — the actual JButton, not a copy and not its name. Because it is the same object, you compare it with ==:

public void actionPerformed(ActionEvent e) {
    if (e.getSource() == clearButton) {
        // ... } else if (e.getSource() == addTextButton) { // ... } }

Here == is exactly right, and .equals would be wrong-headed: the question is not "does this button look like that one" but "is this the very same object". That is what == on references asks, and it is Lecture 8's rule, unchanged.

The price is that the buttons must be fields of the class, not local variables of the constructor, or actionPerformed has no name to compare against.

Worked Example— both techniques, and what breaks each one

Two buttons, Up and Down, and one listener that reports both answers for every click. Then two things happen to the Up button that a real program might do: it gets relabelled, and then it is given an explicit command string.

CommandProbe.java

import java.awt.event.ActionEvent;
import java.awt.event.ActionListener;

import javax.swing.JButton;

class Reporter implements ActionListener {
   private JButton up, down;

   public Reporter(JButton up, JButton down) {
      this.up = up;
      this.down = down;
   }

   public void actionPerformed(ActionEvent e) {
      System.out.println("getActionCommand() -> " + e.getActionCommand());
      System.out.println("getSource() == up    ? " + (e.getSource() == up));
      System.out.println("getSource() == down  ? " + (e.getSource() == down));
      System.out.println();
   }
}

public class CommandProbe {
   public static void main(String args[]) {
      JButton up   = new JButton("Up");
      JButton down = new JButton("Down");
      Reporter listener = new Reporter(up, down);
      up.addActionListener(listener);
      down.addActionListener(listener);

      up.doClick();
      down.doClick();

      System.out.println("Now relabel the Up button:");
      up.setText("Increase");
      up.doClick();

      System.out.println("Now pin the command down explicitly:");
      up.setActionCommand("UP");
      up.setText("Go Higher");
      up.doClick();
   }
}

The action command followed the label. Rename the button and the string your if compares against changes with it. A method containing if (command.equals("Up")) silently stops working the moment somebody edits the button's text — or capitalises it differently, or adds a trailing space.

getSource() never moved. Through the relabel and through the explicit command, e.getSource() == up stayed true, because it is the same object throughout. That is the technique's whole advantage: it does not care what the button says.

setActionCommand decouples the two. The last block gives the button a stable internal name UP while the visible label reads Go Higher. It is the professional fix, and it is worth knowing it exists — but your instructor's notes and exam answers never use it, so on an exam match the labels exactly.

Quick Check 16.9

This actionPerformed belongs to a frame with three buttons made by new JButton("Add"), new JButton("Subtract") and new JButton("Clear").

public void actionPerformed(ActionEvent e) {
    String command = e.getActionCommand();
    if (command == "Add")            total = total + 1;
    if (command.equals("subtract"))  total = total - 1;
    if (command.equals("Clear"))     total = 0;
}

Two of the three branches never run. Say which, why, and how to fix each.

Plan. Go branch by branch and ask two questions each: is the comparison the right kind, and is the string the right text?

The Add branch: wrong kind of comparison. command == "Add" compares two references, and the String that came out of getActionCommand() is not the same object as the literal "Add" in your source. It is the classic Lecture 4 mistake, and it is nastier here than usual because with some strings, in some programs, string interning makes == accidentally work — so it can pass a quick test and fail in front of the grader. Fix: command.equals("Add").

The Subtract branch: wrong text. The button was created with a capital S, so the action command is "Subtract", and "subtract" does not equal it. .equals is case-sensitive. Fix: command.equals("Subtract").

The Clear branch is fine — right kind of comparison, exactly matching text.

public void actionPerformed(ActionEvent e) {
    String command = e.getActionCommand();
    if (command.equals("Add"))       total = total + 1;
    if (command.equals("Subtract"))  total = total - 1;
    if (command.equals("Clear"))     total = 0;
}

Things to notice. Neither bug produces a compiler error or an exception. Two of the three buttons simply do nothing, forever. If this makes you want a technique the compiler can check, that is the right instinct — and it is e.getSource(), where a misspelled field name is a compile error.

A tidier structure for a chain like this is else if, so that at most one branch can run. Your instructor writes plain if statements, which is equivalent here because the conditions are mutually exclusive, but else if says what you mean and stops the machine testing conditions it has already ruled out.

Quick Check 16.10

Two design questions with no code to write.

(a) A window has ten buttons, all built inside a loop from an array of names, and none of them is stored in a field. Which technique must you use to tell them apart?

e.getActionCommand(). There are no field names to compare a source against — the buttons only ever existed as a local variable inside the loop. This is exactly the situation in the Keypad of Quick Check 16.6, and it is why the action command exists at all.

(b) A window has two buttons whose labels are set from a language file, so they read Save in English and Guardar in Spanish. Which technique?

8.Listeners that are not the frame

Every example so far has made the frame its own listener. That is the right default, it is what your instructor's notes do, and it is what the exams ask for. But it is not the only choice, and one of the alternatives turns up in her own posted solutions — so it is worth knowing all three and why you would pick each.

Where the listener livesClass headerCan it reach the frame's private fields?
The frame is the listenerclass Gui extends JFrame implements ActionListenerYes — they are its own fields
A separate top-level classclass MyListener implements ActionListenerNo — they must be passed in

You have already seen the middle one working: ColorSwitcher in §6 took a JPanel through its constructor and stored it in a field, because it had no other way to reach the thing it had to color. That plumbing is the cost of a separate class, and it is exactly what an inner class removes.

Definition— inner class

An inner class is a class declared inside another class. It is a member of the outer class, exactly like a field or a method, and it may be private.

The property that matters here: an inner class object belongs to an object of the outer class, and its methods can use that object's fields and methods directly by name — including the private ones. It does not need a reference passed in, because it already has one.

public class Gui extends JFrame {
    private JLabel message;
    // private to Gui private class Handler implements ActionListener { public void actionPerformed(ActionEvent e) { message.setText("clicked");           // reaches Gui's private field } } }

Notice what the header of Gui does not say: there is no implements ActionListener on it. The frame is not a listener; it merely contains one.

Key Idea— when the inner class is the only way

Java allows one extends. A class that already extends JFrame cannot also extend WindowAdapter. So if you want a window that reacts to its own close box using WindowAdapter's convenience — overriding one method instead of seven — the frame itself cannot be the listener, and a top-level class cannot see the frame's fields.

That is precisely the situation in your instructor's posted solution to the "Are you sure!" practice problem: an inner class WindowDestroyer extends WindowAdapter, declared inside the frame, reaching the frame's displayLabel and closeAttempts directly. Once you have seen the constraint, the design is the only one available.

Worked Example— the same counter, inside and outside

A panel with a label and a button. Each click increases a count and updates the label. The listener is an inner class, so it can touch both clicks and display with no ceremony at all.

CounterPanel.java

import java.awt.FlowLayout;
import java.awt.event.ActionEvent;
import java.awt.event.ActionListener;

import javax.swing.JButton;
import javax.swing.JLabel;
import javax.swing.JPanel;

public class CounterPanel extends JPanel {
   private JLabel display;      // private to CounterPanel
   private JButton up;          // private to CounterPanel
   private int clicks = 0;      // private to CounterPanel

   public CounterPanel() {
      setLayout(new FlowLayout());

      display = new JLabel("Clicks: 0");
      add(display);

      up = new JButton("Click me");
      up.addActionListener(new Counter());   // an object of the inner class
      add(up);
   }

   // An inner class: declared inside CounterPanel, so its one method can use
   // display and clicks directly -- no getters, no constructor argument.
   private class Counter implements ActionListener {
      public void actionPerformed(ActionEvent e) {
         clicks++;
         display.setText("Clicks: " + clicks);
      }
   }

   public String getDisplayText() { return display.getText(); }
   public JButton getButton()     { return up; }
}

import java.awt.BorderLayout;
import java.awt.Container;
import java.awt.GridLayout;
import java.awt.event.ActionEvent;
import java.awt.event.ActionListener;

import javax.swing.JButton;
import javax.swing.JFrame;
import javax.swing.JLabel;
import javax.swing.JPanel;

public class Tally extends JFrame implements ActionListener {
   public static final int WIDTH = 300;
   public static final int HEIGHT = 120;

   private JLabel display;    // a field: actionPerformed needs it
   private int total = 0;     // a field: it has to survive between clicks

   public Tally() {
      super();
      setTitle("Tally");
      setSize(WIDTH, HEIGHT);
      setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);

      Container contentPane = getContentPane();
      contentPane.setLayout(new BorderLayout());

      display = new JLabel("Total: 0", JLabel.CENTER);
      contentPane.add(display, BorderLayout.CENTER);

      JPanel buttonPanel = new JPanel();
      buttonPanel.setLayout(new GridLayout(1, 2));
      contentPane.add(buttonPanel, BorderLayout.SOUTH);

      JButton plus = new JButton("Plus");
      plus.addActionListener(this);
      buttonPanel.add(plus);

      JButton minus = new JButton("Minus");
      minus.addActionListener(this);
      buttonPanel.add(minus);
   }

   public void actionPerformed(ActionEvent e) {
      String command = e.getActionCommand();

      if (command.equals("Plus"))  total = total + 1;
      if (command.equals("Minus")) total = total - 1;

      display.setText("Total: " + total);
   }

   public static void main(String args[]) {
      Tally gui = new Tally();
      gui.setVisible(true);
   }
}

Problem 4 — What is the output? (added for these notes)

This program never opens a window. doClick() makes a JButton fire its ActionEvent exactly as a mouse click would, so every listener runs for real. Give the exact output, line by line.

ClickQuiz.java

import java.awt.event.ActionEvent;
import java.awt.event.ActionListener;

import javax.swing.JButton;

class Watcher implements ActionListener {
    private String name;
    private int count = 0;

    public Watcher(String name) { this.name = name; }

    public void actionPerformed(ActionEvent e) {
        count++;
        System.out.println(name + " heard \"" + e.getActionCommand() + "\", count = " + count);
    }
}

public class ClickQuiz {
    public static void main(String args[]) {
        JButton alpha = new JButton("Alpha");
        JButton beta  = new JButton("Beta");

        Watcher one = new Watcher("one");
        Watcher two = new Watcher("two");

        alpha.addActionListener(one);
        beta.addActionListener(two);

        alpha.doClick();                  // line (a)
        beta.doClick();                   // line (b)
        alpha.doClick();                  // line (c)
        beta.setText("Gamma");
        beta.doClick();                   // line (d)
        alpha.removeActionListener(one);
        alpha.doClick();                  // line (e)
        System.out.println("done");       // line (f)
    }
}

(a) What is printed at line (a)?

one heard "Alpha", count = 1. The alpha button has one listener, one; its action command defaults to its label, Alpha; and count goes from 0 to 1.

(b) What is printed at line (b)?

two heard "Beta", count = 1. A different button, a different listener object, and therefore a different count field — which is still at 0 when the method starts. Each Watcher has its own copy.

(c) What is printed at line (c)?

one heard "Alpha", count = 2. Same button, same listener object as line (a), so count picks up where it left off. This is the behavior every "count the clicks" GUI depends on: the listener is an object, and its fields persist between events.

(d) What is printed at line (d)?

two heard "Gamma", count = 2. beta.setText("Gamma") changed the button's label, and because the action command defaults to the label, it changed the action command with it. The listener is unchanged and its count goes to 2 — but the string it reports is different from line (b).

In a real program that had if (command.equals("Beta")) in it, that one setText call would have silently broken the button.

(e) What is printed at line (e)?

Nothing. removeActionListener(one) undid the registration, so alpha now has no listeners at all. doClick() still runs — the button really is pressed and released — and there is nobody to tell.

That is the unregistered button from Problem 3, produced deliberately: a working button, a working handler, and no connection between them.

(f) Write out the complete output of the program.

two heard "Beta", count = 1
one heard "Alpha", count = 2
two heard "Gamma", count = 2
done

Things to notice across all six parts. Five clicks produced four lines, and the missing one is the whole point of the exercise. Registration is a link between two objects that can be made and unmade at run time; it is not a property of either one.

The two counters ran independently because they are fields of two different Watcher objects. Had both buttons been registered with the same Watcher, there would have been one count reaching 4. That distinction — one listener object shared, or one per component — is a design decision you make every time you write a GUI, and it decides what the state means.

TrafficLight.java

import java.awt.BorderLayout;
import java.awt.Color;
import java.awt.Container;
import java.awt.GridLayout;
import java.awt.event.ActionEvent;
import java.awt.event.ActionListener;

import javax.swing.JButton;
import javax.swing.JFrame;
import javax.swing.JPanel;

public class TrafficLight extends JFrame implements ActionListener {
   public static final int WIDTH = 300;
   public static final int HEIGHT = 400;

   private JPanel redLamp, yellowLamp, greenLamp;

   public TrafficLight() {
      super();
      setTitle("Traffic Light");
      setSize(WIDTH, HEIGHT);
      setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);

      Container contentPane = getContentPane();
      contentPane.setLayout(new BorderLayout());

      // The three lamps, stacked vertically in the center.
      JPanel lampPanel = new JPanel();
      lampPanel.setLayout(new GridLayout(3, 1));
      contentPane.add(lampPanel, BorderLayout.CENTER);

      redLamp = new JPanel();
      redLamp.setBackground(Color.DARK_GRAY);
      lampPanel.add(redLamp);

      yellowLamp = new JPanel();
      yellowLamp.setBackground(Color.DARK_GRAY);
      lampPanel.add(yellowLamp);

      greenLamp = new JPanel();
      greenLamp.setBackground(Color.DARK_GRAY);
      lampPanel.add(greenLamp);

      // The three buttons, side by side along the bottom.
      JPanel buttonPanel = new JPanel();
      buttonPanel.setLayout(new GridLayout(1, 3));
      contentPane.add(buttonPanel, BorderLayout.SOUTH);

      makeButton(buttonPanel, "Stop");
      makeButton(buttonPanel, "Wait");
      makeButton(buttonPanel, "Go");
   }

   private void makeButton(JPanel panel, String name) {
      JButton b = new JButton(name);
      b.addActionListener(this);
      panel.add(b);
   }

   public void actionPerformed(ActionEvent e) {
      // Every click starts by turning all three lamps off.
      redLamp.setBackground(Color.DARK_GRAY);
      yellowLamp.setBackground(Color.DARK_GRAY);
      greenLamp.setBackground(Color.DARK_GRAY);

      String command = e.getActionCommand();
      if (command.equals("Stop")) redLamp.setBackground(Color.RED);
      if (command.equals("Wait")) yellowLamp.setBackground(Color.YELLOW);
      if (command.equals("Go"))   greenLamp.setBackground(Color.GREEN);
   }

   public static void main(String args[]) {
      TrafficLight gui = new TrafficLight();
      gui.setVisible(true);
   }
}

GridLayout(3, 1) for the lamps and GridLayout(1, 3) for the buttons is worth reading twice. Rows first, columns second: three rows of one is a column, and one row of three is a row. Swapping them gives you three lamps side by side and three buttons stacked up the bottom left, which compiles and looks absurd.

Finally: the lamps are JPanel objects with nothing in them. A JPanel is opaque by default, so it paints its background — which is why a bare panel makes a perfectly good colored rectangle. A JLabel is not opaque, which is why coloring one usually appears to do nothing. That difference is worth remembering the next time a setBackground seems to be ignored.

Lecture Summary
  • A layout manager is an object that decides the position and size of every component in a container. The container asks it whenever it is shown or resized, so the arrangement is a rule rather than a set of pixel coordinates — which is what makes it survive a different font, a different platform and a dragged window corner.
  • FlowLayout lays components left to right and wraps to a new row when it runs out of width. Every component keeps its preferred size; nothing is stretched. It is the default for a JPanel, it centers each row, and new FlowLayout(FlowLayout.LEFT) changes that.
  • BorderLayout divides a container into NORTH, SOUTH, EAST, WEST and CENTER. North and south run the full width; east and west keep their own width; CENTER absorbs everything left over, including the whole of any resize. It is the default for a content pane, add with no region means CENTER, and adding two components to one region leaves the first one sized 0 by 0 and invisible.
  • GridLayout(rows, cols) makes equal cells, filled left to right then top to bottom, and stretches each component to fill its cell. A count of 0 means "as many as it takes" in that direction; if the numbers do not match the components you added, the row count wins and the columns are recomputed.
  • A JPanel is a container that is also a component, so it counts as one thing to the container above it while holding many things of its own, under a different layout manager. Every real window is that trick nested a level or two deep: a BorderLayout content pane with panels in the regions that need more than one component.
  • A JButton needs four things: create it, register a listener on it with addActionListener, add it to a container, and write actionPerformed. Forget the registration and the button compiles, draws, presses — and does nothing.
  • ActionListener is an interface in java.awt.event with the single method public void actionPerformed(ActionEvent e). The pattern this course and its exams use is to make the frame its own listener: public class Foo extends JFrame implements ActionListener, with addActionListener(this) at each button.
  • One actionPerformed serves every button, so it must tell them apart: e.getActionCommand() returns the button's label and is compared with .equals, while e.getSource() returns the button object itself and is compared with ==. The action command follows the label if you ever change it; the source never moves, but it needs the buttons to be fields.
  • A listener does not have to be the frame. A separate class must be handed everything it needs through its constructor; an inner class, declared inside the frame, reaches the frame's private fields directly. The inner class is the only option left when the frame's one extends is already spent — which is exactly the case when you want a WindowAdapter.
