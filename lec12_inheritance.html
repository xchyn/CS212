Inheritance

How one class can be built on top of another — the third of the four pillars of object-oriented programming, and the one that finally lets you stop copying code between classes.

Learning Objectives

1."is-a" and "has-a": two ways one class can use another

For the last two lectures you built the parking-ticket system, and every relationship in it had the same shape. A ParkedCar contained a ParkingMeter. A ParkingTicket contained a PoliceOfficer and a ParkedCar. You wrote that relationship by declaring an instance variable whose type was another one of your classes:

public class ParkedCar {
    private String make, model, color, license;
    private ParkingMeter meter;
    // a ParkedCar HAS-A ParkingMeter ... }

That is one of the two ways classes relate to each other, and it is the only one you have had so far. Today we add the other one.

Definition— "has-a" and "is-a"

A "has-a" relationship — also called composition — means one object contains another as a part. A car has a meter. You express it with an instance variable. This is what Lectures 7 and 10–11 were about.

An "is-a" relationship means one class is a more specific kind of another. A square is a rectangle. A savings account is a bank account. You express it with inheritance, and that is what today is about.

Definition— inheritance, superclass, subclass

Inheritance is one of the fundamental principles of object-oriented programming, alongside encapsulation, abstraction and polymorphism. It allows a class to inherit properties and methods from another class, establishing an "is-a" relationship.

  • The superclass (also called the parent class, or the base class) is the class whose features are inherited.
  • The subclass (also called the child class, or the derived class) is the class that inherits those features.

The subclass gets everything the superclass has, without your typing it again, and then adds whatever makes it more specific.

The word "inherit" is doing real work here. When Rectangle inherits from Shape, no code is copied. There is exactly one copy of getArea in the whole program, written once in Shape, and every Rectangle object can use it. If you later fix a bug in getArea, every subclass is fixed at the same instant.

Key Idea— the test that decides which one you need

Read the relationship out loud in English.

If "a Square is a Rectangle" sounds true, you want inheritance.
If "a ParkedCar is a ParkingMeter" sounds absurd — and it does, a car is not a meter, it has one — you want a field.

This sounds too simple to be a real engineering rule. It is a real engineering rule. Almost every bad inheritance hierarchy you will ever meet failed this one sentence.

Quick Check 12.1

For each pair, decide whether the relationship is "is-a" (use inheritance) or "has-a" (use an instance variable), and say what the code would look like.

(a) ParkingTicket and PoliceOfficer, from the parking-ticket system.

has-a. A ticket is not a kind of officer — it records which officer wrote it. So ParkingTicket gets a field: private PoliceOfficer officer;. That is exactly what you wrote in Lecture 11.

(b) SavingsAccount and BankAccount.

is-a. A savings account is a bank account, with an extra interest rate on top. So public class SavingsAccount extends BankAccount. Everything a bank account can do — deposit, withdraw, report its balance — a savings account can do too, unchanged. You will write exactly this class in Practice Problem 1.

(c) Circle and Shape.

is-a. A circle is a shape. public class Circle extends Shape. This is the hierarchy we build for the rest of the lecture.

(d) Circle and double radius.

Neither, and that is the point of including it. radius is not a class at all, it is a plain double. Not every relationship in a program is between two classes; most of the data in your objects is still primitives and Strings.

Things to notice across all four parts. The two mechanisms are not in competition — a realistic program uses both, often in the same class. Your SavingsAccount will be a BankAccount (inheritance) and could perfectly well have a Customer (a field) at the same time. What matters is that you never reach for inheritance just because two classes happen to share a few lines of code. Shared code is not a reason; being a more specific kind of the same thing is.

2.The extends keyword

Definition— extends

extends is the Java keyword that creates an inheritance relationship. It goes in the class header:

public class Subclass extends Superclass { ... }

Read it as "Subclass is a Superclass, plus more". A class may extend exactly one superclass — Java has no multiple inheritance of classes. (C++ does; Java deliberately dropped it, and Lecture 14 shows what replaced it.)

Our running example for this lecture is a small hierarchy of shapes. Here is the superclass. It is an ordinary class of the kind you have been writing since Lecture 7 — two private fields, a constructor, two getters and a toString. Nothing about it announces that it is going to be a superclass, and that is normal: any class can be extended.

Shape.java

public class Shape {
    private final double perimeter;
    private final double area;

    public Shape(double perimeter, double area) {
        this.perimeter = perimeter;
        this.area = area;
    }

    public double getPerimeter() {
        return perimeter;
    }

    public double getArea() {
        return area;
    }

    public String toString() {
        return "Shape with area: " + area + " and perimeter: " + perimeter;
    }
}

The final on those two fields is worth a note in passing, because it comes up again at the end of the lecture.

Definition— the final keyword

final is a non-access modifier that can be applied to variables, methods and classes. It indicates that something cannot be changed or extended further.

  • A final variable can be assigned once and never reassigned. A final instance variable must be given its value by the time the constructor finishes.
  • A final method cannot be overridden by a subclass.
  • A final class cannot be extended at all. String is final, which is why you cannot write class MyString extends String.

Shape's perimeter and area are final because a shape's size never changes after it is built. That is a deliberate design choice, and §7 shows what it buys us.

Now the subclass. A rectangle is a shape, so Rectangle extends Shape. It adds two fields of its own — base and height — and it does not re-declare perimeter or area, because it already has them.

Worked Example— the first subclass

Read the header line first, then the constructor. The line super(2 * base + 2 * height, base * height); is new; it is the subject of §4. For now read it as "run the Shape constructor with these two numbers."

Rectangle.java

public class Rectangle extends Shape {
    private final double base;
    private final double height;

    public Rectangle(double base, double height) {
        super(2 * base + 2 * height, base * height);
        this.base = base;
        this.height = height;
    }

    public double getBase() {
        return base;
    }

    public double getHeight() {
        return height;
    }

    @Override
    public String toString() {
        return "Rectangle with base: " + base + ", height: " + height +
               ", area: " + getArea() + ", perimeter: " + getPerimeter();
    }
}

3.What a subclass inherits — and the access modifiers

"A subclass gets everything" was a useful first approximation. Now the exact rules, because two of the exceptions produce compiler errors that confuse people for an entire semester.

Key Idea— the inheritance rules, precisely

A subclass inherits:

  • every public and protected field and method of its superclass;
  • every package-private field and method, if the subclass is in the same package.

A subclass does not inherit:

  • constructors. Ever. A constructor builds one specific class; it makes no sense to hand it to another. This is why Quick Check 12.2(d) failed.

And the case that trips everyone:

  • A private field is part of the subclass object — the memory is there, the data is real — but the subclass's code cannot name it.

That last point deserves a demonstration, because "the data is there but you cannot touch it" sounds contradictory until you see it.

Worked Example— a private field the subclass cannot reach

Shape stores area in a private field. Rectangle extends Shape, so every Rectangle object contains that area. Here is a Rectangle whose toString tries to print it directly instead of going through getArea(). Does it compile?

Rectangle.java

public class Rectangle extends Shape {
    private final double base;
    private final double height;

    public Rectangle(double base, double height) {
        super(2 * base + 2 * height, base * height);
        this.base = base;
        this.height = height;
    }

    @Override
    public String toString() {
        return "Rectangle with base: " + base + ", height: " + height +
               ", area: " + area;
    }
}
Rectangle.java:14: error: area has private access in Shape ", area: " + area;
^
1 error

Read the message literally: area exists (the compiler found it, in Shape), it simply has private access there. private means "visible inside this class body only", and a subclass is a different class body.

The fix is the one Shape already provides: call the public getter. ", area: " + getArea() compiles, because getArea is public and getArea's own code is inside Shape, where area is visible. That is the version in her notes and the version we use for the rest of the lecture.

This is encapsulation working exactly as designed, not a limitation to route around. The superclass author decided that the outside world — including subclasses — reads area through a method. If you want to relax that, you change the modifier deliberately, and the next box says how.

Definition— protected

protected is the access modifier invented for inheritance. A protected member is visible inside its own class, inside every class in the same package, and inside every subclass — even a subclass in a different package.

It sits between private (nobody else) and public (everybody), and it says: my descendants may use this; strangers may not.

Here is the full table. There are four levels, and the third one has no keyword at all — you get it by writing no modifier, which is why it is easy to produce by accident.

Change Shape's two fields from private final to protected final and the Rectangle above compiles unchanged, printing Rectangle with base: 5.0, height: 4.0, area: 20.0, perimeter: 18.0. Nothing else in the program has to change.

Warning— protected is not free

It is tempting to make every field protected so subclasses never hit that error. Resist it. A protected field is a promise to every future subclass that the field exists with that name and that type, forever — you can no longer rename it, change its type, or compute it on demand without breaking code you may not even be able to see.

The usual advice, and the advice this course follows: keep fields private, give subclasses protected methods when they need privileged access, and use public only for the interface you genuinely want the whole world to call. Notice that her Shape keeps its fields private and hands subclasses getArea() and getPerimeter() instead.

The package-private row is the one you can trip over without meaning to. If Shape declares a field with no modifier at all, a subclass in the same package can read it happily — and the same subclass moved to a different package suddenly cannot:

app/Rectangle.java:11: error: area is not public in Shape; cannot be accessed from outside package return "perimeter " + perimeter + ", area " + area;
^
1 error

The protected field on the same line compiled fine; only the one with no modifier failed. If you ever see "is not public in ...; cannot be accessed from outside package", you have found a field somebody forgot to put a modifier on.

4.super(...) and the constructor chain

You have now written super(...) three times without a definition. Here it is.

Definition— super

The super keyword refers to the superclass part of the current object. It has two distinct uses, and they look different:

  • super(arguments); — written as a statement inside a constructor, calls the superclass constructor. This is §4.
  • super.methodName(arguments) — written anywhere in the class, calls the superclass's version of a method. This is §5.
Procedure— writing a subclass constructor
  1. Decide what the subclass constructor needs from the caller. Square needs one number; Rectangle needs two.
  2. From those parameters, work out what the superclass constructor needs. For Rectangle(base, height) the superclass wants a perimeter and an area, so compute 2 * base + 2 * height and base * height.
  3. Write super(...) with those values as the first statement of the constructor.
  4. Only then assign the subclass's own fields.
Common Mistake— super(...) must come first

It is natural to want to store your own fields before calling up. Java does not allow it:

public Rectangle(double base, double height) {
    this.base = base;
    this.height = height;
    super(2 * base + 2 * height, base * height);
    // too late }
Rectangle.java:8: error: call to super must be first statement in constructor super(2 * base + 2 * height, base * height);
^
1 error

The reason is not arbitrary. Until the superclass constructor has run, the superclass part of the object is not initialized — area and perimeter are still zero. Java refuses to let any of your code run on a half-built object, so it insists the foundation is poured before you start on the walls.

The same rule produces a second, much more confusing error when you forget super(...) altogether. If the superclass has no no-argument constructor, Java's attempt to insert an invisible super() for you fails:

Circle.java:4: error: constructor Shape in class Shape cannot be applied to given types; public Circle(double radius) {
^
  required: double,double
  found:    no arguments
  reason: actual and formal argument lists differ in length
1 error

The caret points at your own constructor's closing parenthesis, and the message talks about "no arguments" even though you passed one. Translate it as: you did not call super(...), so I tried super(), and Shape has no such constructor.

So a subclass constructor always begins by running its superclass's constructor. Apply that rule to Square, which is two levels down, and something worth seeing happens.

StepWhat happens
1new Square(6) enters the Square constructor.
2Its first statement is super(6, 6), so control leaves at once for Rectangle. Nothing in Square's body has run yet.
3Rectangle's first statement is super(24.0, 36.0), so control leaves again for Shape.
4Shape has no explicit super(...), so Java inserts super() — the Object constructor, which does nothing visible. Then Shape's body runs and prints. The chain has reached the top and is now unwinding.
5Control returns to Rectangle, whose body runs and prints.
6Control returns to Square, whose body runs and prints. The object is now complete.

Two things follow from this that are worth writing down.

  • Every object is built top-down. The Object part first, then Shape, then Rectangle, then Square. By the time your constructor body runs, everything you inherited is already initialized — which is precisely why super(...) has to be first.
  • The chain always reaches Object. Even Shape, which extends nothing explicitly, calls a constructor above itself. §7 says what is up there.

Same error as (a), one level down: the inserted super() looks for a no-argument Rectangle constructor and there isn't one. Things to notice across all three parts. Every one of these is the same underlying rule: the superclass part of the object gets built first, no exceptions. If you remember only one sentence from §4, make it that one — all three error messages fall out of it.

5.Overriding, @Override and super.method()

Every class in our hierarchy has a toString, and they are all different. That is not a collision — it is the second big thing inheritance gives you.

Definition— method overriding

Overriding is redefining, in a subclass, a method that was already defined in the superclass. To override a method the subclass version must have:

  • the same name,
  • the same parameter list — same types, same number, same order,
  • a return type that is the same (or a subclass of the original's, which Java calls covariant),
  • access that is not more restrictive than the original's.

When those match, the subclass version replaces the superclass version for objects of the subclass. Recall the search rule from §2: start at the object's class and walk up, stopping at the first match. An override is simply a match found earlier.

You have already seen the effect. Square's toString wins over Rectangle's, which wins over Shape's. What you have not seen is what happens when the match is almost right.

Worked Example— one letter, and the override disappears

Here is Rectangle with a single typo: the method is called toSting, not toString. There is no @Override annotation on it. The class compiles cleanly — javac prints nothing at all.

    }

    public double getBase()   { return base; }

This class of bug is why the annotation exists.

Definition— the @Override annotation

@Override written immediately above a method declaration tells the compiler: I believe this method overrides something in a supertype; please check. It changes nothing at run time. Its entire value is that it turns a silent failure into a compile error.

Add @Override above that misspelled method and the same file stops compiling:

Rectangle.java:11: error: method does not override or implement a method from a supertype @Override
^
1 error

The caret points at the annotation, not at the method name, which reads oddly until you see what it means: you claimed this overrides something, and it does not. Write @Override on every method you intend as an override. It costs nine characters and it catches misspellings, wrong parameter types, and a superclass method somebody renamed last week.

Quick Check 12.5

(a) public String toString(int digits)

(b) protected String toString()

Going the other way is fine: a protected superclass method may be overridden as public. You may widen access, never narrow it.

Does not compile. final on a method means "no subclass may replace this":

Things to notice across all three parts. Only (a) is a silent problem — without @Override it compiles and quietly does nothing useful. (b) and (c) are caught for you regardless. That asymmetry is the argument for writing @Override habitually: it is insurance against exactly the one case the compiler cannot otherwise see.

Overriding replaces the superclass version. Sometimes you want to extend it instead — do what the superclass did, plus something extra. That is the second use of super.

super.method() is how "override to add behavior" is written in Java, and you will use it constantly:

@Override public void withdraw(double amount) {
    super.withdraw(amount);
    // do the normal thing transactionCount++;              // then the extra thing }

One limitation to know: super reaches exactly one level up. From Square you can call super.toString() to get Rectangle's version, but there is no way to write super.super.toString() and reach Shape's. Java does not allow a class to skip past its immediate parent.

6.Overriding is not overloading

The two words look alike, both involve several methods with one name, and they are asked about on every exam. They are unrelated mechanisms.

Definition— overloading, from Lecture 2

Overloading is writing several methods with the same name and different parameter lists in scope at once. System.out.println is overloaded about ten times — one for int, one for double, one for String, one for Object. Overloading needs no inheritance at all; the methods can sit in one class.

Overriding is a subclass supplying its own version of a method with the identical signature. It requires inheritance by definition.

Here is her table of the differences.

AspectOverridingOverloading
DefinitionSame method in subclassSame method name, different parameters
ResolutionRun time (dynamic binding)Compile time (static binding)
InheritanceRequires inheritanceCan be in the same class or a subclass
ParametersMust be the sameMust be different (type, number or order)
Return typeMust be the same or covariantCan be different
Access modifierCannot be more restrictiveCan be different
Key Idea— who decides, and when

Overloading is decided by the compiler, from the declared types in your source. Which of the same-named methods you meant is fixed before the program starts, and the compiler only knows what the variable is declared as.

Overriding is decided while the program runs, from the actual object. Which version of one method runs depends on what the reference really points at.

The two decisions happen at different times, so one program can show both at once — which is exactly what the next example does.

Worked Example— her ShapeProcessor, doing both at once

Quick Check 12.8

Classify each pair of method declarations: overriding, overloading, or neither (a compile error). B extends A in every part.

(a) A has public void draw(int n); B has public void draw(double n).

Overloading. Different parameter types, so B now has two draw methods: the inherited draw(int) and its own draw(double). b.draw(3) calls the inherited int one; b.draw(3.0) calls the new one. Putting @Override on B's version would be a compile error.

(b) A has public void draw(int n); B has public void draw(int count).

Overriding. Parameter names are irrelevant — only the types, count and order form the signature. int n and int count are the same signature, so B's version replaces A's.

(c) A has public String label(); B has public int label().

Neither — a compile error. The signatures are identical (no parameters), so this must be an override attempt, but int is not String and not a subtype of it. Return types are not part of the signature, so this cannot be an overload either. Java reports that label() in B cannot override label() in A because the return type is incompatible.

(d) A has public void draw(int n, String s); B has public void draw(String s, int n).

Overloading. Same types, different order — and order is part of the signature, so these are two distinct methods. b.draw(3, "x") and b.draw("x", 3) go to different places, which is exactly the sort of thing that makes overloaded APIs hard to read.

Things to notice across all four parts. A one-line test settles every one of them: write the parameter types out in order and compare. Identical list means override (then check return type and access); different list means overload; same list with a clashing return type means an error. Names of parameters never matter.

7.Object, the root of everything — and one design question

In §4 the constructor chain kept going after Shape, even though Shape extends nothing. Here is what is above it.

Definition— the Object class

java.lang.Object is the root of the entire class hierarchy. A class that does not say extends anything implicitly extends Object, so every class in Java — yours, the library's, everyone's — has Object as an ancestor.

That means every object you will ever create already has these methods, inherited, before you write a line:

  • toString() — a text description. You met it in Lecture 9.
  • equals(Object other) — equality. Also Lecture 9.
  • hashCode() — an int summary of the object, used by hash-based collections.
  • getClass() — the object's actual class, at run time.
Worked Example— walking the chain to the top

getClass() returns an object describing a class, and that object has a getSuperclass(). Following it repeatedly walks the hierarchy upward until there is nothing left. Triangle here extends Shape and deliberately does not override toString; Badge extends nothing and overrides nothing.

ObjectRoot.java

public class ObjectRoot {
    public static void main(String args[]) {
        Square square = new Square(6);

        Class<?> c = square.getClass();
        while (c != null) {
            System.out.println(c.getName());
            c = c.getSuperclass();
        }

        System.out.println();
        System.out.println(new Triangle(4));
        System.out.println(new Badge(7));
    }
}

Triangle.java

public class Triangle extends Shape {
    private final double side;

    public Triangle(double side) {
        super(3 * side, Math.sqrt(3) / 4 * side * side);
        this.side = side;
    }

    public double getSide() {
        return side;
    }
}

    private final int number;

    public Badge(int number) {

Three things to read out of this output.

  • The chain from Square ends at java.lang.Object, four levels up. Shape never wrote extends Object; Java supplied it.
  • Triangle prints Shape's toString. It did not override it, so the upward search found Shape's first. An equilateral triangle of side 4 has perimeter 12 and area about 6.93, so the inherited method is telling the truth — it just cannot mention the side.
  • Badge prints Badge@66d3c617, which is Object's toString: the class name, an @, and the hash code in hex. Whenever you see that pattern in your own output, it means "this class never overrode toString" — and it is normally a bug you have just caught.
Quick Check 12.9

Suppose you delete the toString method from Square but leave Rectangle's and Shape's alone.

(a) What does System.out.println(new Square(6)); print now?

Rectangle with base: 6.0, height: 6.0, area: 36.0, perimeter: 24.0. The search starts at Square, finds nothing, and stops at the first match one level up. It never reaches Shape's version, and it certainly never reaches Object's.

(b) And if you delete Rectangle's as well?

Shape with area: 36.0 and perimeter: 24.0. Two levels up. The numbers are still right, because they were computed by the super(...) chain when the object was built.

(c) And if you delete Shape's too?

Something of the form Square@1b6d3586 — Object's version, the last stop on the search. The exact digits vary from run to run.

Things to notice across all three parts. There is no such thing as a class without a toString; the only question is how far up the chain the search has to go before it finds one. The same is true of equals and hashCode, and that is why Lecture 9 talked about overriding equals rather than writing it.

One last thing, and it is a design question rather than a syntax rule. Her hierarchy has Square extends Rectangle. That reads perfectly in English — a square is a rectangle — and passes the §1 test. But it is the most famous debatable example in object-oriented design, and it is worth seeing why.

Worked Example— the same hierarchy, made mutable

Suppose Rectangle had setters, as a shape class perfectly well might. Square still extends it and still passes a side length up to both dimensions. Nothing here looks unreasonable.

MutableRectangle.java

public class MutableRectangle {
    private double base;
    private double height;

    public MutableRectangle(double base, double height) {
        this.base = base;
        this.height = height;
    }

    public void setBase(double base)     { this.base = base; }
    public void setHeight(double height) { this.height = height; }

    public double getArea() { return base * height; }

    @Override
    public String toString() {
        return "base " + base + ", height " + height + ", area " + getArea();
    }
}

MutableSquare.java

public class MutableSquare extends MutableRectangle {

    public MutableSquare(double sideLength) {
        super(sideLength, sideLength);
    }
}

DesignDemo.java

public class DesignDemo {
    public static void main(String args[]) {
        MutableSquare square = new MutableSquare(10);
        System.out.println("A square of side 10: " + square);

        MutableRectangle r = square;      // a square is-a rectangle
        r.setBase(6);                     // perfectly reasonable for a rectangle

        System.out.println("After r.setBase(6): " + square);
    }
}

r and square are the same object. What does the second line print?

A square of side 10: base 10.0, height 10.0, area 100.0
After r.setBase(6): base 6.0, height 10.0, area 60.0

The square is no longer square. setBase is a method every MutableRectangle is entitled to, MutableSquare inherited it without thinking about it, and the object is now in a state its own class says is impossible.

The principle being broken has a name — the Liskov substitution principle: anywhere a superclass object is expected, a subclass object should work without surprising anyone. A mutable Square cannot honor setBase, so it is not really substitutable for a mutable Rectangle, however good the English sentence sounds.

Now look again at what her Shape and Rectangle actually do. Every field is private final, there are no setters, and the only way to set a rectangle's dimensions is the constructor. An immutable Square is perfectly substitutable for an immutable Rectangle, because there is no operation that could break it. The design question does not arise. That is not luck — immutability is one of the standard answers to this problem, and this is a good example of a final keyword doing more than it appears to.

Three ways out, for reference: make the classes immutable (what she did); have Square hold a Rectangle as a field instead of extending it (has-a rather than is-a); or drop Square as a class and let a rectangle with equal sides simply be a rectangle.

Quick Check 12.10

Someone proposes fixing MutableSquare by overriding both setters so that each one sets both dimensions:

@Override public void setBase(double base) {
    super.setBase(base);
    super.setHeight(base);
}
@Override public void setHeight(double height) {
    super.setBase(height);
    super.setHeight(height);
}

Does this fix the problem? Argue for or against.

Plan. Ask two questions: does the object stay square, and does code written against MutableRectangle still behave the way that code expects?

It fixes the first problem and creates a second. The object does stay square — r.setBase(6) now yields base 6, height 6, area 36. But consider a method that was written for rectangles and is entirely reasonable:

public static void makeTwiceAsWide(MutableRectangle r) {
    double h = r.getHeight();
    r.setBase(r.getBase() * 2);
    // the caller is entitled to assume the height is still h }

Hand it a MutableSquare and the height silently doubles too. No exception, no error — just a routine that no longer does what its name and its contract say. You have moved the violation from "the object is in an impossible state" to "the object quietly disobeys the superclass's contract", which is harder to find, not easier.

Things to notice. This is the honest answer to the classic interview question, and it is worth internalizing the shape of it: you cannot patch a broken is-a relationship with more overriding. If the subclass cannot honor everything the superclass promises, the relationship itself was wrong. Removing the setters — her design — removes the promise, and then there is nothing to break.

Problem 1 — SavingsAccount extends BankAccount (from CSCI 212 Midterm, Summer 2026)

Assume the class BankAccount below is correctly implemented. Write complete Java code for a class SavingsAccount that inherits from BankAccount.

  • SavingsAccount should have exactly one additional private instance variable interestRate of type double.
  • The constructor should take three parameters: owner, balance and interestRate. It should call the constructor of BankAccount to initialize owner and balance.
  • The class should also have a getInterestRate method and an addInterest method.
  • addInterest should add balance * interestRate to the account by using the inherited deposit method.
  • Override toString so that it returns a String of the form getOwner() + " has savings balance " + getBalance() + " at rate " + interestRate.

BankAccount.java

public class BankAccount {
    private String owner;
    private double balance;

    public BankAccount(String owner, double balance) {
        this.owner = owner;
        this.balance = balance;
    }

    public String getOwner() { return owner; }

    public double getBalance() { return balance; }

    public void deposit(double amount) {
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount <= balance) {
            balance -= amount;
        }
    }

    public String toString() {
        return owner + " has balance " + balance;
    }
}

Plan. Work through the four inheritance decisions in order.

  1. The header. "Inherits from" means extends BankAccount.
  2. The constructor. BankAccount has no no-argument constructor, so the first statement must be super(owner, balance);. Then store interestRate. Forgetting this line is the error that costs the most points on this question.
  3. addInterest. The problem insists you use the inherited deposit, so do not reach for balance — you cannot anyway, it is private in BankAccount. Read the balance with getBalance() and hand the interest to deposit(...).
  4. toString. Same reason: owner and balance are private up there, so build the string from getOwner() and getBalance().

SavingsAccount.java

public class SavingsAccount extends BankAccount {
    private double interestRate;

    public SavingsAccount(String owner, double balance, double interestRate) {
        super(owner, balance);
        this.interestRate = interestRate;
    }

    public double getInterestRate() {
        return interestRate;
    }

    public void addInterest() {
        deposit(getBalance() * interestRate);
    }

    @Override
    public String toString() {
        return getOwner() + " has savings balance " + getBalance()
                          + " at rate " + interestRate;
    }
}

        for (int i = 0; i < times; i++) {
            printInfo();
        }
    }
}

Plan. "Has only one method" is a constraint, not a hint — but a constructor is not a method, and you need one, because Document has no no-argument constructor. So: a constructor that passes the content straight up with super(content), and exactly one method, the overridden printInfo(). content is private in Document, so read it through getContent().

public class FormattedDocument extends Document {

        super(content);
    }

    @Override
    public void printInfo() {
        System.out.println(getContent().toUpperCase());
    }
}

Things to notice. The last three lines are the interesting part. FormattedDocument never overrode printInfo(int) — it inherited Document's version unchanged. That inherited loop calls printInfo(), and because this is a FormattedDocument, the call lands on the override. So a method written in the superclass, months earlier, is now shouting.

That is the mechanism from Quick Check 12.7 line (c), and it is the reason overriding is worth so much more than it looks: every existing call to printInfo() anywhere in the program — including inside the superclass — automatically picks up your new behavior. It is also why overriding a method changes more than you might intend, and why final exists for the cases where you want to forbid it.

If the original exam question's "only one method" is read strictly enough to exclude the constructor too, the class cannot be written at all, since Document has no no-argument constructor to fall back on. The intent is clearly "one method, plus whatever plumbing", and the rubric's answer includes the constructor.

Problem 3 — What is the output? (from Exam 2 Practice Problems)

Consider the following program and the two classes it uses.

Question.java

class A {
    int x = 0;

    public void increment() { x++; }

    public String toString() { return "class A: " + x; }

    public B getB() { return new B(); }
}

class B extends A {
    public String toString() { return "Class B: " + x; }

    public A getA() { return getB(); }
}

public class Question {
    public static void main(String args[]) {
        B b = new B();
        A a = b;
        System.out.println(a);          // line A
        b.increment();
        System.out.println(a);          // line B
        a = new A();
        System.out.println(a.getB());   // line C
        System.out.println(b.getA());   // line D
    }
}

(a) What is the output generated at line A?

Class B: 0. a and b are two references to the same B object — A a = b; copies the reference, not the object. println calls toString, and the search starts at the object's real class, B. B's version wins, with x still 0. The capital C in Class B is B's own spelling; A writes a lowercase class, and that difference is how you tell which one ran.

(b) What is the output generated at line B?

Class B: 1. b.increment() runs A's inherited increment, which does x++ on the one and only x in that object. a sees the change because a is that object.

Note also that B's toString reads x directly. That compiles because x in A is declared with no modifier — package-private — and A and B are in the same file, hence the same package. Had A written private int x = 0;, B's toString would not compile.

(c) What is the output generated at line C?

Class B: 0. Two steps. a = new A(); makes a point at a fresh, plain A. Then a.getB() runs A's getB, which returns new B() — a brand-new B object with x at its default 0. Printing that new B uses B's toString.

The trap is the declared return type. getB is declared to return B, and it does; the fact that it was called on an A changes nothing about the object it hands back.

(d) What is the output generated at line D?

Class B: 0. b.getA() runs B's getA, whose body is return getB(); — the inherited getB, which again returns a fresh B. So although the method is named getA and is declared to return an A, the object it actually returns is a B, with x at 0, and B's toString prints it.

Things to notice across the whole problem. Every line here is decided by the same question: what class is the object, really? Lines A and B answer "a B, which a merely happens to be pointing at". Lines C and D answer "a B, because getB built one, whatever the variable or the return type is called".

The two counters are also worth separating. There is exactly one x per object. The x that reached 1 belongs to the original b; the objects printed at lines C and D are new, so their x is 0. Nothing about inheritance makes fields shared — that would be static, from Lecture 9.

Problem 5 — CheckingAccount, overriding with super (added for these notes)

Using the same BankAccount from Problem 1, write a class CheckingAccount that extends it. It has one additional private field, overdraftFee of type double, a three-parameter constructor, and a getOverdraftFee method. It must override withdraw so that:

  • if the account has enough money, the withdrawal happens normally — and your override must perform it by calling the superclass's withdraw, not by touching the balance itself;
  • otherwise no money is withdrawn, the overdraft fee is taken out of the balance instead, and a message is printed.

Also override toString to return getOwner() + " has checking balance " + getBalance() + " with overdraft fee " + overdraftFee.

Plan. The overriding rules first: same name withdraw, same parameter list (double), same return type void, and access no more restrictive than public. That fixes the signature before you write any logic.

Then the logic. You cannot read balance — it is private in BankAccount — so test with getBalance(). And you must not write balance -= amount, for the same reason; every change to the balance goes through the inherited withdraw or deposit. Charging the fee is itself just a withdrawal, so super.withdraw(overdraftFee) does it.

CheckingAccount.java

public class CheckingAccount extends BankAccount {
    private double overdraftFee;

    public CheckingAccount(String owner, double balance, double overdraftFee) {
        super(owner, balance);
        this.overdraftFee = overdraftFee;
    }

    public double getOverdraftFee() {
        return overdraftFee;
    }

    @Override
    public void withdraw(double amount) {
        if (amount <= getBalance()) {
            super.withdraw(amount);
        } else {
            super.withdraw(overdraftFee);
            System.out.println("Declined. Overdraft fee of " + overdraftFee + " charged.");
        }
    }

    @Override
    public String toString() {
        return getOwner() + " has checking balance " + getBalance()
                          + " with overdraft fee " + overdraftFee;
    }
}

CheckingTest.java

public class CheckingTest {
    public static void main(String args[]) {
        CheckingAccount checking = new CheckingAccount("Ana", 200.0, 35.0);
        System.out.println(checking);

        checking.withdraw(50.0);
        System.out.println(checking);

        checking.withdraw(500.0);
        System.out.println(checking);
    }
}
Ana has checking balance 200.0 with overdraft fee 35.0
Ana has checking balance 150.0 with overdraft fee 35.0
Declined. Overdraft fee of 35.0 charged.
Ana has checking balance 115.0 with overdraft fee 35.0

Things to notice. super.withdraw(amount) and plain withdraw(amount) are completely different here. The plain call would mean this.withdraw(amount), which is the method you are currently inside — infinite recursion and a StackOverflowError. Any time an override calls "the normal version", it must say super.

The if test is deliberately duplicated: CheckingAccount checks amount <= getBalance() and then BankAccount.withdraw checks it again. That is a little wasteful and completely safe. The alternative — calling super.withdraw(amount) unconditionally and inspecting the balance afterwards to see whether it worked — is worse, because it depends on a detail of the superclass that its author never promised.

Finally, note that CheckingAccount and SavingsAccount are siblings: both extend BankAccount, neither knows about the other, and each changes exactly the behavior it needs to. That is the shape a healthy hierarchy has.

Lecture Summary
  • Inheritance models an "is-a" relationship; a field models "has-a". Say the sentence out loud before you choose.
  • class Sub extends Super gives Sub everything Super has, transitively, all the way up. One superclass only — Java has no multiple inheritance of classes.
  • A subclass inherits public and protected members (and package-private ones in the same package). It does not inherit constructors, and it cannot name a private field even though that field is part of its objects.
  • Four access levels: private, package-private (no keyword), protected, public. protected exists for subclasses — but prefer private fields plus getters, which is what her Shape does.
  • super(...) calls the superclass constructor and must be the first statement. Constructors run top-down: Object first, your class last. Omit super(...) and Java inserts super(), which fails loudly if the superclass has no no-argument constructor.
  • A method is overridden when a subclass declares the same name, the same parameter list, a compatible return type and access no more restrictive. Write @Override — it turns a silent typo into a compile error. Use super.method() to extend the superclass version rather than replace it.
  • Overloading is different parameter lists, chosen by the compiler from the declared types. Overriding is the identical signature, chosen while the program runs from the actual object. displayType(polyShape1) says "shape" while println(polyShape1) prints a rectangle — same variable, different mechanism.
  • Every class extends Object in the end, which is why every object already has toString, equals, hashCode and getClass. A printout like Badge@66d3c617 means nobody overrode toString.
