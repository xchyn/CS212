1.Why a collection hands out an iterator

Two lectures ago you built a LinkedList out of Node objects, and last time you made it generic so it could hold anything. Both times, walking the list looked like this:

Node<T> n = head;
while (n != null) {
    System.out.println(n.getData());
    n = n.getNext();
}

That loop works, but look at what it needs to know. It needs to know there is a field called head. It needs to know the elements live in objects called Node. It needs to know the way to step forward is getNext(), and that the end is marked by null. Every one of those is an internal detail of how the list is built — and every caller who writes that loop is now welded to those details. Change the class from a singly linked list to a doubly linked list, or to an array underneath, and every one of those loops breaks.

Now compare it with the loop you have been writing since Lecture 6 for an ArrayList:

for (int i = 0; i < list.size(); i++) {
    System.out.println(list.get(i));
}

Different loop, different vocabulary, same intention. And on a linked list this second form is not just different — it is a disaster, which we will measure in §6.

Key Idea— the problem an iterator solves

Walking a collection is one idea. But every kind of collection stores its elements differently, so every kind of collection would otherwise need its own kind of loop, and every piece of code that walks a collection would be locked to one implementation.

The fix is to make walking into an object. The collection builds that object and hands it to you. It knows how to get from one element to the next; you do not, and you do not need to.

Definition— iterator

An iterator is an object that lets you traverse a collection of objects, one element at a time, without exposing how that collection stores them.

The four things an iterator buys you, in your instructor's words:

  • a uniform way to access the elements of different collections;
  • the underlying implementation of the collection stays hidden;
  • you can traverse a collection without modifying it;
  • the operations you need are just hasNext() and next().

The word for this arrangement is the iterator pattern: a way to reach the elements of some aggregate object in sequence without exposing its underlying representation. You have met the idea before under other names. A Scanner is essentially an iterator over the tokens of an input stream: hasNextInt() and nextInt() are hasNext() and next() wearing a different hat.

Quick Check 23.1

Your LinkedList class currently gives callers a getHead() method, and callers use it to walk the list with getNext().

(a) Name one thing you can no longer safely change about LinkedList once callers are doing that.

Anything about the storage. You cannot switch to a doubly linked list with a different Node class, you cannot add a dummy header node, and you certainly cannot re-implement the list on top of an array — every caller's loop names Node, getNext() and null directly, so all of them would stop compiling.

There is a second cost that is easier to miss: getHead() hands out a reference to your internal node. A caller can call setData or setNext on it and quietly corrupt your list. That is the encapsulation lesson from Lecture 7 all over again.

(b) If instead the class hands out an iterator, what exactly does the caller now know about the list?

Only two things: whether there is another element, and what it is. That is the whole contract. The caller does not know whether the elements sit in nodes, in an array, in a file, or are computed on demand — and because it does not know, you are free to change any of that later without breaking a single line of caller code.

Things to notice across both parts. This is the same trade you made when you made instance variables private and added getters. An iterator is a getter for traversal: the smallest possible public window onto a private structure.

2.The Iterator interface

Java does not leave "what an iterator looks like" up to each collection. It is fixed by an interface in java.util, and it has exactly three methods.

Definition— the Iterator interface
public interface Iterator<E> {
    boolean hasNext();     // true if the iteration has more elements
    E       next();        // return the next element in the iteration
    void    remove();      // remove the last element returned  (optional)
}
  • hasNext() asks a question and changes nothing. You may call it as many times as you like.
  • next() returns the next element and advances. Calling it twice gives you two different elements. This is the one that must be handled with care on an exam.
  • remove() deletes the element that next() most recently returned. It is marked optional, which has a precise meaning we come back to in §6.

The E is a type parameter, exactly as in Lecture 22: an Iterator<String> returns a String from next(), an Iterator<Integer> returns an Integer, and no cast is needed anywhere.

Every collection in the Java library will hand you one of these when you ask, by calling its iterator() method. That gives the standard loop, and it is worth memorizing as a shape:

Procedure— the standard iterator loop
Iterator<E> it = collection.iterator();   // 1. ask the collection for a walker
while (it.hasNext()) {                    // 2. is there another element?
    E element = it.next();                // 3. take it, and advance
    // process element                    // 4. do the work
}
  1. Ask the collection for an iterator. The iterator starts before the first element.
  2. Test hasNext() in the loop condition.
  3. Call next() exactly once per iteration, and store what it gives you.
  4. Use the stored value as many times as you want.

Step 3 is where marks are lost. it.next() is not a variable you can read repeatedly; it is a request that consumes an element.

Worked Example— the even numbers in a list

This is your instructor's first iterator example. Arrays.asList wraps an array in a List so we have a collection to iterate; then the loop is exactly the shape above.

Before you open the toggle: how many lines does this print, and what is on them?

Example1.java

import java.util.Arrays;
import java.util.Iterator;
import java.util.List;

public class Example1 {
   public static void main(String args[]) {
      Integer a[] = {3, 1, 4, 1, 5, 9, 2, 6};
      List<Integer> l = Arrays.asList(a);
      Iterator<Integer> x = l.iterator();
      System.out.println("The even numbers in your list are: ");
      while (x.hasNext()) {
         int i = x.next();
         if (i % 2 == 0) System.out.print(i + " ");
      }
      System.out.println();
   }
}
The even numbers in your list are:
4 2 6

Two lines. The first is a println, so it ends immediately; the evens are then printed with print onto a single second line, which the final println() closes.

Three details are worth pulling out of this small program.

  • int i = x.next(); — next() returns an Integer, and it is assigned to an int. That is auto-unboxing, from Lecture 6. It also shows the payoff of generics: because l is a List<Integer>, x is an Iterator<Integer> and next() is already typed. Without generics you would be writing int i = ((Integer) x.next()).intValue();.
  • next() is called once per iteration, and its value is stored in i. The if then tests i, not x.next(). Had the condition been if (x.next() % 2 == 0) the loop would consume two elements per pass and fall off the end.
  • The array is untouched. Iterating reads; it does not consume the collection. After the loop, l still holds all eight numbers.
Quick Check 23.2

Let list be an ArrayList<String> holding a, b, c and let Iterator<String> it = list.iterator();. Give the output of each fragment, or say what goes wrong.

(a) System.out.println(it.next() + it.next());

ab. Both calls happen, left to right, and each one advances. The + then concatenates the two different elements. This is the single most common exam trick with iterators, and it is why you assign next() to a variable when you mean to use one element twice.

(b) while (it.hasNext()) System.out.print(it.next() + it.next());

It prints ab and then throws. First pass: hasNext() is true, and the two next() calls take a and b, printing ab. Second pass: hasNext() is still true, because c is left. The first next() returns c; the second has nothing to return and throws a NoSuchElementException, which nothing catches, so the program stops.

Note carefully that nothing is printed on the second pass. The whole expression it.next() + it.next() has to be evaluated before print is called, and the evaluation threw partway through.

(c) System.out.println(it.hasNext() + " " + it.hasNext() + " " + it.hasNext());

true true true. hasNext() is a pure question — it does not advance anything, so asking it three times in a row gives the same answer three times.

Things to notice across all three parts. The whole of iterator arithmetic on an exam comes down to one rule: count the next() calls, not the iterations. Put a tick mark on the page for every next() you see in the loop body, and walk the collection that many elements at a time. Parts (a) and (b) are two next() calls per pass; part (c) is none.

Common Mistake— calling next() once too often

hasNext() promises that one more element exists. It says nothing about two. A loop written like this is wrong on any collection with an odd number of elements:

while (it.hasNext()) {
    System.out.println(it.next() + " and " + it.next());   // two per pass, one guarantee
}

On a three-element list holding a, b, c it prints one line and then throws:

a and b
Exception in thread "main" java.util.NoSuchElementException
	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1052)
	at PairLoop.main(PairLoop.java:10)

If you genuinely want to consume elements in pairs, you must check again in the middle: if (it.hasNext()) before the second next(). Your instructor's exam questions deliberately put two next() calls in one loop body and then ask what happens — see the Practice Problems.

3.Iterable: one loop for every collection

Iterator describes the walker. There is a second, even smaller interface that describes "a thing that can produce a walker".

Definition— the Iterable interface
public interface Iterable<T> {
    Iterator<T> iterator();
}

One method. A class that implements Iterable<T> promises it can hand out an Iterator<T> on request.

Iterable is the root interface for everything that can be iterated over. ArrayList, LinkedList, Stack, HashSet — all of them implement it, which is exactly why they all answer to .iterator(). And any class of your own can implement it too.

Key Idea— two interfaces, two jobs

Iterable is the collection side: "I can be walked." Iterator is the walker: "I am partway through walking something." A collection is an Iterable and hands out Iterators — possibly several at once, all independent of each other.

Mixing the two up is the most common error on this topic. list.hasNext() does not compile; it.iterator() does not compile either.

Here is why the distinction earns its keep. Once you write a method whose parameter type is Iterable<T>, that one method works on every collection in the library at once — and on every class you ever write that implements the interface.

Worked Example— one method, every collection

This is your instructor's Example2. The print method knows nothing at all about stacks or lists: it takes an Iterable<T>, asks it for an iterator, and walks.

Example2.java

import java.util.ArrayList;
import java.util.Iterator;
import java.util.Stack;

public class Example2 {
   public static <T> void print(Iterable<T> x) {
      Iterator<T> it = x.iterator();
      while (it.hasNext()) {
         System.out.print(it.next() + " ");
      }
      System.out.println();
   }

   public static void main(String args[]) {
      Stack<String> s = new Stack<>();
      ArrayList<Integer> l = new ArrayList<>();
      int array[] = {3, 1, 4, 1, 5, 2, 6};
      for (int i = 0; i < array.length; i++) {
         s.push("array[" + i + "] = " + array[i] + ", ");
         l.add(array[i]);
      }
      print(l);
      print(s);
      System.out.println(s.pop());
   }
}

Two questions before you reveal. First, in what order does the stack print — the order things were pushed, or the order they would pop? Second, after print(s) has walked the whole stack, what is left on it?

3 1 4 1 5 2 6
array[0] = 3,  array[1] = 1,  array[2] = 4,  array[3] = 1,  array[4] = 5,  array[5] = 2,  array[6] = 6,
array[6] = 6,

The stack iterates bottom to top — array[0] first — which is the opposite of pop order. That surprises nearly everyone. java.util.Stack extends java.util.Vector, and it inherits Vector's iterator, which walks index 0 upward. Pushing adds at the end, so the first thing pushed is index 0 and comes out of the iterator first. Remember this: iterating a Stack is not popping it. It is worth two points on the final.

And the stack is still full. The last line pops and gets array[6] = 6, — the top, the last thing pushed. Iteration reads; it does not consume.

Notice also the double spaces in the middle line. Each pushed string already ends with ", ", and print adds " " after every element, so you get both. That is not a typo in the notes; it is what the program really prints.

4.The for-each loop is an iterator in disguise

You have been writing for (String s : list) since Lecture 6 without being told what it is. Now you can be told, and it is the payoff of the whole lecture.

Key Idea— what the compiler does with a for-each loop

The enhanced for loop is not a separate kind of loop. The compiler rewrites

for (String s : list) {
    body(s);
}

into exactly this:

Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    body(s);
}

That is the entire feature. It is a shorthand for the standard iterator loop — which is why it works on anything that implements Iterable, including a class you wrote yourself, and why it cannot work on anything that does not.

You do not have to take that on faith. Here is a small Iterable whose iterator(), hasNext() and next() each announce themselves, walked by a plain for-each loop. It is built on the same generic Node<T> from Lecture 22 — shown here trimmed to just the constructor and the two getters these classes actually use.

Worked Example— watching the for-each loop call the iterator

TracedList is a stripped-down linked list; TracedIterator is its walker. Both print a bracketed note every time one of their methods runs. Then main does nothing but a for-each loop over three elements.

Node.java

public class Node<T> {
    private T data;
    private Node<T> next;

    public Node(T d, Node<T> n) {
        data = d;
        next = n;
    }

    public T getData() { return data; }
    public Node<T> getNext() { return next; }
}

TracedIterator.java

import java.util.Iterator;
import java.util.NoSuchElementException;

public class TracedIterator<T> implements Iterator<T> {
    private Node<T> current;

    public TracedIterator(Node<T> head) { this.current = head; }

    public boolean hasNext() {
        System.out.println("      [hasNext() -> " + (current != null) + "]");
        return current != null;
    }

    public T next() {
        if (current == null) throw new NoSuchElementException();
        T data = current.getData();
        current = current.getNext();
        System.out.println("      [next() -> " + data + "]");
        return data;
    }
}

TracedList.java

import java.util.Iterator;

public class TracedList<T> implements Iterable<T> {
    private Node<T> head;

    public void addFirst(T item) { head = new Node<>(item, head); }

    public Iterator<T> iterator() {
        System.out.println("      [iterator() called]");
        return new TracedIterator<T>(head);
    }

    public static void main(String[] args) {
        TracedList<String> list = new TracedList<>();
        list.addFirst("gamma");
        list.addFirst("beta");
        list.addFirst("alpha");

        System.out.println("The for-each loop:");
        for (String w : list) {
            System.out.println("   body sees: " + w);
        }
    }
}

The for-each loop in main mentions none of these methods. Before you reveal: how many times will iterator() run, and how many times will hasNext() run?

The for-each loop:
      [iterator() called]
      [hasNext() -> true]
      [next() -> alpha]
   body sees: alpha
      [hasNext() -> true]
      [next() -> beta]
   body sees: beta
      [hasNext() -> true]
      [next() -> gamma]
   body sees: gamma
      [hasNext() -> false]

iterator() runs once, at the top. hasNext() runs four times for three elements — three times to say yes and once to say no. That final false is what ends the loop.

Read the trace against the rewrite in the Key Idea box and they match line for line: iterator(), then repeatedly hasNext() / next() / body, then a last hasNext(). Nothing else is going on. The for-each loop is sugar, and this is the sugar dissolved.

One consequence you can now predict: a for-each loop gives you no index and no handle on the collection. There is no i, and the loop variable w is a fresh local copy of the reference each time. Assigning to w inside the body changes nothing in the list, because the rewrite makes w a local variable initialized from next().

Two footnotes to the rewrite, both of which show up on exams.

Common Mistake— an iterator() method is not enough

The rewrite is triggered by the type of the thing after the colon, not by whether it happens to have a suitable method. This class has a perfectly good iterator() method, but forgot implements Iterable<T>:

public class Bag<T> {                      // <-- no "implements Iterable<T>"
    private Node<T> head;
    public void addFirst(T item) { head = new Node<>(item, head); }
    public Iterator<T> iterator() { return new LinkedListIterator<T>(head); }
}
Bag.java:12: error: for-each not applicable to expression type
        for (String s : b) System.out.print(s + " ");
                        ^
  required: array or java.lang.Iterable
  found:    Bag<String>

Read the required: line — it tells you the whole rule. Add implements Iterable<T> to the class header and the identical code compiles and runs.

Definition— the array special case

Arrays do not implement Iterable — you saw the compiler say so in Quick Check 23.3. Yet for (int i : array) works.

That is because the enhanced for loop has a second, separate rewrite for arrays: over an array it becomes an ordinary indexed for loop with a hidden counter, no iterator object involved at all. One piece of syntax, two rewrites, chosen by the type. The required: line in the error message above names both: array or java.lang.Iterable.

Worked Example— the same loop over an array, a list and a stack

Your instructor's Example3 uses all three in eight lines. The loop bodies differ; the loop syntax does not.

import java.util.Stack;

public class Example3 {
   public static void main(String args[]) {
      Stack<String> s = new Stack<>();
      ArrayList<Integer> l = new ArrayList<>();
      int array[] = {3, 1, 4, 1, 5, 2, 6};

      // Using for-each loop with array

      for (int i : l) System.out.print(i + " ");

Before you reveal: the stack was pushed in the order 3, 1, 4, 1, 5, 2, 6. What order does the last loop print?

3 1 4 1 5 2 6
3, 1, 4, 1, 5, 2, 6,

The same order, not the reverse. This is the point from §3 again, and it is worth seeing twice: a for-each over a Stack walks it bottom to top, because it uses the stack's iterator, and Stack inherits Vector's bottom-to-top iterator. If you want pop order you must actually pop.

Note the loop variable types too. for (int i : l) over an ArrayList<Integer> unboxes each element into an int; for (String i : s) over a Stack<String> needs String. Writing for (int i : s) would not compile — the element type of the collection has to be assignable to the loop variable.

Quick Check 23.5

A Stack<String> has red, blue, green pushed onto it in that order.

(a) What does for (String c : s) System.out.print(c + " "); print?

5.Writing your own iterator

Everything so far has used iterators the library already wrote. Now write one. The exercise at the end of your instructor's notes is exactly this: implement an iterable LinkedList, using the generic Node<T> you already have.

It takes two classes, and between them they are about twenty lines.

Procedure— making one of your classes iterable
  1. Write a class XIterator<T> implements Iterator<T>. Give it one field: a cursor that remembers where the walk has reached. For a linked list that is a Node<T> current.
  2. Its constructor takes whatever the walk should start from — here, the head node.
  3. hasNext() returns whether the cursor still points at something: current != null.
  4. next() does three things in this order: check there is something (throw if not), save the current element, advance the cursor, and return the saved element.
  5. Make the collection class say implements Iterable<T> and add public Iterator<T> iterator() { return new XIterator<>(head); }.

Step 4's order matters. You must read the data before you move the cursor, or you will return the wrong element — and you must move it before you return, or the iterator never advances and hasNext() is true forever.

Worked Example— an iterable LinkedList

Here is your instructor's solution to the exercise, complete and compilable. Node<T> is the generic node from Lecture 22; LinkedListIterator is the walker; LinkedList is a small list that implements Iterable<T> by handing one out.

LinkedListIterator.java

import java.util.Iterator;
import java.util.NoSuchElementException;

public class LinkedListIterator<T> implements Iterator<T> {
    private Node<T> current;

    public LinkedListIterator(Node<T> head) { this.current = head; }

    @Override
    public boolean hasNext() { return current != null; }

    @Override
    public T next() {
        if (!hasNext()) {
            throw new NoSuchElementException();
        }
        T data = current.getData();
        current = current.getNext();
        return data;
    }
}

LinkedList.java

import java.util.Iterator;

public class LinkedList<T> implements Iterable<T> {
    private Node<T> head;
    private int size;

    public LinkedList() {
        head = null;
        size = 0;
    }

    public void addFirst(T item) {
        head = new Node<>(item, head);
        size++;
    }

    public int size() { return size; }

    public Node<T> getHead() { return head; }

    // Implementation of the iterator() method required by Iterable
    @Override
    public Iterator<T> iterator() {
        return new LinkedListIterator<>(head);
    }
}

And the driver, which walks the same list twice — once with the iterator by hand, once with a for-each loop that has no idea any of this exists. Note that addFirst puts each new item at the head, so the list ends up in the reverse of the order the calls were made.

Two remarks on the driver's third line. The cast (LinkedListIterator<String>) list.iterator() is legal but unnecessary — iterator() is declared to return Iterator<String>, and every method the loop uses is declared there. The @Override annotations are optional but worth writing. They ask the compiler to check that the method really does override something; misspell hasNext as hasnext and you get an error instead of a class that silently fails to implement the interface.

Quick Check 23.6

Each of these three versions of next() is wrong. Say what goes wrong when it runs.

(a) public T next() { current = current.getNext(); return current.getData(); }

It advances first and then reads, so it skips the first element entirely and reads one element too far at the end. On the two-element list holding Hello then World it returns World and then, on the second call, throws a NullPointerException when it calls getData() on null.

Read data first, then advance. That is the whole of step 4 in the Procedure box.

(b) public T next() { return current.getData(); }

It never advances the cursor. hasNext() is true forever, so a while (it.hasNext()) loop prints the first element over and over and never terminates — an infinite loop that produces infinite output.

This is the most common bug when writing your first iterator, and it is easy to spot: if next() does not assign to the cursor field, it is wrong.

(c) public T next() { T d = current.getData(); current = current.getNext(); return d; } — correct order, but with the if (!hasNext()) throw ... line deleted.

It works perfectly for every call that should succeed, and then throws a NullPointerException instead of a NoSuchElementException on the call that should fail. The program still stops, but the message now blames a null reference rather than saying "you asked for an element that does not exist".

Things to notice across all three parts. The guard is not there to make the code work; it is there to make the failure legible. A NullPointerException sends the reader hunting for which reference was null. NoSuchElementException names the actual mistake, and it is the exception the Iterator documentation promises, so code that catches it will keep working with your class.

Quick Check 23.7

Write a class Range that implements Iterable<Integer> so that for (int k : new Range(1, 6)) prints 1 2 3 4 5 — the low end included, the high end excluded. Nothing is stored: the iterator counts. Give both the Range class and the iterator class it uses.

RangeIterator.java

import java.util.Iterator;
import java.util.NoSuchElementException;

public class RangeIterator implements Iterator<Integer> {
    private int cursor, hi;

    public RangeIterator(int lo, int hi) {
        this.cursor = lo;
        this.hi = hi;
    }

    public boolean hasNext() { return cursor < hi; }

    public Integer next() {
        if (!hasNext()) throw new NoSuchElementException();
        return cursor++;
    }
}

6.Two iterators, remove(), and the modification trap

Three loose ends, and all three appear on the final.

Iterators are independent objects

Nothing stops you from asking one collection for two iterators. You get two separate objects, each with its own cursor, neither aware of the other.

Worked Example— two walkers, one list

Predict all six lines before you reveal — especially the first.

TwoIterators.java

import java.util.ArrayList;
import java.util.Iterator;

public class TwoIterators {
    public static void main(String[] args) {
        ArrayList<String> list = new ArrayList<>();
        list.add("a"); list.add("b"); list.add("c");

        Iterator<String> y = list.iterator();
        Iterator<String> z = list.iterator();

        System.out.println("y == z ? " + (y == z));
        System.out.println("y.next() -> " + y.next());
        System.out.println("y.next() -> " + y.next());
        System.out.println("z.next() -> " + z.next());
        System.out.println("y still has more? " + y.hasNext());
        System.out.println("z still has more? " + z.hasNext());

y.next() -> a

y == z is false. Each call to iterator() executes a new, so you get two distinct objects — the reference comparison from Lecture 8, applied to iterators. This exact line is on both of your instructor's finals.

y has consumed a and b; z has consumed only a. Advancing one has no effect at all on the other. Both still report more to come, because y has c left and z has b and c left.

The practical use of this is walking a collection twice at the same time, for instance to compare every element against every other. The exam use of it is simpler: a question hands you two iterators over the same list, drains one at a different rate from the other, and asks what each prints.

remove() is optional — and that is a technical term

The third method of Iterator deletes the element next() most recently returned. Because it is declared with a default implementation in the interface, a class may simply not provide one.

Definition— an optional operation

An optional operation is a method an interface declares, but which an implementing class is permitted to refuse. The refusal is not a compile error — the method exists and can be called — it is a run-time UnsupportedOperationException.

The LinkedListIterator above never mentions remove, so it inherits the interface's default, and the default throws. A fixed-size list such as the one Arrays.asList returns behaves the same way, because there is nothing it could remove an element from.

Worked Example— what an unimplemented remove() does

Both remove() calls here are wrapped in a try so the program survives them and we can see both messages.

OptionalRemove.java

import java.util.Arrays;
import java.util.Iterator;
import java.util.List;

public class OptionalRemove {
    public static void main(String[] args) {
        LinkedList<String> mine = new LinkedList<>();
        mine.addFirst("World");
        mine.addFirst("Hello");
        Iterator<String> it = mine.iterator();
        it.next();
        try {
            it.remove();
        } catch (UnsupportedOperationException e) {
            System.out.println("our LinkedListIterator: " + e);
        }

        Integer a[] = {3, 1, 4};
        List<Integer> fixed = Arrays.asList(a);
        Iterator<Integer> jt = fixed.iterator();

Both refuse, for different reasons. Ours refuses because nobody wrote the method. Arrays.asList refuses because it is a fixed-size view onto an array — you can set an element through it, but you cannot change its length, and removing would.

UnsupportedOperationException is unchecked, so neither call is a compile error. That is the price of "optional": the compiler cannot help you, and you have to know which collections support which operations. An ArrayList iterator supports remove and is the case you will actually use.

Modifying a collection while you iterate it

The definition in §1 said an iterator lets you traverse a collection without modifying it. That is not just a description of good manners; the library enforces it.

It never gets there. The removal succeeds, and then the next call to next() notices and throws.

How it notices: an ArrayList keeps a private counter of how many structural changes have been made to it. When it hands out an iterator, the iterator copies that number. Every call to next() compares its copy against the list's current value, and if they differ, the list was changed behind the iterator's back and the iterator refuses to continue. That is the method named checkForComodification in the stack trace.

Definition— ConcurrentModificationException

A ConcurrentModificationException is thrown when a collection is structurally modified — an element added or removed — while an iterator over it is still in use. "Concurrent" here does not mean threads; a single thread doing both things is the usual cause.

It is unchecked, so nothing forces you to catch it, and you should not want to: it is telling you the loop is wrong, not that the data is unusual.

Warning— the version that does not throw is worse

The check is not perfect. hasNext() on an ArrayList iterator is simply cursor != size, and it does not compare the modification counts. So if you remove the second-to-last element, the size drops to equal the cursor, hasNext() says false, the loop ends early, and next() never gets the chance to complain:

ArrayList<String> a = new ArrayList<>();
a.add("Ann"); a.add("Bob"); a.add("Cal"); a.add("Dee");
for (String n : a) {
    if (n.equals("Cal")) a.remove(n);      // Cal is second-to-last
}
System.out.println("no exception. list is now " + a);
no exception. list is now [Ann, Bob, Dee]

This looks like it worked, and on this input it did. But Dee was silently never visited. Change the list slightly and you get either a skipped element or an exception, essentially at random. Do not modify a collection inside a for-each loop over it — not because it always throws, but because it sometimes does not.

Worked Example— the safe way, with Iterator.remove()

remove() exists precisely for this. Because the deletion goes through the iterator, the iterator updates its own bookkeeping and the traversal stays valid. There is no for-each form of this — you need the explicit iterator, because you need to name it.

SafeRemove.java

import java.util.ArrayList;
import java.util.Iterator;

public class SafeRemove {
    public static void main(String[] args) {
        ArrayList<String> b = new ArrayList<>();
        b.add("Ann"); b.add("Bob"); b.add("Cal"); b.add("Dee");

        Iterator<String> it = b.iterator();
        while (it.hasNext()) {
            String n = it.next();
            if (n.startsWith("B") || n.startsWith("C")) it.remove();
        }
        System.out.println("list is now " + b);
    }
}
list is now [Ann, Dee]

Two elements removed in one pass, no exception, nothing skipped. Note the shape: call next(), look at what you got, and only then call it.remove() — remove() deletes the element the most recent next() returned, so calling it before any next(), or twice in a row, throws an IllegalStateException.

This is the one situation where the explicit iterator loop is not merely equivalent to a for-each loop but strictly better. Remember it as the answer to "how do I delete some elements of a list while I am looking at them".

Why an iterator is the only sane way to walk a linked structure

One last argument, and it is a measurable one. On an ArrayList, get(i) jumps straight to a slot — the index-based loop is fine. On a linked list, get(i) has to start at the head and follow i links, so the index-based loop restarts the walk from the beginning on every iteration. Walking n elements does about n2/2 link-follows instead of n.

Worked Example— the same walk, two ways, timed

Fifty thousand elements in a java.util.LinkedList, summed twice. Same answer both times; the only difference is how the walk is done.

WalkCost.java

import java.util.Iterator;

public class WalkCost {
    public static void main(String[] args) {
        java.util.LinkedList<Integer> list = new java.util.LinkedList<>();
        for (int i = 0; i < 50000; i++) list.add(i);

        long start = System.currentTimeMillis();
        long sum = 0;
        for (int i = 0; i < list.size(); i++) sum += list.get(i);
        long indexed = System.currentTimeMillis() - start;

        start = System.currentTimeMillis();
        long sum2 = 0;
        Iterator<Integer> it = list.iterator();
        while (it.hasNext()) sum2 += it.next();
        long walked = System.currentTimeMillis() - start;

        System.out.println("both sums agree: " + (sum == sum2));
        System.out.println("index-based for loop: " + indexed + " ms");
        System.out.println("iterator:             " + walked + " ms");
    }
}

Guess the ratio before you look. Timings depend on the machine, so the exact numbers below are one run on one computer and yours will differ — but the shape of the answer will not.

both sums agree: true
index-based for loop: 908 ms
iterator:             2 ms

Roughly four hundred times slower, for a loop that looks perfectly innocent. Three consecutive runs on the same machine gave 908, 820 and 899 ms for the indexed loop against 2, 4 and 2 ms for the iterator, so this is not measurement noise.

The reason is entirely structural. list.get(30000) follows thirty thousand getNext() links, and the loop asks for get(0), get(1), get(2) and so on, redoing the whole walk each time. The iterator keeps its cursor between calls, so each next() is one link.

This is the practical reason the iterator exists. The encapsulation argument in §1 is the reason a designer cares. This is the reason your program cares. Any time the collection might be a linked structure, walk it with an iterator or a for-each loop — never with an index.

Quick Check 23.9

Things to notice across all three parts. This is why the choice of loop is a real decision and not a style preference. If you write the for-each loop you are correct on every collection; if you write the indexed loop you are correct only on the ones that support fast random access, and nothing warns you when you are not.

7.A look at threads: start, sleep, join

Every program you have written this semester does one thing at a time. Statement follows statement; a method call runs to completion before the caller continues. That single line of execution has a name.

Definition— thread, multithreading

A thread is a single path of execution through a program — a lightweight sub-process, the smallest unit the operating system schedules. Your programs so far have had one, called main.

Multithreading is running several threads at once inside one program, so that two or more parts of it make progress concurrently.

Why you would want it: better use of a multi-core processor, better use of time that would otherwise be spent waiting on a disk or a network, an interface that stays responsive while a long job runs, and a simpler structure for problems that really are several activities at once.

What it costs: synchronization problems, deadlocks, race conditions, and debugging that is genuinely hard because the bug may not reproduce.

Java gives you two ways to make a thread, and your instructor's notes list both.

Procedure— two ways to create a thread

Extend Thread.

  1. Write a class that extends Thread.
  2. Override run() with the work the thread should do.
  3. Create an object of the class and call start() on it.

Implement Runnable.

  1. Write a class that implements Runnable.
  2. Implement run().
  3. Wrap it: Thread t = new Thread(myRunnable);
  4. Call t.start().

The second is usually preferred, for the reason you learned in Lecture 14: Java has single inheritance, so extends Thread uses up your one superclass slot, while implements Runnable leaves the class free to extend something else. Runnable is an interface with exactly one method, void run().

Common Mistake— calling run() instead of start()

run() is an ordinary method. If you call it, it runs like any other method call, on whatever thread you were already on. No new thread is created.

start() is the one that asks the JVM for a new thread and arranges for run() to be executed on it. Calling run() yourself compiles cleanly, produces plausible-looking output, and gives you a completely single-threaded program.

Worked Example— run() versus start(), and who is executing

This output was the same on every run, because there is nothing left in main to race against Worker-B. The moment two threads have work to do at the same time, that stops being true — which is the whole of the next example.

The constructor calls super(name), which is Thread's one-argument constructor: it sets the thread's name. Without it the threads get automatic names like Thread-0, Thread-1.

Key Idea— thread output is not deterministic

Once two threads are running, the operating system decides when each one gets the processor, and it does not have to tell you or be consistent about it. The order in which lines from different threads appear is not fixed, and can differ every time you run the same program.

Every thread output on the rest of this page is therefore one representative run. Run the same program yourself and you should expect something different. That is not a defect in the program; it is the thing the program is demonstrating.

Both are possible, and so are the other four orderings. Starting order does not determine running order. A B C is perhaps the most likely, because A had a head start, but nothing in the language promises it.

(b) The author replaces the three start() calls with run() calls. Now what is the output?

Exactly A B C, every single time. With run() there are no new threads: the three calls are three ordinary method calls made in sequence on the main thread, and each finishes before the next begins.

This is precisely why the mistake is dangerous. The program looks like it works — the output is even tidier than the threaded version — and none of the concurrency you asked for is happening.

(c) How could you get the guaranteed order A B C and real threads?

Start each thread and then join() it before starting the next: a.start(); a.join(); b.start(); b.join(); c.start(); c.join();. join() blocks the calling thread until the thread it is called on has finished.

That does give you three real threads in a guaranteed order — and no concurrency whatsoever, since only one of them is ever running. Which is the honest answer to the question: if you need a strict order, you do not want threads for that part of the work. Use join() to wait for results, not to sequence everything.

Things to notice across all three parts. "Possible output" questions about threads are answered by asking what the program forces, never by what it happened to print. Two lines printed by one thread are always in order relative to each other; two lines printed by different threads are in no order at all unless something like join() or a lock puts one there.

8.Sharing data: race conditions, synchronized, deadlock

Interleaved output is untidy. Interleaved data is a bug.

Definition— race condition

A race condition occurs when two or more threads access the same data at the same time, and the result depends on which of them happens to get there first.

The classic case is count++. It looks like one step, but it is three: read count, add one, write it back. If two threads read the same value before either writes, both write the same result and one increment is silently lost.

Worked Example— two threads, one counter, missing increments

This version uses implements Runnable, the second creation style from §7. Two threads each add one to a shared static counter one hundred thousand times, so the total ought to be exactly 200000. join() makes main wait for both before printing.

Counter.java

public class Counter implements Runnable {
    static int count = 0;

    public void run() {
        for (int i = 0; i < 100000; i++) count++;
    }

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(new Counter());
        Thread t2 = new Thread(new Counter());
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("count should be 200000, and is " + count);
    }
}

Definition— synchronized and the monitor lock

Every Java object has a lock (also called a monitor) associated with it. Writing

synchronized (someObject) {
    // ... critical section ...
}

means: acquire that object's lock, run the block, release the lock. Only one thread can hold a given object's lock at a time, so only one thread at a time can be inside any block synchronized on that same object. Everyone else waits.

The synchronized keyword can also be written on a method, which is shorthand for synchronizing the whole body on this.

Worked Example— the same counter, fixed

One change from the previous program: the increment now happens inside a synchronized block on a shared lock object.

SyncCounter.java

public class SyncCounter implements Runnable {
    static int count = 0;
    static final Object lock = new Object();

    public void run() {
        for (int i = 0; i < 100000; i++) {
            synchronized (lock) {
                count++;
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(new SyncCounter());
        Thread t2 = new Thread(new SyncCounter());
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("count should be 200000, and is " + count);
    }
}

Correct every time. Read-add-write can no longer be split, because a thread that wants to start it must first take the lock, and the thread already inside holds it until it is done.

lock must be static, so that both Counter objects use the same lock. If you make it an instance field, each of the two objects has its own, no thread ever waits for the other, and the bug comes straight back — the code still says synchronized and still loses increments. Synchronizing on the wrong object is the same as not synchronizing at all.

This does cost something. Threads now spend time waiting, and the synchronized version does measurably more work per increment than the broken one. Keep critical sections small: lock around the shared data, not around the whole loop.

Definition— deadlock

A deadlock occurs when two or more threads are blocked forever, each waiting for a lock that another one holds. The classic two-thread shape is:

  • Thread A holds resource X and waits for resource Y;
  • Thread B holds resource Y and waits for resource X.

Neither can proceed, neither will ever give up what it holds, and nothing times out. The program simply stops making progress, forever.

Worked Example— her deadlock, and what it looks like

Two threads, two locks. Thread 0 takes locks[0] and then wants locks[1]; thread 1 takes locks[1] and then wants locks[0]. The sleep in the middle is there to make sure both have taken their first lock before either asks for its second.

DeadLock.java

public class DeadLock extends Thread {

    static Object[] locks = new Object[2];
    int n;

    public DeadLock(int i) {
        n = i;
    }

    public static void main(String args[]) {
        for (int i = 0; i < 2; i++)
            locks[i] = new Object();
        for (int i = 0; i < 2; i++) {
            DeadLock d = new DeadLock(i);
            d.start();
        }
    }

    public void run() {
        synchronized (locks[n % 2]) {
            System.out.println("Thread " + n + " starting");
            try {
                sleep((int) (Math.random() * 1000));
            } catch (InterruptedException e) {
            }
            synchronized(locks[(n + 1) % 2]) {
                System.out.println("Thread " + n + " ending");
            }
        }
    }
}

Two lines, and then nothing. The program hangs. It does not crash, it does not print an error, it does not exit — the two ending lines never appear and the JVM never terminates. Walk through why. Thread 0 evaluates locks[0 % 2], which is locks[0], and takes it. Thread 1 evaluates locks[1 % 2], which is locks[1], and takes it. Both print starting. Both sleep. Thread 0 wakes and asks for locks[(0+1) % 2] = locks[1] — held by thread 1, so it blocks. Thread 1 wakes and asks for locks[(1+1) % 2] = locks[0] — held by thread 0, so it blocks. Key Idea— the standard cure: lock ordering

The cycle exists only because the two threads take the locks in opposite orders. Agree on a fixed global order — always locks[0] before locks[1] — and no cycle can form, because whoever holds the lower-numbered lock is never waiting on someone who holds it.

Worked Example— the same program, deadlock removed

Exactly one change: both threads now take locks[0] first and locks[1] second, instead of starting from locks[n % 2].

public class NoDeadLock extends Thread {

    static Object[] locks = new Object[2];
    int n;

    public NoDeadLock(int i) {
        n = i;
    }

    public static void main(String args[]) {
        for (int i = 0; i < 2; i++)
            locks[i] = new Object();
        for (int i = 0; i < 2; i++) {
            NoDeadLock d = new NoDeadLock(i);
            d.start();
        }
    }

    public void run() {
        synchronized (locks[0]) {              // always locks[0] first
            System.out.println("Thread " + n + " starting");
            try {
                sleep((int) (Math.random() * 1000));
            } catch (InterruptedException e) {
            }
            synchronized (locks[1]) {          // then always locks[1]
                System.out.println("Thread " + n + " ending");
            }
        }
    }
}

All four lines, and the program exits. On the six runs we made, thread 0 always won the race for locks[0] and went first; the reverse order — all of thread 1's lines, then all of thread 0's — is equally legal and you may well see it.

What you will not see is the two threads interleaved, because whichever thread wins locks[0] holds it across its sleep and its inner block. The fix removes the deadlock; it does not restore concurrency. Getting both usually means holding fewer locks, or holding them for less time, and that is where a course on concurrent programming starts.

Quick Check 23.11

Two threads share a static int balance = 100;. Each runs if (balance >= 100) { balance = balance - 100; System.out.println("withdrew 100"); }.

(a) Describe an interleaving in which balance ends up at −100.

Thread A tests balance >= 100 and finds it true. Before A does the subtraction, the operating system switches to thread B, which also tests balance >= 100, finds 100, and is also true. Both then subtract 100 from a balance that only ever had 100 in it, both print withdrew 100, and the balance ends at −100.

The bug is that the test and the update are two separate steps with a gap between them, and the gap is where the other thread gets in.

(b) Fix it.

Put the test and the update inside one synchronized block on a shared lock:

synchronized (lock) {
    if (balance >= 100) {
        balance = balance - 100;
        System.out.println("withdrew 100");
    }
}

Now no thread can slip between the test and the subtraction, because it would have to take the lock to get in and the lock is held.

(c) Someone "fixes" it instead by synchronizing only the assignment: if (balance >= 100) { synchronized (lock) { balance = balance - 100; } ... }. Does that work?

No. The test is still outside the lock, so both threads can still pass it before either subtracts. All this version guarantees is that the two subtractions do not corrupt each other — and they were never the problem.

Things to notice across all three parts. The unit that has to be protected is not "the write". It is the whole sequence that must appear to happen at once — here, check-then-modify. Naming that sequence correctly is most of the work; synchronized is the easy part.

Quick Check 23.12

Rewrite ThreadDemo from §7 so that it uses implements Runnable instead of extends Thread, and so that main prints all threads finished only after every thread has genuinely finished.

Plan. Three changes. First, the class implements Runnable and keeps its own name field, since it is no longer a Thread and cannot be given one by super(name). Second, each Runnable gets wrapped: new Thread(new Worker("T" + i)). Third, to wait for all of them we must keep the Thread objects — put them in an array, start them all, then join() each one in a second loop. Starting and joining in the same loop would run them one at a time.

    private String name;

        } catch (InterruptedException e) {

        Thread[] all = new Thread[5];

            all[i] = new Thread(new Worker("T" + i));
            all[i].start();
        }
        for (int i = 0; i < all.length; i++) {
            all[i].join();
        }
        System.out.println("all threads finished");

This is the part students miss. An iterator is not reusable: once it has reached the end, it stays there. To walk a3 again you would have to call a3.iterator() a second time and get a fresh one.

Problem 4 — An iterable Bag (added for these notes)

Write a class Bag<T> that stores items in a linked chain of Node<T> objects and can be used directly in a for-each loop, so that this driver works:

Bag<String> b = new Bag<>();
b.add("apples");
b.add("pears");
b.add("plums");

for (String s : b) System.out.print(s + " ");
System.out.println();
System.out.println("size = " + b.size());

Items may come out in any order. Give Bag, and the iterator class it needs.

Plan. This is the Procedure from §5 applied once more. Bag stores a chain of nodes and a count; add pushes at the head, which is one line and keeps the order question honest. BagIterator holds a Node<T> current cursor. The two things that make the for-each loop legal are the words implements Iterable<T> in the class header and the iterator() method — leave either out and the driver will not compile.

BagIterator.java

import java.util.Iterator;
import java.util.NoSuchElementException;

public class BagIterator<T> implements Iterator<T> {
    private Node<T> current;

    public BagIterator(Node<T> head) { this.current = head; }

    public boolean hasNext() { return current != null; }

    public T next() {
        if (!hasNext()) throw new NoSuchElementException();
        T data = current.getData();
        current = current.getNext();
        return data;
    }
}

Bag.java

import java.util.Iterator;

public class Bag<T> implements Iterable<T> {
    private Node<T> head;
    private int size;

    public void add(T item) {
        head = new Node<>(item, head);
        size++;
    }

    public int size() { return size; }

    public Iterator<T> iterator() {
        return new BagIterator<T>(head);
    }

    public static void main(String[] args) {
        Bag<String> b = new Bag<>();
        b.add("apples");
        b.add("pears");
        b.add("plums");

        for (String s : b) System.out.print(s + " ");
        System.out.println();
        System.out.println("size = " + b.size());

        // a second for-each loop over the same Bag starts over
        for (String s : b) System.out.print(s.length() + " ");
        System.out.println();
    }
}
plums pears apples

Things to notice. The items come out in reverse of the order they were added, because add pushes at the head. That is fine — a bag makes no promise about order, and the driver was written not to care. If you wanted insertion order you would keep a tail reference and add there, exactly as addTail did in Lecture 21.

The second for-each loop works, and starts from the beginning again. That is because iterator() constructs a new BagIterator every time it is called. If you had stored the cursor in Bag itself, the second loop would print nothing — the single most common design error when writing a first Iterable.

BagIterator is a separate public class here to keep the two jobs visibly separate. Java lets you nest it inside Bag as a private inner class, which is what the library does, and which has the advantage that it can see Bag's private fields directly.

Problem 5 — Fix the filter (added for these notes)

This method is supposed to delete every string shorter than four characters from a list. It compiles. Explain what it actually does, and fix it.

Filter.java

import java.util.ArrayList;

public class Filter {
    public static void dropShort(ArrayList<String> words) {
        for (String w : words) {
            if (w.length() < 4) words.remove(w);
        }
    }

    public static void main(String[] args) {
        ArrayList<String> a = new ArrayList<>();
        a.add("ox"); a.add("cat"); a.add("horse"); a.add("emu");
        dropShort(a);
        System.out.println(a);
    }
}

Plan. The loop modifies words while a for-each loop is iterating it, so the iterator's modification count no longer matches the list's. Whether that is detected depends entirely on where in the list the removal happens, which is why the method is not merely wrong but unpredictably wrong. Run it first and see.

Exception in thread "main" java.util.ConcurrentModificationException
	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1095)
	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1049)
	at Filter.dropShort(Filter.java:5)
	at Filter.main(Filter.java:13)

The fix is to remove through the iterator, which means naming it, which means an explicit while loop:

Filter.java

import java.util.ArrayList;
import java.util.Iterator;

public class Filter {
    public static void dropShort(ArrayList<String> words) {
        Iterator<String> it = words.iterator();
        while (it.hasNext()) {
            String w = it.next();
            if (w.length() < 4) it.remove();
        }
    }

    public static void main(String[] args) {
        ArrayList<String> a = new ArrayList<>();
        a.add("ox"); a.add("cat"); a.add("horse"); a.add("emu");
        dropShort(a);
        System.out.println(a);
    }
}
[horse]

Things to notice. Three of the four words are removed in a single pass, with no exception and nothing skipped, because it.remove() keeps the iterator's own bookkeeping in step with the list's.

Now the important part. Change the input to just a.add("ox"); a.add("horse");, so that the word to be deleted is the second-to-last — here, the first of two. The broken version then prints [horse] with no exception at all, looking entirely correct. It is the §6 silent-skip case: removing the second-to-last element makes hasNext() return false one step early, so next() never gets the chance to notice. That is why "it did not crash" is no evidence that a loop like this is right.

A second, perfectly good fix is to build a new list instead of editing the old one: loop with for-each, copy the words you want to keep into a fresh ArrayList, and return it. That never modifies anything it is reading, and it is usually the clearest answer when the method is allowed to return a value rather than being required to edit in place.

Problem 6 — Which outputs are possible? (added for these notes)

Consider this program.

Possible.java

public class Possible extends Thread {
    private String tag;

    public Possible(String tag) { this.tag = tag; }

    public void run() {
        System.out.println(tag + "1");
        System.out.println(tag + "2");
    }

    public static void main(String[] args) {
        Possible a = new Possible("A");
        Possible b = new Possible("B");
        a.start();
        b.start();
    }
}

(a) Is the output A1 A2 B1 B2 (one per line) possible? Is B1 A1 A2 B2? Is A2 A1 B1 B2?

The first two are possible; the third is not.

The rule is that lines printed by the same thread keep their order — thread A executes its two statements in sequence, so A1 always precedes A2. Lines printed by different threads have no order imposed on them at all, so any interleaving that respects A1 before A2 and B1 before B2 can occur. A2 A1 ... violates thread A's own program order, so it cannot happen.

There are six possible outputs in total: the ways to interleave two ordered pairs.

(b) Change a.start(); b.start(); to a.run(); b.run();. Now which outputs are possible?

Exactly one: A1 A2 B1 B2. With run() there are no extra threads — a.run() is an ordinary method call that runs to completion on the main thread before b.run() starts.

(c) Go back to start(), and add synchronized (System.out) around the body of run(). Now which outputs are possible?

Two: A1 A2 B1 B2 and B1 B2 A1 A2. The lock makes each thread's pair atomic with respect to the other, so the pairs cannot interleave — but which thread gets the lock first is still undecided.

Things to notice across all three parts. These three answers — six outputs, one output, two outputs — are the whole of §7 and §8 in miniature. start() buys you concurrency and costs you determinism; run() gives up the concurrency; synchronized buys back as much determinism as you are willing to pay for in waiting.

When a question asks "is this output possible", never answer by running the program. Answer by listing what the program forces: statements within a thread, and whatever the locks and join() calls add on top.

Lecture Summary
  • An iterator is an object that walks a collection one element at a time without exposing how the collection stores things. The collection builds it; you just use it.
  • Iterator<E> has three methods: hasNext() (asks, changes nothing), next() (returns and advances), and the optional remove(). The standard loop is Iterator<E> it = c.iterator(); while (it.hasNext()) { E e = it.next(); ... }.
  • Iterable<T> has one method, iterator(). Iterable is the collection; Iterator is the walker. Do not confuse them.
  • The enhanced for loop is compiled into iterator(), hasNext() and next() calls. That is why it works on any Iterable, including a class of your own, and why declaring implements Iterable<T> — not merely having an iterator() method — is what makes it legal. Arrays are a separate special case.
  • To write your own iterator: one cursor field, hasNext() tests it, next() reads the data, advances the cursor, and returns — in that order — and throws NoSuchElementException when there is nothing left.
  • Two iterators from one collection are two independent objects: y == z is false, and advancing one does not move the other. An exhausted iterator stays exhausted.
  • Modifying a collection while a for-each loop walks it gives a ConcurrentModificationException — or, worse, silently skips an element. To delete while iterating, use the explicit iterator and call it.remove().
  • On a linked structure, an index-based loop restarts the walk every iteration. Measured on 50,000 elements it was hundreds of times slower than the iterator.
  • A thread is one path of execution. extends Thread or implements Runnable, then start() — never run(), which is just a method call on the current thread.
  • Thread output order is not deterministic. Two runs of the same program can differ, and a "possible output" question is answered by what the program forces, not by what it printed once.
  • A race condition is two threads touching the same data with the result depending on timing; synchronized on a shared lock object fixes it, and synchronizing on the wrong object fixes nothing. join() waits for a thread to finish.
  • A deadlock is two threads each holding what the other wants. Her DeadLock hangs every time and has to be killed. Taking locks in a fixed global order prevents it.
