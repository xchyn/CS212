1.The four text components

Two lectures ago you put a window on the screen. Last time you filled it: FlowLayout, BorderLayout and GridLayout decide where components go, a JPanel groups them, and a JButton runs your actionPerformed when it is clicked. All of that is assumed from here on and none of it is re-derived today.

What is missing is the other half of a conversation. So far the user can only click. Every program you have written this semester that actually asked the user something used a Scanner and the keyboard. Today the window learns to accept typing, and — this is the part the final exam cares about — your program learns to turn what was typed into a number it can compute with.

Definition— the text components

Swing provides several components for text input and display:

All four live in javax.swing, so they all start with J, and all four are components that go into a container exactly the way a JButton does.

Three of them share almost the same interface, which is why they are worth learning together rather than one at a time:

Key Idea— every text component is a String in a box

Whatever else a text component does on screen, from your program's point of view it holds one String, and there are exactly two operations that matter: getText() hands you that String, and setText(s) replaces it. Almost every exam GUI in this course is read a String out of one component, compute something, write a String into another.

Note the type carefully. getText() returns a String — never an int, never a double, even when the user typed digits. Converting is your job, and §4 is about nothing else.

Every GUI on the CSCI 212 finals is built out of exactly that pairing, usually twice: a label naming what to type, a field to type it in, a label naming the answer, and a field where the answer appears.

2.JLabel: text the program writes

You have used JLabel since Lecture 15, but only to put a fixed string in a window. It has one more trick, and it is the trick that makes it useful as an output.

Definition— JLabel

A JLabel displays a short piece of text, an image, or both. It is non-editable: the user can neither type into it nor click it into doing anything. It has no listener of its own.

The methods you need today:

  • new JLabel("some text") — create it with its text.
  • new JLabel() — create it empty, and fill it in later.
  • label.setText("new text") — replace the text while the program is running. The window redraws itself; you do not have to ask.
  • label.getText() — read back whatever is currently shown.
  • label.setForeground(Color.RED) — the color of the text. setBackground is the color behind it, and on a label it only shows if you also call setOpaque(true).
Key Idea— setText is how a GUI "prints"

A console program answers the user with System.out.println. A GUI program has no console to print to, and the equivalent is setText. When an exam question says "the GUI should display the message Are you sure!", the code it is asking for is one line: message.setText("Are you sure!");

That is why the label almost always has to be an instance variable rather than a local variable in the constructor. The constructor creates it; actionPerformed, a completely different method, has to change it. A local variable would be gone by then.

Common Mistake— the label the listener cannot reach

This constructor compiles, and the label appears on screen:

public MyGui() {
   JLabel answer = new JLabel("Result will appear here");   // local variable
   getContentPane().add(answer);
}

public void actionPerformed(ActionEvent e) {
   answer.setText("done");        // error: cannot find symbol
}

answer is a local variable of the constructor. It ceases to exist the moment the constructor returns, and actionPerformed has never heard of it. Declare it as a private field of the class and assign it in the constructor:

private JLabel answer;           // field: every method of the class can see it

public MyGui() {
   answer = new JLabel("Result will appear here");
   getContentPane().add(answer);
}

The rule is easy to apply: anything actionPerformed needs to read or change must be a field. Anything the constructor uses once and forgets — a JPanel, a JLabel that never changes — can stay local.

3.JTextField: text the user writes

Definition— JTextField

A JTextField is a single-line box the user can type into. Its features:

  • Fixed height, variable width — it is always one line tall.
  • It can be set to read-only (§6).
  • It supports selection, copy and paste, for free, from the operating system.

The methods:

CallWhat it does
new JTextField(15)Creates an empty field about 15 characters wide.
new JTextField("hello", 15)Same, but starting with the text hello.
field.getText()Returns whatever is in the box right now, as a String.
field.setText("abc")Replaces the contents. setText("") empties it.
field.setColumns(20)Changes the preferred width after construction.
field.setEditable(false)Makes it read-only (§6).
Common Mistake— the number is a width, not a limit

The number in new JTextField(15) is a column count. A column is roughly the width of one character in the field's font, so the number is a request to the layout manager: please make me about this wide.

It is not a maximum length. The user can type as much as they like into a new JTextField(5); the text simply scrolls sideways inside the little box, and getText() hands you every character of it. Here is a five-column field with forty characters put into it:

ColumnProbe.java

        System.out.println("getColumns() -> " + small.getColumns());

        System.out.println("length of getText() -> " + small.getText().length());

        System.out.println("new JTextField() columns -> " + wide.getColumns());

Forty characters came back out of a five-column field. If you genuinely need to stop the user typing more than n characters you have to check the length yourself in your listener, or install a document filter — which is well beyond this course. Treat the constructor argument purely as a sizing hint.

Note the last line too: new JTextField() with no argument has zero columns, so a layout manager will make it as narrow as it can get away with. That is why every example in this course passes a number.

Quick Check 17.3

A JTextField called field currently contains the four characters 2025.

(a) What is the type and value of field.getText()?

Type String, value "2025". It looks like a number and it is not one. This is the single most important sentence in the lecture.

(b) What does System.out.println(field.getText() + 1); print?

20251. Lecture 1's rule about +: one operand is a String, so this is concatenation, not addition. The 1 is appended as a character.

(c) The user then clears the box completely. What does field.getText() return now — null, or something else?

Not null — the empty string "", whose length() is 0. getText() on a text component never returns null. That matters, because it means you can safely call .trim() or .length() on the result without checking for null first.

Things to notice across all three parts. The three most common beginner bugs with a text field are all in this question: treating getText() as a number, using + and getting concatenation, and expecting null for an empty box. If you can answer (a), (b) and (c) without hesitating you have the hard part of §4 already.

4.From text to number, and the exception waiting for you

This is the section the final exam is about. Every recent CSCI 212 final has one problem worth fifteen points that is a window with a text field, a button, and a calculation — a tip calculator, a temperature converter, a kilometre converter. The GUI part of those questions is last lecture's material. The part that decides whether the program works is three characters long: getText() returns a String, and you cannot multiply a String.

Definition— parsing

To parse a string is to read it as something else. Java's wrapper classes each provide a static method that parses text into their primitive type:

CallTakesReturnsExample
Integer.parseInt(s)a Stringan intInteger.parseInt("25") is 25
Double.parseDouble(s)a Stringa doubleDouble.parseDouble("45.5") is 45.5

Both are static, so you call them on the class, not on an object: it is Integer.parseInt(...), never myString.parseInt(). Both are in java.lang, so there is nothing to import.

Procedure— the three lines inside every exam actionPerformed
  1. Read. String s = input.getText(); — pull the text out of the input field.
  2. Convert and compute. double bill = Double.parseDouble(s); then double tip = bill * 0.20; — or both in one line, which is what the instructor's answers do.
  3. Write. output.setText("" + tip); — put the answer into the output component. The leading "" turns the number into a String, because setText will not accept a double.

That is the whole method. Once you can write those three lines from memory, the fifteen point question is a layout exercise.

Quick Check 17.4

A JTextField named input contains 12. For each expression, give the value and the type, or say that it does not compile.

(a) input.getText() * 2

Does not compile. * is not defined for a String: bad operand types for binary operator '*'. This one at least the compiler catches for you, which makes it the friendliest of the four.

(b) input.getText() + 2

Compiles. Value "122", a String. This is the dangerous one: no error, wrong answer.

(c) Integer.parseInt(input.getText()) * 2

Compiles. Value 24, an int. This is the correct form.

(d) Double.parseDouble(input.getText()) / 5

Compiles. Value 2.4, a double. Note that this is not integer division even though the 5 is written without a decimal point: parseDouble already made the left operand a double, and Lecture 1's rule says one double operand is enough.

Things to notice across all four parts. Compare (c) with the version a lot of students write first, Integer.parseInt(input.getText() * 2). Look at where the closing parenthesis is: that one multiplies the String and then parses, which is (a) with extra steps and does not compile. Parse first, compute second — the parseInt call goes around the getText() and nothing else.

Now the part nobody warns you about. Integer.parseInt is given a String that the user typed, and users type anything.

Definition— NumberFormatException

If the text handed to parseInt or parseDouble is not a valid number, the method cannot return anything sensible, so it throws a NumberFormatException. An exception thrown and not dealt with stops the method it was thrown in, then the method that called that one, and so on until the program itself stops and prints a stack trace.

Exceptions proper — what throwing means, and how try and catch stop the damage — are Lecture 20. What you need today is to recognise this one on sight and know exactly which inputs cause it.

Key Idea— a crash inside a listener does not close the window

In a console program an uncaught exception ends the program. In a Swing program it does not, and the difference confuses people badly. Your actionPerformed runs on the event dispatch thread from Lecture 15, and when an exception escapes it, that thread prints the stack trace and carries on waiting for the next click. The window stays open, the output box keeps its old contents, and unless the user happens to be watching a console they see nothing at all — a button that silently did nothing.

That is why the instructor's answer to every one of these exam problems wraps the parse in try and catch. You will meet the mechanism properly in Lecture 20; you will meet the shape of it in the practice problems at the bottom of this page, because the rubric awards two points for it.

Quick Check 17.5

For each string, say whether Integer.parseInt succeeds, and if not, why.

(a) "0042"

Succeeds, giving 42. Leading zeros are fine; they are just digits.

(b) "42 " (one trailing space)

Throws NumberFormatException. A space is not a digit and parseInt does not trim for you. "42 ".trim() would parse fine.

(c) "42.0"

Throws. It is a valid number, but not a valid int. Double.parseDouble would accept it and give 42.0.

(d) "+5"

Succeeds, giving 5. A leading + is allowed, just as a leading - is. This one surprises people in both directions, and it is not worth memorising — the useful summary is an optional sign, then digits, then nothing else at all.

Things to notice across all four parts. Every failing case here is something a user could type by accident in half a second. That is the point. The question is never "will bad input arrive?" but "what does my program do when it does?", and the answer today is it throws, and the button appears to do nothing.

Quick Check 17.6

Write the complete class SquareIt that extends JFrame implements ActionListener. The window is 350 by 120 pixels, titled Square It, uses FlowLayout, and contains a label reading Enter a whole number:, a text field 8 columns wide, a button reading Square, and a label where the answer appears. Clicking the button must read the field, square the number and put n squared is n*n into the answer label. Closing the window ends the program.

Plan. Two of the four components are touched by actionPerformed — the input field and the answer label — so those two are fields of the class and the other two are created inline. The constructor is the Lecture 15 checklist plus four add calls and one addActionListener. The response method is the three lines from the procedure box: read, parse and compute, write.

Because the input is a whole number, Integer.parseInt is the right method, and because a user can type anything, the parse is wrapped so that bad input becomes a message rather than a silent nothing. Catching NumberFormatException by name is better style than catching Exception, and it is what you should write when the question does not print a template for you.

5.JTextArea: many lines at once

Definition— JTextArea

A JTextArea is a rectangle of editable text with many lines. Its features:

  • Variable height and width — unlike a JTextField, which is always one line tall.
  • It can display and edit large amounts of text.
  • It supports selection, copy and paste.

The methods, on top of the getText and setText you already know:

CallWhat it does
new JTextArea(10, 30)An empty area about 10 rows tall and 30 columns wide. Rows first, then columns.
area.append("more\n")Adds text at the end, keeping what is already there.
area.setText("")Replaces everything — the way to clear it.
area.setLineWrap(true)A line too long for the width continues on the next line instead of running off the edge.
area.setWrapStyleWord(true)When wrapping, break between words rather than in the middle of one.
area.setRows(n) / area.setColumns(n)Change the preferred size after construction.
Key Idea— append versus setText

setText(s) replaces everything in the component with s. append(s) adds s to the end. Confusing them is the commonest JTextArea bug: a log that only ever shows the most recent line was written with setText where it wanted append.

append exists only on JTextArea. To add to a JTextField you have to do it by hand: field.setText(field.getText() + more);

Warning— the rows and columns are a request, not a promise

new JTextArea(10, 30) does not mean "hold at most 10 lines of 30 characters". It means "when a layout manager asks how big I would like to be, say ten rows by thirty columns". The area will happily hold a thousand lines; you just will not be able to see them all, and there is no scroll bar unless you add one.

That is why real code almost always puts a JTextArea inside a JScrollPane: contentPane.add(new JScrollPane(area), BorderLayout.CENTER); Scroll panes are the next lecture, so today's examples add the area directly, exactly as your instructor's notes do — but remember that any text area a user can type freely into wants a scroll pane around it.

6.setEditable and setEnabled

Two methods that sound like the same thing and are not. Every text component has both, and exam questions and real interfaces use them for different purposes.

Definition— read-only versus disabled

setEditable(false) makes a text component read-only. The user cannot type into it. Everything else still works: the text is drawn normally, the user can select it and copy it, the component still takes part in the interface, and your program can still change it with setText.

setEnabled(false) disables the component altogether. It is drawn greyed out, it cannot take keyboard focus, it does not respond to the mouse, and if it is a button it fires no events at all. setEnabled exists on every component, not just text ones.

Worked Example— three fields and two buttons

The difference is easiest to believe when you watch it. This program makes one normal field, one read-only field and one disabled field, reports the state of each, writes into the read-only one from code, and then clicks an enabled button and a disabled button. 7.Menus: the bar, the menu, the item

MemoSaver, the program in your instructor's notes, puts five buttons in a row along the bottom of the window: Save Memo 1, Save Memo 2, Clear, Get Memo 1, Get Memo 2. It works, and it does not scale. Add three more commands and the row wraps; add ten and the window is mostly buttons. Real applications put commands in menus, and the same program with a menu instead of a button row is MemoGUI.

Definition— JMenuBar, JMenu, JMenuItem

Three classes, in javax.swing, that nest inside one another:

  • JMenuBar — the strip across the top of the window. It holds menus.
  • JMenu — one drop-down menu, such as File or Memos. It holds items.
  • JMenuItem — one clickable line inside a menu, such as Save or Exit. This is the thing the user actually chooses.

And one method on JFrame, which is the only place the bar can go:

  • setJMenuBar(bar) — attaches a JMenuBar to the frame. Note the capital J in the middle of the name; it is not setMenuBar, which is the old AWT method for an AWT MenuBar and will not accept a JMenuBar.
Key Idea— the hierarchy, in the order you build it

Everything about menus follows from four sentences, and every menu bug is one of them written backwards.

  1. A JMenuItem goes on a JMenu: fileMenu.add(saveItem);
  2. A JMenu goes on a JMenuBar: bar.add(fileMenu);
  3. A JMenuBar goes on the frame: setJMenuBar(bar);
  4. The listener goes on the JMenuItem: saveItem.addActionListener(this);

Sentence 4 is the one that costs marks. The user clicks the item, so the item is the event source, so the item is what needs the listener. The menu is a container; it fires nothing you care about.

Written out, the whole skeleton is eight lines:

JMenuBar bar = new JMenuBar();           // 1. the bar
JMenu fileMenu = new JMenu("File");      // 2. a menu
bar.add(fileMenu);                       //    menu onto bar
setJMenuBar(bar);                        //    bar onto frame

JMenuItem saveItem = new JMenuItem("Save");   // 3. an item
saveItem.addActionListener(this);             //    listener on the ITEM
fileMenu.add(saveItem);                       //    item onto menu
Common Mistake— the listener on the menu instead of the item

Here is the thing that makes this error so expensive: JMenu has an addActionListener method, inherited from AbstractButton — a menu is technically a kind of button, which is how it knows to open when clicked. So fileMenu.addActionListener(this); compiles perfectly, and then your menu items do nothing.

This program registers the listener both ways and clicks the item in each case. doClick() on a JMenuItem fires exactly what a real click fires:

Once several menu items share one listener, actionPerformed has to work out which one was chosen. Section 5 did that with e.getSource() and ==; from here on we use the other technique, which is what your instructor's notes use throughout.

Definition— the action command

Every ActionEvent carries a String called its action command, read with e.getActionCommand(). For a JButton or a JMenuItem it defaults to the component's label, so the item created by new JMenuItem("Save Memo 1") delivers the command "Save Memo 1".

Common Mistake— the label is the command

Because the action command defaults to the label, changing the label of a menu item silently changes what actionPerformed receives. Rename the item to "Save memo 1" with a small m and the branch command.equals("Save Memo 1") stops matching, and the item quietly does nothing. The string in the constructor and the string in the comparison have to agree character for character, capitals included.

If that makes you nervous — it should — the fix is setActionCommand, shown above: give the item a stable internal name like "SAVE1" and compare against that, and the visible label becomes free to change. Your instructor's notes do not use it, and neither do the exam answers, so for this course match the labels exactly.

8.A menu that saves to a file

MemoGUI calls itself a memo saver and saves nothing. Close the window and both memos are gone, because they only ever lived in two String fields in memory. A program that saves should put the text somewhere that outlives the program — and you already know how, from Lecture 5.

Nothing new is needed. theText.getText() gives you a String; a PrintWriter writes a String to a file; close() flushes it. The only genuinely new question is where the file code goes, and there is one obstacle.

Common Mistake— you cannot put throws on actionPerformed

Every file program in Lecture 5 wrote throws FileNotFoundException on main. Try the same on a listener method:

BadFiler.java

public void actionPerformed(ActionEvent e) throws FileNotFoundException {
   PrintWriter output = new PrintWriter("memo.txt");
   output.print(theText.getText());
   output.close();
}
BadFiler.java:11: error: actionPerformed(ActionEvent) in BadFiler cannot implement actionPerformed(ActionEvent) in ActionListener
   public void actionPerformed(ActionEvent e) throws FileNotFoundException {
               ^
  overridden method does not throw FileNotFoundException
1 error

Read the second line of the message: overridden method does not throw FileNotFoundException. ActionListener declares void actionPerformed(ActionEvent e) with no throws clause at all, and an implementing method is not allowed to add one. If it could, every piece of library code that calls a listener would suddenly have to handle exceptions it has never heard of.

So inside a listener there is no throws escape hatch, and the file code has to deal with the exception itself — either with try/catch right there, or by calling a helper method that does. That is Lecture 20's material arriving a little early because Swing forces it, and it is the same reason the exam rubrics wrap every parseDouble in a try/catch.

Worked Example— MemoFiler: a File menu that really writes a file

A text area, a File menu with Save and Exit, and a label along the bottom reporting what happened. The file work lives in its own static method, saveMemo, which knows nothing about Swing — that is the design point of the whole example, and the reason the next code block can be run for real.

MemoFiler.java

import java.awt.BorderLayout;
import java.awt.Container;
import java.awt.event.ActionEvent;
import java.awt.event.ActionListener;
import java.io.FileNotFoundException;
import java.io.PrintWriter;

import javax.swing.JFrame;
import javax.swing.JLabel;
import javax.swing.JMenu;
import javax.swing.JMenuBar;
import javax.swing.JMenuItem;
import javax.swing.JTextArea;

public class MemoFiler extends JFrame implements ActionListener {
   public static final int WIDTH = 500;
   public static final int HEIGHT = 300;
   public static final String FILE_NAME = "memo.txt";

   private JTextArea theText;
   private JLabel status;

   public MemoFiler() {
      super("Memo Filer");
      setSize(WIDTH, HEIGHT);
      setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);

      JMenuBar bar = new JMenuBar();          // 1. the bar
      JMenu fileMenu = new JMenu("File");     // 2. a menu
      bar.add(fileMenu);                      //    menu goes on the bar
      setJMenuBar(bar);                       //    bar goes on the frame

      JMenuItem saveItem = new JMenuItem("Save");   // 3. an item
      saveItem.addActionListener(this);             //    listener on the ITEM
      fileMenu.add(saveItem);                       //    item goes on the menu

      JMenuItem exitItem = new JMenuItem("Exit");
      exitItem.addActionListener(this);
      fileMenu.add(exitItem);

      Container contentPane = getContentPane();
      contentPane.setLayout(new BorderLayout());

      theText = new JTextArea(10, 40);
      theText.setLineWrap(true);
      contentPane.add(theText, BorderLayout.CENTER);

      status = new JLabel(" Nothing saved yet.");
      contentPane.add(status, BorderLayout.SOUTH);
   }

   public void actionPerformed(ActionEvent e) {
      String command = e.getActionCommand();
      if (command.equals("Save")) {
         status.setText(" " + saveMemo(theText.getText()));
      } else if (command.equals("Exit")) {
         System.exit(0);
      }
   }

   // Everything here is Lecture 5 and nothing here is Swing.
   public static String saveMemo(String memo) {
      try {
         PrintWriter output = new PrintWriter(FILE_NAME);
         output.print(memo);
         output.close();
         return "Saved " + memo.length() + " characters to " + FILE_NAME;
      } catch (FileNotFoundException e) {
         return "Could not write " + FILE_NAME;
      }
   }

   public static void main(String args[]) {
      MemoFiler gui = new MemoFiler();
      gui.setVisible(true);
   }
}

Because saveMemo is static and takes a plain String, it can be called without a window ever existing. For the counting: trim() first, so that an area holding only spaces counts as zero rather than one. Then split on runs of whitespace. split("\\s+") means "one or more whitespace characters" — in a Java string literal the backslash has to be doubled, so what the regular expression engine sees is \s+.    public static final int WIDTH = 450;

      toolsMenu.add(countItem);

      toolsMenu.add(clearItem);

      contentPane.add(theText, BorderLayout.CENTER);

      contentPane.add(status, BorderLayout.SOUTH);

      String command = e.getActionCommand();
      if (command.equals("Count Words")) {

      } else if (command.equals("Clear")) {

      }
   }

   public static int countWords(String text) {
      String trimmed = text.trim();
      if (trimmed.isEmpty()) {
         return 0;
      }
      return trimmed.split("\\s+").length;
   }

   static final double FACTOR = 9.0 / 5.0;   // conversion factor for C to F
   static final double OFFSET = 32.0;        // offset for C to F formula

   public TemperatureConverter() {
      super();
      setSize(400, 200);
      setTitle("Temperature Conversion");
      setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);

      input = new JTextField(50);
      output = new JTextField(50);

      Container content = getContentPane();
      content.setLayout(new BorderLayout());

      JPanel p = new JPanel();
      content.add(p, BorderLayout.CENTER);
      p.setLayout(new GridLayout(2, 2));
      p.add(new JLabel("Enter a temperature in Celsius"));
      p.add(input);
      p.add(new JLabel("Temperature in Fahrenheit"));
      p.add(output);

      JButton b = new JButton("Convert");
      b.addActionListener(this);
      content.add(b, BorderLayout.SOUTH);
   }

   public void actionPerformed(ActionEvent e) {
      try {
         Double fahrenheit = Double.parseDouble(input.getText()) * FACTOR + OFFSET;
         output.setText("" + fahrenheit);
      } catch (Exception ex) {
         output.setText("Please enter a number");
      }
   }

   public static void main(String[] args) {
      TemperatureConverter converter = new TemperatureConverter();
      converter.setVisible(true);
   }
}

Driving that actionPerformed with three temperatures typed into the input field:

25 Celsius      -> F       77.0
100 Celsius     -> F       212.0
-40 Celsius     -> F       -40.0

Things to notice. The three test values are chosen so you can check them in your head: 25 °C is 77 °F, water boils at 100 °C and 212 °F, and −40 is the one temperature that is the same on both scales. If your converter gets −40 right it has both the multiplication and the addition in the correct order.

Two departures from the printed rubric, both deliberate. The published answer writes setSize(1200, 800), which is an enormous window for two text boxes; any sensible size is accepted, and 400 by 200 is easier to picture. The published answer also leaves the catch block empty, for the reasons discussed in Problem 1.

The title is set with setTitle after super(), rather than by passing it to super. Both work. Note that super() with no argument must still come first if you write it at all, and that super("Temperature Conversion") would let you delete the setTitle line.

The window below is meant to read a whole number from the text field, double it when the button is clicked, and show the answer in the label. Three of the numbered lines are wrong. Give the number of each incorrect line and a corrected version of it. Any line without a number is correct as written.

Broken.java

import java.awt.*;

Plan. Two of the three are compile errors, so start by asking what the compiler would object to. Read every method call and check that the argument types match what the method wants. The third is the one the compiler cannot see: a line that is legal Java but wrong about what the user might type.

Error 1 — line 2. addActionListener needs to be told which listener to notify. The class already says implements ActionListener and already has actionPerformed, so the listener is this very object:

Broken.java:19: error: method addActionListener in class AbstractButton cannot be applied to given types;
        go.addActionListener();                           // line 2
          ^
  required: ActionListener
  found:    no arguments
  reason: actual and formal argument lists differ in length

Corrected: go.addActionListener(this);

Without it the program still compiles once the other errors are fixed, and it still opens a perfectly good-looking window — the button just does nothing when clicked. Forgetting addActionListener is the most common reason a Swing button is silent.

Error 2 — line 3. getText() returns a String, always. There is no automatic conversion to int:

Broken.java:27: error: incompatible types: String cannot be converted to int
        int n = input.getText();                          // line 3
                             ^

Corrected: int n = Integer.parseInt(input.getText());

Error 3 — line 3 again, and this one the compiler will not help with. Even written correctly, Integer.parseInt throws a NumberFormatException the moment the user types something that is not a whole number — and a user typing into a text box will eventually type twelve, or a blank, or 3.5. Proving it outside the GUI:

Probe.java

public class Probe {
    public static void main(String args[]) {
        String typed = "21";
        int n = Integer.parseInt(typed);
        System.out.println("typed \"" + typed + "\" -> label shows: " + (n * 2));
        try {
            Integer.parseInt("twelve");
        } catch (NumberFormatException ex) {
            System.out.println("typed \"twelve\" -> " + ex);
        }
    }
}
typed "21" -> label shows: 42
typed "twelve" -> java.lang.NumberFormatException: For input string: "twelve"

In a real application you would wrap the parse in a try/catch and put a polite message in the label instead of letting the exception escape. That is Lecture 20's machinery, and on an exam it is enough to say so — but you should know the hole is there.

Here is the corrected class, which compiles cleanly:

Doubler.java

import javax.swing.*;
import java.awt.*;
import java.awt.event.*;

public class Doubler extends JFrame implements ActionListener {
    private JTextField input;
    private JLabel result;

    public Doubler() {
        setTitle("Doubler");
        setSize(320, 120);
        setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
        setLayout(new FlowLayout());

        input  = new JTextField(8);
        JButton go = new JButton("Double it");
        result = new JLabel("result");

        go.addActionListener(this);
        add(input);
        add(go);
        add(result);
        setVisible(true);
    }

    public void actionPerformed(ActionEvent e) {
        int n = Integer.parseInt(input.getText());
        result.setText("" + (n * 2));
    }

    public static void main(String args[]) {
        new Doubler();
    }
}

Things to notice. Line 4 is correct, and it is worth understanding why, because it looks suspicious. setText wants a String and n * 2 is an int, so the leading "" is doing real work: it forces the + to concatenate rather than add, exactly as in Lecture 1. Without it, setText(n * 2) would not compile.

Notice also the shape of the class, because it is the shape every GUI question on your exams wants: the components that the listener has to reach are fields, everything else is a local variable, the frame itself implements ActionListener, and addActionListener(this) wires them together. go can be local because nothing outside the constructor ever mentions it again; input and result cannot, because actionPerformed needs them.

Lecture Summary
  • JLabel displays text the program controls; JTextField collects one line from the user; JTextArea handles many lines. All three are just components — you build them, add them to a container, and a layout manager places them.
  • getText() returns a String, always, and setText() takes a String, always. Nothing about a text component knows or cares about numbers.
  • Turning typed text into a number is your job: Integer.parseInt or Double.parseDouble. Both throw a NumberFormatException on anything they cannot read, and a user will eventually type such a thing. Lecture 20 gives you the tool to handle it gracefully; today you at least know the hole is there.
  • Going the other way, remember "" + — setText will not accept a number.
  • A JTextArea normally lives inside a JScrollPane, and setLineWrap(true) is what stops long lines running off the right edge. Lecture 18 covers scroll panes properly.
  • setEditable(false) leaves a component looking normal but refusing typing; setEnabled(false) greys it out and stops it responding at all. Use setEditable for a results box, setEnabled for a control that is temporarily unavailable.
  • Menus are a three-level hierarchy: a JMenuBar goes on the frame with setJMenuBar, a JMenu goes on the bar, and a JMenuItem goes on the menu. The ActionListener goes on the item — never on the menu or the bar.
  • The exam pattern for every one of these questions is the same forty lines: fields for the components the listener must reach, a constructor that sets the title, size, close operation and layout and then builds and adds the components, addActionListener(this), and an actionPerformed that reads, computes and writes back. Learn the frame; the question only ever changes the formula in the middle.
