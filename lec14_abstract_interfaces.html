1.The shape that is not a shape

Last time we got paid for inheritance. A Shape variable could hold a Circle, a single print(Shape) method printed four different strings, and one loop over a Shape[] did the right thing for every element. All of that still stands, and none of it is being retaught today — you may assume it.

But there was something quietly wrong with that Shape class, and we said so at the end of the lecture. Here is the line:

Shape s = new Shape(10, 20);

What is that? It is an object whose area is 20 and whose perimeter is 10, and which has no shape. Nothing checks that 10 and 20 are consistent with each other, because there is nothing to check them against. We had to hand the constructor an area, because a plain Shape has no dimensions from which an area could be computed.

Key Idea— the sentence this whole lecture is about

A shape has an area. But there is no such thing as a generic shape whose area you can compute.

Both halves of that sentence are true at once, and ordinary classes cannot express it. You want getArea() to exist on Shape, so that general code can call it — and you want it to be impossible to write on Shape, because there is no formula. What you need is a way to declare a method and refuse to implement it.

That is exactly what abstract gives you, and everything else in this lecture follows from it. The same idea shows up all over real programs:

  • Every Employee has a computePay(), but "an employee" in general does not — a salaried employee and an hourly employee compute it completely differently.
  • Every Account can applyMonthlyInterest(), but the rate depends entirely on whether it is a checking account or a savings account.
  • Every Swing component can paint itself, but there is no drawing that a generic component would perform.

In every case the general class knows that the operation exists and has no idea how to do it. Today we learn to say that in Java.

Quick Check 14.1

For each pair, say which of the two classes you would want to stop anyone from instantiating, and give the method that has no sensible general implementation.

(a) Shape and Circle.

Shape. new Circle(3) is a perfectly meaningful thing to build — a radius is all a circle needs. new Shape(...) is not, because there is no set of numbers that describes "a shape". The method with no general implementation is getArea() (and getPerimeter()): you cannot write a body for it without knowing what kind of shape you have.

(b) Animal and Dog.

Animal. Every animal makes a sound, so makeSound() belongs on Animal — but there is no sound "an animal" makes. new Dog() is fine; new Animal() is a category error dressed up as an object.

(c) Rectangle and Square.

Neither. This is the pair that is not like the others. A rectangle is a completely concrete thing: give it a width and a height and it can compute its own area. Square is more specific still. Both should stay instantiable.

Things to notice across all three parts. The test is not "is this class at the top of the hierarchy?" — it is "can I write every method's body using only what this class knows?" Rectangle passes that test even though other classes extend it. Being a superclass and being abstract are separate questions.

2.The abstract keyword

abstract is a modifier, and it goes in two places: on a method, and on a class.

Definition— abstract method

An abstract method is a method declared with the keyword abstract and no body at all — the signature is followed by a semicolon where the braces would normally be:

public abstract double getArea();

It says: every object of this type has a getArea() that returns a double, and I am not the one who writes it. The declaration is a promise to callers and an obligation on subclasses, both at once.

Definition— abstract class

An abstract class is a class declared with the keyword abstract. Two things follow immediately:

  • It cannot be instantiated. new AbstractShape() is a compile error.
  • It may contain abstract methods. An ordinary class may not.

The two rules are connected: if a class has a method with no body, building one of them would give you an object you could call a method on that does not exist. Java closes that door by refusing to build it.

Key Idea— the rule that decides everything else

A class containing an abstract method must itself be declared abstract. The reverse is not true: a class may be abstract with no abstract methods in it at all, if you simply want to forbid instantiating it.

Here is the instructor's AbstractShape. Read the class header and the first two methods together — the abstract on line 1 is there because of the abstract on lines 3 and 4.

AbstractShape.java

public abstract class AbstractShape {
    // Abstract methods (no implementation)
    public abstract double getArea();
    public abstract double getPerimeter();

    // Concrete methods (with implementation)
    public void printInfo() {
        System.out.println("Area: " + getArea());
        System.out.println("Perimeter: " + getPerimeter());
    }

    // Abstract classes can have constructors
    public AbstractShape() {
        System.out.println("Creating a shape");
    }
}

Look at printInfo() for a moment, because it is doing something that should feel impossible. It is a fully written, working method, and it calls getArea() — a method whose body does not exist anywhere in this file. That compiles, and at run time it works, because the object that printInfo() is running on is never really an AbstractShape; it is always some concrete subclass that did write getArea(). This is the payoff for everything we did last lecture.

Definition— concrete class

A concrete class is any class that is not abstract — an ordinary class you can call new on. A concrete subclass of an abstract class must supply a body for every abstract method it inherits, or the compiler rejects it.

The escape hatch is to not be concrete: a subclass may leave some or all of them unimplemented if it declares itself abstract too, passing the obligation further down.

AbstractCircle is the concrete subclass. It writes both missing bodies, and then adds a method of its own that AbstractShape has never heard of.

AbstractCircle.java

// Concrete subclass must implement all abstract methods
public class AbstractCircle extends AbstractShape {
    private double radius;

    public AbstractCircle(double radius) { this.radius = radius; }

    @Override
    public double getArea() { return Math.PI * radius * radius; }

    @Override
    public double getPerimeter() { return 2 * Math.PI * radius; }

    public void resize(double factor) {
        this.radius *= factor;
        System.out.println("Circle resized to radius " + radius);
    }
}

A student writes this subclass of AbstractShape and it will not compile.

public class AbstractTriangle extends AbstractShape {
    private double base;

        this.height = height;

    @Override

(a) What does the compiler say, and which line does it point at?

It points at the class header, not at any method:

AbstractTriangle.java:1: error: AbstractTriangle is not abstract and does not override abstract method getPerimeter() in AbstractShape
public class AbstractTriangle extends AbstractShape {
       ^
1 error

getArea() was supplied; getPerimeter() was not. The message names the exact method that is missing and the class it came from, which is the most useful thing about it. It points at the header because the problem is not with any line that is present — it is with a line that is absent.

(b) Give the two different ways to make this compile, and say when you would choose each.

Fix 1 — supply the missing body. This is what you want almost every time. A triangle's perimeter needs the two other sides, so the class needs two more fields:

public class AbstractTriangle extends AbstractShape {
    private double base, height, side1, side2;
    // ... constructor sets all four ...

    @Override
    public double getArea() { return 0.5 * base * height; }

    @Override
    public double getPerimeter() { return base + side1 + side2; }
}

Fix 2 — declare the class abstract as well. This compiles too:

public abstract class AbstractTriangle extends AbstractShape {
    // getArea() implemented, getPerimeter() still abstract
}

It is legal because an abstract class is allowed to have holes in it — you simply pass the obligation down to its subclasses. Choose this only when the missing method genuinely cannot be written yet: an AbstractTriangle that does not know whether it is equilateral or scalene is a reasonable place to stop.

Things to notice across both parts. The rule is "implement every abstract method or be abstract yourself", and the compiler's message spells out both halves — is not abstract and does not override. Fixing either half removes the error. Fix 1 gives you a usable class; Fix 2 just moves the problem one level down, so it is the right choice much less often than students expect.

3.What an abstract class still has

The word "abstract" makes people expect a stripped-down thing. It is the opposite. An abstract class is an ordinary class in every respect except that you cannot say new to it. It may have private fields, constructors, concrete methods, static methods, toString, anything. AbstractShape has two of those three already.

Common Mistake— trying to instantiate it anyway

This is the error the instructor demonstrates in class, and it is worth learning by sight because the wording is unusual:

AbstractShape abstractShape = new AbstractShape();
NoInstance.java:3: error: AbstractShape is abstract; cannot be instantiated
        AbstractShape abstractShape = new AbstractShape();
                                      ^
1 error

The caret points at new, not at the variable. Declaring a variable of an abstract type is completely fine — AbstractShape shape = circle; on the previous page did exactly that. What is forbidden is constructing one.

Which raises the obvious question, and it is the best question in this lecture.

Key Idea— why does an abstract class have a constructor?

Because a subclass constructor must call it. new AbstractCircle(5.0) does not build a circle and stop; it builds the AbstractShape part of the object first, then the AbstractCircle part. That first step runs AbstractShape().

The constructor of an abstract class is never called by you. It is called by super(...) — written explicitly, or inserted by Java when you leave it out. Its job is to initialise the fields that the parent owns, on behalf of an object that will end up being some subclass.

An abstract class with private fields and a constructor that initialises them is completely normal design, and it is the main reason to prefer an abstract class over an interface. Hold that thought until section 7.

Quick Check 14.4

Decide whether each statement is true or false, and say why in one sentence.

(a) An abstract class must contain at least one abstract method.

False. The implication runs one way only. A class with an abstract method must be abstract; an abstract class need not have any. Marking a fully implemented class abstract is a legitimate way of saying "this is a base class, do not instantiate it directly."

(b) An abstract class cannot have private fields, because subclasses would not be able to see them.

False on both counts. It can have private fields, and subclasses not seeing them is fine — they reach them through inherited public getters, exactly as AbstractSquare.getSide() reaches the width by calling getWidth(). Private fields plus public getters is the normal design, in an abstract class as much as anywhere else.

(c) AbstractShape shape = circle; is illegal because AbstractShape cannot be instantiated.

False. That line creates no object at all — it points a new reference at an object that already exists. Declaring a variable, a parameter, a return type or an array element type as an abstract class is not only legal, it is the entire reason for having one.

(d) public abstract double getArea() { return 0; } is a legal way to give an abstract method a fallback answer.

False. abstract and a body are contradictory, and the compiler says so directly:

BadShape2.java:2: error: abstract methods cannot have a body
    public abstract double getArea() { return 0; }
                           ^
1 error

If you want a fallback, write an ordinary concrete method — drop the word abstract and keep the body. Subclasses may then override it or not, as they please. The difference is exactly whether overriding is required or merely permitted.

Things to notice across all four parts. Three of these four are false because people over-read the word "abstract" as meaning "empty" or "special". It only ever means two things: cannot be instantiated, and allowed to have holes. Everything you know about ordinary classes still applies.

4.Interfaces: a contract, not a parent

An abstract class solves the "declare it, do not write it" problem, but it does so by being a parent. Everything that gets getArea() from AbstractShape also gets its fields, its constructor, its printInfo(), and — the expensive part — uses up its one and only extends slot. Sometimes all you want to say is much smaller than that.

Definition— interface

An interface is a reference type in Java, similar to a class, that can contain only constants, method signatures, default methods, static methods and nested types. Interfaces cannot be instantiated — they can only be implemented by classes, or extended by other interfaces.

You declare one with the keyword interface instead of class, and a class signs up to it with implements instead of extends.

The instructor gives four reasons to reach for one, and they are worth reading as four different sentences rather than a list:

  • Define a contract. An interface says what a class can do, without saying anything at all about how it does it.
  • Enable multiple inheritance. A class may implement as many interfaces as it likes, while it may extend only one class. This is section 5, and it is the big one.
  • Support loose coupling. Code can depend on the interface rather than on any particular class that implements it, so the implementation can be swapped out later.
  • Facilitate polymorphism. Different classes — with no common ancestor whatsoever — can be treated the same way as long as they implement the same interface.

Here are the two interfaces the instructor writes for the shape hierarchy. They are tiny on purpose.

Drawable.java

public interface Drawable {
    void draw();

    default void displayDrawInfo() {
        System.out.println("This object can be drawn on screen");
    }
}

Resizable.java

public interface Resizable {
    void resize(double factor);
}
Key Idea— the two words you do not have to type

void draw(); inside an interface means public abstract void draw();. Every method declared in an interface is implicitly public and implicitly abstract, whether you write those words or not.

That is why the semicolon on the end looks like an abstract method — it is an abstract method. An interface is, in the original design, a class in which every method is abstract and nothing else is allowed.

Now AbstractRectangle, which is the class the whole lecture has been building toward. Read the header slowly: it extends one class and implements two interfaces, and the order of those words in the header is fixed — extends always comes first.

AbstractRectangle.java

public class AbstractRectangle extends AbstractShape implements Drawable, Resizable {
    private double width;
    private double height;

    public AbstractRectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    public double getWidth() {
        return width;
    }

    public double getHeight() {
        return height;
    }

    @Override
    public double getArea() {
        return width * height;
    }

    @Override
    public double getPerimeter() {
        return 2 * (width + height);
    }

    // Implementing Drawable
    @Override
    public void draw() {
        System.out.println("Drawing a rectangle with width " + width +
                           " and height " + height);
    }

    // Implementing Resizable
    @Override
    public void resize(double factor) {
        this.width *= factor;
        this.height *= factor;
        System.out.println("Rectangle resized proportionally to width: " +
                           width + ", height: " + height);
    }

    // Original resize method is still available
    public void resize(double widthFactor, double heightFactor) {
        this.width *= widthFactor;
        this.height *= heightFactor;
        System.out.println("Rectangle resized to width: " + width +
                           ", height: " + height);
    }
}

Count the obligations that header creates. From AbstractShape: getArea() and getPerimeter(). From Drawable: draw(). From Resizable: resize(double). Four methods that must appear, from three different sources, and the class supplies all four. The two-argument resize(double, double) at the bottom is not required by anything — it is an ordinary overload the class happens to offer as well.

And here is AbstractSquare, the class the previous section kept referring to. Its header mentions no interfaces at all — and it is still a Drawable and a Resizable, because implements is inherited exactly like extends. What it does do is override the three inherited methods that need to know they are dealing with a square.

AbstractSquare.java

public class AbstractSquare extends AbstractRectangle {

    public AbstractSquare(double side) {
        super(side, side);   // call the parent constructor with equal sides
    }

    public double getSide() {
        return getWidth();   // or getHeight(); they are always the same
    }

    @Override
    public void resize(double widthFactor, double heightFactor) {
        // Use the larger factor so the square stays a square
        double factor = Math.max(widthFactor, heightFactor);
        super.resize(factor, factor);
        System.out.println("Square constraint maintained: using factor " +
                           factor + " for both dimensions");
    }

    @Override
    public void draw() {
        System.out.println("Drawing a square with side length " + getSide());
    }

    @Override
    public String toString() {
        return "Square with side length: " + getSide() +
               ", area: " + getArea() +
               ", perimeter: " + getPerimeter();
    }
}

Notice what getSide() does not do: it does not read a side field, because there isn't one. The side length is already stored, twice over, as the parent's width and height, so getSide() just asks for one of them. Section 7 shows what goes wrong if you keep your own copy instead.

Common Mistake— forgetting public

Interface methods are implicitly public. When you implement one, you must write public yourself — leaving it off is not "the same as the interface", it is package-private, which is narrower, and Java never lets an override reduce visibility:

public class Sticker2 implements Drawable {
    @Override
    void draw() {                          // no "public"
        System.out.println("Drawing a sticker");
    }
}
Sticker2.java:7: error: draw() in Sticker2 cannot implement draw() in Drawable
    void draw() {
         ^
  attempting to assign weaker access privileges; was public
1 error

Read the second line of the message: was public. The compiler is telling you what the interface promised on your behalf. This exact error is a question on the instructor's practice problems, and it catches people every time, because the omission looks like nothing.

5.Many interfaces, one superclass

This is the difference that decides which of the two tools you reach for in real code.

Key Idea— the one-parent rule

A Java class may extends exactly one class. It may implements as many interfaces as it likes, separated by commas.

So extends is a scarce resource and implements is not. Spend the extends slot on the thing the class fundamentally is; use interfaces for everything it can do.

Try to take two parents and the parser gives up before it even gets to the meaning:

TwoParents.java

abstract class Shape1 { public abstract double getArea(); }
abstract class Drawing { public abstract void draw(); }

class Both extends Shape1, Drawing {         // does not compile
    public double getArea() { return 0; }
    public void draw() { }
}
TwoParents.java:4: error: '{' expected
class Both extends Shape1, Drawing {
                         ^
1 error

Java forbids multiple class inheritance deliberately. If two parents both had a describe() method with a body, an object of the child would carry two different bodies for one call and nobody could say which should win. Interfaces sidestep the problem completely: in the original design they have no bodies to conflict, so inheriting ten of them creates no ambiguity at all.

Definition— interface as a reference type

An interface name may be used anywhere a type is wanted: a variable, a parameter, a return type, an array element type. A reference of interface type may point at an object of any class that implements it, and through that reference you may call exactly the methods the interface declares — no more.

Crucially, those classes need share nothing else. Two classes with no common ancestor above Object can sit in the same Drawable[].

Worked Example— an array of things that have nothing in common

TextLabel is not a shape. It does not extend AbstractShape, it has no area, and it would be absurd to give it one. All it promises is that it can be drawn.

6.What else may live inside an interface

So far every interface on this page has been a list of method signatures plus, in one case, a method that came with a body. Java allows four kinds of member in an interface, and the instructor's fuller Drawable shows all four at once. This is a separate program from the short Drawable in section 4 — same name, more inside it — so read it on its own.

Drawable.java

import java.awt.Color;

public interface Drawable {
    // Constants (implicitly public, static and final)
    Color DEFAULT_COLOR = Color.BLACK;

    // Abstract methods (implicitly public and abstract)
    void draw();
    boolean isVisible();

    // Since Java 8: default methods, which come with an implementation
    default void displayInfo() {
        System.out.println("This is a drawable object");
    }

    // Since Java 8: static methods, called on the interface itself
    static void printHelp() {
        System.out.println("Drawable objects can be drawn on a surface");
    }
}
Definition— constants, default methods, static methods

A field in an interface is implicitly public static final — a shared, unchangeable constant. You must give it a value on the spot, because final means it can never be assigned later. There is no such thing as an instance variable in an interface.

A default method is declared with the keyword default and has a body. Every implementing class inherits it and may override it. Default methods were added in Java 8 so that a method could be added to an existing interface without breaking every class that already implemented it.

A static method in an interface has a body and belongs to the interface, not to any object. You call it as Drawable.printHelp(), exactly like Math.sqrt.

Worked Example— a default method taken and a default method overridden

Two classes implement the interface above. Circle is the instructor's, and it overrides displayInfo(). Square is added here for contrast and does not override it. Both supply the two genuinely abstract methods, because there is no choice about those.

Circle.java

public class Circle implements Drawable {
    private double radius;
    private boolean visible;

    public Circle(double radius) {
        this.radius = radius;
        this.visible = true;
    }

    // Must implement all abstract methods from the interface
    @Override
    public void draw() {
        System.out.println("Drawing a circle with radius " + radius);
    }

    @Override
    public boolean isVisible() {
        return visible;
    }

    // The displayInfo() default method can be used as is,
    // or can be overridden if needed
    @Override
    public void displayInfo() {
        System.out.println("Circle with radius: " + radius);
    }
}

Square.java

public class Square implements Drawable {
    private double side;

    public Square(double side) { this.side = side; }

    @Override
    public void draw() {
        System.out.println("Drawing a square with side " + side);
    }

    @Override
    public boolean isVisible() { return true; }
    // displayInfo() is NOT overridden here
}

It compiles, and it prints the interface's own text. That is precisely what "default" means: a body that applies unless the class supplies a better one. Circle supplied a better one, so Circle printed its own line.

Drawable.printHelp() is called on the interface name. There is no object involved and there could not be — a static method is not inherited by implementing classes in a way that lets you call c.printHelp().

Drawable.DEFAULT_COLOR prints as java.awt.Color[r=0,g=0,b=0], which is the toString that java.awt.Color happens to define for black. The point is not the formatting — it is that a single shared constant lives in the interface and every implementing class can read it by name.

Warning— three things an interface may not contain

Each of these is a one-line compile error, and the messages are terse because the parser gives up early.

1. An abstract method with a body (you forgot the word default)

    void draw() {
        System.out.println("drawing");
    }
}

BadIface1.java:2: error: interface abstract methods cannot have body

2. A field with no value (there are no instance variables in an interface)

public interface BadIface2 {
    int count;
    void draw();
}

BadIface2.java:2: error: = expected

3. A constructor (there is nothing to construct)

    BadIface4() { }
    void draw();
}

The = expected message in case 2 is the compiler being helpful in a roundabout way: every field in an interface is final, so the only legal continuation after int count is = something. And because the fields are final, assigning to one later fails too — Drawable.DEFAULT_COLOR = Color.RED; gives cannot assign a value to static final variable DEFAULT_COLOR.

One more thing an interface can do: extend another interface, with extends, exactly as a class would. Here is the instructor's example.

Shape.java

public interface Shape {
    double getArea();
    double getPerimeter();
}

ColoredShape.java

import java.awt.Color;

public interface ColoredShape extends Shape {
    Color getColor();
    void setColor(Color color);
}

A class that says implements ColoredShape must now write all four methods, because ColoredShape carries Shape's two along with its own. And a ColoredShape reference may call all four, while a Shape reference pointed at the same object may call only two — the same widening rule as always. Unlike a class, an interface may extend several interfaces at once: interface A extends B, C is legal, because there are still no competing bodies to choose between.

7.Abstract class or interface?

You now have two mechanisms that both let you declare a method without writing it. They overlap, they are not interchangeable, and this table is the thing to memorise. It is the instructor's, with a few rows added.

Key Idea— is-a versus can-do

Read an extends as "is a": an AbstractRectangle is an AbstractShape. Read an implements as "can": an AbstractRectangle can be drawn and can be resized.

A class has exactly one answer to "what is it?" and any number of answers to "what can it do?" — which is precisely why Java gives you one extends and unlimited implements.

The instructor's decision rule, which is the same idea stated as a checklist:

Procedure— choosing between the two

Use an interface when:

  1. You need to define common behavior for unrelated classes.
  2. You need multiple inheritance — the class already extends something else, or will need to.
  3. You want to specify what a class does, not how it does it.

Use an abstract class when:

  1. You want to share code among closely related classes.
  2. You need to declare non-public members.
  3. You need instance variables or constructors.
  4. You want to provide a partial implementation.

And when both apply — which is common — use both, exactly as AbstractRectangle does. The two mechanisms were never meant to compete.

Quick Check 14.10

For each design, say whether you would write an interface, an abstract class, or both, and give one sentence of justification.

(a) Every employee in a payroll system has a name, an ID and a hire date, and every employee can compute their pay — but salaried, hourly and commissioned employees compute it completely differently.

Abstract class. Three fields shared by every subclass means instance variables and a constructor to initialise them, and neither is possible in an interface. computePay() is the abstract method; getName() and toString() are concrete and written once.

(b) A file, a database row and a network message can all be saved, and your program has one saveAll routine that should handle a mixture of them.

Interface. The three classes have nothing in common — no shared fields, no shared code, and they almost certainly already extend different things. All they share is a capability, which is exactly what an interface is for. saveAll takes a Saveable[].

(c) The shape hierarchy on this page: shapes share an area and a perimeter, some of them can be drawn on screen, and some of them can be resized.

Both, and this is why the instructor's example is built the way it is. "Has an area and a perimeter" is what a shape is, and printInfo() is real shared code, so that is the abstract class. "Can be drawn" and "can be resized" are capabilities that some shapes have and some non-shapes also have — TextLabel can be drawn and is not a shape at all — so those are interfaces.

(d) A Comparable notion: any two objects of the same kind can be put in order.

Interface — and Java agrees, which is why java.lang.Comparable is one. Being orderable is a capability, it applies to classes with no relationship (String, Integer, Date), and there is no shared code or state to inherit. Any class that wants to be sortable implements it, whatever else it already extends.

Things to notice across all four parts. Ask two questions in order. Is there shared state or shared code? If yes, you need an abstract class, because an interface cannot hold either. Do unrelated classes need this? If yes, you need an interface, because they cannot all extend one parent. Answer both yes and you write both, as in part (c).

Common Mistake— storing the same fact twice

AbstractSquare inherits width and height from AbstractRectangle, and it is tempting to add a side field of its own so the class has a name for the thing it cares about. Do not — unless you are prepared to keep it in step forever:

class BadSquare extends AbstractRectangle {
    private double side;                       // a second copy of the same fact

    public BadSquare(double side) {
        super(side, side);
        this.side = side;
    }

    public double getSide() { return side; }   // reads the copy, not the parent

    @Override
    public void draw() {
        System.out.println("Drawing a square with side length " + getSide());
    }
}

        sq.draw();
        sq.resize(2.0);
        sq.draw();

The square was resized to 10 and still says 5, because resize is inherited from AbstractRectangle and knows nothing about a side field it has never heard of. This is not a rule about squares. Any time a subclass duplicates state that its parent already owns, a parent method that updates the original will silently leave the copy stale. Derive, do not duplicate.

Quick Check 14.11

Which of these headers are legal Java? AbstractShape, AbstractRectangle, Drawable and Resizable are as on this page.

(a) class H1 extends AbstractRectangle implements Drawable

Legal. It is also redundant — AbstractRectangle already implements Drawable, so H1 would be a Drawable without the second clause — but saying it again compiles and costs nothing. You have now seen this redundancy three times: here, in Practice Problem 2's Square, and in Practice Problem 4's Orange.

(b) class H2 implements Drawable extends AbstractShape

Not legal. The order is fixed: extends first, then implements. Getting it backwards is a pure syntax error, and the parser gives up at the word it did not expect:

H2.java:1: error: '{' expected
public class H2 implements Drawable extends AbstractShape {
                                   ^
1 error

There is a reason for the order beyond convention: there is at most one extends, so putting it first keeps the interesting, unbounded part of the header at the end.

(c) interface H3 extends Drawable, Resizable

Legal. An interface uses extends (not implements) to build on other interfaces, and unlike a class it may extend several at once — there are no competing method bodies to choose between. A class that says implements H3 must then supply draw(), resize(double) and anything H3 adds of its own.

(d) class H4 extends AbstractShape, Object

Not legal, for the reason section 5 gave: one extends per class, full stop. The parser reports the same '{' expected at the comma.

Things to notice across all four parts. Two words, two rules. extends takes exactly one name and appears at most once, whether the class is abstract or not. implements takes a comma-separated list of any length — and on an interface, confusingly, that list is spelled extends too. When you see extends in a header, look at the first keyword of the declaration to know which rule applies.

FormattedDocument is where the marks are lost. It must call super(content), because Document has no no-argument constructor. And it has to read content — which is private, so it cannot touch it directly. The cleanest fix that respects the stated requirement is a protected getter on Document.

Document.java

public class Document implements Printable {
    private String content;

    public Document(String content) {
        this.content = content;
    }

    protected String getContent() {
        return content;
    }

    @Override
    public void printInfo() {
        System.out.println(content);
    }

    @Override
    public void printInfo(int times) {
        for (int i = 0; i < times; i++) {
            printInfo();
        }
    }
}

public class FormattedDocument extends Document {

    @Override

public interface A {

A small library system needs to model books, DVDs and staff members.

  • Every library item has a title and an ID number, can report a getLateFeePerDay(), and can describe() itself. Books and DVDs charge different late fees. The describe() output is the same shape for every item: the title, then the ID.

Plan. Apply the two questions from Quick Check 14.10. Is there shared state or shared code? Yes — every item has a title and an ID, and describe() is written once for all of them. Quick Check 14.12

One line each. These are the whole lecture.

(a) You have written a class with one abstract method and forgotten to mark the class abstract. What does the compiler say?

It reports the class as not overriding its own abstract method — which reads oddly until you realise the rule is uniform:

BadShape.java:1: error: BadShape is not abstract and does not override abstract method getArea() in BadShape
public class BadShape {
       ^
1 error

Note in BadShape at the end: the method it is complaining about is in the very class it is complaining about. Every concrete class must have a body for every abstract method visible to it, and it makes no difference where the declaration came from.

(b) Why can an interface not have a constructor?

Because a constructor's job is to initialise the fields of a new object, and an interface has neither — no instance fields to initialise, and no objects, since it cannot be instantiated. An abstract class cannot be instantiated either, but it does own fields, and some subclass object will contain them, so its constructor has real work to do.

(c) A class already extends AbstractShape. You now want it to be usable anywhere a Comparable is wanted. What do you write, and what could you not have done if Comparable had been an abstract class?

Add implements Comparable to the header and write the required method. You could not have done it at all if Comparable were an abstract class: the one extends slot is already spent on AbstractShape, and Java has no second one.

This is the practical reason the Java library defines capabilities as interfaces. Comparable, Runnable and Swing's listener types are all interfaces precisely so that any class, whatever it already extends, can sign up.

(d) In one sentence each: what does an abstract class give you that an interface cannot, and what does an interface give you that an abstract class cannot?

An abstract class gives you state and construction — instance fields, non-public members, and a constructor that runs on every object in the hierarchy.

An interface gives you multiplicity — a class may implement any number of them, so completely unrelated classes can share a type.

Things to notice across all four parts. Every question on this page comes back to those two sentences. If a design needs shared data, only an abstract class will do. If it needs unrelated classes to share a type, only an interface will do. Needing both is normal, and writing both is the answer. The header class AbstractRectangle extends AbstractShape implements Drawable, Resizable is not a compromise; it is the design.

Lecture Summary
  • An abstract method is a signature with a semicolon and no body. A class containing one must be declared abstract; the reverse does not follow.
  • An abstract class cannot be instantiated — AbstractShape is abstract; cannot be instantiated — but variables, parameters, return types and arrays of that type are all perfectly legal.
  • A concrete subclass must implement every inherited abstract method, or declare itself abstract too. The error names the exact method: is not abstract and does not override abstract method getPerimeter().
  • An abstract class keeps everything else a class has: private fields, concrete methods, and a constructor, which runs on every subclass object via super(...) even though you can never call new on it yourself.
  • A concrete method may call an abstract one — printInfo() calls getArea(). That is the whole point: shared code in the parent, the unwritable part left as a hole.
  • An interface declares a contract. Its methods are implicitly public and abstract; leaving public off an implementation gives attempting to assign weaker access privileges.
  • A class extends one class and implements as many interfaces as it likes. That is the difference that decides the design. extends is "is a"; implements is "can".
  • An interface name is a reference type, so a Drawable[] can hold classes with no common ancestor — and through it you may call only what the interface declares.
  • Interfaces may also hold constants (public static final), default methods with bodies, and static methods; and one interface may extends another.
  • Choose an abstract class when you need shared state, constructors or non-public members; an interface when unrelated classes need a common type. Needing both is normal.
