1.When an array is the wrong container

Last time you learned to handle things that go wrong at run time: try/catch, throw, throws, and how to write an exception class of your own. Today we put that to work almost immediately — the very first data structure we build will throw an exception when you ask it for an element it does not have.

But the real starting point is a complaint about arrays. You have used them since Lecture 3, and they have two properties you have probably been quietly working around.

Definition— data structure

A data structure is a specialized format for organizing, processing, retrieving and storing data. Choosing one is a design decision: each structure makes some operations cheap and others expensive, and you pick the one whose cheap operations are the ones your program does most.

Today we build three of the most fundamental: a linked list, a stack and a queue.

Here is the complaint, made concrete. Suppose you have five numbers in an array and you need to insert a sixth in the middle.

Worked Example— what an array makes you pay for

This program stores 10, 20, 30, 40, 50 and then inserts 25 at index 2. Before you open the toggle, answer two questions: how many elements have to move, and what happens to the 50?

ArrayLimits.java

public class ArrayLimits {
    public static void main(String args[]) {
        int[] a = new int[5];
        a[0] = 10; a[1] = 20; a[2] = 30; a[3] = 40; a[4] = 50;
        System.out.print("Start:  ");
        print(a);

        // Insert 25 at index 2. Everything from index 2 rightward must shift.
        int newValue = 25, at = 2;
        for (int i = a.length - 1; i > at; i--)
            a[i] = a[i - 1];       // 4 moves for a 5-slot array
        a[at] = newValue;
        System.out.print("After:  ");
        print(a);

        System.out.println("The 50 fell off the end: the array cannot grow.");

        // And there is no room for a sixth element at all.
        try {
            a[5] = 60;
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("a[5] = 60 threw " + e);
        }
    }

    public static void print(int[] a) {
        for (int i = 0; i < a.length; i++) System.out.print(a[i] + " ");
        System.out.println();
    }
}
Start:  10 20 30 40 50
After:  10 20 25 30 40
The 50 fell off the end: the array cannot grow.
a[5] = 60 threw java.lang.ArrayIndexOutOfBoundsException: Index 5 out of bounds for length 5

Two separate problems, both structural:

  • Fixed size. new int[5] reserves exactly five slots, once, forever. There is no a.grow(). To get a sixth slot you must allocate a whole new array and copy everything across.
  • Insertion means shifting. To open a hole at index 2 in a list of n items, you move the n − 2 items after it. Insert near the front of a million-element array and you move nearly a million values to store one.

What the array is good at is the thing we are about to lose: a[7] reaches the eighth element instantly, no matter how big the array is, because the slots are laid out consecutively in memory and the JVM can compute the address.

You have met one fix already: ArrayList from Lecture 6 grows for you. But look at how it does it — internally it holds an array, and when that array fills up it allocates a bigger one and copies. add(0, x) still shifts everything. The growth is hidden, not free.

The alternative is to stop insisting that the elements sit next to each other in memory. If each element carries directions to the next one, they can live anywhere, and inserting means rewriting one set of directions rather than moving a thousand values.

Key Idea

An array stores its elements next to each other and finds element i by arithmetic. A linked list stores its elements anywhere and finds element i by following i arrows. That single trade decides everything else: the list gives up instant random access, and buys unlimited growth and cheap insertion.

Quick Check 21.1

For each operation, say whether an array or a linked list handles it better, and why.

(a) "Give me the 500th element."

Array. a[499] is one address calculation, and it costs the same whether the array holds 500 elements or 500 million. A linked list has no way to jump: it must start at the first node and follow 499 arrows.

(b) "Insert a new value right after the first element."

Linked list. Every later element in an array shifts one slot to the right — that is work proportional to the size of the array. In a linked list you create one node and change two arrows, and the cost is the same whether the list has three elements or three million.

(c) "I have no idea how many values there will be — somewhere between 3 and 300,000."

Linked list. An array forces you to guess. Guess low and you overflow; guess high and 299,997 slots sit empty. A linked list allocates exactly one node per value as the values arrive, which is what her notes mean by dynamic size and no wasted memory allocation.

Things to notice across all three parts. There is no winner here, only a trade. Write down the operations your program actually performs most often, and pick the structure that makes those cheap. That habit is most of what "choosing a data structure" means in practice.

2.The Node: a value, and an arrow

Everything today is built from one small class. It has two fields: a piece of data, and a reference to another object of the same class.

Definition— node, linked list, head, tail

A node is an object holding two things: the data (the value being stored) and a reference to the next node in the sequence.

A linked list is a linear data structure made of nodes chained together by those references. The head is a reference to the first node; the tail is a reference to the last node. The last node's next is null, which is how a traversal knows it has reached the end.

An empty list is head == null. There is nothing else to it — the list is the reference to its first node.

This is the moment Lecture 8 pays off. A field of a class type does not hold an object; it holds a reference — an arrow to an object living somewhere on the heap. The next field of a Node is exactly that: an arrow to another Node. Nothing is nested, nothing is copied, and a Node does not "contain" the rest of the list. It points at it.

Node.java

public class Node {
   private Integer data;    // Stores the actual value
   private Node next;       // Reference to the next node

   // Default constructor
   public Node() {
      data = null;
      next = null;
   }

   // Parameterized constructor
   public Node(Integer d, Node n) {
      data = d;
      next = n;
   }

   // Getters and setters
   public Integer getData() { return data; }

   public Node getNext() { return next; }

   public void setData(Integer d) { data = d; }

   public void setNext(Node n) { next = n; }
}

Two details in that class are worth pausing on.

  • The field next has type Node. A class may declare a field of its own type, because the field is a reference, not a copy. If Java tried to embed one Node inside another the definition would be infinitely large; an arrow costs the same regardless of what it points at.
  • The data is Integer, not int. Integer is the wrapper class from Lecture 6 — an object holding an int. Because it is an object, data can be null, and because of autoboxing you can still write new Node(10, null) and let Java wrap the 10 for you. Remember this choice; §7 comes back to it.
Worked Example— a chain built by hand, with no list class at all

Before we write a LinkedList class, build a list out of nothing but three Node objects. Notice that the nodes are created back to front: to hand a node its next you need the next node to already exist.

Predict two things before you open the toggle: what the first loop prints, and what the list looks like after head.setNext(extra).

NodeChain.java

public class NodeChain {
    public static void main(String args[]) {
        // Build the chain back to front, so each node can point at the one after it.
        Node third  = new Node(30, null);
        Node second = new Node(20, third);
        Node first  = new Node(10, second);

        // "The list" is nothing more than a reference to the first node.
        Node head = first;

        // Walk it. This loop is the traversal you will write a hundred times.
        Node n = head;
        while (n != null) {
            System.out.print(n.getData() + " --> ");
            n = n.getNext();
        }
        System.out.println("null");

        // Proof that these are references, not copies.
        System.out.println("head.getNext() == second ? " + (head.getNext() == second));
        System.out.println("third.getNext() is        " + third.getNext());

        // Splice a new node between first and second — no shifting, two assignments.
        Node extra = new Node(15, head.getNext());
        head.setNext(extra);

        n = head;
        while (n != null) {
            System.out.print(n.getData() + " --> ");
            n = n.getNext();
        }
        System.out.println("null");
    }
}
10 --> 20 --> 30 --> null
head.getNext() == second ? true
third.getNext() is        null
10 --> 15 --> 20 --> 30 --> null

The traversal loop. Learn these three lines as a single unit; you will write them in every method for the rest of the lecture.

Node n = head;                 // start at the front
while (n != null) {            // stop when you fall off the end
    // ... do something with n.getData() ...
    n = n.getNext();           // step to the next node
}

n is a walker: a local reference that moves along the chain. Assigning n = n.getNext() does not move any node — it moves the arrow that is looking at them, exactly like i++ in an array loop. And while (n != null) is the termination test only because the last node's next is null.

head.getNext() == second is true because == on references asks "same object?", and there is genuinely only one object called 20. second and first.next are two arrows to it.

The splice. Inserting 15 between 10 and 20 took two assignments and moved nothing:

Splicing 15 in between 10 and 20

before                head
                       |
                       v
                    [10| o-]--------->[20| o-]-->[30|null]

step 1: new Node(15, head.getNext())
        the new node points at 20; nothing else has changed yet
                    [10| o-]--------->[20| o-]-->[30|null]
                                       ^
                    [15| o-]-----------/

step 2: head.setNext(extra)
        the 10 now points at the new node instead of at 20
                    [10| o-]-->[15| o-]-->[20| o-]-->[30|null]

The order matters enormously. The new node is given its forward link first, while head.getNext() still reaches the 20. Do it the other way round — head.setNext(extra) before extra knows where to point — and you have overwritten the only arrow to the rest of the list, and 20 and 30 are gone.

Quick Check 21.2

Someone tries to build the same three-node chain front to back instead of back to front:

Node first  = new Node(10, null);
Node second = new Node(20, null);
Node third  = new Node(30, null);
Node head = first;

(a) What does the traversal loop print now, and why?

It prints 10 --> null. Three Node objects exist, but none of them points at another: every next was set to null. The walker starts at first, prints 10, then n = n.getNext() makes n null and the loop ends. The 20 and the 30 are perfectly good objects that simply are not in the list.

(b) Add the two statements that repair the chain, without creating any new Node.

first.setNext(second);      // the 10 node now points at the 20 node
second.setNext(third);      // the 20 node now points at the 30 node

Now the arrows exist and the same loop prints 10 --> 20 --> 30 --> null.

Things to notice across both parts. Creating the objects and linking them are two separate jobs. Building back to front lets the constructor do the linking for you (new Node(20, third)); building front to back means you must come back with setNext afterwards. Both are fine — what is not fine is doing only half of it, which is the most common way a first linked list quietly loses its data.

3.Building the LinkedList: addHead, addTail, removeHead

Handling loose Node variables works, but it puts the bookkeeping on whoever uses the list. Wrap it in a class instead. The class holds three private fields — the head, the tail and the size — and every method's job is to keep all three consistent.

Procedure— the three invariants a list method must preserve

Every method you write on this class must leave all three of these true:

  1. head refers to the first node, or is null if the list is empty.
  2. tail refers to the last node — the one whose next is null — or is null if the list is empty.
  3. size equals the number of nodes reachable from head.

Almost every linked-list bug you will ever write is one of these three quietly going false. When a list misbehaves, check them in order.

Here is the class from the Spring 2025 notes, in full.

LinkedList.java

public class LinkedList {
   // Instance variables
   private Node head, tail;  // References to first and last nodes
   private int size;         // Number of elements in the list

   // Constructor
   public LinkedList() {
      head = tail = null;    // Empty list has no nodes
      size = 0;
   }

   // Utility methods
   public int size() {
      return size;
   }

   public boolean isEmpty() {
      return size == 0;
   }

   // Add element to the front of the list
   public void addHead(Integer d) {
      // Create new node that points to current head
      Node n = new Node(d, head);
      head = n;              // New node becomes the head
      size++;
      if (tail == null)      // If list was empty
         tail = head;        // Head is also the tail
   }

   // Add element to the end of the list
   public void addTail(Integer d) {
      Node n = new Node(d, null);
      if (tail == null)      // If list is empty
         head = tail = n;    // New node is both head and tail
      else {
         tail.setNext(n);    // Current tail points to new node
         tail = n;           // New node becomes the tail
      }
      size++;
   }

   // Remove the first element
   public Integer removeHead() throws Exception {
      if (head == null)
         throw new Exception("Empty List");
      Node n = head;
      head = head.getNext(); // Second node becomes head
      if (head == null)      // If list becomes empty
         tail = head;        // Tail is also null
      size--;
      return n.getData();    // Return removed value
   }

   // Display the list
   public String toString() {
      String ans = "";
      Node n = head;
      while (n != null) {
         ans += n.getData();
         ans += "-->";
         n = n.getNext();
      }
      return ans;
   }
}

Read the three interesting methods one at a time.

addHead is two lines plus a special case. new Node(d, head) builds a node whose next is whatever the head currently is — that is the entire insertion. Then head is moved to the new node. If the list was empty, head was null, so the new node's next is null, which is correct; the only extra work is pointing tail at it too, because a one-node list has the same node as head and tail.

addHead(5) on the list 10 20 30

before      head ---> [10| o-]-->[20| o-]-->[30|null] <--- tail

new Node(5, head)
            head ---> [10| o-]-->[20| o-]-->[30|null] <--- tail
                       ^
            [ 5| o-]---/

head = n
            head ---> [ 5| o-]-->[10| o-]-->[20| o-]-->[30|null] <--- tail

addTail needs the tail field to be fast. Without it you would have to walk the whole list to find the last node every single time. With it, appending is: build a node, point the old tail at it, and move tail. The if (tail == null) branch covers the empty list, where there is no old tail to point at and the new node becomes both ends.

removeHead is where the exception lives. There is no sensible Integer to return from an empty list, so the method throws instead — the Lecture 20 material, used in anger on the first day it is available. Note the signature: throws Exception is a checked exception, so every caller must either catch it or declare throws itself. That is not an accident; it forces the caller to decide what an empty list means for their program.

Quick Check 21.3

Suppose the class had no tail field at all — only head and size.

(a) Write addTail under that restriction.

You would have to find the last node yourself, by walking there:

public void addTail(Integer d) {
    Node n = new Node(d, null);
    if (head == null) {          // empty list: the new node is the head
        head = n;
    } else {
        Node p = head;
        while (p.getNext() != null) p = p.getNext();   // walk to the last node
        p.setNext(n);
    }
    size++;
}

Note the loop condition: p.getNext() != null, not p != null. You want to stop on the last node, not one past it — if p became null you would have nothing to call setNext on.

(b) Which of addHead, addTail and removeHead would get slower, and by how much?

Only addTail, and it goes from a fixed handful of steps to one step per node in the list. Building a list of 1,000 elements with addTail would do about half a million pointer-follows instead of 1,000.

addHead and removeHead are untouched, because they only ever work at the front, which head already gives you directly.

Things to notice across both parts. The tail field is not decoration — it is the entire reason enqueue is cheap, and therefore the reason a Queue built on this list is worth having. Extra fields that make an operation fast are a standard trade: you pay a little memory and a little bookkeeping (every method that could change the last node must maintain tail) to make a common operation cheap.

Common Mistake— forgetting to reset the tail

The two lines inside removeHead that look like a formality are not:

if (head == null)      // If list becomes empty
   tail = head;        // Tail is also null

Delete them and every existing test still passes, because nothing that only adds and reads can tell the difference. The damage appears one step later. Here is a copy of the class with exactly those two lines removed:

class BadList {
    private Node head, tail;
    private int size;

    public BadList() { head = tail = null; size = 0; }

    public boolean isEmpty() { return size == 0; }
    public int size() { return size; }

The list now claims to hold one element and prints as empty. tail was still pointing at the removed 10, so addTail(99) attached the 99 to a node that head can no longer reach. The 99 exists; it is simply not in the list. Invariants 2 and 3 both went false, and no exception was thrown to tell you.

This is the shape of most linked-list bugs: not a crash, but a structure that lies about itself. Check the invariants after every method you write, especially in the empty-list and last-node cases.

Quick Check 21.5

Add two methods to LinkedList: sum(), returning the total of every value in the list (0 for an empty list), and count(), returning the number of nodes by walking the chain rather than returning the size field. Then write a main that tests both, including on an empty list.

Plan. Both methods are the same traversal loop with a different accumulator. Start the walker at head, loop while it is not null, do the work, step forward. Neither method modifies anything, so neither can break an invariant, and neither needs to throw: an empty list has a perfectly good sum of 0 and count of 0.

Both go inside LinkedList.java, alongside the methods that are already there — they need direct access to the private head field, which is exactly why they belong in the class rather than in the driver.

LinkedList.java

// Add up every value in the list.
public int sum() {
   int total = 0;
   Node n = head;
   while (n != null) {
      total += n.getData();
      n = n.getNext();
   }
   return total;
}

// Count the nodes by walking, instead of trusting the size field.
public int count() {
   int c = 0;
   Node n = head;
   while (n != null) {
      c++;
      n = n.getNext();
   }
   return c;
}

4.Traversal, search and deletion — the pointer surgery

Her class can add at both ends and remove from the front. That is enough to build a stack and a queue, which is where we are going, but a list you cannot search or delete from the middle is not much of a list. Three more methods finish the job, and the third one is the one students lose the thread on, so we will go through it slowly.

Definition— traversal

A traversal is a walk from the head to the end of the list, visiting each node once. It is the only way to reach an element that is not the head, and it costs one step per node — so a linked list has no fast get(i).

Every method in this section is a traversal that stops somewhere interesting.

contains and indexOf stop when they find the value. remove stops at the node before the one it wants to unhook, and that difference is the whole trick.

Key Idea— to delete a node, you need the node in front of it

A singly linked node has no arrow pointing backwards. To remove the node holding 30 from 10 --> 20 --> 30 --> 40, you must change the next of the node holding 20 — and from 30 there is no way to reach 20. So the search loop must stop one node early, holding a reference conventionally called prev.

Here is the complete class with the three methods added. Everything above the comment line is unchanged from §3.

LinkedList.java

public class LinkedList {
   private Node head, tail;
   private int size;

   public LinkedList() { head = tail = null; size = 0; }

   public int size()          { return size; }
   public boolean isEmpty()   { return size == 0; }

   public void addHead(Integer d) {
      Node n = new Node(d, head);
      head = n;
      size++;
      if (tail == null) tail = head;
   }

   public void addTail(Integer d) {
      Node n = new Node(d, null);
      if (tail == null) head = tail = n;
      else { tail.setNext(n); tail = n; }
      size++;
   }

   public Integer removeHead() throws Exception {
      if (head == null) throw new Exception("Empty List");
      Node n = head;
      head = head.getNext();
      if (head == null) tail = head;
      size--;
      return n.getData();
   }

   // ---- the three new methods -------------------------------------------

   // Does the list contain this value? Traversal, stopping early on a hit.
   public boolean contains(Integer d) {
      Node n = head;
      while (n != null) {
         if (n.getData().equals(d)) return true;
         n = n.getNext();
      }
      return false;
   }

   // Position of the first node holding d, or -1 if there is none.
   public int indexOf(Integer d) {
      Node n = head;
      int i = 0;
      while (n != null) {
         if (n.getData().equals(d)) return i;
         n = n.getNext();
         i++;
      }
      return -1;
   }

   // Remove the first node holding d. Returns true if something was removed.
   public boolean remove(Integer d) {
      if (head == null) return false;

      if (head.getData().equals(d)) {        // case 1: it is the head
         head = head.getNext();
         if (head == null) tail = null;      // the list is now empty
         size--;
         return true;
      }

      Node prev = head;                      // case 2: it is further along
      while (prev.getNext() != null && !prev.getNext().getData().equals(d))
         prev = prev.getNext();

      if (prev.getNext() == null) return false;   // ran off the end: not found

      Node victim = prev.getNext();
      prev.setNext(victim.getNext());        // the one link that does the work
      if (victim == tail) tail = prev;       // we just removed the last node
      size--;
      return true;
   }

   public String toString() {
      String ans = "";
      Node n = head;
      while (n != null) {
         ans += n.getData();
         ans += "-->";
         n = n.getNext();
      }
      return ans;
   }
}
Common Mistake— comparing Integer values with ==

The search loops use n.getData().equals(d), not n.getData() == d. The data is an Integer, which is an object, so == compares references — the Lecture 9 lesson, in a new place. It appears to work for small values because Java caches the Integer objects for −128 through 127 and hands out the same one every time, and then silently stops working at 128. Use equals for every wrapper and every String, always.

Two more things about remove before the example.

  • The head is a separate case. There is no node in front of the head, so there is no prev to re-point. Instead you move head itself. Every deletion routine you ever write on a singly linked list will have this shape: a special case for the front, then a general loop for everything else.
  • The condition is written in that order for a reason. prev.getNext() != null && !prev.getNext().getData().equals(d) tests for the end of the list first. && short-circuits, so when prev is the last node the second half is never evaluated and there is no NullPointerException. Swap the two halves and the method crashes on every search that fails.

(b) Explain exactly why. What does n = n.getNext(); actually change?

n is a local reference variable. Assigning to it moves the arrow that n holds; it does not touch any Node object and it certainly does not touch the next field of the node before it. This is the Lecture 8 distinction between rebinding a variable and mutating an object: you have rebound n, and nothing in the list has been mutated.

// The largest value in the list. An empty list has no largest value.
public Integer max() throws Exception {
   if (head == null)
      throw new Exception("Empty List");
   Integer best = head.getData();
   Node n = head.getNext();          // start comparing from the second node
   while (n != null) {
      if (n.getData() > best) best = n.getData();
      n = n.getNext();
   }
   return best;
}

5.Stack: last in, first out

Now the payoff. A stack and a queue are not new storage — they are the list you already have, with a rule about where you are allowed to touch it.

Definition— stack, LIFO

A stack is a linear data structure that follows the Last-In-First-Out (LIFO) principle: the last element added is the first one removed. Elements are added to the top (push) and removed from the top (pop). Looking at the top without removing it is peek.

The picture is a stack of plates. You put a plate on top; you take a plate off the top; you never reach into the middle.

The list gives us addHead and removeHead, and both of them work at the same end. That end is the top of the stack, and that is the entire implementation.

Stack.java

public class Stack {
   private LinkedList data;  // The underlying LinkedList

   public Stack() {
      data = new LinkedList();
   }

   // Remove from top (LIFO principle)
   public Integer pop() throws Exception {
      return data.removeHead();
   }

   // Add to top
   public void push(Integer x) {
      data.addHead(x);
   }

   // Additional useful methods
   public boolean isEmpty() {
      return data.isEmpty();
   }

   public int size() {
      return data.size();
   }
}
Key Idea— the stack owns a list; it is not a list

private LinkedList data; is composition, not inheritance. The Stack has a list rather than being one, and because data is private, nobody outside can call addTail on it. That is the point: the restriction is the data structure. A stack is exactly a list that has had every operation except the two at the front taken away.

Every method here is a one-liner. There is no new storage code anywhere in this file, which is a good sign that you built the list right.

6.Queue: first in, first out

Definition— queue, FIFO

A queue is a linear data structure that follows the First-In-First-Out (FIFO) principle: the first element added is the first one removed. Elements are added at the rear (enqueue) and removed from the front (dequeue). Looking at the front without removing it is front, or peek.

The picture is a line at a counter. You join at the back; you are served from the front; nobody cuts in.

The only change from the stack is which end things go in. A queue adds at the tail and removes from the head, so it uses addTail and removeHead — and this is exactly why the list keeps a tail field. Without it, every enqueue would have to walk the whole list first.

Queue.java

public class Queue {
   private LinkedList data;  // The underlying LinkedList

   public Queue() {
      data = new LinkedList();
   }

   // Remove from front (FIFO principle)
   public Integer dequeue() throws Exception {
      return data.removeHead();
   }

   // Add to rear
   public void enqueue(Integer x) {
      data.addTail(x);
   }

   // Additional useful methods
   public boolean isEmpty() {
      return data.isEmpty();
   }

   public int size() {
      return data.size();
   }
}

Three differences from ours worth naming.

Quick Check 21.12

You want a linked list of Strings as well as one of Integers.

(a) Using only what this lecture covers, what are your two options, and what is wrong with each?

Option 1: copy the files and replace Integer with String throughout, giving StringNode, StringLinkedList and so on. You would write the class once, leaving the element type as a blank to be filled in later, and say at the point of use which type this particular list holds: something like "a list of String" versus "a list of Integer", with the compiler checking every call against whichever you chose. Problem 3 — Insert into the middle (added for these notes)

Add a method insertAfter(Integer target, Integer d) to LinkedList. It inserts a new node holding d immediately after the first node holding target, and returns true. If target is not in the list it changes nothing and returns false. Keep size and tail correct. Then write a driver that inserts into the middle, after the last node, and after a value that is not present.

Plan. This is the mirror image of remove, and it is easier, because the node you need to modify is the one you are searching for — not the one before it. Walk until p holds target or you fall off the end. Then do the two-step splice from §2, in the right order: give the new node its forward link first, then re-point p. The only case needing extra thought is inserting after the last node, which makes the new node the tail.

LinkedList.java

// Insert d immediately after the first node holding target.
// Returns false (and changes nothing) if target is not in the list.
public boolean insertAfter(Integer target, Integer d) {
   Node p = head;
   while (p != null && !p.getData().equals(target))
      p = p.getNext();

   if (p == null) return false;        // target not found

   Node n = new Node(d, p.getNext());  // 1. new node points where p pointed
   p.setNext(n);                       // 2. p now points at the new node
   if (p == tail) tail = n;            // inserted after the last node
   size++;
   return true;
}

Problem 4 — Reverse a linked list in place (added for these notes)

Add a method reverse() to LinkedList that reverses the order of the elements without creating a single new Node — only by re-pointing the links that already exist. It must leave head, tail and size all correct, and it must work on a one-element list and on an empty list.

Plan. Every node's arrow has to be turned around. Walk the list with three markers: prev (the node behind you, which is where the current node should now point), cur (the node you are flipping) and ahead (where you were going to go next — you must save it before you overwrite cur's link, or you lose the rest of the list). When the walk ends, cur is null and prev is sitting on the old last node, which is the new head. The old head becomes the tail, so capture that at the start.

LinkedList.java

// Reverse the list in place: no new nodes, only re-pointed links.
public void reverse() {
   Node prev = null;
   Node cur  = head;
   tail = head;              // the old first node becomes the last
   while (cur != null) {
      Node ahead = cur.getNext();   // remember where we were going
      cur.setNext(prev);            // flip this link backwards
      prev = cur;                   // step both markers forward
      cur  = ahead;
   }
   head = prev;              // prev stopped on the old last node
}

Problem 5 — Reverse a queue using a stack (added for these notes)

Write a static method reverse(Queue q) that reverses the contents of a queue, using only a Stack and the public methods of both classes — no Node, no LinkedList, no array. Then write a main that builds a queue of 1 through 5, prints it, reverses it, and prints it again. Printing a queue is itself part of the exercise: the only way to see the contents is to take them out.

Plan. A queue hands things back oldest-first and a stack hands them back newest-first, so pouring one into the other flips the order. Dequeue everything onto a stack, then pop everything back onto the queue: the item that was at the front went onto the stack first, so it comes off last and ends up at the back.

For printing, dequeue each item, print it, and immediately enqueue it again. After size() rounds every item has been round the loop exactly once and the queue is back in its original order — capture the size before the loop, since the queue is being modified as you go.

ReverseQueue.java

public class ReverseQueue {
    // Empty the queue into a stack, then pour the stack back into the queue.
    public static void reverse(Queue q) throws Exception {
        Stack s = new Stack();
        while (!q.isEmpty()) s.push(q.dequeue());
        while (!s.isEmpty()) q.enqueue(s.pop());
    }

    public static void main(String args[]) throws Exception {
        Queue q = new Queue();
        for (int i = 1; i <= 5; i++) q.enqueue(i);

        System.out.print("before: ");
        show(q);

        reverse(q);

        System.out.print("after:  ");
        show(q);
    }

    // Print a queue by emptying it and putting everything back.
    public static void show(Queue q) throws Exception {
        int n = q.size();
        for (int i = 0; i < n; i++) {
            Integer x = q.dequeue();
            System.out.print(x + " ");
            q.enqueue(x);
        }
        System.out.println("  (size still " + q.size() + ")");
    }
}

after:  5 4 3 2 1   (size still 5)

Things to notice. int n = q.size(); before the loop is essential. Write for (int i = 0; i < q.size(); i++) instead and the condition is re-evaluated every iteration against a queue whose size never changes — you dequeue and enqueue one item each time — so the loop never ends.

Both methods declare throws Exception, because dequeue does and neither of them has anything useful to do about an empty queue. Note that neither can actually throw: both are guarded by isEmpty or by a count. The compiler cannot know that, so the declaration is required anyway — a routine annoyance of checked exceptions.

The reverse method is four lines and touches no nodes at all. That is what a well-designed data structure buys you: the caller works in the vocabulary of the problem (push, pop, enqueue, dequeue) and never has to think about links.

Problem 6 — Decimal to binary, with our own Stack (added for these notes)

Problem 1 converted 50 to binary with java.util.Stack. Do the same job with the Stack we built in §5: write static String toBinary(int n) that returns the binary representation of a positive n, and returns "0" for n equal to 0. Test it on 50, 1, 8 and 255.

Plan. Identical algorithm: repeatedly push n % 2 and halve n, then pop everything back off. n = 0 needs its own answer up front, because the while loop would never run and you would return the empty string.

ToBinary.java

public class ToBinary {
    public static void main(String args[]) throws Exception {
        int[] tests = {50, 1, 8, 255};
        for (int t : tests)
            System.out.println(t + " in binary is " + toBinary(t));
    }

    public static String toBinary(int n) throws Exception {
        if (n == 0) return "0";
        Stack s = new Stack();
        while (n > 0) {
            s.push(n % 2);      // remainders come out least-significant first
            n = n / 2;
        }
        String ans = "";
        while (!s.isEmpty()) ans += s.pop();   // the stack reverses them
        return ans;
    }
}

1 in binary is 1
8 in binary is 1000
255 in binary is 11111111

Things to notice. The only differences from the library version are the missing <> on new Stack() — ours is not generic — and the throws Exception, because our pop is checked and the library's is not. The algorithm is untouched. That is a good sanity check on an implementation: if swapping in your own class changes nothing but the declarations, you have got the behaviour right.

s.push(n % 2) autoboxes an int into an Integer, and ans += s.pop() unboxes and then converts to text. Both happen silently. And 8 giving 1000 is worth a glance: the loop pushes 0, 0, 0, 1, and the stack turns that into 1000.

Lecture Summary
  • An array has a fixed size and makes you shift everything to insert in the middle. A linked list fixes both, and gives up fast random access in exchange.
  • A Node holds a value and a reference to the next node. The last node's next is null, and the list is the reference to its first node.
  • The traversal loop is Node n = head; while (n != null) { ...; n = n.getNext(); }. Every method in the class is a version of it.
  • LinkedList keeps three things true at all times: head is the first node, tail is the last, size is the count. Almost every bug is one of the three going false in the empty-list or last-node case.
  • To insert, point the new node forward first, then re-point the node in front of it. To delete, you need prev — the node before the victim — because a singly linked node has no way back.
  • A Stack is LIFO: push and pop both act on the head. A Queue is FIFO: enqueue adds at the tail, dequeue removes from the head. Both are one private LinkedList and a handful of one-line methods — the same storage, different access rules.
  • removeHead throws a checked Exception("Empty List"), so pop and dequeue do too, and every caller must catch it or declare it. The library classes differ: java.util.Stack.pop throws an unchecked EmptyStackException, and ArrayDeque.poll returns null.
  • Naming your own class Stack, Queue or LinkedList collides with java.util. A wildcard import loses to your class; a single-type import silently shadows it. Prefer a name the library does not use.
  • Everything we built stores Integer and only Integer. Copying the files per type duplicates code; storing Object throws away type checking.

It is the same Node you wrote today with one letter changed, and it is the reason ArrayList<String> has angle brackets in it.
