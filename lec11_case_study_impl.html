1.Where we left off, and the order to build in

Back in Lecture 10 — before the review and the exam — we took an English description — a street with twenty parking spaces, cars that come and go, officers who patrol, meters that run down, tickets that get written — and turned it into a design. We found the nouns, made each important one a class, gave each class its own data, and worked out which class holds which. Today we build it.

Two sessions have passed since then, so start by getting the design back in your head. Here it is in one table. Nothing in it is new; if any row surprises you, reopen Lecture 10 before reading on — today assumes all of it.

Today we write all five, in a specific order, and we run the program at the end of every step. That last habit is the single most useful thing in this lecture, so we start with it.

Definition— dependency

Class A depends on class B if A mentions B anywhere — as the type of a field, as a parameter type, as a return type, or in a new expression. You cannot compile A unless the compiler can also see B.

Reading the design table right to left gives us the dependencies: ParkedCar depends on ParkingMeter; ParkingTicket depends on PoliceOfficer and ParkedCar; PoliceOfficer depends on ParkedCar and ParkingTicket; the simulation depends on everything. ParkingMeter depends on nothing at all.

Key Idea— build inward-out

Write the class with no dependencies first. Then write the class that depends only on what already exists. Keep going. At every point in the build you have a program that compiles and that you can actually run — which means that when something breaks, the thing that broke it is the ten lines you just typed.

Procedure— growing a multi-class program
  1. Pick the next class whose dependencies are all already written.
  2. Write its fields and its constructor. Nothing else yet.
  3. Write a small throwaway class with a main that creates one object and prints it. Compile. Run. Look at the output.
  4. Add one method. Add a line to the throwaway main that calls it. Compile. Run.
  5. Repeat step 4 until the class is done, then throw the test class away (or keep it — it costs nothing and it is the beginning of a real test suite).

The throwaway main is not wasted work. It is how you find out that isExpired returns true a step earlier than you expected, at a moment when the only code in the program is the twenty lines you are looking at.

Quick Check 11.1

Using the dependency list above, write down a legal order in which to compile the five classes, one at a time. Is there more than one legal order? Is there a pair of classes that makes the question impossible to answer as stated?

Plan. Work out, for each class, which other classes it names. A class can go next only if everything it names is already written.

ParkingMeter names nobody, so it goes first. ParkedCar names only ParkingMeter, so it goes second. ParkingTicketSimulation names everything, so it goes last.

The awkward pair. ParkingTicket names PoliceOfficer in its constructor signature, and PoliceOfficer names ParkingTicket as the return type of issueTicket. They depend on each other. There is no order in which one is finished before the other starts, so neither can be compiled on its own.

That is not a design flaw, and it is not rare. Java's answer is that you hand javac both files at once — javac ParkingTicket.java PoliceOfficer.java — and it works the two out together.

Things to notice. A cycle between two classes is fine. A cycle between eight classes usually means the design has a lump in it that wants to be split. Two mutually aware classes that model two things which genuinely refer to each other — an officer writes a ticket, a ticket records an officer — are exactly what you would expect.

2.ParkingMeter: the class with no dependencies

The meter is the smallest class in the system and the only one that mentions no other class, so it goes first. Its entire state is one int.

Definition— timeLeft

timeLeft is the number of minutes of parking still paid for. It starts positive, drops by 5 every simulated five minutes, and is allowed to go negative. A negative timeLeft is not a bug: it is the record of how long the car has been overstaying, and it is exactly the number the fine is computed from.

That one decision — let the counter go past zero instead of clamping it — is what lets a single int carry both "is this car in violation?" and "by how much?".

ParkingMeter.java

import java.util.Random;

public class ParkingMeter {
    private static Random rng = new Random(42);

    private int timeLeft;

    public ParkingMeter() {
        // pay for up to 100 minutes, in multiples of 5
        timeLeft = (rng.nextInt(20) + 1) * 5;
    }

    public boolean isExpired() {
        return timeLeft < 0;
    }

    public void remove(int x) {
        timeLeft -= x;
    }

    public int getTimeLeft() {
        return timeLeft;
    }

    public String getFine() {
        if (timeLeft > -60) return "$25";
        int fine = 25 + (-10) * ((timeLeft + 5) / 60);
        return "$" + fine;
    }
}

Four things about this class are worth stopping on.

  • rng is static. A random-number generator is not part of what makes one meter different from another, so it should not be one per meter. One generator, shared by the whole class, is both correct and cheaper. This is the standard use of static from Lecture 9: a field the class owns rather than a field each object owns.
  • The seed is fixed. new Random(42) produces the same sequence of numbers every time the program runs. That is what makes every output on this page reproducible: run these files yourself and you will get these exact numbers. Write new Random() with no argument and each run is different — which is what you want for a real simulation and a nightmare while you are debugging one.
  • (rng.nextInt(20) + 1) * 5. nextInt(20) gives 0 through 19, so the expression gives 5, 10, 15, …, 100. Reading it inside out is the only way to see that: the + 1 moves the range off zero, and the * 5 makes it a multiple of five so it lines up with the simulation's five-minute clock.
  • getFine returns a String. It hands back "$25", not 25. Keep that in mind — we come back to it, twice.
Worked Example— the throwaway main for step 1

Before writing a second class, prove this one works. Buy some time, then let three simulated hours pass five minutes at a step, printing every half hour.

Quick Check 11.2

The rule from the problem statement is: first hour 25 dollars, each additional hour 10 dollars more. Work out what getFine returns for each of these values of timeLeft, using integer division exactly as Java does it.

public String getFine() {
    if (timeLeft > -60) return "$25";
    int fine = 25 + (-10) * ((timeLeft + 5) / 60);
    return "$" + fine;
}

(a) timeLeft is -30.

$25. -30 > -60 is true, so the method returns from the first line and the formula never runs. The car is half an hour over, which is inside the first hour.

(b) timeLeft is -60.

$25. -60 > -60 is false, so we reach the formula: (-60 + 5) / 60 is -55 / 60. Java truncates toward zero, so that is 0, and 25 + (-10) * 0 is 25. Exactly one hour over is still the first hour.

(c) timeLeft is -65.

$35. (-65 + 5) / 60 is -60 / 60, which is exactly -1, and 25 + (-10) * (-1) is 35. Five minutes past the hour boundary the fine jumps by ten dollars.

(d) timeLeft is -125.

$45. (-125 + 5) / 60 is -120 / 60, which is -2, giving 25 + 20.

Things to notice across all four parts. The + 5 inside the parentheses is doing real work: without it, -60 / 60 would be -1 and a car exactly one hour over would be charged 35 dollars instead of 25. And the truncation matters as much as the arithmetic. If Java rounded toward negative infinity the way some languages do, -55 / 60 would be -1 and every answer above would be ten dollars too high. When you see integer division applied to a negative number, always write out the exact quotient and then chop toward zero.

3.ParkedCar: a class that has-a meter

The meter compiles and behaves. Next up is the only class that depends on it.

Definition— composition, and the has-a relationship

Composition is having an object as an instance variable of another object. We say ParkedCar has-a ParkingMeter. The type of the field is the name of another class:

private ParkingMeter meter;

Declaring the field does not create a meter. It creates a place to put a reference to one, initially null. Somebody has to write meter = new ParkingMeter();, and in this design that somebody is ParkedCar's constructor.

ParkedCar.java

import java.util.Random;

public class ParkedCar {
    static String makes[]  = {"Toyota", "Honda", "Hyundai", "BMW",
                              "Porsche", "Maserati", "Ford", "Chevrolet"};
    static String models[] = {"Sedan", "Station Wagon", "SUV", "Light Truck"};
    static String colors[] = {"Red", "Orange", "Yellow", "Green",
                              "Blue", "White", "Silver"};

    private static Random rng = new Random(1234);

    private String make;
    private String model;
    private String color;
    private String license;
    private ParkingMeter meter;

    public ParkedCar() {
        make    = pickOne(makes);
        model   = pickOne(models);
        color   = pickOne(colors);
        license = generateLicense();
        meter   = new ParkingMeter();
    }

    private String pickOne(String[] choices) {
        return choices[rng.nextInt(choices.length)];
    }

    private String generateLicense() {
        String answer = "";
        for (int i = 0; i < 3; i++)
            answer += (char) ('A' + rng.nextInt(26));
        for (int i = 0; i < 4; i++)
            answer += (char) ('0' + rng.nextInt(10));
        return answer;
    }

    public boolean expiredMeter() {
        return meter.isExpired();
    }

    public void adjustMeter(int x) {
        meter.remove(x);
    }

    public String getFine() {
        return meter.getFine();
    }

    public String getMake()    { return make;    }
    public String getModel()   { return model;   }
    public String getColor()   { return color;   }
    public String getLicense() { return license; }

    public String toString() {
        return getColor() + " " + getMake() + " " + getModel()
             + " License number: " + getLicense();
    }
}

The three arrays at the top are static for the same reason rng is: the list of car makes is a fact about cars in general, not about any one car. If they were instance variables, every one of the hundreds of cars created during the simulation would carry its own copy of the same eight strings.

generateLicense builds a plate like MDL7613 out of characters. 'A' + rng.nextInt(26) is an int between 65 and 90 — remember from Lecture 1 that a char is a number — so the cast (char) is what turns 77 back into the letter M. The digits work the same way from '0'.

Definition— delegation

Delegation is a method that does its work by asking a field object to do the work. ParkedCar.expiredMeter is three words long:

public boolean expiredMeter() { return meter.isExpired(); }

It computes nothing. It forwards the question to the meter and hands the answer back. So do adjustMeter and getFine.

Key Idea— why not just ask the meter directly?

Because nobody outside ParkedCar is allowed to see the meter. meter is private, and there is deliberately no getMeter(). The only way the simulation can find out whether a car is in violation is to ask the car.

That buys you something concrete: in §8 we add a monthly-permit car that is never in violation no matter what its meter says. Because every caller goes through expiredMeter(), that change is four lines inside ParkedCar and nothing anywhere else. Had the simulation been writing street[i].getMeter().isExpired(), the rule would have had to be bolted onto every caller.

Common Mistake— declaring the field but never creating the object

Delete one line from the constructor — meter = new ParkingMeter(); — and the class still compiles perfectly. meter is simply left at its default value of null. Here is what running it looks like:

Quick Check 11.3

ParkedCar has getMake, getModel, getColor and getLicense, but no getMeter.

(a) Suppose you added public ParkingMeter getMeter() { return meter; }. Write the line the simulation could then use, instead of street[i].expiredMeter(), to find out whether space i is in violation.

street[i].getMeter().isExpired() — two dots, because you first ask the car for its meter and then ask the meter the question.

It compiles and it gives the right answer today. What it costs you is that the simulation now knows ParkedCar is built out of a ParkingMeter, and knows the name isExpired. Change either of those inside ParkedCar and the simulation breaks.

(b) With getMeter() present, what could a caller do that the current design makes impossible?

Anything the meter's public methods allow — including street[i].getMeter().remove(-500);, which quietly puts eight hours of free parking on somebody else's meter. getMeter() hands out a reference to the car's own internal object, and once a caller holds that reference the car has no say in what happens to it.

Things to notice across both parts. A getter that returns a String or an int gives away a copy of a value. A getter that returns an object gives away the object itself. That is why getLicense() is harmless and getMeter() is not, even though they look like the same kind of method.

Quick Check 11.4

Write the method ParkedCar.addTime(int minutes), which puts more time on the car's meter. Do not add any field, and do not add anything to ParkingMeter — use the methods it already has. Then say what addTime(30) does to a meter that currently reads -45.

Plan. ParkingMeter has exactly one method that changes timeLeft: remove(int x), which does timeLeft -= x. Adding time is removing a negative amount. Like every other method in this class, addTime delegates.

public void addTime(int minutes) {
    meter.remove(-minutes);
}

Starting from -45, remove(-30) computes -45 - (-30), which is -15. The car is still expired, just less so.

Things to notice. remove(-minutes) works but reads badly — "remove minus thirty" is a sentence nobody says. If this method mattered, the honest fix would be to add public void add(int x) { timeLeft += x; } to ParkingMeter and have addTime call that. A method whose name says the opposite of what it does is a bug waiting for the next person who reads it.

4.ParkingTicket: composing two objects

A ticket is the piece of paper. It records three things: which car, how much, which officer. It is the first class in this system that takes two different object types in its constructor.

ParkingTicket.java

public class ParkingTicket {
    private String officer = "Officer badge number: ";
    private String car = "Parked Car information: ";
    private String fine = "Fine: ";

    public ParkingTicket(PoliceOfficer policeOfficer, ParkedCar parkedCar) {
        officer += policeOfficer.getBadgeNumber();
        car += parkedCar.toString();
        fine += parkedCar.getFine();
    }

    public String toString() {
        return car + " | " + fine + " | " + officer;
    }
}

Every field is initialized at its declaration to a label, and the constructor appends the data to that label with +=. When the constructor finishes, car holds the single string "Parked Car information: Yellow Honda Sedan License number: IJO0277" and nothing else.

Key Idea— where the fine is computed, and where it is recorded

Follow the money through one line of the constructor: fine += parkedCar.getFine();

  • ParkingMeter.getFine() computes the amount. It is the only object that knows timeLeft, so it is the only object that can compute it.
  • ParkedCar.getFine() forwards the question. It knows which meter.
  • ParkingTicket records the answer. A ticket is a permanent statement of what was owed at a moment in time, so the amount has to be stored somewhere that will not change afterwards.
  • PoliceOfficer does none of this. It never sees a number.

The general rule: the arithmetic belongs to whoever owns the data it is computed from. If the fine formula had been written inside PoliceOfficer, the officer would have needed the meter's timeLeft, ParkingMeter would have needed a public getter for it, and a change to the fine schedule would mean editing the officer. Instead, changing the fine schedule means editing eight lines of ParkingMeter and recompiling.

Quick Check 11.5

The city raises fines: the first hour becomes 40 dollars and each additional hour adds 15. Which of the five classes must you edit? Which of the five must you recompile?

Plan. Ask where the numbers 25 and 10 physically appear, and separately ask which files javac needs to see again.

Edit: one class. ParkingMeter, and only its getFine method. The numbers 25 and 10 appear nowhere else in the system. ParkedCar forwards a String it never inspects; ParkingTicket glues that String onto a label; PoliceOfficer and the simulation never see it.

Recompile: all of them, in practice. Editing a .java file means its .class file is stale, and the simplest safe thing is javac *.java. javac is fast and getting this wrong — running against a .class file compiled from source you have since changed — produces some of the most confusing bugs there are.

Things to notice. "How many classes do I have to edit to make this change?" is the practical test of a design. One is the answer you want. If your answer had been "ParkingMeter, and also PoliceOfficer, and also the simulation", the fine calculation would be in the wrong place.

Worked Example— a ticket is a snapshot, not a live view

Here is the subtlest thing in the whole case study. ParkingTicket does not store the ParkedCar. It stores three String values pulled out of the car at the moment the constructor ran.

So: issue a ticket, let two more hours go by, and print the same ticket object again. Predict what happens before you open the toggle.

SnapshotDemo.java

public class SnapshotDemo {
    public static void main(String args[]) {
        ParkedCar car = new ParkedCar();
        PoliceOfficer officer = new PoliceOfficer();

        for (int step = 1; step <= 25; step++) car.adjustMeter(5);
        ParkingTicket first = officer.issueTicket(car);
        System.out.println("ticket issued now: " + first);

        // Two more hours go by; the meter falls further behind.
        for (int step = 1; step <= 24; step++) car.adjustMeter(5);
        System.out.println("the car's fine now: " + car.getFine());
        System.out.println("the same ticket:   " + first);
    }
}

the car's fine now: $55
the same ticket:   Parked Car information: Yellow Maserati Station Wagon License number: YQH9977 | Fine: $35 | Officer badge number: 17

The car now owes 55 dollars. The ticket still says 35, because the ticket never had a way to ask again — the number 35 was copied into a String and the connection to the car was dropped on the spot.

That is the correct behaviour for a ticket. A citation states what was owed when it was written; it does not silently inflate while it sits in the officer's book.

Now the alternative. LiveTicket stores the two objects instead of copying text out of them, and rebuilds the line every time it is printed. Same program, same meter, one field-type change:

LiveTicket.java

public class LiveTicket {
    private PoliceOfficer officer;
    private ParkedCar car;

    public LiveTicket(PoliceOfficer policeOfficer, ParkedCar parkedCar) {
        officer = policeOfficer;
        car     = parkedCar;
    }

    public String toString() {
        return "Parked Car information: " + car
             + " | Fine: " + car.getFine()
             + " | Officer badge number: " + officer.getBadgeNumber();
    }
}

Run SnapshotDemo again with LiveTicket in place of ParkingTicket. Both printed lines come from the same object, two hours apart. Are they the same line?

The fine changed from 35 to 55 without anybody touching the ticket, because car is a reference to the same object the simulation is still driving. toString recomputes from live data every time it is called.

5.PoliceOfficer, and errors in files you did not touch

The officer is the shortest class in the system, and one of its four lines contains the keyword this lecture has been building toward.

PoliceOfficer.java

import java.util.Random;

public class PoliceOfficer {
    private static Random rng = new Random(7);

Quick Check 11.6

Suppose a student rewrites issueTicket like this, thinking it is simpler:

  2. Find the part of it that belongs to another class: meter.getFine().

  4. Ask what this method promises to return. Look up two lines: public String getFine().

Warning— the ripple that stops silently

When you change a method's return type, the compiler will catch every caller that assigns the result or returns it. It will not catch callers that only concatenate it into a String, because concatenation accepts every type there is. After a change like this, run the program and read the output, do not just wait for javac to go quiet.

6.The simulation driver

Four classes, all compiling, all tested. The last file contains no new class design at all — it is a main that sets up a street and lets a day run.

Procedure— the simulation, in English first
  1. Make an empty ArrayList<ParkingTicket> to collect violations.
  2. Make a ParkedCar[] of length 20. Every element starts as null, and null is what "this space is empty" means.
  3. For each of 24 hours, for each 5-minute slot in the hour:
    1. With probability 5%, an officer shows up for this slot.
    2. For each of the 20 spaces: if it is empty, fill it with probability 20%. Otherwise, with probability 9% the car drives away; if it does not, take 5 minutes off its meter and, if an officer is here and the meter has expired, write a ticket.
  4. Print the count, and the tickets.

ParkingTicketSimulation.java

import java.util.ArrayList;
import java.util.Random;

public class ParkingTicketSimulation {
    public static void main(String args[]) {
        ArrayList<ParkingTicket> tickets = new ArrayList<ParkingTicket>();
        ParkedCar street[] = new ParkedCar[20];
        Random x = new Random(42);

        for (int hour = 0; hour < 24; hour++) {
            for (int minutes = 0; minutes < 60; minutes += 5) {

                PoliceOfficer pol = null;
                if (x.nextInt(100) < 5) pol = new PoliceOfficer();

                for (int i = 0; i < 20; i++) {
                    if (street[i] == null) {
                        if (x.nextInt(100) >= 80) street[i] = new ParkedCar();
                    } else if (x.nextInt(100) < 9) {
                        street[i] = null;
                    } else {
                        street[i].adjustMeter(5);
                        if (pol != null && street[i].expiredMeter())
                            tickets.add(pol.issueTicket(street[i]));
                    }
                }
            }
        }

        System.out.println("Total number of parking tickets generated: " + tickets.size());
        System.out.println("--------------------------------------------------");
        for (int i = 0; i < 10 && i < tickets.size(); i++)
            System.out.println(tickets.get(i));
        System.out.println("... (" + (tickets.size() - 10) + " more)");
    }
}

Quick Check 11.7

x.nextInt(100) returns an int from 0 to 99 inclusive, each equally likely.

(a) if (x.nextInt(100) < 5) — what probability is that, and what does it control?

The values 0, 1, 2, 3, 4 satisfy it: five values out of a hundred, so 5%. It controls whether an officer patrols during this five-minute slot.

(b) if (x.nextInt(100) >= 80) — what probability is that, and why is it written with >= rather than <?

80 through 99 is twenty values, so 20% — the chance an empty space gets filled. Writing x.nextInt(100) < 20 would be exactly equivalent. >= 80 is just a different habit; there is no behavioural difference at all.

(c) A classmate replaces x.nextInt(100) < 9 with x.nextInt(100) <= 9. What has changed?

0 through 9 is ten values, so the chance a parked car drives away goes from 9% to 10%. Cars now turn over slightly faster, meters are on average younger, and the day produces fewer tickets.

Things to notice across all three parts. nextInt(n) never returns n itself — the upper bound is exclusive, exactly like an array index. Every off-by-one in this class of code comes from forgetting that. When you read a condition like this, say the count out loud: "zero through eight, that is nine values, nine percent."

Common Mistake— forgetting that most of the array is null

ParkedCar street[] = new ParkedCar[20]; creates twenty slots, all null. It does not create twenty cars. Every single use of street[i] has to be guarded, and the whole shape of the inner loop — if (street[i] == null) ... else ... — exists for that reason.

Drop the guard and you get this on the first empty space you touch:

space 0: Exception in thread "main" java.lang.NullPointerException: Cannot invoke "ParkedCar.adjustMeter(int)" because "street[i]" is null at NoNullCheck.main(NoNullCheck.java:13)

If you compile without debug information — a plain javac at the command line, as opposed to what most IDEs do — the JVM cannot recover your variable names and the same exception reads:

space 0: Exception in thread "main" java.lang.NullPointerException: Cannot invoke "ParkedCar.adjustMeter(int)" because "<local1>[<local3>]" is null at NoNullCheck.main(NoNullCheck.java:13)

<local1>[<local3>] means "element <local3> of local array <local1>" — the same information with the names stripped out. Compile with javac -g to get the readable version back.

Quick Check 11.8

The instructor's original driver began the array like this:

ParkedCar street[] = new ParkedCar[20];
for (int i = 0; i < 20; i++) street[i] = null;

(a) The version on this page does not have that loop. Why is it safe to delete?

Because new ParkedCar[20] already fills every element with null. Java guarantees that a newly created array is zero-filled: 0 for numeric element types, false for boolean, and null for every reference type. The loop assigns null over null twenty times.

It is not wrong, and some people write it deliberately to make the intent obvious to a reader. But it is not doing any work.

(b) Now suppose the field had been a local variable instead: ParkedCar first = null; versus just ParkedCar first;. Is that initialization also redundant?

No — and this is the distinction worth carrying away. Array elements and instance variables are given default values automatically. Local variables are not. Java refuses to compile a read of a local variable it cannot prove was assigned first:

error: variable first might not have been initialized

Things to notice across both parts. "Everything starts at zero" is true for fields and array elements, and false for locals. The rule looks inconsistent until you see the reason: the compiler can see every path through a method body, so it can enforce the stronger rule there; it cannot see every path through a whole program, so for fields it falls back on a guaranteed default.

Quick Check 11.9

PoliceOfficer pol = null; is declared inside the minutes loop, so a new one is created 5% of the time and thrown away at the end of every slot. Rewrite the inner test

if (pol != null && street[i].expiredMeter()) tickets.add(pol.issueTicket(street[i]));

with the two conditions swapped, and say whether the program still behaves identically. Then say what would go wrong if pol were declared once, above the hour loop.

Plan. Java's && short-circuits: if the left side is false the right side is never evaluated. So swapping the operands of && changes what work gets done, even when it does not change the answer.

if (street[i].expiredMeter() && pol != null) tickets.add(pol.issueTicket(street[i]));

Same result, more work. Both conditions have to be true for a ticket, so the tickets written are identical. But in the swapped version expiredMeter() is called on every occupied space in every one of the 288 slots — roughly 5,000 pointless calls — where the original only asks when an officer is actually present. Cheap tests first is the habit.

(Note that street[i] is known to be non-null here: we are in the else branch of if (street[i] == null). If it were not, the swapped version would also throw a NullPointerException, and that would be a real bug rather than an inefficiency.)

Hoisting pol out of the loop. If pol were declared above the hour loop, then once an officer had appeared the variable would keep pointing at that officer forever. Every subsequent slot would still be "patrolled" — pol != null would stay true for the rest of the day — and every expired car would be ticketed every five minutes by the same badge number. The declaration's position is what makes the officer's visit temporary.

7.Who holds what at run time

Everything so far has been about the five source files. Now stop looking at the code and look at the objects. At any instant while the simulation is running there are dozens of objects alive, and the only thing holding them together is a web of references — some in local variables, some in array slots, some in instance variables inside other objects.

Definition— object diagram

A class diagram (Lecture 10) shows the classes and which class can hold which. An object diagram shows one frozen instant of a running program: the actual objects that exist right now, and the actual arrows between them.

One class diagram; a different object diagram every five simulated minutes. The class diagram says "a ParkedCar has a ParkingMeter". The object diagram says "the car in space 7 has that meter, the one reading −35."

Quick Check 11.10

Count the objects StreetSnapshot creates, from the first line of main to the last. Do not count the String objects; count the objects of the four classes we wrote, plus the array.

(a) How many ParkedCar objects, and how many ParkingMeter objects?

Two of each. new ParkedCar() appears twice, and each ParkedCar constructor runs meter = new ParkingMeter(); exactly once. street[3] = street[1]; creates nothing — there is no new in it.

The rule is worth stating baldly: the number of objects of a class is the number of times new runs for that class, and nothing else. Assignment moves arrows around; only new makes an object.

(b) How many PoliceOfficer objects, and how many ParkingTicket objects?

One officer — new PoliceOfficer() on line 4. One ticket, and it is created inside a method we did not visibly call new in: officer.issueTicket(street[3]) runs return new ParkingTicket(this, parkedCar);. Counting new means counting every new the program reaches, including the ones inside other people's methods.

(c) How many arrays?

One: new ParkedCar[5]. An array is itself an object in Java, which is why street can be null, why street.length is a field access rather than a method call, and why passing an array to a method lets that method modify it.

Things to notice across all three parts. Seven objects total — two cars, two meters, an officer, a ticket, an array — and main has direct names for only three of them. Everything else is reached by following an arrow from something else. That gap between "objects that exist" and "objects you can name" is the whole reason object diagrams are worth drawing.

Key Idea— nothing is deleted, things become unreachable

Java has no delete and no destructor. street[i] = null; does not destroy a car. It removes one reference to it. If that was the last reference, the object becomes unreachable: no chain of arrows starting from a local variable or a static field can get to it any more, so no code will ever mention it again.

Unreachable objects are collected by the garbage collector, at a moment nobody controls and with no visible effect. You never see it happen and you never need to make it happen. What matters to you as a programmer is the reachability, not the collection: a car that is still reachable from somewhere is still using memory, and a car that is unreachable is gone whether you meant it or not.

Quick Check 11.11

Back in the real driver, street[i] = null; is how a car drives away, and unlike StreetSnapshot there is no second slot pointing at it.

(a) What happens to that ParkedCar object, and to the ParkingMeter it was holding?

Both become unreachable, and both are eventually collected. The car goes first in the sense that matters: once nothing points at the car, nothing can reach the car's meter field either, so the meter goes with it. A reference held only by a dead object is a dead reference.

Nothing prints. No method runs. The next new ParkedCar() that lands in that slot is a different car with a brand-new meter and a fresh random time on it.

(b) Suppose that car was ticketed ten simulated minutes earlier, and the ticket is sitting in the ArrayList. Does driving away damage the ticket?

No. ParkingTicket holds three String fields and no reference to the car at all, so there is nothing for the disappearing car to break. Printing the list at the end of the day prints that ticket exactly as it was written.

(c) Now answer (b) again for LiveTicket from §4, which stores the ParkedCar object itself.

Still no damage — but for the opposite reason. LiveTicket holds a reference to the car, so the car is not unreachable: the arrow from the ArrayList to the ticket to the car keeps it alive. street[i] = null; removes one of the two arrows and the other one is enough. The ticket prints fine, and the car object outlives the parking space it occupied.

Things to notice across all three parts. The two ticket designs differ in something you would never guess from reading either class: how long the cars live. Copy the text and the car is collected the moment it drives away; keep the reference and every car ever ticketed is still in memory at midnight. For 88 tickets that is nothing. For a real city, holding a reference to every object you ever mentioned is exactly how a program runs out of memory while looking perfectly correct.

8.Extending the system

A design is worth what it saves you on the next change, not on the first one. So let us make two changes to the finished system and count the files we have to touch.

Procedure— adding a feature to a multi-class program
  1. Say the new rule in one English sentence.
  2. Underline the data the rule depends on, and find the class that already owns it.
  3. Put the rule in that class. If step 2 named a class that does not have the data, you are about to add a getter to somebody else — stop and reconsider.
  4. Ask whether anything outside needs to ask for the new behavior. If not, you are done and no other file changes.
  5. If it does, that means a new method or a new constructor parameter, and every caller of that constructor changes too. Count them before you start.

A second meter rate

The rule: some meters on this street are long-stay meters and sell up to four hours instead of one hour forty. The data is timeLeft and the number it is initialized from, both owned by ParkingMeter, so the change is entirely inside ParkingMeter.

Definition— constructor chaining with this(...)

this(100); as the first statement of a constructor means call my own other constructor, the one that takes an int, with the argument 100. This is a third use of the word this, alongside this.field = field from Lecture 7 and new ParkingTicket(this, …) from §5.

It exists so that two constructors do not contain two copies of the same initialization code. Write the general one, and let every convenience constructor delegate to it with sensible defaults — the same delegation idea as §3, pointed inward at the class itself.

Common Mistake— this(...) anywhere but first

The call to this(...) must be the first statement in the constructor. Put a harmless println above it and the file stops compiling:

ParkingMeter.java:10: error: call to this must be first statement in constructor this(100);
^
1 error

The reason is that the other constructor is what actually builds the object. Until it has run, the object is not initialized, so Java refuses to let any of your code run first. The identical rule applies to super(...), which you meet next lecture.

Quick Check 11.12

Third change: every ticket must record the hour of day it was written, and print it. Work out which of the five classes have to change and why, and say why this one is more expensive than the permit.

Plan. Underline the data. The hour of day is not owned by any of the five classes — it is the simulation's hour loop variable. Nothing downstream can compute it, so it has to be handed along, and every method it passes through changes shape.

    car     += parkedCar.toString();

PoliceOfficer changes. issueTicket is the only caller of that constructor, so it must accept an hour and pass it through: public ParkingTicket issueTicket(ParkedCar parkedCar, int hour). The test of a design is not "can I always change one file" but "does the number of files I touch match the size of the idea". A rule about a car touches the car; a new fact travelling from the simulation to the ticket touches everything in between.

Lecture Summary
  • Build a multi-class program in dependency order: the class that mentions nobody first, then the class that mentions only what exists. Two classes that mention each other cannot be ordered, and that is fine — hand javac both files at once.
  • After every class, write a throwaway main, compile it and run it. The habit is worth more than any single technique in this lecture, because it keeps the amount of untested code down to what you can hold in your head.
  • Composition is a field whose type is another class. Declaring private ParkingMeter meter; only makes room for a reference; somebody still has to run meter = new ParkingMeter();, and forgetting it costs you a NullPointerException at the first method call, not at compile time.
  • Delegation is a method whose whole body forwards the question to a field object. It looks like waste and it is not: because meter is private and there is no getMeter(), the permit rule in §8 was four lines in one file.
  • this is an ordinary reference to the current object. new ParkingTicket(this, car) hands the officer over; new PoliceOfficer() in the same slot compiles, runs, and signs the ticket with a stranger's badge.
  • Put the arithmetic where the data is. ParkingMeter computes the fine, ParkedCar forwards it, ParkingTicket records it, PoliceOfficer never sees a number — which is why raising the fines is an edit to one method.
  • Copy the text for a record, keep the reference for a view. ParkingTicket freezes what was owed; LiveTicket would keep changing. Neither is right; knowing which one you built is.
  • An edit to one class surfaces as a compile error in its users. Read the caret, find the part of the line that belongs to another class, and ask what that method returns now — and remember that String + anything is legal, so some ripples never reach javac at all.
  • At run time, street[i] = null deletes an arrow, not an object. An object lives while anything can still reach it, and disappears silently when nothing can.
