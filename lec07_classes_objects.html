1.Blueprints and instances

Everything in the first six lectures was your code operating on Java's types. You declared an int, you built a String, you filled an array, you grew an ArrayList. Somebody else designed those types; you used them. Today that stops. From here to the end of the semester you design the types.

Start with the problem that makes this necessary. Suppose you are keeping a roster of people, and each person has a name and an age. With what you know so far you would reach for two arrays.

Worked Example— why two arrays is not enough

Here is a roster of three people held in two parallel arrays, and a small edit: move the first person to the end of the list. The programmer rotates the names array correctly — and forgets the ages array, because nothing in the code ties them together.

Roster.java

public class Roster {
    public static void main(String[] args) {
        String names[] = {"Ana", "Ben", "Cara"};
        int ages[]     = {20, 22, 21};

        // Put the roster in a different order: move the first entry to the end.
        String tempName = names[0];
        names[0] = names[1];
        names[1] = names[2];
        names[2] = tempName;

        for (int i = 0; i < 3; i++) {
            System.out.println(names[i] + " is " + ages[i]);
        }
    }
}

Ana is 20, Ben is 22, Cara is 21. What does this print?

Ben is 20 Cara is 22 Ana is 21

Every single age is now attached to the wrong person, and the program did not complain once. Nothing in Java knows that names[1] and ages[1] describe the same human being. That knowledge existed only in the programmer's head, and the moment it slipped, the data silently became wrong.

Now the same edit, written with a Person type that we are about to build. Read the rotation code carefully: it is the same three assignments, on one array instead of two.

Roster2.java

public class Roster2 {
    public static void main(String[] args) {
        Person people[] = { new Person("Ana", 20),
                            new Person("Ben", 22),
                            new Person("Cara", 21) };

        // Put the roster in a different order: move the first entry to the end.
        Person temp = people[0];
        people[0] = people[1];
        people[1] = people[2];
        people[2] = temp;

        for (int i = 0; i < 3; i++) {
            System.out.println(people[i].getName() + " is " + people[i].getAge());
        }
    }
}
Ben is 22 Cara is 21 Ana is 20

Correct, and — more importantly — it could not have gone wrong. A name and an age are no longer two facts that happen to sit at the same index in two places. They are one thing. When you move that thing, both facts move with it, because there is nothing left to move separately.

That is the whole argument for object-oriented programming in one example. The rest of the semester is detail.

Definition— class and object

A class is a blueprint or template that defines the structure and behavior of objects. Car, Person, BankAccount are classes. A class is a description; writing one creates nothing at run time.

An object is an instance of a class, created in memory. myCar, student1, person2 are objects. Each object made from a class has its own copy of that class's data, and there can be as many of them as you like.

Key Idea

The blueprint of a house is not a house. You can hand one blueprint to a builder and get a hundred houses, each with its own address and its own furniture, all laid out the same way. class Person is the blueprint. Every new Person(...) is another house.

2.Writing a class: the recipe

Every class you write this semester follows the same five steps, in the same order. Learn the order and the blank page stops being frightening.

Procedure— how to create a class
  1. Define the class structure. Start with the class keyword and a name. Use PascalCase — Person, BankAccount, TrafficSignal — and put the class in a file with exactly that name plus .java.
  2. Declare instance variables. These define the object's state. Mark them private for encapsulation (§3).
  3. Create constructors. Constructors initialize an object at the moment it is created. You can write both a default (no-argument) version and parameterized versions (§4).
  4. Add getters and setters. Controlled access to the private variables: accessors that read (getters) and mutators that write (setters) (§5).
  5. Add methods. The object's behavior — anything else it can do.
Definition— instance variable

An instance variable (also called a field or an attribute) is a variable declared directly inside a class, outside every method. Each object gets its own copy of every instance variable, which is exactly why two Person objects can hold two different names.

Contrast this with a local variable, declared inside a method: a local variable exists only while that method runs and belongs to nobody. An instance variable lives as long as the object does.

Here is the recipe carried out end to end. This is the class we will keep coming back to.

Worked Example— the Person class, all five steps

Read it against the five steps: the header, then two private instance variables, then two constructors, then four accessors and mutators, then one behavior method. The comments mark the boundaries.

Person.java

public class Person {
    // Instance variables
    private String name;
    private int age;

    // Default constructor (no-args)
    public Person() {
        this.name = "Unknown";
        this.age = 0;
    }

    // Non-default constructor
    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    // Getters
    public String getName() { return name; }
    public int getAge() { return age; }

    // Setters
    public void setName(String name) { this.name = name; }
    public void setAge(int age) {
        if (age >= 0) {
            this.age = age;
        }
    }

    // Methods
    public void introduce() {
        System.out.println("Hi, I'm " + name + ".");
    }
}

Two things to notice before we run anything. First, there is no main here at all. A class does not have to be a program; Person.java is a type, and something else will use it. Second, introduce is not static. It has no parameters and yet it prints a name — because it is called on a particular person, and name means "the name of the object I was called on".

Now a second file that actually does something. Both files go in the same folder; javac Person.java Main.java compiles them together.

Main.java

public class Main {
    public static void main(String[] args) {
        // Create objects using the constructors
        Person person1 = new Person();
        Person person2 = new Person("John", 18);

        // Call methods
        person1.introduce();
        person2.introduce();

        // Use setters and getters
        person1.setAge(21);
        System.out.println(person1.getAge());
    }
}

A static method could not do this — it has no object to read from. That is why almost nothing you write from today on will be static.

3.private, and why encapsulation matters

Every instance variable in Person is declared private. That word is doing real work, and the reason is not tidiness.

Definition— private and encapsulation

private means: this member can be used only by code inside this class. Any other class that mentions it by name gets a compile error.

Encapsulation is the practice of making the data private and exposing it only through methods you wrote. The object keeps control of its own state: nothing gets in or out except through a door you built and can inspect.

Watch what the compiler does when another class reaches for a private field directly.

Peek.java

public class Peek {
    public static void main(String[] args) {
        Person p = new Person("John", 18);
        System.out.println(p.age);
    }
}
Peek.java:4: error: age has private access in Person System.out.println(p.age);
^
1 error

That is the entire mechanism. There is no runtime check, no permission system, no cost: the compiler simply refuses to build a program that pokes at another object's insides.

So why bother, when public int age; would have compiled and p.age would have worked? Three reasons, in increasing order of how much they will matter to you.

  • You can validate. If the only way to change the age is setAge, then setAge gets to decide. Ours refuses negative ages. A public field cannot refuse anything: p.age = -400; would just be true from then on.
  • You can change your mind later. Suppose next month you decide to store a birth year instead of an age. If everybody outside used getAge(), you rewrite getAge() to compute the age and every other file in the project keeps compiling. If everybody used p.age, every one of those files breaks.
  • You can find the bug. When an age goes wrong and there is exactly one method in the program that can write it, you know where to put the breakpoint. When the field is public, "who set this?" has no answer short of reading the whole project.
Key Idea— the default posture

Instance variables private, methods public, unless you have a specific reason to do otherwise. Say what the object does in public and keep what it has to yourself. On this instructor's exams, a class written with public instance variables loses points even when it runs.

Quick Check 7.3

Here is a class and a program that uses it.

public class Temperature {
    private double celsius;
    public Temperature(double celsius) {
        this.celsius = celsius;
    }
    public double getCelsius() {
        return celsius;
    }
    public double getFahrenheit() {
        return celsius * 9 / 5 + 32;
    }
}

(a) A user of this class writes t.celsius = 100;. What happens, and when?

It fails at compile time, with error: celsius has private access in Temperature. The program never runs, so there is no chance of a wrong answer reaching a user. Errors caught by the compiler are the cheapest errors there are.

(b) The class stores only celsius, yet it offers getFahrenheit(). Is that legal? Should a getter always just return a field?

Perfectly legal, and rather good design. A getter is an ordinary method; nothing requires it to return a stored value. getFahrenheit() computes its answer, so the two temperatures can never disagree — which is exactly the bug you would get if you stored both and updated one.

This is the second bullet from the section above, in miniature: callers say what they want, not how it is stored, so you are free to change how it is stored.

(c) There is no setCelsius. Is the class broken?

No. A class is under no obligation to provide a setter for every field. Leaving setCelsius out makes a Temperature immutable: once constructed it can never change, so no other part of the program can corrupt it, and you never have to wonder whether it changed behind your back. String works exactly this way, which is why s.toUpperCase() returns a new string instead of modifying s.

Things to notice across all three parts. "Getter and setter for every field" is a habit, not a rule. Provide the doors your class actually needs. Every setter you leave out is a way the object can no longer be broken.

4.Constructors, and the this keyword

Definition— constructor

A constructor is a special method that runs once, automatically, when an object is created with new. Its job is to put the new object's instance variables into a sensible starting state.

Two rules of syntax, both of which trip people up:

  • Its name is exactly the class name, capital letter and all.
  • It has no return type — not even void. Writing public void Person() does not declare a constructor; it declares an ordinary method that happens to be called Person, and Java will never call it for you.

A class may have several constructors as long as their parameter lists differ — this is just method overloading from Lecture 2, applied to constructors. Person has two: a no-arg (or default) constructor that installs placeholder values, and a parameterized one that takes the values from the caller.

Worked Example— the constructor you get for free

If you write no constructor at all, Java supplies an invisible no-arg constructor that does nothing. The instance variables are still initialized — not to garbage, as they would be in C++, but to Java's fixed defaults. This class has no constructor anywhere in it, yet new Book() compiles:

public class Book {

}

The this keyword

Definition— this

Inside any constructor or instance method, this refers to the object the method was called on — the current object. this.name therefore means "the name instance variable of the object I am working on", as opposed to any local variable or parameter that happens to also be called name.

Most of the time you can leave this out: inside introduce() the bare word name already means this.name, because there is nothing else called name in scope. There is exactly one situation where you cannot leave it out, and it is a situation Java programmers deliberately walk into several times per class.

Worked Example— what happens when you forget this

The convention is to name a constructor's parameter after the field it initializes: Person(String name, int age). That is good for readability, but it means the parameter name shadows the field name — inside the constructor, the bare word name refers to the parameter. Here is the same constructor with the this. removed.

Broken.java

public class Broken {
    private String name;
    private int age;

    public Broken(String name, int age) {
        name = name;    // no 'this' -- does nothing useful
        age = age;      // no 'this' -- does nothing useful
    }

    public String toString() {
        return "name = " + name + ", age = " + age;
    }
}

BrokenDemo.java

public class BrokenDemo {
    public static void main(String[] args) {
        Broken b = new Broken("John", 18);
        System.out.println(b);
    }
}

Before revealing: does this even compile? And if it does, what does it print?

name = null, age = 0

It compiles cleanly — no error, and no warning either, even with javac -Xlint:all. name = name; assigns the parameter to itself, which is legal and pointless. The fields are never written, so they keep the defaults from the previous example: null and 0.

Read the middle row aloud as "this object's name gets the name I was passed" and the line stops looking like a tautology. The left side is the field because of this.; the right side is the parameter because it is the nearest thing in scope.

You can avoid the whole issue by naming the parameter something else — the instructor's Point class does exactly that with xValue and yValue, and then plain x = xValue; is unambiguous. Both styles are correct and you will see both. What you must never do is use the same name and forget the this., because nothing will tell you.

5.Getters, setters, and the setter that says no

Definition— accessor and mutator

An accessor, or getter, is a method that reports the value of a private instance variable. By convention it is named getSomething, takes no parameters, and returns the field's type. For a boolean the convention is isSomething instead.

A mutator, or setter, is a method that changes a private instance variable. By convention it is named setSomething, takes one parameter of the field's type, and returns void.

Written mechanically, a getter and setter pair looks like pure ceremony — five lines to do what one public field would have done. The payoff is that a setter is a method, and a method can think before it acts. Look again at the two setters in Person:

public void setName(String name) {
    this.name = name;
}
public void setAge(int age) {
    if (age >= 0) {
        this.age = age;
    }
}

setName accepts anything. setAge does not: an age below zero is meaningless, so the assignment is guarded, and a bad value simply does not get in. A public age field could not have done this.

Worked Example— the guard in action

Using the Person class from §2 unchanged:

SetterDemo.java

public class SetterDemo {
    public static void main(String[] args) {
        Person p = new Person("John", 18);
        System.out.println("Start:        " + p.getAge());

        p.setAge(21);
        System.out.println("After 21:     " + p.getAge());

        p.setAge(-5);
        System.out.println("After -5:     " + p.getAge());

        p.setName("Johnathan");
        System.out.println("Name is now:  " + p.getName());
    }
}

The third line is the interesting one. What does the age become?

Start:        18
After 21:     21
After -5:     21
Name is now:  Johnathan

The age stays 21. setAge(-5) ran, the condition age >= 0 was false, the body was skipped, and the method returned normally. The object protected itself and the caller never knew.

That last clause is worth arguing about, and you should notice that this design has a real weakness: a rejected value is silently rejected. A program that calls setAge(-5) and then reads getAge() gets 21 and has no way to tell that its request was thrown away. There are three standard ways to do better, all of them beyond today:

  • Return a boolean from the setter so the caller can check — simple, but easy to ignore.
  • Print a message, as the instructor's Distance class does in Practice Problem 5.
  • Throw an exception, which forces the caller to deal with it. That is Lecture 20, and it is what professional code does.

For now, take the point that matters: the validation lives in the class, not in every caller. Write it once, in the setter, and no amount of careless calling code can put a negative age into a Person.

Things to notice. 6.toString

We now have objects, but printing one is still clumsy: person1.getName() + " is " + person1.getAge() at every call site. Java has a standard answer, and it is the first method you will write that Java itself calls on your behalf.

Definition— toString

toString() is a method every Java object has. Its job is to return a String describing the object. Whenever an object is used where text is required — passed to System.out.println, or joined with + to a String — Java calls that object's toString() and uses the result.

Its signature is fixed: public String toString(), no parameters.

The instructor's Point class is the standard example, and it is worth reading in full because it also shows an instance method that takes another object of the same class as a parameter.

Point.java

public class Point {
    private double x, y;

    public Point() {
        x = 0.0;
        y = 0.0;
    }

    public Point(double xValue, double yValue) {
        x = xValue;
        y = yValue;
    }

    public double getX() { return x; }
    public double getY() { return y; }
    public void setX(double xValue) { x = xValue; }
    public void setY(double yValue) { y = yValue; }

    public double distanceTo(Point other) {
        return Math.sqrt((x - other.x) * (x - other.x) + (y - other.y) * (y - other.y));
    }

    public String toString() {
        return "(" + x + ", " + y + ")";
    }
}

Two details in distanceTo deserve a sentence each.

  • x with no qualifier is this point's x; other.x is the other point's x. One method body, two objects, distinguished only by the dot. This is the usual way a method compares or combines two instances.
  • other.x is legal even though x is private. private restricts access to the class, not to the individual object, so code inside Point may read any Point's private fields. If that surprises you, it should — it is the one place the word "private" is slightly misleading.

Now delete the toString method from Point and change nothing else. PointTester still compiles, because every object has a toString whether you write one or not — you inherit a default. What does it look like?

Point@2a139a55 Point@15db9742 5.0

The hexadecimal part is machine-dependent: yours will differ, and it may differ between two runs on the same machine. The values above are representative, not something to memorize. The shape is fixed, though: the class name, an @, and the object's hash code in hexadecimal.

Three consequences worth writing down.

  • The default is useless for reading, which is why defining toString is close to mandatory for any class you intend to print.
  • It is not useless for identity: the two points printed different codes, so you can see at a glance that they are different objects. That becomes a diagnostic tool in Lecture 8.
  • distanceTo is unaffected. toString changes how an object is displayed, and nothing else.
Common Mistake

toString takes no arguments and is spelled with a lowercase t and a capital S. Write public String ToString() or public String toString(int digits) and you have simply defined some other method — the class compiles, println ignores it, and you get Point@2a139a55 while staring at a toString you are sure you wrote.

Also: System.out.println(p.toString()) and System.out.println(p) do the same thing. Writing the explicit call is not wrong — the instructor's own Test.java in §7 does it — but the short form is what you will read most often, and it is the reason toString exists.

7.Objects inside objects

An instance variable can have any type — including a class you wrote. That single fact is what lets you build programs out of small parts instead of one enormous class.

Definition— composition

Composition is building a class out of objects of other classes: a Triangle has three Points, a Circle has a center Point, a Car has an Engine. It is often called the "has-a" relationship, to contrast it with the "is-a" relationship of inheritance in Lecture 12.

Nothing new is required to do it. A Point field is declared, constructed and used just like a String field — and String was an object all along.

Worked Example— a Triangle made of three Points

The instructor's Triangle holds three Point objects and reports the lengths of its three sides. Notice that Triangle does no geometry of its own: it asks each Point for the distance to the next one. That is composition working properly — the class that owns the data does the arithmetic.

DecimalFormat comes from java.text; the pattern #.## means "up to two decimal places, and drop them if they are zero", which is why 3.0 prints as 3 below.

Triangle.java

import java.text.DecimalFormat;

public class Triangle {
    private Point a, b, c;

    public Triangle(Point pA, Point pB, Point pC) {
        a = pA;
        b = pB;
        c = pC;
    }

    public String toString() {
        DecimalFormat round = new DecimalFormat("#.##");
        String ans = "Triangle sides: ";
        ans += round.format(a.distanceTo(b)) + ", " +
               round.format(b.distanceTo(c)) + ", " +
               round.format(c.distanceTo(a)) + "\n";
        return ans;
    }
}

TriangleDemo.java

public class TriangleDemo {
    public static void main(String[] args) {
        Point p1 = new Point(0, 0);
        Point p2 = new Point(3, 0);
        Point p3 = new Point(0, 4);

        Triangle t = new Triangle(p1, p2, p3);
        System.out.print(t);

        Triangle unit = new Triangle(new Point(0, 0), new Point(1, 0), new Point(0, 1));
        System.out.print(unit);
    }
}

The first triangle has legs 3 and 4. Predict both lines, including how many decimal places each number gets.

Triangle sides: 3, 5, 4 Triangle sides: 1, 1.41, 1

The sides are listed in the order a-to-b, b-to-c, c-to-a, so the 3–4–5 triangle reports 3, 5, 4 — the hypotenuse in the middle. Reading the order off the code rather than assuming it is the whole skill here.

The second triangle is the unit right triangle, whose hypotenuse is the square root of 2. DecimalFormat("#.##") rounds 1.4142135623730951 to 1.41, and prints the two legs as 1 rather than 1.00 because # means "a digit, but only if there is one". Compare with the pattern 0.00, which would have given 1.00 and 1.41.

Notice System.out.print, not println: Triangle's toString already ends with "\n". Building the newline into toString is a slightly unusual choice — most toString methods return a single line and let the caller decide — and it is the reason you see a stray blank line in the next example.

Finally: TriangleDemo never touches x or y. It hands Point objects to a Triangle and gets a String back. Three classes, three jobs, no class reaching into another's data.

The instructor's own driver builds the three vertices from user input with a Scanner, and stores them in an array of Point. An array of objects works exactly like the array of Person in §1: new Point[3] creates three slots, all null, and each slot must then be filled with its own new Point(...).

The area and circumference are calculated with the formulas πr2 and 2πr, where r is the radius. (The value of π is written Math.PI in Java.) Plan. Read the specification as a checklist and write the class in the order of the recipe from §2. Two private instance variables with the stated types.         return Math.PI * radius * radius;

    public double circumference() {
        return 2 * Math.PI * radius;

    public boolean isOutside(Point p) {
        return center.distanceTo(p) > radius;
    }
}

BankAccount.java

public class BankAccount {
    private String owner;
    private double balance;

    public BankAccount(String owner, double balance) {
        this.owner = owner;
        this.balance = balance;
    }

    public String getOwner() { return owner; }

    public double getBalance() { return balance; }

    public void deposit(double amount) {
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount <= balance) {
            balance -= amount;
        }
    }

Problem 3 — Write the class TrafficSignal (from Exam 1 Practice Problems)

Write complete code for a class called TrafficSignal. The class represents a traffic signal that cycles through four states: green, yellow, red and leftTurn, in this order — so leftTurn comes just after red and before green.

The class should have only one attribute, light, of type int. The value of this attribute determines the state of the signal; for example, if light has value 0, the signal shows green. The class should have one (default) constructor and only three additional methods. The default color of the light should be red. The three methods are currentLight(), which returns the integer corresponding to the current state; changeLight(), which changes light from the current state to the next state; and toString(), which returns the state as green, yellow and so on.

Plan. The whole problem is a numbering decision, so make it first and write it down as a comment: green 0, yellow 1, red 2, leftTurn 3. Everything else follows.

  • "The default color should be red" means the no-arg constructor sets light = 2;.
  • "changes to the next state", wrapping from leftTurn back to green, is the classic % idiom: light = (light + 1) % 4;. Adding 1 and taking the remainder on division by 4 turns 3 into 0 for free. Resist writing four if statements.
  • toString has to turn 0..3 into a word. An array of the four names, indexed by light, is one line; an if/else if chain is four times longer and does the same thing.

TrafficSignal.java

public class TrafficSignal {
    // 0 = green, 1 = yellow, 2 = red, 3 = leftTurn
    private int light;

    public TrafficSignal() {
        light = 2;              // the default color is red
    }

    public int currentLight() {
        return light;
    }

    public void changeLight() {
        light = (light + 1) % 4;
    }

    public String toString() {
        String names[] = {"green", "yellow", "red", "leftTurn"};
        return names[light];
    }
}

SignalDemo.java

public class SignalDemo {
    public static void main(String[] args) {
        TrafficSignal s = new TrafficSignal();

        for (int i = 0; i < 6; i++) {
            System.out.println(s.currentLight() + "  " + s);
            s.changeLight();
        }
    }
}
2  red 3  leftTurn 0  green 1  yellow 2  red 3  leftTurn

Things to notice. Six changes bring the signal back to where it started after four, which is the evidence that the wraparound works. If you had written light = light + 1; the fifth line would have printed 4 and the sixth would have thrown an ArrayIndexOutOfBoundsException from toString.

The one attribute is private, and currentLight() is the only way out. That is what makes the invariant "light is always between 0 and 3" something the class can actually promise: the only method that writes light is changeLight, and it cannot produce anything else.

Declaring names as a local array inside toString rebuilds it on every call, which is slightly wasteful. The tidy fix is to make it a constant shared by all signals rather than a fresh local — that needs the static keyword, and it is Lecture 9. A local array is entirely correct in the meantime and gets full credit.

Problem 5 — Write the class Distance (from Exam 1 Practice Problems)

Write a class Distance meeting all of the following requirements.

  • Two instance variables, feet and inches, stored as ints, and a private constant INCHES_IN_A_FOOT with value 12.
  • A no-argument constructor initializing a Distance to zero feet, zero inches.
  • A two-argument constructor accepting two positive integers for feet and inches. An access (get) method for feet and a mutator (set) method for inches.
  • A public method add that accepts another Distance object and adds that object's distance to the current distance. For example, if x1 is 5 feet 8 inches and x2 is 2 feet 7 inches, then after x1.add(x2); the object x1 is 8 feet 3 inches.
  • A public method metricDistance returning, as a double, the number of meters in the distance. It should use a private variable for the number of meters in a foot (1 foot = 0.3048 meters).
  • Finally, modify the two-argument constructor so that if the number of inches is greater than 11, it prints Illegal number of inches and sets inches to 11.

Plan. Only add needs real thought; everything else is the recipe. Take the worked example seriously: 5 feet 8 inches plus 2 feet 7 inches is 8 feet 3 inches, not 7 feet 15 inches. So add must carry: total the inches, convert every whole 12 of them into a foot, and keep the remainder.

The order of those two statements is the trap. Compute the total first, into its own variable, then use it twice — once divided by 12 for the carry, once modulo 12 for the leftover inches. If you overwrite inches before computing the carry, the carry is always zero and x1 comes out as 7 feet 3 inches: an answer that looks nearly right, which is the worst kind.

Distance.java

public class Distance {
    private int feet;
    private int inches;
    private final int INCHES_IN_A_FOOT = 12;

    public Distance() {
        feet = 0;
        inches = 0;
    }

    public Distance(int feet, int inches) {
        this.feet = feet;
        if (inches > INCHES_IN_A_FOOT - 1) {
            System.out.println("Illegal number of inches");
            this.inches = INCHES_IN_A_FOOT - 1;
        } else {
            this.inches = inches;
        }
    }

    public int getFeet() { return feet; }

    public void setInches(int inches) { this.inches = inches; }

    public void add(Distance other) {
        int totalInches = inches + other.inches;
        feet = feet + other.feet + totalInches / INCHES_IN_A_FOOT;
        inches = totalInches % INCHES_IN_A_FOOT;
    }

    public double metricDistance() {
        final double METERS_PER_FOOT = 0.3048;
        return (feet + (double) inches / INCHES_IN_A_FOOT) * METERS_PER_FOOT;
    }

    public String toString() {
        return feet + " feet, " + inches + " inches";
    }
}

        Distance zero = new Distance();

        Distance x1 = new Distance(5, 8);
        Distance x2 = new Distance(2, 7);
        x1.add(x2);
        System.out.println("x1 after add: " + x1);
        System.out.println("x2 is still:  " + x2);

        System.out.println("x1 in meters: " + x1.metricDistance());

Things to notice. add changes the object it is called on and leaves its argument alone — x2 is still 2 feet 7 inches afterwards. That asymmetry is deliberate and it is what "adds the other object's distance to the current distance" means. Compare with Point.distanceTo, which changes neither object and returns a value instead. Deciding whether a method mutates or returns is a design choice you now have to make every time.

add reads other.inches and other.feet directly, which is legal because add is inside Distance — the same rule that let Point.distanceTo read other.x.

(double) inches / INCHES_IN_A_FOOT is doing essential work in metricDistance. Without the cast, 8 / 12 is integer division and gives 0, so 5 feet 8 inches would come out as exactly 5 feet of metres. This is the Lecture 1 trap, still costing points in Lecture 7.

The constant is declared final, so the compiler rejects any attempt to change it. Making it private as the spec asks keeps it out of other classes. One shared copy for all Distance objects would be better still, but that needs static — Lecture 9.

Last, notice that the guard is in the constructor, not only in a setter. setInches as specified is unguarded, so x.setInches(99) still gets through. If you wanted the rule enforced everywhere, you would put it in setInches and have the constructor call setInches(inches).

Things to notice across all eight parts. Three separate lecture ideas each produce exactly one line here, and each is worth a point on an exam: the missing this. in (e), the rejected setter argument in (c), and the independence of two objects in (h). Most of the marks are decided there before the program has printed anything.

Lecture Summary
  • A class is a blueprint; an object is an instance of it, created with new. One class, any number of objects, each with its own copy of every instance variable.
  • The recipe never changes: class header, private instance variables, constructors, getters and setters, then methods.
  • private means "this class only", and the compiler enforces it. Keep fields private and methods public so the object controls its own state.
  • A constructor has the class's name and no return type. Write public void Person() and you have written a method, not a constructor.
  • Writing any constructor removes the free no-arg one. If you still want new Thing() to work, write the no-arg constructor yourself.
  • Instance variables get defaults — null, 0, 0.0, false — where local variables get nothing.
  • this is the current object. this.name = name; is required whenever a parameter shadows a field, and forgetting it compiles silently and leaves the field at its default.
  • A setter can validate: setAge accepts only age >= 0, so no caller can ever put a negative age into a Person. Write the check once, in the class.
  • public String toString() decides what your object looks like when printed. Define it and System.out.println(p) gives (0.0, 0.0); leave it out and you get the inherited default, Point@ followed by a hash code.
  • An instance variable can be an object: a Triangle has three Points, a Circle has a center. Let the inner object do its own arithmetic and ask it for the answer.
