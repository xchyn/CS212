1.Recall: what = and == really do

Last time we found out that an object variable does not hold an object. It holds a reference to one, and two variables can hold the same reference. Everything in today's lecture grows out of that single fact, so we start by putting it in one table you should be able to reproduce from memory.

Primitive (int, double, char, boolean, …)Object (String, Point, ArrayList, anything you write)

Definition— identity and equality

Identity asks: are these two variables pointing at the very same object? That is what == tests for objects.

Equality asks: do these two objects hold the same information? Java has no operator for that. It is a method call, a.equals(b), and its behavior is whatever the author of the class decided it should be.

Two identical twins are equal but not identical. One person seen in a mirror is identical to himself. Java keeps those two questions strictly separate, and most bugs in this area come from asking one and meaning the other.

2.equals: comparing contents instead of addresses

So == on objects is nearly useless for the question you usually want to ask. Java's answer is a method, and it is not a method you have to invent: every object in Java already has one.

Definition— the class Object, and inherited methods

Every class in Java, including every class you write, is automatically a descendant of a class called Object. You never write that connection down; it is there whether you want it or not. We study what "descendant" means in Lecture 12, but the consequence matters today: your class starts life already owning the methods Object defines.

Two of them are the subject of this lecture:

  • public boolean equals(Object obj) — asks whether this object equals another.
  • public String toString() — returns a text description of this object.

You get both for free. The trouble is that the free versions do something almost useless, so a well-written class replaces them. Replacing an inherited method with your own is called overriding it.

Key Idea— what the inherited equals does

Object's own equals is written like this:

public boolean equals(Object obj) { return this == obj; }

That is, the default equals is just ==. If you do not override it, calling a.equals(b) on your class asks exactly the identity question you were trying to get away from. Nothing about the word "equals" makes it compare contents; a human has to write that.

Quick Check 9.3

Give the value of each expression, and say in one phrase why.

(a) With String x = "java"; and String y = "java"; — what is x == y?

true. Two identical string literals are the same object: Java interns literals in the string pool, so the second "java" reuses the first. This is the one case where == on strings accidentally works, and relying on it is how people get burned.

String's author wrote a real one, so strings compare by content. Nobody wrote one for Student, so students compare by address. Whenever you meet a new class, the question "does this class override equals?" has a real answer and it changes your code.

3.Writing your own equals, and the trap that eats it

This is the most important section on the page, and the reason is that the natural way to write equals compiles perfectly, passes a casual test, and is wrong.

Procedure— how to write equals for your class
  1. Use exactly this title line: public boolean equals(Object obj). The parameter type is Object, not the name of your class. This is not negotiable — §3 is about what happens if you change it.
  2. Check the type: if (!(obj instanceof Point)) return false;. Anything can be passed in, including a String or null, and none of those equal your object.
  3. Cast: Point other = (Point) obj;. Step 2 has just proved this cast is safe.
  4. Compare the fields that define equality: return x == other.x && y == other.y;. You decide which fields count. For Point it is both coordinates; for a Book it might be the ISBN alone.
  5. Compare object-valued fields with .equals, not ==: a String field is compared name.equals(other.name).
Definition— instanceof

obj instanceof Point is a boolean expression that is true when obj refers to a Point object, and false otherwise — including when obj is null. It is how you ask a reference what it is actually pointing at before you commit to treating it as one.

A cast (Point) obj does not change the object. It tells the compiler "trust me, this really is a Point, let me call Point methods on it". If you are wrong, the program throws a ClassCastException at run time.

Worked Example— the overload trap, then the fix

Start with the Point from §1, whose equals takes a Point:

Point.java

public class Point {
    private double x, y;

    public Point(double xValue, double yValue) {
        x = xValue;
        y = yValue;
    }

    public double getX() { return x; }
    public double getY() { return y; }
    public void setX(double xValue) { x = xValue; }
    public void setY(double yValue) { y = yValue; }

    public String toString() {
        return "(" + x + ", " + y + ")";
    }

    public boolean equals(Object obj) {
        if (!(obj instanceof Point)) return false;
        Point other = (Point) obj;
        return x == other.x && y == other.y;
    }
}

  • o1.equals(o2) is true.   • list.contains(p2) is true. The library call now reaches your method.

Common Mistake— skipping the instanceof check

It is tempting to write only the cast, because the cast is what you actually need:

public boolean equals(Object obj) {
    Point other = (Point) obj;
    // no instanceof guard return x == other.x && y == other.y; }

That compiles, and it works for every call where the argument really is a Point. Pass it anything else and it does not return false — it dies:

Exception in thread "main" java.lang.ClassCastException: class java.lang.String cannot be cast to class Point at Point.equals(Point.java:7) at CastCrash.main(CastCrash.java:5)

equals is supposed to answer a yes/no question about any object at all. Crashing is not one of the permitted answers. The instanceof line is two seconds of typing and it also handles null for free.

Key Idea— let the compiler catch it: @Override

Write @Override on the line above any method you believe replaces an inherited one:

@Override public boolean equals(Object obj) { ... }

It changes nothing at run time. What it does is instruct the compiler to verify your belief. Put it above the broken version and javac refuses to compile:

Point.java:8: error: method does not override or implement a method from a supertype @Override
^
1 error

A silent wrong answer has become a compile error, for the cost of nine characters. Use @Override on every equals and every toString you write from now on.

4.toString, seen properly as an override

You wrote a toString in Lecture 7 and saw what happens without one. Now you can say what you were really doing: toString is the second method inherited from Object, and writing your own is an override in exactly the sense of §3.

Definition— toString

public String toString() returns a String describing the object. Java calls it for you whenever an object turns up where text is needed:

  • System.out.println(obj) — println has an overload taking an Object, and it calls toString.
  • "Result: " + obj — string concatenation converts the object by calling toString.
  • Printing a collection: System.out.println(list) calls toString on the list, which calls toString on every element.

Its signature is fixed: public, returns String, takes no parameters. Any deviation is an overload, and an overload will never be called by println.

Key Idea— what you get if you do not write one

The inherited toString returns the class name, @, and the hash code in hexadecimal: Student@2a139a55. The hexadecimal part is machine-dependent and varies between machines and between runs — never write it into an expected-output answer, and never rely on it in a program.

It is useless for reading but genuinely useful for one thing while debugging: two objects printing different codes proves they are different objects.

Common Mistake— printing inside toString

Two versions that look similar and are not:

public void toString() {
    // WRONG - does not compile System.out.println("(" + x + ", " + y + ")"); } public String toString() {                      // right return "(" + x + ", " + y + ")"; }

toString builds text and hands it back; the caller decides what to do with it. That is why the same method works for println, for concatenation and for writing to a file. A toString that prints can only ever do one of those.

One more detail worth knowing: System.out.println(x) where x is a null reference prints null rather than throwing. Java checks for null before it would call toString. But x.toString() written out by hand on a null reference throws a NullPointerException — the check is in println, not in the language.

5.static fields: one copy for the whole class

Everything we have written inside a class so far belongs to an object. Each Point has its own x. Each Student has its own name. Some information does not fit that shape at all: how many students have been created is a fact about the class, not about any one student. That is what static is for.

Definition— static and instance members

A member declared static belongs to the class. There is exactly one copy of it, created when the class is first loaded, and it exists whether or not a single object has ever been made. It is also called a class variable or class method.

A member declared without static belongs to an object. Every object gets its own copy, created by new. It is also called an instance variable or instance method.

6.static methods, main, and this

A static method follows the same rule as a static field, and the rule has one consequence that generates more compiler errors than anything else in this lecture.

Key Idea— a static method has no object

When a static method runs, there is no "current object". Nobody called it on anything. Therefore:

  • It cannot read or write an instance field, because it would have no way to know whose.
  • It cannot call an instance method, for the same reason.
  • It cannot use this.
  • It can use static fields and call static methods freely.
  • It can use an object it is given as a parameter, or one it creates itself: n.x is fine inside a static method, because n names a specific object.

The reverse direction has no restriction at all. An instance method may use static members whenever it likes, because by then an object certainly exists.

Try to break the rule and javac says so in one of two nearly identical sentences. Learn to read both; you will meet them repeatedly.

Counter.java:7: error: non-static variable x cannot be referenced from a static context System.out.println(x);

Widget.java:9: error: non-static method growSize() cannot be referenced from a static context static void callGrow()

"A static context" means "inside a static method" — and main is a static method, so most of the times you will see this message, the static context is main.

Procedure— fixing "cannot be referenced from a static context"

You have three choices, and which one is right depends on what the member means.

  1. Give the method an object to work on. If the method genuinely acts on one object, either drop static from the method and call it as obj.method(), or keep static and pass the object in, then say n.field instead of field. This is the fix the exam problem in §Practice wants.
  2. Make the field static. Correct only if the data really is one-per-class — a counter, a shared constant. Do not reach for this just to silence the compiler: making an instance field static means every object now shares it, which is usually a much worse bug than the one you started with.
  3. Create an object in main. The everyday fix. main cannot touch your instance members, so main does Thing t = new Thing(); and then talks to t.
Definition— why main is static

Read the chicken-and-egg problem: the JVM has just started your program. No objects exist, because your code is what creates objects, and none of your code has run yet. The JVM must call something, and it has nothing to call it on.

Declaring main static solves it. A static method can be called using only the class name — java Robot means "load the class Robot and call Robot.main" — and no object is required.

Remove the word and the program still compiles. It just will not start:

Error: Main method is not static in class NotStatic, please define the main method as: public static void main(String[] args)

That is the same category of failure as the wrong main signature in Lecture 1: a clean compile is not proof that a program runs.

7.final and static final

One keyword left, and it is the smallest idea in the lecture. static says how many copies there are; final says whether the value may change.

Definition— final

A variable declared final may be assigned once and never again. A local final is assigned where it is declared. A final instance field may be left unassigned in the declaration and set by the constructor, which is how you write a field that is fixed for an object's whole lifetime.

static final together means one copy, never changes — a constant. By universal Java convention constants are named in UPPER_CASE_WITH_UNDERSCORES, which is why Math.PI and Integer.MAX_VALUE are shouted.

Worked Example— a constant, and a field fixed at construction

PI is static final: one value for the program. radius is final but not static: each circle has its own, assigned by the constructor and unchangeable afterwards.

Circle.java

public class Circle {

    private final double radius;      // set once, in the constructor

    public Circle(double r) {
        radius = r;
    }

    public double area() { return PI * radius * radius; }
    public double getRadius() { return radius; }
}

Do not be distracted by lines 1, 2, 3, 5, 6 and 7. Lines 1–3 are inside a constructor, which always runs on a brand-new object, so bare x and y are fine and so is the static a. Lines 5 and 6 are inside an instance method, which also has an object. Line 7 looks suspicious — n.a reaches a static field through an object reference — but that is legal Java, as §5 noted, so it is not one of the three errors.

Error 1 — line 4. fix(MyNumbers n) is static, and x is an instance field. Whose x?

        // line 4
^

Corrected: n.x = a; — the method was handed an object, so name it. (Deleting static from the method header would also compile, but it would then break line 10's call from main, so it is not the fix the problem wants.)

Error 2 — line 10. fix(MyNumbers n) is declared void. It returns nothing, so there is nothing to assign to k.

        // line 10
^

Corrected: fix(k);

Error 3 — line 11. The two-parameter fix has no static, so it is an instance method, and main is calling it with no object.

MyNumbers.java:25: error: non-static method fix(MyNumbers,MyNumbers) cannot be referenced from a static context fix(k, k);
        // line 11
^

Corrected: k.fix(k, k);

    static int a;
    int x, y;

    public MyNumbers() {
        a = 111;                        // line 1
        x = 211;                        // line 2
        y = 212;                        // line 3
    }

    public static void fix(MyNumbers n) {
        n.x = a;                        // line 4  FIXED
    }

        x = n.x;                        // line 5
        y = m.y;                        // line 6
        return n.a;                     // line 7
    }

        System.out.println(a);          // line 8
        MyNumbers k = new MyNumbers();  // line 9

        System.out.println(a);          // line 12

Things to notice. Line 8 prints 0 and that is not an accident of the exercise — it is the definition of a static field. a is declared static int a; with no initializer, so it exists from the moment the class loads, holding the default int value 0. No MyNumbers object has been created at that point, and none is needed. An instance field could not have been printed there at all.

Line 12 prints 111 because the constructor on line 9 assigned to the shared a. Every MyNumbers you construct sets the one copy of a to 111; construct a thousand and it is still 111. Contrast that with x and y, which are re-created fresh for every object.

Notice too that javac reports all three errors in one run here. That is because they are semantic errors — the file parsed cleanly — unlike a missing semicolon, which stops the parser and hides everything after it.

Finally, the two methods called fix are an overload, and they coexist happily because their parameter lists differ. Overloading is not the bug in this problem; static is.

Consider the following Java program. The five lines below ask only about object identity and content. (The full eight-part version of this problem, which also covers equalsIgnoreCase and case sensitivity, is in the Lecture 4 practice set.)

Output.java

        String b = "java";
        String c = new String("java");
        String d = c;
        String e = "Java";

            a, c, e}
        ;

        // line (a) System.out.println(a == c);                  // line (b) System.out.println(c == d);                  // line (c) System.out.println(a.equals(c));             // line (d) words[1] = b; c = "CSCI"; System.out.println(words[1] == a);           // line (g) } }

(a) What is the output at line (a)?

true. Both are string literals with the same characters, and Java interns literals: the second "java" reuses the object created for the first. Same object, so == is true.

(b) What is the output at line (b)?

false. new String("java") is an explicit instruction to build a new object. It has the same characters and a different address, and == asks about the address.

(c) What is the output at line (c)?

true. String d = c; copied the reference, so c and d are aliases for the one object built by new. This is p1 == p3 from §1 wearing different letters.

(d) What is the output at line (d)?

true. String overrides equals to compare characters, and both hold java. Compare with line (b): same two variables, different question, different answer.

(g) What is the output at line (g)?

true. Read the two lines above it carefully.

words[1] = b; stores the reference held by b into slot 1 of the array. b refers to the interned literal "java", and so does a. So words[1] and a are the same object.

c = "CSCI"; then repoints the variable c. It does not touch the array at all — the array is holding a reference it was given a moment ago, not a link to the variable c. This is the c2 = new Counter(0) distinction from Quick Check 9.1 for the third time.

Things to notice across all five parts. One program, one pair of variables, and the answer flips depending on whether you asked == or .equals. Every exam this course has ever set contains a question of this shape, and the technique is always the same: draw the objects as boxes, the variables and array slots as arrows, and redraw the arrows after every assignment. Then read the answer off the picture instead of off the text.

Problem 3 — Give Fraction an equals and a toString (added for these notes)

Write a complete class Fraction with private int fields numerator and denominator, a two-parameter constructor, getters for both fields, a toString that prints a fraction as 3/4, and an equals that treats two fractions as equal when they represent the same value — so 1/2 must equal 2/4. Your equals must work when it is called through an Object reference and when it is called by ArrayList.contains.

Plan. The signature and the guard are the same boilerplate as always. The interesting decision is the comparison. Reducing both fractions to lowest terms would work but needs a greatest-common-divisor loop; cross-multiplying is one line and exactly equivalent: a/b equals c/d precisely when a*d == c*b. Do not compare numerator to other.numerator and denominator to other.denominator — that is the "same written form" test, not the "same value" test, and it would call 1/2 and 2/4 different.

Fraction.java

public class Fraction {
    private int numerator;
    private int denominator;
    public Fraction(int n, int d) {
        numerator = n;
        denominator = d;
    }
    public int getNumerator() {
        return numerator;
    }
    public int getDenominator() {
        return denominator;
    }
    @Override public String toString() {
        return numerator + "/" + denominator;
    }
    @Override public boolean equals(Object obj) {
        if (!(obj instanceof Fraction)) return false;
        Fraction other = (Fraction) obj;
        return numerator * other.denominator == other.numerator * denominator;
    }
}

import java.util.ArrayList;

Things to notice. System.out.println(list) prints [1/2, 1/3]. ArrayList has its own toString that walks the elements and calls toString on each — so writing one method on Fraction made printing a whole collection work. That is the compounding benefit of overriding the standard methods rather than inventing your own display().

list.contains(twoQuarters) is true even though no Fraction object with numerator 2 is in the list. contains calls equals, equals says a half is a half, and the library agrees. Every collection method that searches — contains, indexOf, remove(Object) — behaves according to the equals you wrote.

Problem 4 — A class that counts itself (added for these notes)

Write a complete class Ticket for a parking-violation system.

  • Two public constants: FIRST_HOUR_FINE, worth 25.0, and EXTRA_HOUR_FINE, worth 10.0. They must be readable as Ticket.FIRST_HOUR_FINE without creating an object, and must not be assignable.
  • A private static counter of tickets issued, with a public static getIssued().
  • Private instance fields: a ticket number that is fixed once the ticket exists, a String plate, and an int hoursExpired.
  • A constructor taking the plate and the hours expired. It must assign this ticket the next number in sequence: the first ticket built is #1, the second #2.
  • A method fine() returning the amount owed: 0 if no hours have expired, otherwise 25 for the first hour plus 10 for each additional hour.
  • A toString producing Ticket #1 plate ABC1234 fine $25.0.

Plan. Sort the members into the two piles before writing anything. The two fine amounts and the issued counter are facts about the whole system: static. The number, plate and hours belong to one ticket: instance. The two fine amounts never change: static final. The ticket number is fixed for the life of the object but different for every object, which is precisely a final instance field — assigned in the constructor, never again.

The numbering trick is the one from §5: increment the shared counter first, then copy its new value into this object's field.

Ticket.java

public class Ticket {
    public static final double FIRST_HOUR_FINE = 25.0;
    public static final double EXTRA_HOUR_FINE = 10.0;
    private static int issued = 0;
    private final int number;
    private String plate;
    private int hoursExpired;
    public Ticket(String plate, int hoursExpired) {
        this.plate = plate;
        this.hoursExpired = hoursExpired;
        issued++;
        number = issued;
    }
    public static int getIssued() {
        return issued;
    }
    public double fine() {
        if (hoursExpired <= 0) return 0.0;
        return FIRST_HOUR_FINE + (hoursExpired - 1) * EXTRA_HOUR_FINE;
    }
    @Override public String toString() {
        return "Ticket #" + number + " plate " + plate + " fine $" + fine();
    }
}

TicketDemo.java

public class TicketDemo {
    public static void main(String args[]) {
        System.out.println("Tickets issued: " + Ticket.getIssued());
        System.out.println("First hour fine: $" + Ticket.FIRST_HOUR_FINE);

        Ticket t1 = new Ticket("ABC1234", 1);
        Ticket t2 = new Ticket("XYZ9876", 3);

        System.out.println(t1);
        System.out.println(t2);
        System.out.println("Tickets issued: " + Ticket.getIssued());
    }
}

Things to notice. The first two lines of main run before any ticket exists, and both work. That is the practical meaning of "belongs to the class": Ticket.getIssued() and Ticket.FIRST_HOUR_FINE are questions you can ask an empty system.

fine() uses FIRST_HOUR_FINE with no qualification at all. An instance method may read a static field directly — the arrow runs that way — and writing Ticket.FIRST_HOUR_FINE inside the class would be correct but noisy.

number being final is not decoration. It documents that a ticket number is issued once and never edited, and it makes any later number = ... a compile error rather than a subtle accounting bug. Meanwhile hoursExpired is deliberately not final, because an officer might correct it.

The three-hour ticket costs 45.0: 25 for the first hour plus 10 for each of the two extra hours. If your answer came out 55, you charged the first hour twice — the hoursExpired - 1 is the whole content of that formula.

Problem 5 — What is the output? (added for these notes)

Consider the following Java program.

Gadget.java

public class Gadget {
    static int made = 0;
    static String label = "none";
    int id;
    String name;

    public Gadget(String name) {
        made++;
        id = made;
        this.name = name;
        label = name;
    }

    public boolean equals(Object obj) {
        if (!(obj instanceof Gadget)) return false;
        Gadget g = (Gadget) obj;
        return name.equals(g.name);
    }

    public String toString() { return "Gadget " + id + ":" + name; }

    public static void main(String args[]) {
        Gadget a = new Gadget("bolt");
        Gadget b = new Gadget("bolt");
        Gadget c = a;

        System.out.println(a);                          // line (a)
        System.out.println(a == b);                     // line (b)
        System.out.println(a.equals(b));                // line (c)
        System.out.println(a == c);                     // line (d)
        System.out.println(made + " " + a.made);        // line (e)
        System.out.println(label);                      // line (f)
        Gadget d = new Gadget("nut");
        System.out.println(a.label + " " + b.label);    // line (g)
        System.out.println(a.id + " " + d.id);          // line (h)
        Object o = b;
        System.out.println(o.equals(a));                // line (i)
        System.out.println(o);                          // line (j)
    }
}

(a) What is the output at line (a)?

Gadget 1:bolt. println calls the overridden toString. a was the first object built, so the constructor took made from 0 to 1 and copied 1 into a.id.

(b) What is the output at line (b)?

false. Two new calls means two objects, so the references differ.

(c) What is the output at line (c)?

true. equals was overridden correctly — the parameter is Object — and it compares name, which is "bolt" on both.

(d) What is the output at line (d)?

true. Gadget c = a; copied the reference; a and c are one object.

(e) What is the output at line (e)?

2 2. made is static, so made and a.made are two spellings of the same variable, and two gadgets have been built. Reading a static field through an object reference is legal — and it is exactly what an exam question is testing when it writes a.made instead of Gadget.made.

(f) What is the output at line (f)?

bolt. label starts as "none", but every constructor call overwrites the one shared copy. Two gadgets have been built, both named bolt, so it holds "bolt".

(g) What is the output at line (g)?

nut nut. Building d ran the constructor again, which set the shared label to "nut". There is only one label, so a.label and b.label both report it — even though neither a nor b is a nut. This is the classic argument against mutable static state: an object's own name field says bolt while the class-level label says nut.

(h) What is the output at line (h)?

1 3. id is an instance field, frozen at construction. a got 1 and kept it; d was the third object and got 3. Compare this line with (g): same program, one field per object versus one field per class.

(i) What is the output at line (i)?

true. o is declared Object, so at compile time Java selects equals(Object) — and because this class genuinely overrides that method, the call is dispatched at run time to Gadget's version. Had the class written equals(Gadget g) instead, this line would print false.

(j) What is the output at line (j)?

Gadget 2:bolt. Same reasoning: o is declared Object, but toString is a real override, so the object's own version runs. Declaring a variable Object changes which methods you may call; it never changes which version of an overridden method runs.

Things to notice across the whole problem. Lines (e)–(h) are the static story: one made, one label, but a separate id and name in every object. Lines (i)–(j) are the override story: correct signatures survive being called through an Object reference. Get both of those and you have the whole lecture.

If you want to feel the difference, change the header of equals to public boolean equals(Gadget g), delete the instanceof and the cast, and re-run. Lines (a) to (h) are unchanged and line (i) flips to false. One word in one header, and a method that looked fine in testing stops being called by anything that holds your object as an Object — which includes every collection in the standard library.

Lecture Summary
  • For objects, = copies a reference and == compares references. For primitives both work on the value. Two objects with identical contents are never ==.
  • Every class inherits equals and toString from Object. The inherited equals is just ==; the inherited toString returns ClassName@hashcode, which is machine-dependent and useless for reading. A serious class overrides both.
  • The signature of equals is public boolean equals(Object obj) — the parameter is Object, always. Guard with instanceof, cast, then compare the fields that matter, using .equals for object-valued fields.
  • Writing equals(MyType t) overloads instead of overriding. It works when you test it directly and silently fails through an Object reference — including inside ArrayList.contains. Write @Override and the compiler catches it.
  • toString returns a String; it does not print. Any change to the signature turns it into an overload that println will never call.
  • A static member belongs to the class: one copy, alive before any object exists, normally named ClassName.member. An instance member belongs to an object: one copy per new. A counter of objects created is the standard example.
  • A static method has no object, so it cannot touch instance fields or instance methods and cannot use this — hence non-static variable x cannot be referenced from a static context. Fix it by passing an object in, creating one, or (only if the data really is class-wide) making the field static. main is static because the JVM has no object to call it on.
  • final allows one assignment. static final is how you write a constant, named in UPPER_CASE. On an object variable, final freezes the reference, not the object.
