1.The shape of the final, and how to spend 120 minutes

Eighty marks in a hundred and twenty minutes is ninety seconds a mark. That sounds generous, and it is — provided you do not spend forty minutes polishing one constructor. The published rubrics award marks per line, by goal, and they are unusually explicit about it. Three real examples:

  • On the Summer 2026 Problem 1, the class header alone is 1 mark, the three private fields together are 1 mark, and the constructor is 2. That is 4 of the 15 before you have written a single method, and every one of those lines can be written straight off the specification.
  • On both papers, the whole of Problem 5(a) — the main method — is 2 marks for two lines that are the same two lines every year: construct the frame, then setVisible(true).
  • On Problem 4(c), the title line public static <T> T middleElement(T array[]) is worth 2 marks on its own, and the body is worth 3.

Add those up and there are roughly ten marks on the paper for lines that do not depend on solving anything. Write them first.

Procedure— a sane two hours
  1. Five minutes: read all five problems. You cannot budget time for a paper you have not seen, and you will find that two of the five are questions you have already worked.
  2. Problem 2 first (the output prediction, 20 marks). It is the fastest scoring on the page, it is mechanical, and it warms you up. Twenty-five minutes.
  3. Then the two class-writing problems (1 and 3, 30 marks). Do them in the order that looks easier to you. Twenty minutes each.
  4. Then Problem 4 (15 marks), which is three small independent functions — three separate part-marks, so a blank on one costs you nothing on the other two. Fifteen minutes.
  5. Then Problem 5 (15 marks), the window. Write main and the class-header changes immediately, then the constructor, then actionPerformed. Twenty minutes.
  6. Fifteen minutes left over. Go back to whatever you abandoned, and fill in every blank space with the part of the answer you do know.
Key Idea— never leave a part blank

Every rubric in this course ends with the same sentence: "If a program follows a different (but reasonable) plan, try to award partial credit for meeting similar goals in the program." A class header with the right private fields and a constructor collects marks even when the last method is empty. An empty space collects nothing. If you can only remember half of actionPerformed, write that half.

One more piece of arithmetic, because it changes what you should practise. The final has no multiple choice and nothing to circle: every mark on the paper is a line of Java you have to produce from memory, in pen. Reading a constructor and nodding is a different skill from writing one on a blank page, and only the second one is examined. So work the problems on this page with a pen before you open the toggles.

2.Writing a class, and writing its subclass

Problem 1 is fifteen marks and it has been the same shape for two years: here is a description, write the class; here is a second description, write the subclass. Problem 3 is another fifteen for a single class. Between them that is nearly forty per cent of the paper, and it is all one skill — turning an English specification, or a UML box, into Java without adding anything that was not asked for.

Procedure— the fifteen-mark class, in order
  1. public class Name { — and if the specification says "exactly three instance variables", write exactly three.
  2. The instance variables, each private, each on its own line. A UML box lists them for you: the middle compartment is the fields, the bottom compartment is the methods.
  3. The constructor: the class's name, no return type, one parameter per instance variable, body assigning this.field = parameter;.
  4. The methods the specification names, in the order it names them, and no others.
  5. toString, which returns a String and never prints one. Copy the required format character for character out of the question.

Then, for the subclass:

  1. public class Sub extends Super {
  2. Only the extra fields. "It should have no extra instance variables" means write none.
  3. A constructor whose first statement is super(...), passing up whatever the parent needs.
  4. Only the extra or overridden methods.

Four details decide most of the lost marks on this problem.

  • Constructors are never inherited. Square gets area() and isOutside() from Rectangle free; it does not get Rectangle's constructor. If you want new Square(p, 5) you must write that constructor yourself, even when its whole body is one super(...) call.
  • super(...) must come first, before you store your own fields. And if you leave it out altogether, Java inserts a silent super() — which fails whenever the parent has no no-argument constructor, with a message that points at your constructor and complains about one you never wrote.
  • A private field of the parent is part of the object but invisible to the subclass's code. The Summer 2026 EBook.toString has to say getTitle() and getPages(), not title and pages, because LibraryItem declared them private. That is not a stylistic preference; the file does not compile otherwise.
  • A method that changes the object returns nothing. checkOut(), addOn(...) and multiplyBy(...) are all void: they modify the object they were called on. x.addOn(y); is a complete statement. x = x.addOn(y); is a compile error.

3.Lists, stacks and aliasing

Problem 2 is twenty marks — a quarter of the paper — and it is ten independent two-mark answers, so it is also the most forgiving question on the page. Its first half is built out of three ideas you met long before Lecture 21: what a reference is, what == compares, and what equals compares.

  • a3 = a2; does not copy a list. It copies the arrow. There is one list with two names, and a change made through either name is visible through the other. That is why lines (c) and (d) of both real papers print exactly the same thing after a3.add(...).
  • == on two object variables asks "the same object?" Two separate new ArrayList<>() calls are never ==, however identical their contents. a1 == a2 is false on both papers; a2 == a3 is true on both, because of the assignment.
  • .equals on two ArrayLists compares contents, element by element, in order. Same size, same values, same positions gives true. ArrayList inherits this from AbstractList, and it in turn calls .equals on the elements — which is why it works for Integer and String without your doing anything.
  • A Stack is last-in-first-out. push puts on top, pop takes off the top and removes it, peek looks without removing, isEmpty is how you know when to stop. Pushing 1 2 3 4 5 and popping until empty prints 5 4 3 2 1.
  • pop empties the stack as it goes. Both real papers pop the stack dry at line (e), push two more values, and then ask again at line (g) — and the answer at (g) is only those two values, because the first five are gone.

Removing from a list while you are walking it is the one operation that behaves differently depending on which element you remove. Predict all three lines.

import java.util.ArrayList;

The iterator remembers a cursor and the list's modification count; next() compares the two and throws if they disagree, but hasNext() only checks cursor != size. So removing an element changes the size and the count, and which of the two checks you hit first decides what happens.

Common Mistake— the list-and-stack traps, collected
  • Thinking a3 = a2 copies the list. It copies the reference. If you want a genuine copy, that is new ArrayList<Integer>(a2), and neither exam asks for one.
  • list.remove(20) on an ArrayList<Integer> removes index 20 and throws IndexOutOfBoundsException on a short list. To remove the value, list.remove(Integer.valueOf(20)).
  • ArrayList<int> does not compile. The type argument must be a class, so it is ArrayList<Integer>, and ArrayList<Double>, and ArrayList<Character>.
  • Comparing wrapper values with ==. Two Integer objects holding 127 usually are ==, because Java caches the small ones; two holding 128 are not. Use .equals for every wrapper and every String, always. The same applies to String values that came from the user.
  • Forgetting that pop removes. Popping a stack dry and then asking what is in it is a favourite: after line (e) of both real papers the stack is empty, and lines (f) and (g) only ever see what was pushed afterwards.
  • Mixing up a.length, s.length() and list.size(). Three containers, three spellings, and getting one wrong is a compile error every time.
  • Removing inside a for-each loop — ConcurrentModificationException, or worse, silence. Practice Problem 28.4 above.

4.Iterators, and the loop that runs out

The second half of Problem 2 is five more two-mark answers, and all five come from one small interface. An iterator is a separate little object that remembers a position in a collection. hasNext() asks whether there is at least one more element; next() returns the next one and advances. That is the whole of it, and every part of the question is a consequence.

  • collection.iterator() makes a new iterator every time you call it. Two calls give two objects, each with its own cursor starting at the beginning. That is why line (h) of both real papers prints false: y == z compares two different objects.
  • hasNext() promises exactly one element, not two. A loop body that calls next() twice is checked once, and on a collection with an odd number of elements the second call in the last pass throws NoSuchElementException.
  • next() advances even when its value is thrown away. A body that prints one element and then calls next() again without printing it visits every second element.
  • The try/catch in her question is doing real work. The exception is caught, the message is printed, and then the while condition is tested again — and because the failed next() did not advance anything, the loop ends there. So the answer to those parts always looks like values, values, values, then the message.
  • A Stack's iterator runs bottom to top — the opposite of pop. java.util.Stack extends Vector, and a Vector's iterator walks the underlying array from index 0, which is the bottom of the stack. This is the single most surprising line on the paper, and it is worth two marks both years.

Things to notice across all three parts. After the catch the while condition is tested once more. The failed next() did not move the cursor, and the successful one left it at the end, so hasNext() is now false and the loop stops. If it did not, this would be an infinite loop — and that is exactly what happens to people who write the same code with the catch inside a loop the exception cannot advance.

The exception's full name is java.util.NoSuchElementException, and her answer keys write the catch message rather than the class name. Read the question: if the catch prints " No such element", that string is the answer.

Key Idea— if you can only do one thing for the second half of Problem 2

Count. Write the collection's elements in a row, put a finger at the front, and move it one place for every single next() in the loop body — including the ones whose value is discarded. When your finger runs off the end in the middle of a pass, that is where the exception message goes. The whole question is bookkeeping, and it is two marks a line for doing it carefully.

Common Mistake— the iterator traps, collected
  • Expecting a Stack's iterator to match pop. It does not. Bottom to top, every time.
  • Calling next() twice under one hasNext(). If you really want elements in pairs, you must check again in the middle: if (it.hasNext()) before the second call.
  • Forgetting that a discarded next() still advances. System.out.print(z.next()); z.next(); prints every other element, and the elements it skips are gone.
  • Thinking two iterators share a position. y and z from the same list are independent; running y to the end leaves z untouched at the start.
  • Answering y == z with true because they iterate the same list. They are two objects. == is false, and so is equals — ArrayList's iterator does not override equals, so it inherits the version from Object, which is == again.
  • Writing a class with an iterator() method and expecting a for-each loop to work. The for-each rewrite is triggered by the type: the class must say implements Iterable, or you get for-each not applicable to expression type.
  • Modifying the collection during the walk — ConcurrentModificationException if you are lucky, a skipped element if you are not.

5.Generics

Generics were the whole of Problem 3 on the Summer 2026 paper and one third of Problem 4 on both. A generic class or method is written once and works for any reference type, with the compiler checking each use. There are only two shapes to memorise, and they are short enough to write on the inside of your eyelids.

Procedure— the two shapes

A generic class. The type parameter goes on the class header, after the name, and can then be used anywhere inside as if it were a real type.

public class StorageBox<T> {
    private T item;
    private int count;

    public StorageBox(T item, int count) {
        this.item = item;
        this.count = count;
    }

    public T getItem() { return item; }
}

A generic method. The type parameter goes on the method, between the modifiers and the return type. It is the only place in Java where something in angle brackets comes before the return type, which is why it looks so odd and why it is worth two marks on its own.

public static <T> T middleElement(T array[]) {
    if (array == null || array.length == 0) {
        return null;
    }
    return array[array.length / 2];
}

The rest is small print, and all of it has been examined:

  • The type argument must be a class. StorageBox<Integer> and StorageBox<String> are fine; StorageBox<int> gives unexpected type / required: reference / found: int.
  • T is a name, not a keyword. <T>, <E>, <K, V> are conventions. Two parameters are written class Pair<K, V> and used as new Pair<String, Integer>(...).
  • Inside the class, T behaves like a type you cannot construct. You may declare fields and parameters of type T, return T, and call Object methods on a T — toString, equals. You may not write new T().
  • A generic method infers its type argument from the call. You write middleElement(words) with no angle brackets at the call site, and the compiler works out that T is String.
  • Generics do not work on primitive arrays. int[] is not T[] for any T, and Java will not box a whole array for you. Declare it Integer[] if it has to go through a generic method.
  • Leaving the angle brackets off entirely gives a raw type: the class with its type checking switched off, an unchecked or unsafe operations note from javac, and a ClassCastException waiting at run time.

6.Exceptions

Exceptions carry more marks on this paper than their one lecture suggests, because they turn up in two other problems. Problem 4(a) is a try/catch around Integer.parseInt. Problem 5(c) — the response method of the GUI — is a try/catch around Double.parseDouble, and her own answer key wraps it every year. Both are five-line answers, and both are marked as 2 points for the try and catch block.

  • The shape. try { risky work } catch (SomeException e) { what to do instead }, with an optional finally { cleanup } that runs whichever way the block ends.
  • Checked versus unchecked. Anything below RuntimeException is unchecked and the compiler ignores it: NullPointerException, ArrayIndexOutOfBoundsException, NumberFormatException, ArithmeticException, ClassCastException, NoSuchElementException, ConcurrentModificationException. Everything else that extends Exception is checked, and you must catch it or declare it: IOException, FileNotFoundException, ClassNotFoundException, and every exception class you write yourself.
  • throw is a statement; throws is a clause in the header. throw new AgeException("too big"); raises one now. throws AgeException only warns callers that one might get out. One letter, two completely different jobs.
  • Writing your own exception is three lines. public class EmptyArrayException extends Exception plus a constructor that passes its String up with super(message). Extend Exception for a checked one, RuntimeException for an unchecked one — her practice question specifies "are exceptions but are not run time exceptions", which means extends Exception.
  • catch clauses are tried in order, most specific first. A catch (Exception e) above a catch (NumberFormatException e) makes the second unreachable, and unreachable catch blocks are a compile error, not a warning.
  • The rest of the try block is abandoned. There is no resuming where the throw happened, and a variable declared inside the try does not exist in the catch.

8.The rest of the course, in one page

Neither of the last two finals asked directly about recursion, files, graphics, interfaces or polymorphic dispatch. That does not make them safe to forget, for two reasons: her practice sets ask about all of them, and more importantly you cannot answer the questions that were on the paper without them. Problem 1 is Lecture 7 and Lecture 12. Problem 2 is Lecture 8 with a Stack in it. Problem 5's actionPerformed is Lecture 16 wrapped around Lecture 20. Here is the rest of the course, compressed to what you would need to recognise a question.

Lectures 1 to 5 — the language. Integer division: if both operands of / are int, the fraction is thrown away, and casting the result afterwards cannot get it back. + means addition until the first String appears and concatenation from then on. A char is a number. A String is an object, so content comparison is .equals and "abc" == someInput is a trap; String methods return a new string and change nothing, so s.trim(); on its own line does nothing at all. Arrays have a.length, strings have s.length(), lists have list.size(). Reading a file is new Scanner(new File(name)) — new Scanner("scores.txt") compiles and reads the file name as text — and writing one is new PrintWriter(name) with a matching close(), without which the file is empty.

Lectures 10 and 11 — design. Nouns suggest classes, verbs suggest methods; a thing with state worth remembering is a class, a plain value is a field. "Has-a" is a field, "is-a" is extends. An array of objects is an array of nulls until you fill it, and every use of street[i] needs a guard.

Lectures 13 and 14 — polymorphism, abstract classes and interfaces. Every reference has two types: the declared type, which decides what you are allowed to write, and the dynamic type of the object, which decides which override actually runs. Fields are the other way round — they use the declared type. A downcast that the compiler cannot rule out is checked at run time and throws ClassCastException; guard it with instanceof. An interface is a list of obligations whose methods are implicitly public, so an implementing method that leaves public off does not compile. You may declare a variable of an abstract type but never construct one.

Lecture 19 — graphics. You override paintComponent(Graphics g), start it with super.paintComponent(g), and never call it yourself — you call repaint(). Ovals and rectangles are given a bounding box, not a centre. A fill covers x through x + w - 1; an outline is drawn on x and on x + w. The last thing drawn is the thing you see.

The mathematical facts you need: the area of a rectangle is its width times its height; a point is inside the rectangle if its x-coordinate lies between the rectangle's left and right edges and its y-coordinate lies between its top and bottom edges; and a square with top-left corner p and side length s is a rectangle with width s and height s.

Rectangle.java

public class Rectangle {
    private Point topLeft;
    private double width;
    private double height;

    public Rectangle(Point tl, double w, double h) {
        topLeft = tl;
        width = w;
        height = h;
    }

    public double area() {
        return width * height;
    }

    public boolean isOutside(Point p) {
        double px = p.getX();
        double py = p.getY();
        return (px < topLeft.getX() || px > topLeft.getX() + width ||
                py < topLeft.getY() || py > topLeft.getY() + height);
    }
}

  • Multiplication gives (ac − bd) + (ad + bc)i.

Plan. Three decisions, and the marks are distributed over them very unevenly: 1 for the header, 1 for the fields, 2 for the constructor, 3 for toString, 3 for addOn and 5 for multiplyBy.

First, both methods are void. x.addOn(y) changes x in place and returns nothing, so their bodies assign to real and imaginary rather than building a new object.

Second, toString has to produce 8.0 - 6.0i and not 8.0 + -6.0i, so it needs an if: when the imaginary part is negative, print a minus sign and the positive version of the number.

Third — and this is the five-mark trap — multiplyBy needs the old real part when it computes the new imaginary part. Assign to two local variables first, and only then copy them into the fields.

ComplexNumber.java

public class ComplexNumber {
    private double real;
    private double imaginary;

    public ComplexNumber(double r, double i) {
        real = r;
        imaginary = i;
    }

    public String toString() {
        if (imaginary >= 0) {
            return real + " + " + imaginary + "i";
        } else {
            return real + " - " + (-imaginary) + "i";
        }
    }

    public void addOn(ComplexNumber c) {
        real = real + c.real;
        imaginary = imaginary + c.imaginary;
    }

    public void multiplyBy(ComplexNumber c) {
        double newReal = real * c.real - imaginary * c.imaginary;
        double newImaginary = real * c.imaginary + imaginary * c.real;
        real = newReal;
        imaginary = newImaginary;
    }
}

The mistakes that have cost the most marks all semester:

  • Forgetting this. when the parameter and the field share a name — the field is silently never set.
  • Reading a private parent field from a subclass instead of calling the getter.
  • Leaving super(...) out, or putting it second.
  • equals(MyClass o) instead of equals(Object o).
  • Leaving public off a method that implements an interface.
  • Leaving out b.addActionListener(this); — the compiler will never tell you.
  • Declaring a component as a local inside the constructor when actionPerformed needs it.
