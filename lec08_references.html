Object References and Aliasing

A variable of a class type does not hold the object. It holds a note saying where the object is — and every confusing program you write this semester will trace back to that one sentence.

1.What a class-type variable really holds

Last time you learned to build a class and make objects out of it. You wrote Point, you wrote Triangle, you handed three Points to a Triangle constructor, and everything worked. The lecture ended with one question left deliberately open: when you write

Point a = new Point(0, 0);
Point c = a;

do you now have two points, or two names for one point? Today's answer decides the meaning of half the code you have already written, so it is worth getting exactly right rather than approximately right.

Start with the thing you already trust. A primitive variable holds its value, and nothing else. The name m is the box that contains 5.

Definition— reference

A variable of a class type does not hold an object. It holds a reference: a value that tells the JVM where in memory the object lives. You can think of it as the object's address, or as an arrow pointing at the object.

The object itself lives somewhere else — in a region of memory called the heap — and it is created by new. Without a new there is no object, no matter how many variables you declare.

Java will not let you see the numeric value of a reference, do arithmetic on it, or turn it into an integer. That is the whole difference between a Java reference and a C++ pointer: same idea, none of the sharp edges.

Key Idea— the one sentence for today

new creates objects. = copies whatever is in the variable. For a primitive that is the value; for a class type that is the arrow. So the number of objects in your program is exactly the number of times you wrote new — assignments never add one.

Worked Example— the same two lines, twice

This program does the identical thing twice: declare a variable, copy it into a second variable, then change the second one. The first time with an int, the second time with a Point. Everything about the shape of the code is the same. Predict both lines before you reveal.

CopyDemo.java

public class CopyDemo {
    public static void main(String args[]) {
        int m = 5;
        int n = m;
        n = 99;
        System.out.println("m = " + m + ", n = " + n);

        Point p = new Point(5, 5);
        Point q = p;
        q.setX(99);
        System.out.println("p = " + p + ", q = " + q);
    }
}
m = 5, n = 99
p = (99.0, 5.0), q = (99.0, 5.0)

The int behaves the way you expect: n = m copied the number 5 into a second box, and changing n left m alone. There were two boxes from the moment int n = m; ran.

The Point does not. Point q = p; copied the arrow, so p and q point at the same object. q.setX(99) did not change q at all — q still holds the same arrow it always did. It reached through q and changed the object, and p is looking at that same object.

2.Aliasing: two names, one object

Definition— alias, aliasing

Two reference variables are aliases when they hold the same reference, so both point at the same object. The situation is called aliasing.

The consequence is the whole point: a change made through one alias is visible through every other alias. There is no copy to fall out of step, because there is no copy.

Worked Example— Point c = a; (the instructor's Example1)

The Point class is unchanged from Lecture 7. It is reprinted here because everything today is built on it.

Point.java

public class Point {
    private double x, y;

    public Point() {
        x = 0.0;
        y = 0.0;
    }

    public Point(double xValue, double yValue) {
        x = xValue;
        y = yValue;
    }

    public double getX() { return x; }
    public double getY() { return y; }
    public void setX(double xValue) { x = xValue; }
    public void setY(double yValue) { y = yValue; }

    public double distanceTo(Point other) {
        return Math.sqrt((x - other.x) * (x - other.x) + (y - other.y) * (y - other.y));
    }

    public String toString() {
        return "(" + x + ", " + y + ")";
    }
}

Procedure— how to trace any reference program

This is a mechanical routine. Done on paper it is nearly impossible to get wrong, and it is exactly what the exam questions are testing.

  1. Draw two columns: variables on the left, objects on the right. Leave room; you will need it.
  2. Every time you meet new, draw a new box on the right and fill in its fields. Number the boxes #1, #2, #3 as you go.
  3. Every time you meet x = y where both are class types, erase x's arrow and redraw it to wherever y's arrow points. No box is created, none is destroyed.
  4. Every time you meet x.setSomething(...), follow x's arrow and edit the numbers inside that box. No arrow moves.
  5. To print x, follow x's arrow and read the box it lands on.

Steps 3 and 4 are the whole lecture. Step 3 moves an arrow and touches no object; step 4 touches an object and moves no arrow.

(b) What is printed at line (b)?

(9.0, 2.0) — the same thing. After r = s, the variables r and s are aliases for object #2, and r.setX(9) edited that object. This is the line students least expect: nothing was ever done "to s", and s changed anyway.

(c) What is printed at line (c)?

r = (9.0, 2.0)
s = (9.0, 2.0)
t = (1.0, 1.0)

t prints (1.0, 1.0). t was aimed at object #1 back when r still pointed there, and moving r afterwards has no effect on t — t holds its own copy of the arrow, and that copy still points at #1.

3.null, and the NullPointerException

If a reference variable is an arrow, there has to be a way to say "this arrow points at nothing". Java spells it null.

Definition— null

null is a special reference value meaning no object. Any reference variable may hold it, whatever its class.

null is the default for every uninitialized instance variable of a class type, and for every slot of a newly created array of objects. new Point[3] gives you three slots holding null — it does not give you three points.

Printing a null reference prints the four letters null. Calling a method on one is a run-time error.

Worked Example— what null does, and what it does not survive

This program deliberately ends badly. Everything up to the last line is fine. Work out how many lines it manages to print.

NullDemo.java

public class NullDemo {
    public static void main(String args[]) {
        Point p = null;
        System.out.println("p is " + p);
        System.out.println("Is p null? " + (p == null));

        p = new Point(1, 2);
        System.out.println("p is " + p);
        System.out.println("Is p null? " + (p == null));

        p = null;
        System.out.println("About to call a method on p...");
        System.out.println(p.getX());
    }
}
p is null
Is p null? true
p is (1.0, 2.0)
Is p null? false
About to call a method on p...
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "Point.getX()" because "p" is null
	at NullDemo.main(NullDemo.java:13)

Five lines, then the crash. Three separate facts are on display.

  • "p is " + p does not crash even when p is null. String concatenation checks for null and substitutes the text null, so printing a null reference is always safe. This is why a crash often happens several lines after the variable actually became null.
  • p == null is the test, and it is legal on any reference at any time.
  • p.getX() is what kills it. The dot means "follow the arrow", and there is no arrow to follow.

The message names the variable — because "p" is null — because this program was compiled with debugging information, which every IDE does by default. A bare javac NullDemo.java with no options prints an internal slot name — local1 in angle brackets — where the variable's real name would be. Either way the first half of the message, Cannot invoke "Point.getX()", tells you which call failed, and the at NullDemo.main(NullDemo.java:13) line tells you exactly where.

Common Mistake— an array of objects is an array of nulls

This is the single most common way students meet a NullPointerException in this course:

Point pts[] = new Point[3];
pts[0].setX(5);                 // NullPointerException

new Point[3] makes one object: the array. It makes no Points at all. You need a second new per slot:

Point pts[] = new Point[3];
for (int i = 0; i < 3; i++) {
    pts[i] = new Point(0, 0);
}

This is exactly why the instructor's Example3 writes pts[i] = new Point(...) inside a loop before ever building a Triangle from the array. Watch for it again in §6.

TotalXFixed.java

public class TotalXFixed {
    public static void main(String args[]) {
        Point pts[] = new Point[4];
        pts[0] = new Point(1, 1);
        pts[2] = new Point(3, 3);

        double total = 0;
        for (int i = 0; i < pts.length; i++) {
            if (pts[i] != null) {
                total += pts[i].getX();
            }
        }
        System.out.println("Total x: " + total);
    }
}
Total x: 4.0

Things to notice. The message even tells you the expression that was null — because "pts[i]" is null — which is far more useful than the bare NullPointerException older versions of Java printed. Read the whole message before you start guessing.

The other repair, filling every slot with new Point(0, 0) first, gives 4.0 as well here, but it is a different program: it says "there are four points, two of them at the origin" rather than "there are two points and two empty slots". Choose the one that matches what the data actually means.

A guard like this only makes sense when null is a legitimate state for your data. If a null in that array would be a bug, do not hide it behind an if — let it crash loudly and go fix whatever failed to fill the slot.

4.== on objects compares references

You have used == since your first week of CSCI 111 and it has always meant what you wanted. On objects it still does exactly what it always did — compare the two values in the two variables — but the values in the variables are now arrows.

Key Idea— what == asks

For primitives, a == b asks "are these the same value?"

For objects, a == b asks "are these arrows pointing at the same object?" It does not look inside the objects. Two separate objects whose fields are identical in every way still give false.

Worked Example— identical contents, different answers

All three points below print the same thing. Predict the three == results anyway.

IdentityDemo.java

public class IdentityDemo {
    public static void main(String args[]) {
        Point p1 = new Point(3, 4);
        Point p2 = new Point(3, 4);
        Point p3 = p1;

        System.out.println("p1 = " + p1);
        System.out.println("p2 = " + p2);
        System.out.println("p3 = " + p3);

        System.out.println("p1 == p2? " + (p1 == p2));
        System.out.println("p1 == p3? " + (p1 == p3));
        System.out.println("p1.getX() == p2.getX()? " + (p1.getX() == p2.getX()));
    }
}
p1 = (3.0, 4.0)
p2 = (3.0, 4.0)
p3 = (3.0, 4.0)
p1 == p2? false
p1 == p3? true

Three lines print (3.0, 4.0) and yet p1 == p2 is false. Two news ran, so there are two objects, and two different objects are never ==, however identical they look. p1 == p3 is true because p3 was never given its own object — it was handed p1's arrow.

The last line is the important contrast. p1.getX() and p2.getX() are double values, so that == is a primitive comparison and answers the question you probably meant to ask. The dot changed the meaning of the operator that follows it.

Common Mistake— using == to ask "are these the same point?"

If what you mean is "do these two points have the same coordinates", == is the wrong tool and will quietly answer false most of the time. Right now the only honest way to write it is to compare the fields yourself:

if (p1.getX() == p2.getX() && p1.getY() == p2.getY()) {
    System.out.println("same coordinates");
}

Java's standard answer to this problem is a method called equals, which every class inherits and which you can define for your own class. Out of the box, equals on a class you wrote does exactly what == does, which is why it is not the fix yet. Writing a real equals for Point is the first thing we do in Lecture 9.

The same trap applies to String, which is an object like any other. That is also next lecture's business — for now, note it and be suspicious of == on anything whose type starts with a capital letter.

5.Objects stored inside objects

In Lecture 7 you built a Triangle out of three Points and it seemed harmless. It is not, and the reason is now obvious: an instance variable of a class type is a reference, exactly like a local variable of a class type. When the constructor runs a = pA; it copies an arrow.

Key Idea— a Triangle does not contain Points

A Triangle object contains three references. The Point objects live outside it, on the heap, and the caller who passed them in is still holding arrows to the very same objects.

So the caller can reach in and change the triangle's geometry at any time, without ever mentioning the triangle. The Triangle has no way to notice and no way to stop it.

Today's Triangle is the instructor's variant whose toString lists the three vertices rather than the three side lengths. We need to see which points a triangle is holding, not how long its sides are.

6.Mutating versus rebinding

Everything so far comes down to one distinction, and it is worth giving it names.

Definition— mutating and rebinding

To mutate an object is to change the data inside it: p.setX(5). The object stays where it is, keeps its identity, and every arrow pointing at it now sees the new value.

To rebind a variable is to point it at a different object: p = new Point(5, 0). The old object is untouched, everybody else's arrows still point at it, and only this one variable moved.

Both are written with code that looks like "changing p". They are opposites.

The instructor wrote two programs, Example3 and Example3b, that differ in exactly two lines out of thirty. They exist to make this distinction impossible to miss, so read them side by side. Both build a triangle from an array of points, then read three more points and build a second triangle from the same array.

after replaceAll: pts[0] = (100.0, 200.0), a = (10.0, 20.0)

Things to notice. After scaleAll the two printed values agree, because pts[0] and a still point at one object. After replaceAll they disagree: pts[0] has moved on to a new object at ten times the size, while a is left holding the one scaleAll produced.

Both methods "work" in the sense that the array now contains scaled points. Which one you want depends entirely on whether anything outside the array is supposed to notice. That is a design question, and the answer has to be decided by you, not discovered by a user at 2am.

Note that replaceAll does successfully change the caller's array, even though we are about to spend §7 saying that a method cannot change its caller's variables. There is no contradiction: the array itself is an object, the method was handed a reference to it, and writing into a slot mutates that object. What replaceAll cannot do is make the caller's variable pts point at a different array.

7.Passing objects to methods

Passing a value to a method is an assignment: the argument is copied into the parameter. So everything in this lecture applies unchanged, and the famous confusing question answers itself.

Definition— pass-by-value

Java is pass-by-value, always, with no exceptions. When you call a method, the value of each argument is copied into the corresponding parameter, and the parameter is a brand-new variable local to the method.

For a primitive argument, the value copied is the number. For an object argument, the value copied is the reference. The object itself is never copied.

Key Idea— what a method can and cannot do

A method that receives an object can change that object's contents, and the caller will see it, because both are looking at the same object.

A method cannot change which object the caller's variable points at. Assigning to the parameter only moves the method's own private arrow, and that arrow ceases to exist when the method returns.

Worked Example— three methods, one of which does nothing

moveIt mutates its parameter. replaceIt rebinds its parameter. bumpIt does the same thing to a double. Decide, for each of the three, whether main sees any effect.

ParamDemo.java

public class ParamDemo {
    public static void moveIt(Point p) {
        p.setX(100);
    }

    public static void replaceIt(Point p) {
        p = new Point(-7, -7);
        System.out.println("    inside replaceIt, p is " + p);
    }

    public static void bumpIt(double d) {
        d = d + 1;
        System.out.println("    inside bumpIt, d is " + d);
    }

    public static void main(String args[]) {
        Point q = new Point(1, 1);
        double v = 1;

        System.out.println("before moveIt:    q is " + q);
        moveIt(q);
        System.out.println("after moveIt:     q is " + q);

        System.out.println("before replaceIt: q is " + q);
        replaceIt(q);
        System.out.println("after replaceIt:  q is " + q);

        System.out.println("before bumpIt:    v is " + v);
        bumpIt(v);
        System.out.println("after bumpIt:     v is " + v);
    }
}
before moveIt:    q is (1.0, 1.0)
after moveIt:     q is (100.0, 1.0)
before replaceIt: q is (100.0, 1.0)
    inside replaceIt, p is (-7.0, -7.0)
after replaceIt:  q is (100.0, 1.0)
before bumpIt:    v is 1.0
    inside bumpIt, d is 2.0
after bumpIt:     v is 1.0

moveIt worked. p received a copy of q's arrow, and p.setX(100) followed that arrow to the one and only Point object. q sees the change because there was never anything else to see.

replaceIt did nothing at all, from main's point of view. It really did build a new point and it really did print (-7.0, -7.0) from inside, proving that its own p moved. But p was a local variable; when the method returned, p vanished and the new Point became garbage. q never moved.

bumpIt did nothing either, and nobody is surprised by that. It is the exact same mechanism: the parameter is a copy, and assigning to a copy is invisible outside. replaceIt and bumpIt are the same story told with different types.

Inside replaceIt just after the assignment

main's q  | ref |------> +---------------+

                         |  y =   1.0    |

replaceIt's p | ref |--> +---------------+

The test that never fails: did the method use a dot, or an equals sign? A dot reaches the caller's object. An equals sign on the parameter itself reaches nothing.

Common Mistake— a "reset" method that resets nothing

This is replaceIt in the wild, and it looks completely reasonable:

ResetDemo.java

public class ResetDemo {
    public static void resetBroken(Point p) {
        p = new Point(0, 0);
    }

    public static void resetWorking(Point p) {
        p.setX(0);
        p.setY(0);
    }

    public static void main(String args[]) {
        Point p = new Point(8, 9);
        resetBroken(p);
        System.out.println("after resetBroken:  " + p);

        resetWorking(p);
        System.out.println("after resetWorking: " + p);
    }
}
after resetBroken:  (8.0, 9.0)
after resetWorking: (0.0, 0.0)

resetBroken compiles, runs, throws no exception and accomplishes nothing. resetWorking reaches through the reference with two dots and edits the object the caller is holding.

If you genuinely need a method to hand back a different object, do not try to write it into the parameter — return it, and let the caller assign: p = reset(p);. That is the only way, and it is why so many library methods return a value you might have expected them to modify in place.

Worked Example— why you cannot write swap in Java

In C++ you would write a swap that takes references and exchanges them. Try the direct translation in Java and watch it fail, then watch the version that works.

SwapDemo.java

public class SwapDemo {
    public static void swapRefs(Point p, Point q) {
        Point temp = p;
        p = q;
        q = temp;
        System.out.println("    inside swapRefs: p is " + p + ", q is " + q);
    }

    public static void swapContents(Point p, Point q) {
        double tx = p.getX(), ty = p.getY();
        p.setX(q.getX());
        p.setY(q.getY());
        q.setX(tx);
        q.setY(ty);
        System.out.println("    inside swapContents: p is " + p + ", q is " + q);
    }

    public static void main(String args[]) {
        Point a = new Point(1, 1);
        Point b = new Point(2, 2);

        System.out.println("start:              a is " + a + ", b is " + b);
        swapRefs(a, b);
        System.out.println("after swapRefs:     a is " + a + ", b is " + b);

        swapContents(a, b);
        System.out.println("after swapContents: a is " + a + ", b is " + b);
    }
}
start:              a is (1.0, 1.0), b is (2.0, 2.0)
    inside swapRefs: p is (2.0, 2.0), q is (1.0, 1.0)
after swapRefs:     a is (1.0, 1.0), b is (2.0, 2.0)
    inside swapContents: p is (2.0, 2.0), q is (1.0, 1.0)
after swapContents: a is (2.0, 2.0), b is (1.0, 1.0)

swapRefs prints the swapped values from inside — its own two parameters really were exchanged — and then main prints the original order. Three assignments, all of them to local variables that stop existing one line later.

swapContents never touches p or q themselves. It moves numbers between the two objects, using getters and setters. main's a and b still point where they always did, and those objects now hold each other's coordinates.

Read what the two versions actually mean, because they are not equivalent even in principle. swapContents changes the objects, so every variable anywhere in the program pointing at those points sees the swap. A true C++-style reference swap would have changed only main's two variables and left everybody else alone. Java simply does not offer the second thing.

The idiomatic Java answer, when you really need to exchange two variables, is to do it in the caller where the variables live:

Point temp = a;
a = b;
b = temp;

(a) Line (a)?

(6.0, 1.0). The method's first statement ran while its parameter still pointed at main's object, so the x really was raised from 1 to 6. Everything the method did afterwards happened somewhere else.

(b) Line (b)?

(0.0, 99.0). After p = new Point(0, 0) the parameter points at a second object; p.setY(99) edits that one, and it is that reference that is returned and stored in r.

(c) Line (c)?

p = (6.0, 1.0)
r = (0.0, 99.0)
p == r? false

false. Two objects; main's p points at the first, r at the second.

Things to notice across all three parts. The parameter is called p and so is main's variable, and they are two different variables that merely started out holding the same arrow. The moment the method reassigned its p, the two parted company permanently. Renaming the parameter would not change a single output — it would just make the program easier to read, which is a good enough reason to do it.

Problem 1 — What is the output? (from CSCI 212 Exam 1, Spring 2025)

Consider the following Java program. DecimalFormat lives in java.text, and Double is the wrapper class for the primitive double — so a Double variable, like any variable of a class type, holds a reference.

Output.java

import java.text.DecimalFormat;

public class Output {
    public static void main(String args[]) {
        DecimalFormat f1, f2, f3;
        f1 = new DecimalFormat("#.##");
        f2 = f1;
        f3 = new DecimalFormat("#.#");
        Double x = 3.1415;
        Double y = x;
        Double z = 2.7182;
        System.out.println(x);                              // line (a)
        System.out.println(f1.format(z));                   // line (b)
        f1 = f3;
        System.out.println(f2.format(y));                   // line (c)
        y = z;
        System.out.println(x);                              // line (d)
        System.out.println(f3.format(x) + y);               // line (e)
        Double a[] = {x, y, z};
        System.out.println(a[0]);                           // line (f)
        a[1] = 1.1;
        a[2] = 2.2;
        x = a[1];
        System.out.println(y);                              // line (g)
        System.out.println(a[0] + "," + a[1] + "," + a[2]); // line (h)
        System.out.println(a[0] + a[1] + a[2]);             // line (i)
        System.out.println(z);                              // line (j)
    }
}

Before you start, note two things about Double that make this problem easier than it looks. It has no setters — a Double object can never be changed after it is built — so nothing in this program mutates anything. Every single one of the assignments is a rebinding. And Double x = 3.1415; is legal because Java autoboxes the primitive into a Double object for you.

(a) What is the output from the instruction beginning on line (a)?

3.1415. Printing a Double prints the number it wraps.

(b) What is the output from the instruction beginning on line (b)?

2.72. f1 points at the "#.##" formatter, which means "up to two decimal places". 2.7182 rounds to 2.72.

(c) What is the output from the instruction beginning on line (c)?

3.14. This is the first real reference question in the problem. The line before it, f1 = f3;, rebound the variable f1 onto the "#.#" formatter — and f2 was never mentioned, so f2 still points at the "#.##" object it was given on line 3. y is still an alias for the 3.1415 object, so f2.format(y) is "#.##" applied to 3.1415, which is 3.14.

If you answered 3.1, you assumed f2 follows f1 around. It does not: f2 = f1 copied an arrow once, on one line, and that was the end of any connection between the two variables.

(d) What is the output from the instruction beginning on line (d)?

3.1415. Same trap in the other direction. y = z; moved y onto the 2.7182 object. x still points at 3.1415, exactly as it has since it was created.

(e) What is the output from the instruction beginning on line (e)?

3.12.7182. Two separate things joined by + with no space between them:

  • f3.format(x) is the "#.#" formatter applied to 3.1415, giving the String "3.1".
  • + y — the left operand is already a String, so this concatenates. y is now the 2.7182 object, so "2.7182" is appended.

This is the Lecture 1 rule about + meeting the Lecture 8 rule about references in one line, which is exactly why it is on the exam.

(f) What is the output from the instruction beginning on line (f)?

3.1415. Double a[] = {x, y, z}; copies the three current arrows into the three slots. At that moment x points at 3.1415, so a[0] does too.

Worth recording the whole picture here, because the last four parts all read off it: a[0] and x point at the 3.1415 object; a[1], a[2], y and z all four point at the single 2.7182 object, since y = z earlier made y an alias for it.

(g) What is the output from the instruction beginning on line (g)?

2.7182. The three lines before it — a[1] = 1.1;, a[2] = 2.2;, x = a[1]; — are all rebindings. They point two array slots and the variable x at new objects. None of them touches y, which still points at the 2.7182 object it was aimed at on the y = z line.

Compare this with Example3 in §6. There, writing into the array changed what t1 printed — because the loop called setters. Here, writing into the array changes nothing else, because assignment into a slot only moves that slot's arrow.

(h) What is the output from the instruction beginning on line (h)?

3.1415,1.1,2.2. The "," in the middle makes the whole expression a concatenation, so each Double is turned into text and joined. a[0] was never reassigned; a[1] and a[2] were.

(i) What is the output from the instruction beginning on line (i)?

The exam answer is 6.4415. The program actually prints 6.4415000000000004, and it is worth knowing why.

There is no String anywhere in this expression, so + means addition. Java unboxes each Double to a primitive double and adds: 3.1415 + 1.1 + 2.2. In exact arithmetic that is 6.4415. In binary floating point none of those three numbers is representable exactly, the tiny errors do not cancel, and the sum comes out a few units in the last place too high. Java prints enough digits to identify the stored value uniquely, so you see the error.

On paper, write 6.4415 — that is what the question is testing and what the answer key expects. But recognize the pattern from Lecture 1: whenever a double sum produces a long tail of digits, this is what happened.

(j) What is the output from the instruction beginning on line (j)?

2.7182. z was assigned once, on the line that created it, and never again. Everything that happened to y, to the array slots and to x happened to their arrows.

Things to notice across all ten parts. Six of the ten lines print a number that was set at the top of the program and never changed, and students lose those points by assuming that assigning to one variable somehow reaches its former partners. It never does. f2 = f1 and y = x create a relationship that lasts exactly one instant.

The reason nothing surprising happens in this program — the reason it is all rebinding and no mutation — is that Double and DecimalFormat values here are only ever replaced, never edited. Lecture Summary
  • A variable of a class type holds a reference — the location of an object — not the object itself. A variable of a primitive type holds the value. Every surprise in this lecture follows from that one difference.
  • Point c = a; copies the reference, so a and c are two names for one object. That is aliasing. A change made through either name is visible through both, because there is only one object to change.
  • null means "this variable points at no object". Calling a method on it gives a NullPointerException at run time, not a compile error — the compiler cannot know what a reference will hold.
  • == between two object variables asks "same object?", not "same contents?". Two separately-constructed points at the same coordinates are never ==. Comparing contents needs a method, and that method is equals — which is next lecture's business.
  • An object stored inside another object is stored by reference. A Triangle built from three Points does not own copies of them; it shares the caller's points, and a later setX on one of those points changes the triangle.
  • Mutating (pts[i].setX(2)) changes the object every name is pointing at. Rebinding (pts[i] = new Point(2, 0)) changes only which object that one name points at and leaves every other name looking at the old object. Her Example3 and Example3b differ by exactly this and produce different answers.
  • Java passes everything by value. For an object the value passed is the reference, so a method can change the object's contents, but assigning to the parameter only re-points the method's own local copy — the caller's variable is untouched. This is why a swap(a, b) method cannot work in Java.
  • The defence is a defensive copy: if a constructor stores new Point(p) rather than p, nobody outside can reach in and change the object's insides later.
  • When a program confuses you, stop reading and draw the boxes and arrows. Count the new keywords — that is exactly how many boxes your diagram should have.
