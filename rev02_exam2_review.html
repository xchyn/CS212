Key Idea— the exam is closed book

There is no compiler in the room and no notes on the desk. Every piece of code you write is written from memory, in pen, on paper. That changes what "knowing it" means: reading a JFrame constructor and nodding is not the same skill as producing one, and only the second one is on the paper.

So work every problem on this page with a pen before you open the toggle. The gap between "I understood that" and "I could have written that" is exactly where the marks go.

2.The case study, in one page

Lectures 10 and 11 took one English paragraph about parking enforcement and turned it into five classes: ParkingMeter (how many minutes are paid for), ParkedCar (a car, which has a meter), ParkingTicket (a car plus an officer plus a fine), PoliceOfficer (who patrols and writes tickets) and a driver class that runs the simulation. The point was never the parking. The point was the method for getting from prose to classes, and the two design rules that came out of it.

  • Nouns suggest classes; verbs suggest methods. Read the description, list the things, then ask of each one: does it have state that has to be remembered? If yes, it is a class. If it is just a value, it is a field.
  • "has-a" means a field, "is-a" means inheritance. A ParkedCar is not a ParkingMeter, so ParkedCar holds one in a private ParkingMeter meter; field. Say the sentence out loud; if it sounds absurd in English it is absurd in Java.
  • Encapsulation is about what you hand back, not just what you declare. Making meter private protects the field, not the object it points at. A getter that returns the meter itself hands a caller the power to reset it, which is why the design exposes expiredMeter(), adjustMeter(int) and getFine() instead.
  • Build in dependency order. ParkingMeter depends on nothing, so it is written and compiled first; ParkedCar uses it; ParkingTicket uses both. Compiling as you go means every error you see belongs to the file you just typed.
  • An array of objects is an array of nulls until you fill it. ParkedCar street[] = new ParkedCar[20]; makes twenty empty slots, not twenty cars. Every use of street[i] needs a null guard.
Key Idea— if you can only do one thing

Be able to look at any two class names on the paper and say, in one sentence, whether they are related by has-a (a field) or by is-a (extends). Every design question on this material, and half the inheritance questions, reduces to that one call.

Common Mistake— the case-study traps, collected
  • Declaring the field but never creating the object. Delete meter = new ParkingMeter(); from the constructor and the class still compiles perfectly — meter is simply null. The car prints its make and color quite happily and then throws a NullPointerException the first time anything touches the meter. An object can be half-built and look completely healthy until you reach the missing part.
  • Forgetting that most of an object array is null. The first empty parking space you touch without a guard throws. The whole shape of the patrol loop — if (street[i] == null) ... else ... — exists for that reason.
  • A getter that hands out the object itself. return meter; compiles and looks like every other getter, and it quietly undoes the private.
  • Boundary arithmetic in the fine. The fine rule changes at every whole hour, so the test cases that matter are 59, 60 and 61 minutes overdue — not 30 and 90. Whenever a rule changes at a boundary, test on the boundary.
  • this(...) anywhere but first. A call to another constructor must be the first statement in the constructor. Put a println above it and the file stops compiling. The identical rule applies to super(...).
Practice Problem 22.1

A campus wants to model its printers. The description reads: "A printer belongs to a building. It has a model name and a page counter. A print job has an owner, a number of pages and the printer it was sent to. A print job costs 10 cents a page, doubled if the job is over 50 pages."

(a) What classes would you create, and what fields would each hold?

Plan. List the nouns, then ask of each whether it has state worth remembering. Printer, building, model name, page counter, print job, owner, number of pages, cost.

Two of those are classes: Printer and PrintJob. The rest are fields.

  • Printer — private String building; private String model; private int pagesPrinted;
  • PrintJob — private String owner; private int pages; private Printer printer;

building and model are Strings, not classes, because nothing in the description asks a building to do anything or to remember anything. If a later requirement said "a building has a street address and a list of printers", Building would become a class — that is the test.

The cost is not a field. It is computed from pages, so it is a method: storing it as well would give you two copies of the same fact that can drift apart.

(b) Is PrintJob a Printer, or does it have one? What does your answer make the Java look like?

Say it in English. "A print job is a printer" — false, obviously. "A print job has a printer" — true. So it is a field, not extends:

public class PrintJob {
    private String owner;
    private int pages;
    private Printer printer;          // has-a

    public PrintJob(String owner, int pages, Printer printer) {
        this.owner = owner;
        this.pages = pages;
        this.printer = printer;
    }
}

This is exactly the ParkedCar/ParkingMeter relationship from Lecture 10 with the names changed, and it is the relationship almost every "design these classes" question is really testing.

(c) Write the method that returns the cost of the job in cents. Why must you be careful about 50 pages exactly?

The rule says over 50 pages, so 50 pages is charged at the ordinary rate and 51 is charged double:

public int getCost() {
    int cost = 10 * pages;
    if (pages > 50) {
        cost = cost * 2;
    }
    return cost;
}

Things to notice across all three parts. The boundary is where the marks are, and it is decided by one character: pages > 50 charges 50 pages at the single rate, pages >= 50 charges them double. The English word was "over", so it is >. This is the same lesson the parking fine taught — when a rule changes at a boundary, the value on the boundary is the test case you have to think about, and it is the one an exam will pick.

3.Inheritance

Inheritance is the third pillar, and the one that finally lets you stop copying code. Writing class Car extends Vehicle says two things at once: a Car is a Vehicle, and a Car gets everything Vehicle has without your typing it again. Everything else in Lecture 12 is a consequence of those two sentences.

  • What is inherited. Every public and protected field and method, and package-private members if the subclass is in the same package.
  • What is not. Constructors — ever. A constructor builds one specific class, so handing it down would make no sense.
  • The private case, which trips everyone. A private field of the superclass is part of the subclass object — the memory is there, the data is real — but the subclass's code cannot name it. Reach it through a public or protected getter, or make the field protected in the first place.
  • super(...) must be the first statement in a constructor, and if you do not write it Java inserts a silent super() for you. If the superclass has no no-argument constructor, that silent insertion fails and you get an error pointing at your own constructor.
  • Construction runs top-down. new Taxi() builds the Vehicle part, then the Car part, then the Taxi part. Every constructor's body runs after the chain above it has finished.
  • Overriding is redeclaring a method with the same name and same parameter list in a subclass. @Override is optional but free insurance: it makes the compiler check that you really did override something.
  • super.method() calls the superclass version from inside the override. It is how you extend behaviour instead of replacing it.
Key Idea— if you can only do one thing

Be able to write a three-line subclass from memory: the header public class Sub extends Super, a constructor whose first statement is super(...), and one @Override method. That skeleton is worth 10 points on its own, and Problem 1 of last year's paper was almost exactly it.

Practice Problem 22.3

Employee is given. Write a subclass Manager that adds a bonus and overrides pay() so that it returns the salary plus the bonus — without repeating the salary calculation.

Employee.java

public class Employee {
    private String name;
    private double salary;

    public Employee(String name, double salary) {
        this.name = name;
        this.salary = salary;
    }

    public String getName() { return name; }

    public double pay() { return salary / 26.0; }

    public String toString() { return name + " is paid " + pay(); }
}

Plan. Three moves, in order. Header with extends. A constructor whose first statement is super(name, salary), because Employee has no no-argument constructor. An @Override of pay() that calls super.pay() rather than re-deriving the fortnightly figure — salary is private, so you could not re-derive it even if you wanted to.

Manager.java

public class Manager extends Employee {
    private double bonus;

    public Manager(String name, double salary, double bonus) {
        super(name, salary);
        this.bonus = bonus;
    }

    @Override
    public double pay() {
        return super.pay() + bonus / 26.0;
    }
}

PayDemo.java

public class PayDemo {
    public static void main(String args[]) {
        Employee e = new Employee("Ana", 52000);
        Employee m = new Manager("Bo", 52000, 13000);

        System.out.println(e);
        System.out.println(m);
    }
}
Ana is paid 2000.0
Bo is paid 2500.0

Things to notice. toString() was written once, in Employee, and it calls pay(). When it runs on the Manager object that call goes to Manager.pay() — a method Employee had never heard of. That is dynamic binding doing your work for you, and it is why the manager's line reads 2500 without toString being touched.

super.pay() is not the same as pay(). Writing return pay() + bonus / 26.0; inside the override calls the override again, forever, and the program dies with a StackOverflowError. When an override wants the old behaviour, super. is the only way to ask for it.

4.Polymorphism and dynamic binding

This is a quarter of the paper and it is entirely mechanical once you separate two questions that feel like one. Every reference variable has two types at the same time: the static type it was declared with, and the dynamic type of the object it currently points at. Shape s = new Circle(3); has static type Shape and dynamic type Circle. Every question in this section is answered by asking which of the two applies.

Key Idea— the two rules, and nothing else

The static type decides what you are allowed to write. The compiler looks only at the declared type and asks: does that class, or something it inherits from, declare a method with this name and these argument types? If not, the program does not compile, regardless of what the object really is.

The dynamic type decides which version runs. Once the compiler has settled which method, the JVM looks at the actual object to decide whose body.

Or, in the form to write at the top of your exam paper: overriding is resolved at run time by the dynamic type; overloading is resolved at compile time by the static type.

The rest follows:

  • Assignment goes one way only. Shape s = new Circle(3); compiles because a Circle is a Shape. Circle c = new Shape(); does not, because a Shape is not a Circle. Read the assignment as "the thing on the right is-a thing on the left" and it is decided.
  • An array of a superclass type holds any mixture of subclasses. Each element has static type Shape, so you may call whatever Shape declares; each element has its own dynamic type, so the right override runs. One loop, no if statements about types.
  • Casting down is how you get the subclass methods back, and the cast is checked at run time. Guard it with instanceof unless you can point at the line that guarantees the type. ((D) a2).change(); and ((Mid) all[2]).extra(); are the shape the exam uses.
  • Fields are not polymorphic. If a subclass declares a field with the same name as the superclass's, both exist in the object, and which one you read is decided by the static type — at compile time, like an overload. This is the single nastiest question in the topic.
  • println(obj) calls toString() polymorphically. That is why System.out.println(a); where a is declared A but holds a B prints B's version.
Procedure— answering any "what is printed at line (x)?"
  1. Write down the declared type of the reference on the left of the dot.
  2. Write down the actual object it holds. If the line before said A a1 = new E();, the object is an E, whatever a1 is declared as.
  3. Ask the compiler's question: does the declared type have a method with that name and those argument types? If no — the answer is "does not compile", and that is a legitimate answer on this exam. If there is a cast in front, use the cast's type instead.
  4. Ask the JVM's question: starting at the actual class and walking up, whose version of that method do you meet first? That body is what runs.
  5. If the thing being read is a field rather than a method, stop at step 3 — fields use the declared type.
Practice Problem 22.4

Using the four-step procedure above, answer each part. The classes are:

class Animal {
    void speak() { System.out.println("Animal speaks"); }
    void eat() { System.out.println("Animal eats"); }
}

class Dog extends Animal {
    void speak() { System.out.println("Woof"); }
    void fetch() { System.out.println("Fetching"); }
}

class Puppy extends Dog {
    void speak() { System.out.println("Yip"); }
}

(a) Animal a = new Puppy(); a.speak();

Yip. Declared type Animal declares speak(), so it compiles. The actual object is a Puppy, and Puppy overrides speak(), so Puppy's body runs.

(b) Animal a = new Puppy(); a.fetch();

It does not compile. The declared type is Animal, and Animal has no fetch(). That the object happens to be a Puppy is irrelevant — the compiler is following a rule that ignores the previous line on purpose, because in real code the previous line is a loop or a method call with nothing to look at.

T.java:18: error: cannot find symbol
        a.fetch();
         ^
  symbol:   method fetch()
  location: variable a of type Animal
1 error

(c) Animal a = new Puppy(); ((Dog) a).fetch();

Fetching. The cast changes the type the compiler consults, and Dog does declare fetch(), so it compiles. At run time the object really is a Puppy, a Puppy is a Dog, so the cast succeeds and Dog's fetch() runs.

(d) Animal a = new Dog(); ((Puppy) a).speak();

It compiles, and then it throws a ClassCastException at run time. The compiler allows the cast because a variable declared Animal could be holding a Puppy. It isn't — it holds a plain Dog, and a Dog is not a Puppy.

Things to notice across all four parts. Parts (b) and (d) fail at different times, and knowing which is which is worth marks. A cast the compiler can prove impossible (casting a declared Rectangle to Circle) is a compile error; a cast that is merely possible is deferred to run time. If a question asks "what happens", say which of the two it is.

The safe form is always if (a instanceof Puppy) { ((Puppy) a).speak(); } — and note that instanceof answers false rather than throwing, so it is exactly the guard you want.

This one separates people who have understood the two rules from people who have memorised "the object decides". Two lines of output.

class P {

Common Mistake— the polymorphism traps, collected
  • "But I can see that it is a Circle." The compiler does not look at the previous line. Shape s = new Circle(3); s.getRadius(); is a compile error and it is supposed to be.
  • The arrow only points one way. Circle c = new Shape(); is incompatible types: Shape cannot be converted to Circle. Read the assignment aloud as "is-a" and you will never get this backwards.
  • Answering an override question with the declared type. A a = new C(); then a.what() prints C's answer, not A's. Circle the new on the previous line before you answer — that is the word that decides.
  • Answering a field question with the dynamic type. The opposite mistake, and the reason a question mixes methods and fields in one program. Fields use the declared type.
  • Forgetting that a missing override means "look upward". When class F extends B and does not declare what(), b1.what() runs B's version. Walk up from the actual class until you find one; you always find one eventually, because Object is at the top.
  • Casting without a guard. A downcast that is merely possible compiles and throws ClassCastException at run time. Guard with instanceof.

5.Abstract classes and interfaces

Lecture 14 was about declaring a method and refusing to write it. A Shape has an area, but there is no formula for the area of a generic shape — both halves of that sentence are true, and ordinary classes cannot express it. Java gives you two tools that can, and the exam has asked about both.

  • An abstract method is a signature followed by a semicolon: public abstract double getArea();. A class containing one must itself be declared abstract. The reverse is not true — a class may be abstract with no abstract methods, if you simply want to forbid new.
  • An abstract class is still a class. It may have fields, constructors, and fully written methods. Its constructor is never called by you; it is called by the subclass's super(...).
  • An interface is a list of obligations. Every method in it is implicitly public and implicitly abstract, whether you write those words or not. Every field in it is implicitly public static final.
  • extends is scarce; implements is not. A class extends exactly one class and implements as many interfaces as it likes. Spend the extends slot on what the class fundamentally is; use interfaces for what it can do.
  • Both give you a type you can declare a variable with. Printable p = new Document("hi"); is legal, and p may then be used for anything Printable declares — and nothing else. That is the Lecture 13 static-type rule again, with an interface in the driving seat.
  • You may declare a variable of an abstract type; you may not construct one. AbstractShape s = circle; is fine. new AbstractShape() is not.
Key Idea— if you can only do one thing

Be able to turn a bullet-pointed English description into a class that implements a given interface: the header, the private field, the constructor, and one @Override public method per interface method. Last year that was Problem 1 and it was 10 of the 40 marks, and the rubric gave 2 marks for the header alone.

Practice Problem 22.6

Given this interface and class:

interface Drawable {
    void draw();
}

class Dot implements Drawable {
    public void draw() { System.out.println("."); }
    public void enlarge() { System.out.println("bigger"); }
}

For each line, say whether it compiles, and if not, what the compiler says.

(a) Drawable d = new Dot();

Compiles. A Dot implements Drawable, so "a Dot is a Drawable" is true and the assignment is legal in that direction. This is the ordinary way you use an interface: the variable's type says what you need, the object supplies it.

(b) Drawable d = new Drawable();

Does not compile. An interface has no bodies and no constructor, so there is nothing to construct. The message is Drawable is abstract; cannot be instantiated — the same message an abstract class gives, because an interface is the extreme case of an abstract class.

(c) Drawable d = new Dot(); d.enlarge();

Does not compile. The declared type is Drawable, and Drawable declares one method. The Dot obviously has enlarge(), and it makes no difference:

T.java:13: error: cannot find symbol
        d.enlarge();
         ^
  symbol:   method enlarge()
  location: variable d of type Drawable
1 error

Note location: variable d of type Drawable — the same message shape you saw in Lecture 13 with a superclass reference, for the same reason. The fix is the same too: ((Dot) d).enlarge();.

(d) Dot is rewritten with void draw() instead of public void draw().

Does not compile, and this is the one that catches people every single time, because the omission looks like nothing:

T.java:6: error: draw() in Dot cannot implement draw() in Drawable
    void draw() { System.out.println("."); }
         ^
  attempting to assign weaker access privileges; was public
1 error

Things to notice across all four parts. Read the second line of that message: was public. Interface methods are implicitly public, so leaving the word off is not "matching the interface" — it is package-private, which is narrower, and Java never lets an override reduce visibility.

Write public on every method that implements an interface, always. On last year's rubric each implemented method was worth one mark, and a class that does not compile is hard to defend.

Practice Problem 22.7

Write an interface Payable that requires two methods: getPay() returning a double, and printPayslip() returning nothing. Then write a class Contractor that implements it, with a private String name, a private double hourlyRate, a private int hours, and a constructor taking all three.

Plan. The interface is signatures plus semicolons — no bodies, no fields, no constructor. The class then owes one public method per interface method, plus whatever state it needs of its own. printPayslip() should call getPay() rather than recompute the product; that keeps one copy of the formula and, as Lecture 14 showed, it means a subclass overriding getPay() fixes the payslip for free.

Payable.java

public interface Payable {
    double getPay();
    void printPayslip();
}

Contractor.java

public class Contractor implements Payable {
    private String name;
    private double hourlyRate;
    private int hours;

    public Contractor(String name, double hourlyRate, int hours) {
        this.name = name;
        this.hourlyRate = hourlyRate;
        this.hours = hours;
    }

    @Override
    public double getPay() {
        return hourlyRate * hours;
    }

    @Override
    public void printPayslip() {
        System.out.println(name + ": " + hours + " hours, pay " + getPay());
    }
}

PayableDemo.java

public class PayableDemo {
    public static void main(String args[]) {
        Payable p = new Contractor("Sam", 32.5, 18);
        p.printPayslip();
        System.out.println("total owed: " + p.getPay());
    }
}

Things to notice. The interface declares double getPay(); with no public and no abstract, because both are automatic there. The class writes public on both methods, because there it is not automatic. Those two facts look contradictory and are the reason part (d) above exists.

Payable p = ... rather than Contractor p = ... is deliberate: the variable now says "something I can pay", so the same line would work for an Employee, a Contractor or an Intern. That is the whole reason interfaces exist, and it is the sentence to write if a question asks "why use an interface here?"

Common Mistake— the abstract-and-interface traps, collected
  • Leaving public off an implementing method. Covered above. It is the single most common way a correct-looking answer fails to compile.

6.Windows, events and listeners

Lecture 15 was the first program in the course with no println in it. Three imports, one class, and a window on the screen — and then the reason interfaces stopped being theory: a button works because you implement one.

  • Three packages. javax.swing (with the x) for the components, java.awt for Color, Container, and the layout managers, java.awt.event (singular) for the listener interfaces and the event classes.
  • The pattern every exam question uses. public class Foo extends JFrame, with a constructor that calls super(), setTitle, setSize and builds the contents, and a main that does nothing but Foo gui = new Foo(); gui.setVisible(true);.
  • Nothing appears until setVisible(true). Constructing a frame builds it in memory; showing it is a separate step, and it belongs in main.
  • Components go in the content pane, not in the frame. Container contentPane = getContentPane(); and then contentPane.add(...).
  • Closing. setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE) ends the whole JVM; DISPOSE_ON_CLOSE closes just that window; DO_NOTHING_ON_CLOSE is what you use when a WindowListener needs to decide.
  • The event model, in one sentence. A source (a button, a window) fires an event object at a listener, and a listener is an object whose class implements the matching interface. Nothing happens until you register the listener with the source.
  • WindowListener has seven methods and you must write all seven if you implement it. WindowAdapter is a class that supplies seven empty ones, so extending it lets you override only windowClosing. But it is a class, so it uses up your one extends.
Key Idea— if you can only do one thing

Be able to write the six-line skeleton from a blank page, in this order, without thinking:

7.Layouts, buttons and actionPerformed

Lecture 16 is the densest lecture on the exam and it is worth the most. Two separate skills live here: putting components where you want them, and making one of them do something.

Where things go. A container never places components itself; it asks its layout manager.

LayoutBehaviourDefault for
FlowLayoutLeft to right, centred, wrapping to a new row when it runs out of width. Every component gets its preferred size and is never stretched.JPanel
BorderLayoutFive regions: NORTH, SOUTH, EAST, WEST, CENTER. Each holds one component. CENTER takes all the space the others do not want.a JFrame's content pane
GridLayout(r, c)Equal cells, filled left to right then top to bottom. Every cell is the same size and every component is stretched to fill its cell. A count of 0 means "as many as needed".—

Anything more complicated than those three is built by nesting: put a JPanel with its own layout manager into a region of another container. Every non-trivial window on the exam is one BorderLayout with a JPanel in CENTER and a JPanel in SOUTH, and the SOUTH one has a GridLayout or a FlowLayout full of buttons.

Procedure— from a picture of a window to code
  1. Draw the tree first, on the exam paper. Frame, content pane, then one line per container with its layout manager and one line per component. Two minutes here saves ten later and it is visible working that earns partial credit.
  2. Write the frame setup: super(); setTitle(...); setSize(...);
  3. Get the content pane and set its layout.
  4. For each panel in the tree, in order: create it, set its layout, add it to its parent, then add its children. Creating and adding in that order means you never lose track of which container you are filling.
  5. Assign to fields, not local variables, anything actionPerformed will need later. Everything else can stay local.

Making it do something is always the same six moves, and they are the ones the exam takes apart and asks for one at a time:

  1. import java.awt.event.*;
  2. Add implements ActionListener to the class header.
  3. Create the button: JButton b = new JButton("SWAP");
  4. Add it to a container.
  5. Register it: b.addActionListener(this);
  6. Write public void actionPerformed(ActionEvent e) { ... }.

Inside actionPerformed, tell several buttons apart with e.getActionCommand(), which returns the button's label as a String, and compare it with .equals(...) — never with ==. e.getSource() compares against the button object itself and is the alternative when the labels might change.

Key Idea— if you can only do one thing

Memorise the three answers that Problem 4 asks for, because they are three separate marks and none of them depends on the rest of the question:

  • the header: public class Foo extends JFrame implements ActionListener
  • the registration line: b.addActionListener(this);
  • the method signature: public void actionPerformed(ActionEvent e)

Last year those were worth 2, 2 and part of 6. If you write nothing else on a GUI question, write those three lines.

Practice Problem 22.8

A content pane 300 by 200 has a BorderLayout. A JLabel goes in NORTH, an empty JPanel in CENTER, and a JPanel with GridLayout(1, 3) holding three buttons goes in SOUTH.

(a) Which of the three regions gets the leftover vertical space, and roughly what size is each component?

CENTER gets the leftover. NORTH and SOUTH are given exactly the height they ask for and the full width; CENTER gets everything in between. Laying it out for real and printing the bounds:

title    at (  0,  0)  size 300 x  15
middle   at (  0, 15)  size 300 x 160
row      at (  0,175)  size 300 x  25
One      at (  0,  0)  size 100 x  25
Two      at (100,  0)  size 100 x  25
Three    at (200,  0)  size 100 x  25

The label wanted 15 pixels of height and got exactly that. The button row wanted 25 and got exactly that. The middle panel got 200 − 15 − 25 = 160. All three are the full 300 wide, because NORTH and SOUTH stretch horizontally.

Inside the row, GridLayout(1, 3) divided 300 pixels into three equal 100-pixel cells and stretched each button to fill its cell — the buttons' own preferred widths were ignored completely. The x-coordinates 0, 100, 200 are relative to the row panel, not to the window.

(b) A student writes contentPane.add(buttonOne); contentPane.add(buttonTwo); contentPane.add(buttonThree); directly on a BorderLayout content pane and sees one enormous button. Why?

add has a one-argument form, so all three lines compile. In a BorderLayout the no-region form means CENTER. Each region holds one component, so each add overwrote the previous one, and the third button is the only one the layout manager still remembers. CENTER stretches to fill the window, which is why it is enormous.

Nothing was thrown away and no exception was raised: all three buttons are still children of the content pane. The first two were simply given a size of zero by zero, so they occupy no pixels. The last one added wins.

(c) The three buttons need to sit side by side and share the width equally. Write the code.

They cannot all go in one region, so they go into a panel of their own and the panel goes in the region:

JPanel buttonPanel = new JPanel();
buttonPanel.setLayout(new GridLayout(1, 3));
contentPane.add(buttonPanel, BorderLayout.SOUTH);

buttonPanel.add(buttonOne);
buttonPanel.add(buttonTwo);
buttonPanel.add(buttonThree);

Things to notice across all three parts. GridLayout(1, 3) rather than the default FlowLayout is what makes them equal width. With FlowLayout they would sit side by side too, but each at its own preferred size and centred with gaps — which is fine if the picture shows that, and wrong if the picture shows three buttons filling the bar. Look at the picture.

The order of the four lines is worth copying: create the panel, set its layout, add it to its parent, then fill it. Adding the panel before filling it is not required by Java, but doing it consistently is how you avoid the commonest layout bug of all — an add aimed at the wrong container.

Practice Problem 22.9

A frame has two buttons labelled UP and DOWN and a JLabel field called count that starts at "0". Write the actionPerformed method that makes them add one and subtract one, and the one line that has to appear where each button is created.

Plan. The number has to survive from one click to the next, so it is a field, not a local. getActionCommand() returns the label as a String, so two ifs on .equals are enough. Then push the new number into the label with setText — a JLabel holds text, so the int has to be converted, and "" + n is the shortest way.

private int n = 0;                          // a field, beside the JLabel field

public void actionPerformed(ActionEvent e) {
    if (e.getActionCommand().equals("UP")) {
        n = n + 1;
    }
    if (e.getActionCommand().equals("DOWN")) {
        n = n - 1;
    }
    count.setText("" + n);
}

And at each button:

up.addActionListener(this);

Things to notice. count must be a field of the class. If the constructor said JLabel count = new JLabel("0"); then count is a local variable that disappears when the constructor returns, and actionPerformed will not compile — cannot find symbol: variable count. The rule is easy to apply: anything actionPerformed reads or changes must be a field.

The strings "UP" and "DOWN" are written twice each — once in new JButton("UP") and once here. They must agree character for character, capitals and spaces included. "Up" does not match "UP", and no error is produced; the button simply does nothing. When one button in a program is dead and its neighbours work, put the two strings side by side and read them a character at a time.

Common Mistake— the GUI traps, collected

These are the ones that actually appear in submitted code, in rough order of how often.

  • The button that does nothing. Leave out b.addActionListener(this); and everything compiles, the window opens, the button draws itself and even presses in when you click it — and nothing happens. actionPerformed is a perfectly good method that nobody ever calls.   • ActionPerformed with a capital A. Same error, and much harder to see, because the method you wrote is sitting right there.
  • The component the listener cannot reach. Declared as a local variable in the constructor instead of a field. cannot find symbol: variable display.
  • Re-declaring a field inside the constructor.   • java.swing instead of javax.swing. The message is package java.swing does not exist, followed by a cascade of cannot find symbol for every Swing class in the file. It is java.awt without an x and javax.swing with one.
  • Two components into one BorderLayout region. Compiles, runs, and silently loses one of them.
  • add aimed at the wrong container. When you are reading GUI code back, read only the receivers — the thing before the dot on each add — and check each against your tree.
  • setBackground on the frame. Compiles, changes nothing visible: the frame's background is completely covered by its content pane. Color the thing that is actually on screen.

Practice Problem 22.10

A window has a JTextField field input and a JLabel field answer. Write an actionPerformed that reads a number of miles from input and puts the equivalent number of kilometers into answer, and does something sensible if the user typed nonsense. One mile is 1.609 kilometers.

Plan. Three steps and a guard. Read the text; convert it; compute; write it back. Double.parseDouble rather than Integer.parseInt, because miles can have a fractional part. The conversion is the only line that can fail, so it and the arithmetic go inside the try, and the message for a bad entry goes in the catch.

public void actionPerformed(ActionEvent e) {
    try {
        double miles = Double.parseDouble(input.getText().trim());
        double km = miles * 1.609;
        answer.setText(miles + " miles = " + km + " km");
    } catch (NumberFormatException ex) {
        answer.setText("Please type a number.");
    }
}

Running the same logic outside the GUI, with getText() replaced by a fixed String so the interesting cases can actually be exercised:

typed [10]  ->  10.0 miles = 16.09 km
typed [ 3.5 ]  ->  3.5 miles = 5.6315 km
typed []  ->  Please type a number.
typed [ten]  ->  Please type a number.
typed [-2]  ->  -2.0 miles = -3.218 km

Things to notice. .trim() matters more than it looks. Without it, a user who types a space after the number gets a NumberFormatException; the empty field throws as well, and so does anything the user typed that is not a number. Those are the three cases a tester will find in ten seconds, and the catch handles all three with one message.

Notice also that there is no throws NumberFormatException on the method, and there cannot be: ActionListener declares actionPerformed with no throws clause, and an implementing method may not add one. Inside a listener there is no escape hatch, so the handling has to happen right there.

9.Graphics and painting

Lecture 19 stopped assembling ready-made components and started drawing pixels. It is the last topic on the exam and the smallest, but it is also where the Shape hierarchy from Lectures 12 to 14 finally gets a job, so a question can combine the two.

  • The origin is the top-left corner and y increases downward. Every coordinate is relative to the component being painted, not to the screen or the window.
  • You override paintComponent(Graphics g) and you never call it. Swing calls it — when the window first appears, when it is uncovered, when it is resized, and when you ask. The first line is always super.paintComponent(g);, which erases the previous frame by filling the background.
  • To ask for a redraw, call repaint(), not paintComponent. repaint() schedules a repaint; Swing decides when, and hands you a Graphics you could not have produced yourself.
  • draw outlines, fill fills. drawRect, fillRect, drawOval, fillOval, drawLine, drawString, drawArc.
  • Ovals and arcs are given their bounding box, not a centre and radius. g.fillOval(50, 50, 100, 100) is a circle 100 across whose bounding box starts at (50, 50), so its centre is (100, 100).
  • A fill covers x through x + w - 1; an outline is drawn on x and on x + w. An outline is one pixel wider than the corresponding fill.
  • The last thing drawn is the thing you see. There are no layers. Calls replace pixels in the order you make them.
  • g.setColor(Color.RED) applies to everything drawn after it until the next setColor.
Key Idea— if you can only do one thing

Be able to write a painting panel from memory:

public class MyPanel extends JPanel {
    public void paintComponent(Graphics g) {
        super.paintComponent(g);
        g.setColor(Color.RED);
        g.fillOval(50, 50, 100, 100);
    }
}

extends JPanel, override paintComponent, super first, setColor then draw. Then read every drawing question by sketching the bounding boxes on paper with their real ranges beside them — "red: 50 to 149 across, 50 to 149 down" — and reading the answer off.

top edge of the box    (20,  20): BLACK
on the diagonal        (60,  40): GREEN

Common Mistake— the graphics traps, collected
  • Leaving out super.paintComponent(g). It is what erases the previous frame. Without it the old ink stays and every new drawing is painted on top of the last one. On a static picture you may never notice; the moment anything moves you get a smear.
  • Calling paintComponent yourself. You have no Graphics to pass it and no business deciding when. Call repaint().
  • setBackground inside paintComponent. Too late — super.paintComponent(g) has already filled the background with the old color on that same pass. Set the background in the constructor.
  • Confusing a bounding box with a centre and radius. fillOval(cx, cy, r, r) does not put a circle at (cx, cy); it puts the box's top-left corner there.
  • Naming your own class Shape. java.awt already has an interface called Shape. Your own class wins against import java.awt.*;, but the moment an IDE adds an explicit import java.awt.Shape; the file falls apart with cannot find symbol messages about fields you are certain you wrote. If a cannot find symbol names something you know exists, check that the type in the message is the class you meant.
  • Drawing in the wrong order. Outline first, then fill the same rectangle, and the fill erases the outline everywhere except the one-pixel right and bottom edges. Fill first, then outline.

Sendable.java

public interface Sendable {
    void send();
    void send(int times);

(a) Write a class Message that implements Sendable. It should have a private String field body, a constructor that takes the body as a parameter, a send() that prints Sending: followed by the body, and a send(int times) that sends the message that many times. [6 marks: 2 for the class header, 1 each for the field, the constructor and the two methods]

Plan. The interface names two obligations, so the class owes two public methods with exactly those signatures. Write send(int) as a loop over send() rather than repeating the println — it is shorter, and part (b) will show that it also does something useful for free.

Add a protected getter while you are here. body is private as the question demands, and the subclass in part (b) will need to read it; protected means "the family may see this", which is exactly the relationship you want.

Message.java

public class Message implements Sendable {
    private String body;

    public Message(String body) {
        this.body = body;
    }

    protected String getBody() {
        return body;
    }

    @Override
    public void send() {
        System.out.println("Sending: " + body);
    }

    @Override
    public void send(int times) {
        for (int i = 0; i < times; i++) {
            send();
        }
    }
}

Every mark in this part is for a single line, and they are independent. Write the header first, then the field, then the constructor, then the two methods — in that order — and even a half-finished answer collects most of them.

(b) Write a subclass UrgentMessage that extends Message and has only one method besides its constructor. That method should override send() so the body is printed in capitals, surrounded by three asterisks on each side. [4 marks: 2 for the class header, 1 for the constructor, 1 for the override]

Plan. Two things are compulsory and one is the trap. Compulsory: the extends header, and a constructor that calls super(body) — Message has no no-argument constructor, so leaving it out will not compile. The trap: body is private, so super.body is not available. Use the getter.

UrgentMessage.java

public class UrgentMessage extends Message {

    public UrgentMessage(String body) {
        super(body);
    }

    @Override

}

Things to notice across both parts. UrgentMessage overrides one method, exactly as the question demands — and u.send(3) still prints three capitalised lines. The inherited send(int) calls send(), and that call goes to the object's own version. One override changed the behaviour of a method that was not overridden. public void actionPerformed(ActionEvent e) {
   if (e.getActionCommand().equals("COOLER")) {
      temperature = temperature - 1;

      dial.setBackground(Color.BLUE);
   } else if (temperature > 72) {
      dial.setBackground(Color.RED);
   } else {
      dial.setBackground(Color.GRAY);
   }
}

         int n = Integer.parseInt(input.getText().trim());
         answer.setText("" + (2 * n));
      } catch (NumberFormatException ex) {
         answer.setText("not a number");
      }
   }

   public static void main(String args[]) {
      Doubler gui = new Doubler();
      gui.setVisible(true);
   }
}

The class compiles. It opens a window and prints nothing, so there is no console output to show — but the body of actionPerformed is ordinary Java, and with getText() replaced by a fixed String it can be run against the cases a user will actually produce:

typed [21]  ->  42
typed [  7 ]  ->  14
typed []  ->  not a number
typed [3.5]  ->  not a number
typed [-4]  ->  -8

Things to notice. The order of the four add calls into top is the order the grid fills: left to right along the first row, then left to right along the second. Swap the third and fourth and the labels end up in the wrong column. GridLayout has no notion of "row 2, column 1" — you get the cells in the order you add.

top.add(new JLabel("Number:")); creates the label and adds it without ever naming it. That is fine here precisely because nothing will ever want it again, and it is a useful habit: the variables you bother to name become a short list of the things that matter.

Three cases go through the catch, not one: an empty field, a word, and — less obviously — 3.5, because Integer.parseInt rejects a decimal point. If the specification had said "a number" rather than "a whole number", Double.parseDouble would be the right call. Read what the question asks for.

.trim() earns its place. Without it, a user who types a space after the digits gets an exception and an unhelpful "not a number", which is the sort of thing that looks like a mysterious bug and is a one-word fix.

Problem 8 — What color is each pixel? (added for these notes)

A JPanel 300 pixels wide and 200 tall has a white background and this paintComponent. For each of the five points, say what color that pixel comes out.

FacePanel.java

import java.awt.Color;
import java.awt.Graphics;

import javax.swing.JPanel;

public class FacePanel extends JPanel {
   public void paintComponent(Graphics g) {
      super.paintComponent(g);

      g.setColor(Color.BLACK);
      g.drawOval(50, 50, 100, 100);

      g.setColor(Color.YELLOW);
      g.fillOval(50, 50, 100, 100);

      g.setColor(Color.BLUE);
      g.fillRect(120, 20, 60, 60);
   }
}

Write down what each call covers before you answer anything. The oval was given the bounding box from (50, 50) to (150, 150); the rectangle the box from (120, 20) to (180, 80). Whether the pixels on 150 and 180 are painted is exactly what parts (c) and (d) turn on.

(a) (100, 100)

Yellow. That is the centre of the oval — the bounding box runs from (50, 50) for 100 in each direction, so the centre is (100, 100). The blue rectangle starts at y = 20 and is 60 tall, so it stops at y = 79 and never reaches here.

(b) (50, 100)

Yellow. This is the leftmost point of the circle, and both calls touch it: drawOval put a black outline pixel there, and fillOval painted over it a moment later. The later call wins.

That is the whole reason the two calls are in this order in the question. Outline first, fill second, and the outline is erased almost everywhere — which is exactly the bug you get when you write drawRect before fillRect on the same rectangle.

(c) (150, 100)

Black. The one pixel where the outline survives. fillOval(50, 50, 100, 100) fills up to but not including x = 150, so the yellow stops at 149. drawOval with the same arguments puts its outline on x = 50 + 100 = 150. An outline is one pixel wider than the corresponding fill, and this is the point that proves it.

(d) (130, 60)

Blue. The rectangle covers x 120 to 179 and y 20 to 79, so this point is inside it, and it was drawn last. The circle covers it too — (130, 60) is well inside the oval — and it makes no difference.

(e) (100, 30)

White — the panel's background, put there by super.paintComponent(g) before anything else was drawn. y = 30 is above the circle's box, and x = 100 is left of the rectangle's.

Painting the panel into an image and reading the five pixels back:

(a) (100, 100): YELLOW
(b) ( 50, 100): YELLOW
(c) (150, 100): BLACK
(d) (130,  60): BLUE
(e) (100,  30): background (white)

Things to notice across all five parts. Two rules answer every question of this kind, and they are worth writing at the top of your paper before you start: a fill covers x through x + w - 1, while an outline is drawn on x and on x + w, and the last thing drawn is the thing you see.

The reliable technique is to sketch the shapes with their real ranges written beside them — "yellow circle: 50 to 149 across, 50 to 149 down" — and then read off each point. Holding two overlapping shapes and an off-by-one rule in your head at once is how this question gets missed.

Note that part (e) depends on super.paintComponent(g) being there. Delete that line and the answer to (e) becomes "whatever happened to be on the component last time" — which on a first painting is unpredictable and on a repaint is the previous picture. It is the first line of the method for a reason.

Before the Exam

A checklist for the last evening. Work down it with a pen; anything you cannot do without looking is where the remaining hours belong.

Things to be able to write from a blank page, in under a minute each:

  • The JFrame skeleton — class header, super(), setTitle, setSize, getContentPane(), setLayout, and the two-line main.
  • The class header with a listener: public class Foo extends JFrame implements ActionListener.
  • b.addActionListener(this); and public void actionPerformed(ActionEvent e).
  • A subclass header, a constructor whose first statement is super(...), and one @Override method.
  • An interface — signatures and semicolons — and a class that implements it, with public on every implemented method.
  • A paintComponent that starts with super.paintComponent(g).

Things to be able to answer in one sentence:

  • Which of two classes is the superclass, given a new and a declaration.
  • Whether a method call uses the declared type or the actual object — and why a field is the other way round.
  • Why Shape s = new Circle(3); s.getRadius(); does not compile, and what fixes it.
  • The difference between a compile error and a ClassCastException.
  • Which region of a BorderLayout gets the leftover space, and how many components a region holds.
  • What getActionCommand() returns, and why you compare it with .equals.

The five mistakes that cost the most marks:

  • Leaving public off a method that implements an interface.
  • Leaving out b.addActionListener(this); — the compiler will not help you.
  • Declaring a component as a local variable when actionPerformed needs it, or re-declaring a field inside the constructor.
  • Answering a dynamic-binding question from the declared type.
  • Forgetting super(...) when the superclass has no no-argument constructor.
